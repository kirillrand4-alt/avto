# Объект «проект»: схема, сборщик, заслоны и числа

Дыра, которую закрывает эта работа, была не в источниках, а в данных: в `enrich.db`
не было ни одной таблицы про проект или стадию, сшивка шла по ИНН, и один завод с
тремя стройками превращался в кучу из трёх новостей под одним номером.

Уточнение владельца по ходу работы поменяло цель: **перегонка 3 725 старых сигналов —
не цель**. Цель — чтобы новое событие сразу ложилось проектом. Поэтому сделан приёмник
потока, а архив из 3 725 сигналов использован как **проба прибора**: на нём мерится
склейка, на нём же стоят заслоны и контроли.

Хранение — там же и так же, как новости: та же база `C:\sender\enrich.db`, новые
таблицы рядом с `signals`, колонки в стиле `signals` (`inn`, `source`, `source_url`,
`ts`, `sum`, `hotness`). Существующие таблицы не изменены ни одной строкой.

## 2. СХЕМА: ЧЕТЫРЕ НОВЫЕ ТАБЛИЦЫ

### `proekty` — карточка проекта

| колонка | что это |
|---|---|
| `proekt_id` | устойчивый ключ `PR-<sha1(инн + место + объект + работы)>`, при столкновении добавляется номер |
| `inn`, `zakazchik`, `zakazchik_iz` | заказчик: ИНН, название и ИЗ КАКОЙ таблицы название взято |
| `otrasl`, `otrasl_prior`, `otrasl_iz` | отрасль (широко, можно несколько), признак приоритетной, чем опознана |
| `region`, `region_iz`, `mesto`, `adres` | субъект РФ, чем доказан, город/площадка, адрес |
| `obekt`, `tip_rabot` | название объекта (КрАЗ, НкАЗ, Амурский ГХК) и класс работ |
| `stadiya`, `stadiya_kod`, `stadiya_data`, `stadiya_iz`, `stadiya_rannyaya` | стадия воронки 0–8, её код, дата, ссылка-доказательство, самая ранняя виденная стадия |
| `ts`, `data_pervaya`, `data_poslednyaya`, `gody_iz_teksta` | даты события: окно и годы, названные в тексте |
| `sum`, `summa_rub`, `hotness` | сумма как в signals (текст) и разобранная в рублях |
| `ulik`, `istochnikov`, `istochniki` | СКОЛЬКО доказательств, сколько РАЗНЫХ источников и их список |
| `zontik` | 1 = это программа компании («модернизация четырёх заводов»), а не проект одной площадки |
| `yakorya`, `goroda`, `regiony`, `raboty` | признаки для поиска проекта новым событием |
| `sklejka_prichiny` | почему улики слиплись — для контроля глазами |
| `event_types`, `klyuch_sostav`, `created_at`, `updated_at` | тип события, состав ключа, времена |

### `proekt_uliki` — доказательства, которые НАКАПЛИВАЮТСЯ

Строка на доказательство: `ulika_id` (хэш источник+ссылка+цитата), `proekt_id`, `inn`,
`source`, `source_url`, `citata` (полный текст сигнала), `event_type`, `sum`, `hotness`,
`stadiya`, `otrasl`, `ts`, `data_sobytiya`, `data_vzyatiya`, `goroda`, `regiony`,
`yakorya`, `raboty`, `inn_conf`, `suspect`, `signal_rowid`, `prichina`, `added_at`.

Ключ доказательства — хэш, вставка `INSERT OR IGNORE`. Одно и то же доказательство не
удваивается, но **разные доказательства одного события складываются, а не заменяют друг
друга**. Это прямо противоположно `seen_news`, где кто первым взял ключ, тот новость и
забрал.

### `proekt_slovar` и `proekt_gashenie` — служебные

`proekt_slovar` (основа, df, число заглавных и строчных написаний, форма) — замороженный
корпусный словарь. `proekt_gashenie` (ИНН, основа) — якоря без различающей силы внутри
предприятия. Зачем заморожен: признак «имя собственное» считается по доле написаний с
заглавной буквы в корпусе, и если пересчитывать его на каждом событии, вчерашняя склейка
перестанет воспроизводиться. Пересчёт — отдельной командой.

## 3. ТОЧКА ВХОДА ПОТОКА

```python
prinyat_sobytie(con, row, slov) -> (proekt_id, 'новый' | 'дополнен' | 'уже было', причина)
```

`row` — ровно та запись, которую коллектор кладёт в `signals`. Порядок работы:

```
пришло событие
   -> разобрали на признаки (место, регион, объект, работы, стадия, отрасль, дата)
   -> взяли проекты ЭТОГО ИНН
   -> проверили на противоречие с КАЖДОЙ уликой проекта
   -> нашёлся совместимый и связанный  -> ДОБАВИЛИ ДОКАЗАТЕЛЬСТВО
   -> не нашёлся                       -> ЗАВЕЛИ ПРОЕКТ
```

Повторная подача того же события ничего не перезаписывает и ничего не удваивает.

## 4. КАК УСТРОЕНА СКЛЕЙКА

Склейка идёт по СОДЕРЖАНИЮ, а не по одному ИНН: предприятие + объект + место + близкие
даты.

**Якорь** — имя собственное, отличающее один проект от другого. Имя собственное
опознаётся не списком, а замером по корпусу: у основы считается доля написаний с
заглавной буквы. «Тайшет» пишут с заглавной всегда, «строительство» — почти никогда,
поэтому первое слово предложения якорем не становится.

Три фильтра гасят якоря без различающей силы:

1. слишком частые по всему корпусу (df > 150);
2. слишком частые ВНУТРИ ИНН (>= 50 % сигналов предприятия) — так гасится собственное
   имя компании: «РУСАЛ» стоит в большинстве из 46 сигналов и потому не может служить
   доказательством, что два сигнала об одном проекте;
3. стоп-лист месяцев, правовых форм и общепромышленных слов.

**Что разрешает склейку** (в порядке силы): совпадение текстов (Жаккар по 4-граммам
>= 0.45) · два общих якоря · один редкий общий якорь (df <= 15) · общий якорь плюс общий
класс работ · общее место плюс общий класс работ · общее место плюс слабое сходство.

**Что запрещает склейку при любом сходстве (заслоны):**

* у обоих названы города и множества не пересекаются;
* у обоих названы регионы и не пересекаются;
* у обоих известна дата события и разрыв больше 540 дней;
* один зонтичный, другой площадочный.

**Полное звено.** Сигнал входит в проект, только если он связан хотя бы с одним
участником И НЕ ПРОТИВОРЕЧИТ НИ ОДНОМУ. Это главный заслон против цепного слипания:
зонтичный сигнал «модернизация четырёх заводов — Братск, Иркутск, Красноярск,
Новокузнецк» иначе сшил бы четыре разных проекта в один.

**Зонтичные сигналы** (три и более разных места в одном тексте) помечаются `zontik=1` и
склеиваются только между собой: программа компании — не проект площадки.
