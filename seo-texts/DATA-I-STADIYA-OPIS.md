# Дата события и стадия проекта: чем меряем «ранность»

Замер и приборы, 16.09.2026. База `C:\sender\enrich.db`, таблица `signals`, 3 725 строк.
Всё ниже померено на живой базе и на живом коде сервера, а не на пересказе.

Вход «от события на ранней стадии» требует двух величин, которых в базе не было ни одной:
**когда** событие случилось и **на какой стадии** проект. Тип события (`event_type`) ни то,
ни другое: «модернизация» бывает и намерением, и перерезанной лентой. Замер по выборке это
подтвердил числом: один и тот же тип «модернизация» разошёлся по пяти стадиям
(эксплуатация 5, ввод 3, намерение 3, оснащение 3, стройка 2).

## 1. Почему `ts` пуст у 76,5% строк. Причина, а не факт

Цепочка, по которой дата доезжает до базы (живой `C:\sender\server\news_scan.py`,
1 866 строк):

```
коллектор кладёт item['pubDate']
   -> строка 1708:  rec['published'] = it.get('pubDate', '')
   -> строка 1781:  add_signal(..., ts=rec.get('published') or '')
   -> enrich_db.add_signal: INSERT OR IGNORE INTO signals(...)
```

**Сначала исключено ложное объяснение.** Версия «дата была, но её затёрли при повторной
записи» неверна: `add_signal` делает `INSERT OR IGNORE`, а не REPLACE, то есть однажды
записанная дата не переписывается никогда. Пустота приезжает из коллектора, и чинить надо
коллектор, а не запись.

**Причина: четыре коллектора из семи ставят `pubDate` пустым прямо в коде.**

| строка | коллектор | что кладёт | сколько строк в базе без даты |
|---|---|---|---|
| 518 | `_mk` внутри `col_xmlriver` (строка 481) - выдача Яндекса и Google | `'pubDate': ''` | почти все «доменные» источники: dzen.ru 54/54, kommersant.ru 49/49, neftegaz.ru 43/43, interfax-russia.ru 34/34, sdelanounas.ru 28/28 |
| 974 | `col_vk` - посты сообществ ВК | `'pubDate': ''` | ВКонтакте 1 126 из 1 126 |
| 640 | `col_frp` - ФРП | `'pubDate': ''` | ФРП 3 из 3 |
| 1051 | `col_browser` - гиперлокал за капчей | `'pubDate': ''` | единицы |

Остальные три дату переносят и в базе она есть: `_rss_items` (строка 427, коллекторы
google и regional), `col_rss` (строка 1028), `col_hh` (строка 621, `published_at`).

**Самое дорогое место - ВК.** В той же функции `col_vk` (начало на строке 930) дата поста
`p['date']` БЕРЁТСЯ на строке 958 и работает фильтром свежести (`fresh_ts(p.get('date'), days)`),
а на строке 974, шестнадцатью строками ниже, в item кладётся пустая строка. То есть дата была в руках, отработала
фильтром и выброшена. Это 1 126 строк, 39,5% всей пустоты.

**Три формата в одной колонке** - вторая половина беды, и она от других писателей
`signals` (`enrich_contacts.py` - 4 места, `news_cron.py` - 1):

```
RFC-822            Sun, 28 Jun 2026 03:18:57 GMT      480 строк   (RSS)
RFC-822, 2 цифры   Wed, 08 Jul 26 08:00:28 +0300      внутри тех же 480
ДД.ММ.ГГГГ         13.07.2026                         268 строк   (tender.pro)
ISO-месяц          2026-07                            117 строк   (ЕИС план 223-ФЗ)
```

Сортировка строкой по такой колонке не работает: «Sun, 28 Jun» всегда «меньше», чем
«Wed, 08 Jul», потому что сравниваются буквы, а не даты.

## 2. Нормализация даты: одно поле ISO и ярлык «откуда»

Модуль `sobytie_data.py`, без сети и без базы - годится и для старых строк, и для нового
события на входе.

**Три РАЗНЫЕ даты разведены по трём полям.** Раньше они были свалены в одну колонку или
отсутствовали:

| поле | что это | почему отдельно |
|---|---|---|
| `data_iso` | когда СООБЩЕНО о событии | это и есть дата новости |
| `data_vzyatiya` | когда МЫ это взяли (`seen_news` / `updated_at`) | известна почти всегда и потому соблазнительна, но событию не принадлежит |
| `data_plana` | срок из текста, лежащий в БУДУЩЕМ («запустят в 2027») | это срок проекта, а не дата события |

Смешивать первое со вторым нельзя, и вот доказательство прямо из выборки: среди
восстановленных карточек ВК попались посты **от 13.04.2021 и 07.06.2023**, взятые
конвейером в июле-августе 2026. По дате взятия они выглядят свежими сигналами. По дате
публикации это протухшее.

**Порядок надёжности** (первый сработавший выигрывает), ярлык пишется в `data_otkuda`:

```
karta_vk      дата поста ВК из wall.getById            - карточка первоисточника
karta         дата в карточке площадки (ЕИС, tender.pro): ISO или ДД.ММ.ГГГГ
karta_mesyac  в карточке только МЕСЯЦ (план закупки ЕИС) - точность помечена отдельно
rss           pubDate фида, RFC-822
url           дата в адресе статьи (/2026/07/16/) - её ставит редакция при публикации
tekst         полная дата из текста, НЕ лежащая в будущем
```

Ничего не сработало - `data_iso` пусто, а в `prichina_bez_daty` лежит причина словами, а
не пустота.

### Числа: сколько строк получают дату

По всей базе, только разбором того, что уже лежит (без единого сетевого вызова):

```
было ts непустых .................. 877 из 3 725 (23,5%), три формата
стало data_iso .................... 1 059 из 3 725 (28,4%), один формат
   rss 480 · karta 268 · url 147 · karta_mesyac 117 · tekst 47
осталось без даты ................. 2 666
```

Прирост дали два источника, которых раньше не читали вовсе: дата из адреса статьи (147) и
дата из текста (47), плюс разбор месяца из плана ЕИС (117 строк, которые числились как
«даты нет», хотя месяц был известен).

**Почему остальные 2 666 без даты - по причинам, а не одной кучей:**

```
1 508  поисковая выдача: коллектор ставит pubDate пустым, в ссылке даты нет
1 146  ВК: дата есть в карточке поста, коллектор её не переносит
   12  в карточке только планируемый месяц закупки, и он в будущем (это срок, не дата)
```

**ВК-строки добираются.** Замер на выборке: из 1 049 ссылок вида `vk.com/wall<id>_<id>`
взяты 24 из 24 запрошенных, `wall.getById` отдаёт до 100 постов за вызов, значит вся ВК-масса
закрывается 11 вызовами. Если добрать, дата будет у ~2 108 строк из 3 725 (56,6%).

### Контроль даты заведомо негодным входом

Прибор, который не умеет отказывать, «находит» дату везде. Проверено (`sobytie_data.kontrol()`):

```
'' · 'вчера утром' · '32.13.2026' · 'Bla, 99 Xyz 2026' · '01.01.1970' · '01.01.2099' ·
'12345' · 'ГОСТ 12.1.005-88' · '2026-13' · '2026'            -> дата НЕ выдана ни разу
url без даты · /v2/12/34/ · номер закупки · /2099/01/01/     -> дата НЕ выдана ни разу
```

И обратная половина того же контроля (иначе ноль проколов достигается отказом всему):
годные входы обязаны разбираться - RFC-822 с четырёх- и двузначным годом, ДД.ММ.ГГГГ, ISO,
ISO-месяц, дата 2009 года и дата в адресе разбираются верно, все шесть.

Границы гейта: 2005-01-01 .. сегодня+2. Нижняя изначально стояла на 2015 и **отбрасывала
живые даты** - замер по базе нашёл 5 строк с датами 2009, 2013, 2014. Это не мусор, а
ценный признак «сигнал протухший», поэтому граница опущена.

## 3. Классификатор стадии

Модуль `sobytie_stadiya.py`. Шкала от ранней к поздней, восемь значений:

```
1 намерение · 2 планирование · 3 проектирование · 4 финансирование ·
5 стройка · 6 оснащение · 7 ввод · 8 эксплуатация
```

Три первые - целевая очередь. Классификация идёт по тексту `what` через провайдерский
шлюз (`claude-fable-5`), промпт задаёт для каждой стадии её признаки и требует ДОСЛОВНУЮ
цитату-зацепку из текста: нет цитаты - нет и стадии.

**Два режима, один и тот же код и один и тот же промпт:**

```python
stadiya_odnogo(tekst)       # одно событие - новый поток идёт по одному
stadiya_pachkoy([...])      # пачка - для испытаний на старых строках, дешевле по вызовам
```

Провайдер берётся по месту запуска: в песочнице `gen_provider.call`, на сервере владельца
`verify_company._provider_call_stdlib` (там `gen_provider` нет). Отрасль ставится тем же
вызовом, широко: химия и нефтехимия, металлургия, пищевая, фармацевтика,
целлюлозно-бумажная, энергетика, стекольная, цементная, прочее.

### Четыре ответа, которые нельзя путать

```
ok                 модель назвала стадию
ne_opredelit       модель ОТВЕТИЛА «признаков стадии в тексте нет»
sboy_provaydera    вызов НЕ СОСТОЯЛСЯ (сеть, шлюз, пустой ответ) - НЕ ГОЛОС
net_v_otvete       ответ пришёл, но строку в нём потеряли - тоже НЕ ГОЛОС
```

Если сбой смешать с «не знаю», распределение по стадиям молча занижается на долю упавших
вызовов: чем хуже связь, тем «раньше» выглядит база. Сбой помечает ВСЮ пачку и ни одна её
строка в распределение не попадает.

## 4. Испытание на 60 старых строках

Старые строки - испытательный материал, не цель: приборы делались под новый поток. Выборка
60 строк, отобрана по жребию со сложением трёх слоёв: 25 ВК (самая большая дыра по датам),
20 из поисковой выдачи без даты, 15 с датой.

### Контроль А: выдуманный текст не должен получать уверенную стадию

В каждую из пяти пачек подмешана одна выдуманная сводка (производство дождевых облаков,
субботник с саженцами, «работаем в штатном режиме», ГОСТ на телепортацию):

```
приманок подмешано ........ 5
получили стадию ........... 0
все пять .................. ne_opredelit, уверенность «низкая»
две из пяти ............... модель сама пометила vydumka=true
```

### Контроль Б: упавший вызов не голосует

Отдельный заведомо ломаный вызов (несуществующая модель `model-kotoroy-net-999`):

```
статус ... sboy_provaydera      стадия ... пусто      ошибка ... HTTP 404 (записана в строку)
сбой отделён от «не знаю»: ДА
```

### Числа прогона

```

дата получена ............ 42   (karta_vk 24 · rss 9 · karta 6 · url 3)
без даты ................. 18   (16 поисковая выдача · 2 ВК без ссылки на пост)
дата плана из текста ..... 5
дата взятия известна ..... 60   (но в data_iso не попадает никогда)

статус ok ................ 49
ne_opredelit ............. 11

```

Распределение по стадиям (голосуют только 49 строк со статусом `ok`):

```

планирование .....  1          |  три самые ранние: 7 строк из 49
проектирование ...  2          |
финансирование ...  2
стройка .......... 11
оснащение ........  9
ввод ............. 12
эксплуатация .....  8
```

Отрасли: прочее 21 · металлургия 9 · пищевая 7 · энергетика 5 · химия и нефтехимия 4 ·
фармацевтика 1 · целлюлозно-бумажная 1 · цементная 1.

### Прибор ли это, или пересказ event_type

Проверено отдельно, потому что классификатор, повторяющий уже имеющееся поле, бесполезен:

```
модернизация -> эксплуатация 5 · ввод 3 · намерение 3 · оснащение 3 · стройка 2
новый завод  -> стройка 9 · ввод 3 · оснащение 2
запуск линии -> ввод 5 · оснащение 3 · эксплуатация 1
```

Один тип расходится по пяти стадиям - значит стадия несёт своё знание, а не переименовывает
тип.

Честная слабость рядом: у 7 строк из 49 зацепка покрывает почти весь текст (сводка вида
«строительство завода» - одна безглагольная строка). Там стадия вычитана из самой
формулировки, и это ближе к типу события, чем к стадии. **Ни одна из этих семи не попала в
три ранние стадии**, то есть целевая очередь однострочниками не надута.

### Правка промпта, сделанная по замеру

На первом прогоне сводка «рассматривает возможность строительства (детали не раскрыты)»
получила `ne_opredelit`, хотя это буквально намерение - самая дорогая для нас стадия. В
промпт добавлены слова-признаки намерения («рассматривает возможность», «изучает вариант»,
«ведёт переговоры о проекте»). Перепроверено на тех же 11 неопределённых строках плюс
приманки:

```
стало «намерение» ... 1 строка (та самая, верная)
осталось «не знаю» .. 10 строк (тексты вида «машиностроительный завод» - и правильно)
приманки ............ по-прежнему 0 стадий
```

То есть правка добавила точность, а не размыла гейт.

## 6. Где это лежит

Результат - в той же `C:\sender\enrich.db`, таблицей `signal_stadiya` (ключ `rid` - это
rowid строки `signals`), в стиле остальных таблиц базы:

```sql
CREATE TABLE IF NOT EXISTS signal_stadiya(
  rid INTEGER PRIMARY KEY,
  inn TEXT, source_url TEXT,
  data_iso TEXT, data_otkuda TEXT, data_tochnost TEXT,
  data_vzyatiya TEXT, data_vzyatiya_otkuda TEXT,
  data_plana TEXT, prichina_bez_daty TEXT,
  stadiya TEXT, nomer_stadii INTEGER, uverennost TEXT, zacepka TEXT, otrasl TEXT,
  status TEXT, vydumka INTEGER DEFAULT 0,
  model TEXT, updated_at TEXT)
```

Индексы: `stadiya`, `data_iso`, `inn`, `nomer_stadii`. Целевая очередь - один запрос:

```sql
SELECT s.inn, s.what, t.data_iso, t.stadiya
  FROM signal_stadiya t JOIN signals s ON s.rowid = t.rid
 WHERE t.status='ok' AND t.nomer_stadii BETWEEN 1 AND 3
 ORDER BY t.data_iso DESC;
```

## 7. Чтобы новый поток получал дату сразу

Разбор ради этого и делался. Правки в `news_scan.py` - по одной строке в четырёх местах:

```
строка  974  col_vk       'pubDate': ''  ->  'pubDate': str(p.get('date') or '')
                          дата уже прочитана на строке 958 для fresh_ts, добывать её заново не надо
строка  518  _mk (col_xmlriver)  'pubDate': ''  ->  дата из карточки выдачи, если её отдаёт xmlriver;
                          иначе оставить пустой и положиться на дату в адресе статьи
строка  640  col_frp      'pubDate': ''  ->  дата из карточки новости ФРП
строка 1051  col_browser  'pubDate': ''  ->  дата со страницы
```

Вызов стадии на одном событии ставится сразу после `add_signal` в `_persist_event`:

```python
obrabotat_sobytie(cx, inn=inn, source=rec.get('source_name'),
                  source_url=rec.get('source_url'), what=_w,
                  published=rec.get('published'), vk_epoch=rec.get('vk_epoch'))
```

Правки в живой `news_scan.py` НЕ внесены: это код владельца в рабочем конвейере, менять его
без спроса нельзя. Готовы к внесению.

## 8. Что не вышло и чего не знаем

- **Даты события по-прежнему нет ни у одной строки.** `data_iso` - это дата СООБЩЕНИЯ о
  событии, а не дата самого события. Из текста извлекается только срок в будущем
  (`data_plana`, 329 строк по всей базе). Строки «завод запущен» дают дату публикации, и
  событие могло случиться раньше.
- **Тир «карточка источника» закрыт только для ВК.** Для площадок (ЕИС, tender.pro) дата
  берётся из того, что уже записано в `ts`; перезапрашивать карточки ради даты не пробовали.
- **1 508 строк из поисковой выдачи так и остаются без даты** - в ссылке даты нет, в тексте
  нет. Единственный путь - перезапросить страницу статьи и взять дату оттуда; не делали.
- **Классификатор проверен на 60 строках**, не на всей базе: владелец прямо снял прогон по
  3 725 старым строкам. Точность на новом потоке может отличаться, потому что там тексты
  длиннее (в `what` у нового потока попадает выжимка из полного текста статьи).
- **Согласие двух независимых разборов не мерено.** Каждая строка классифицирована один
  раз; насколько устойчив ответ при повторном вызове - неизвестно.
