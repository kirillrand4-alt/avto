# Конвейер «новость → компания → письмо»

Состояние на 2026-07-28. Документ для другой сессии: как лид проходит путь от
строчки в новостной ленте до письма в очереди подтверждений, что где живёт и
на какие грабли уже наступали.

Границы: `seo-texts/server/` (сбор и обогащение) + `seo-texts/sender/`
(генерация и отправка). Реальная отправка — ТОЛЬКО ручная, по подтверждению
оператора (холд в CLAUDE.md); автоматическая рассылка и прогрев запрещены.

---

## 1. Схема в одну строку

```
коллекторы → дешёвые фильтры → дедуп → скачивание статьи → extract_event (LLM)
   → фильтр РФ → dadata (ИНН/ОКВЭД) → division kc|meyer → сигнал в enrich.db
   → разведка контактов: сайт → сверка по ИНН → роли → лучший адрес
   → панель: выбор сигнала → блок получателя → генерация письма → гейт
   → верификатор → очередь подтверждений → оператор → SMTP
```

Первая половина (до сигнала) — `server/news_scan.py`. Разведка контактов —
`server/enrich_contacts.py`. Вторая (от сигнала до письма) — `sender/ai_quota.py`
+ `sender/ai_letter.py`.

## 2. Сбор новостей (`server/news_scan.py`)

### 2.1. Коллекторы

| Функция | Источник | Заметки |
|---|---|---|
| `col_vk` | VK `newsfeed.search` | районные паблики, гиперлокал; только сообщества, не реклама/репост |
| `col_xmlriver` | Google + Яндекс через xmlriver | основной массовый источник, свои воркеры на движок |
| `col_google` | выдача Google | легаси-путь |
| `col_rss` / `col_regional` | RSS-ленты доноров | доноры копятся в таблице `donors` |
| `col_zakupki` | ЕИС (zakupki.gov.ru) | закупки как капекс-сигнал |
| `col_hh` | публичная выдача hh.ru | наём в компрессорную = есть компрессорное хозяйство |
| `col_frp` | Фонд развития промышленности | займы под проекты |
| `col_browser` | произвольные URL через дельфин | ручные добивки |

Набор включённых коллекторов — `args['collectors']`, дефолт
`['google','zakupki','hh','frp']`. Оркестрация — `collect_all(args)`.

Отдельный ежедневный прогон по донорам: `server/news_schedule/news_cron.py`
(задача Windows, 07:00). Он импортирует `news_scan` и переиспользует его
функции; своей LLM-логики не имеет.

### 2.2. Дешёвые фильтры (до LLM — берегут деньги)

* `_CAPEX_KW` — обязательный капекс-сигнал в тексте;
* `_VK_TRASH` — минус-словарь мусора (для ВК);
* `fresh_ts` / `fresh` — окно свежести (`--days`);
* кросс-чанковый дедуп `seen_news` по `_news_key(it)` — атомарный `seen_add`
  ДО обращения к провайдеру. **Важно:** повторно прогнать те же новости
  нельзя, пока ключ лежит в `seen_news` — для пересборки есть отдельный режим
  (см. §6).

### 2.3. Полный текст статьи (правка 28.07)

`FULLTEXT_CAP = 20000`, `_page_text(url)` и `fetch_article(it)`.

Раньше классификатор видел только заголовок, и детали («какие именно линии»)
до промпта не доезжали — средняя длина `what` по базе была 56 символов.
Теперь статья скачивается и отдаётся целиком (до 20к).

Правила:
* качаем ПОСЛЕ дедупа — GET тратится только на то, что всё равно пойдёт в LLM;
* `collector == 'hh'` пропускаем: там ссылка на вакансию, а не на статью;
* страница без текста (антибот, редирект-огрызок, <400 символов) → остаёмся
  на заголовке, как раньше;
* `article_chars` в записи события — телеметрия, сколько реально дошло.

## 3. Классификация события (`extract_event`)

Модель — **только `claude-fable-5`** через провайдерский API. haiku на этой
задаче даёт `is_capex=false` на явные капекс-события (терялось 99% событий,
инцидент чанка №1) — не менять.

Возвращает JSON: `is_capex`, `company`, `event_type` (новый завод |
модернизация | запуск линии | расширение | инвестиции | тендер | найм |
прочее), `what` (1-2 предложения конкретики — ЭТО читает генератор письма),
`region`, `country`, `sum`, `hotness` (1-5).

После модели — фильтр «только РФ» (в лентах мелькают Казахстан и Беларусь).

### 3.1. ВК: первоисточник и защита «источник не о том»

`_vk_primary(post, text)` достаёт ссылку-первоисточник из вложения или из
текста поста (сам ВК исключаем). Прежде чем поставить её ссылкой лида,
`_src_confirms(url, company, post_text)` скачивает страницу и проверяет, что
она о ТОЙ ЖЕ компании: токены названия по 5-символьному префиксу (переживает
падежи), без названия — ≥2 длинных слова из поста. Возврат
`match | no-match | fetch-fail`; не `match` → остаёмся на ссылке поста.
Сам пост сохраняется в поле `vk_post` как пруф, где нашли.

## 4. Компания: имя → ИНН (`dadata_suggest`)

Вход — `company` от модели, выход — ИНН, ОКВЭД, полное имя, статус, регион,
ЕГРЮЛ-почты, `confidence`. Скор 0 отсекается внутри: лучше лид без ИНН, чем
ИНН тёзки.

Дальше:
* `division_of(okved)` → `kc` | `meyer` | `kc+meyer` — направление компании;
* `icp_fit` — первые две цифры ОКВЭД против `ICP_OKVED`;
* лид без ИНН НЕ теряется: уходит в jsonl на ручной резолв.

## 5. Запись сигнала (`_persist_event`)

Дуал-сток, оба durable, пишутся СРАЗУ на каждое событие:

1. `news_stream.jsonl` — append + `fsync` (переживает таймаут/рестарт);
2. `enrich.db` (`C:\sender\enrich.db`, WAL): `companies`, `signals`, `emails`,
   `donors`, `seen_news`, `stage_log`.

`signals`: `UNIQUE(inn, source, what)`, вставка `INSERT OR IGNORE`. Кап на
длину `what` **снят 28.07** (был `[:400]`, резал выжимку на полуслове).

Правило durability (урок рестарта 25.07): результат ЛЮБОГО серверного op
писать в серверное хранилище, а не только в возвращаемый JSON — песочница
при рестарте откатывается к снимку.

## 6. Пересборка старых сигналов (`re_enrich`)

Режим `news_scan.py` с `{"re_enrich":1,"limit":N}`. Зачем: сигналы, собранные
до §2.3, содержат огрызки заголовков.

Что делает: берёт сигналы с `source_url LIKE 'http%'` и `source != 'hh'`,
качает статью (для ВК — текст поста через `wall.getById` + проверенный
первоисточник), гоняет `extract_event` по полному тексту и пишет НОВУЮ жирную
строку сигнала рядом со старой (`hotness = max(старый, новый)`). Выборка для
письма сортирует по `hotness`, затем по длине `what` — жирная строка
побеждает сама.

Резюмируемость: `seen_news('reenrich|<rowid>')`, отметка ПОСЛЕ обработки;
свежесозданная строка сразу помечается сделанной, иначе следующий чанк
оплатит её повторно. Телеметрия — `re_enrich.jsonl`.

Итог прогона 28.07: 825 кандидатов, 668 обогащено, средняя длина `what` у
верхнего сигнала выросла с 56 до 186 символов, 106 ВК-лидов переехали на
проверенный первоисточник.

## 7. hh: наём как сигнал

`server/hh_scan.py` парсит стейт `HH-Lux-InitialState` публичной выдачи (API
hh закрыт без токена). Оп `hh_signals` в `enrich_contacts.py` матчит
работодателя с базой обзвона по имени, недостающих резолвит через dadata и
пишет сигнал `source='hh'`, `event_type='наём в компрессорную'`.

Ссылка-первоисточник: конкретная вакансия → страница работодателя → поисковая
выдача (последний фолбэк). Есть ретро-фикс: у старых строк с выдачей
`source_url` подменяется на вакансию того же работодателя. Сейчас 399 из 435
hh-сигналов ведут на конкретную вакансию.

## 7а. Кому писать: сайт компании → контакты → выбор адреса

Между «есть ИНН» и «есть письмо» стоит отдельный конвейер разведки контактов —
`server/enrich_contacts.py`, функция `enrich_one(company, pace)`. Новость даёт
только НАЗВАНИЕ; адрес приходится добывать.

### Шаг 1. Отсев и попутные сигналы

* `_is_competitor` — производителей компрессоров и насосов не разведываем вовсе;
* попутно собираются сигналы: ОПО (`find_opo_signal`), компрессорные вакансии
  этой компании (`find_hh_compressor`), контакты закупщика из карточек ЕИС
  (`find_zakupki_contacts`, роль «закупки (конт. лицо)», часто с ФИО).

### Шаг 2. Найти САЙТ компании

Порядок: кэш `ИНН→сайт` в enrich.db → **xmlriver** (чистая выдача, без капчи —
основной канал) → фолбэки `list-org` и DDG под семафором=1 → Chromium →
антидетект-дельфин для сайтов под Cloudflare. Источник фиксируется в
`site_source` (`cache:enrich-db`, `xmlriver`, `listorg`, …).

`_is_own_site` отбрасывает агрегаторы и каталоги — нужен сайт самой компании.

### Шаг 3. Сверка «это точно ТА компания»

Ключевой момент: совпадения имени мало (тёзок много). Поэтому у каждого адреса
проставляется `verified_by`:

| Значение | Что означает |
|---|---|
| `inn` | на странице найдены реквизиты с НАШИМ ИНН — самый надёжный якорь |
| `site` | адрес взят с сайта, домен которого сошёлся с компанией |
| `card-name-match` | карточка каталога с совпадением названия |
| `name` | только по названию — слабо, требует глаз |

В карточке подтверждения это разворачивается в блок провенанса
(`sender/infopanel.py`, `_contact_provenance`): готовая строка «откуда знаем»,
ссылка на страницу-источник, флаги `provenance_trusted` и
`provenance_conflict` (например, адрес с сайта, а сайта в карточке нет или он
чужой) плюс `domain_mismatch` — домен почты не совпадает с доменом сайта.
Конфликт не прячется: он показывается оператору, а не выдаётся за факт.

### Шаг 4. Роли адресатов

Со страниц контактов вытаскиваются адреса (`_harvest_from_html`: mailto,
JSON-LD, деобфускация) и телефоны; мусор отсекается `_is_junk_email` —
платформенные домены конструкторов, `noreply` и подобное.

Роль каждому адресу ставит разбор страницы (LLM + эвристика): «снабжение/
закупки», «гл.инженер», «директор», «продажи», «приёмная», «бухгалтерия»,
«общий».

### Шаг 5. Выбор ОДНОГО адреса для письма

`_best_by_role(emails, model_pick)` — жёсткий порядок ролей:

```
снабжение/закупки > гл.инженер > директор > продажи > приёмная > бухгалтерия > общий
```

Ответ модели используется ТОЛЬКО как разрешение ничьей внутри одной роли —
порядок ролей главнее мнения модели. Результат кладётся в
`companies.best_email`; `smtp_reject`-адреса из выбора исключаются.

### Шаг 6. Сборка кампании (`op news_campaign`)

Джойн трёх источников: сигналы (новостной повод) + enrich.db (контакты) + база
обзвона (город, точное направление). Правила отбора:
* конкуренты — не берём;
* строк без единого адреса — не берём («нечем слать»);
* направление: компания есть в базе обзвона → берём точное оттуда; нет →
  предложенное по ОКВЭД из checko с пометкой «подтвердить»;
* приоритет строк: `verified` + наличие в базе + `hotness` сигнала.

В карточку оператора едут и `best_email`, и ВСЕ найденные контакты
(`all_contacts` — адрес, роль, страница-источник), чтобы человек мог сменить
получателя одним кликом. Смена адреса в панели пересобирает блок контакта.

### Что здесь слабое место

Роль ставится по разбору сайта, а он есть не у всех: у части компаний
единственный адрес — общий `info@`. Для таких промпт письма умеет адресовать
функцию прямо в теме («для снабжения: …»), но это компенсация, а не решение.
Второй риск — `verified_by='name'` без якоря по ИНН: формально контакт есть,
но это может быть тёзка; такие карточки оператор должен смотреть глазами.

## 8. Сигнал → письмо (панель, `sender/ai_quota.py`)

### 8.1. Выбор сигнала — `_digest(inn)`

Берёт до 5 сигналов компании, сортировка `hotness DESC, LENGTH(what) DESC`.
Вакансия считается поводом ТОЛЬКО если она про профильную технику
(компрессорщик, слесарь КИПиА, оператор сортировки); вакансии кладовщиков и
охраны пропускаются — берётся следующий сигнал. Возвращает `news_detail`,
`news_type`, `news_sum`, `news_url`, `digest`.

### 8.2. Блок получателя — `_request(recipient)`

Собирает `extra` для промпта:
* `news_object` / `news_detail` / `news_url` — из дайджеста. **Правка 28.07:**
  свежий жирный дайджест бьёт устаревший тощий `news_object`, вшитый в
  кампанию при её создании (иначе перегенерация оставалась на огрызке);
* `city` — СНАЧАЛА из новости, потом из карточки; источник помечается, и при
  «городе из карточки» промпт запрещает привязывать к нему событие;
* `equipment` — категории оборудования по ОКВЭД из базы обзвона;
* `role` (роль адресата по разбору сайта), `revenue` → размер бизнеса;
* `idea` — только для GENERIC-писем (три линзы + судья).

### 8.3. Направление письма — `ai_letter.target_division`

Приоритет: явное указание → новость → потребности → метка базы → профиль →
`kc` по умолчанию. Направление письма (`letter_division`) отличается от метки
компании и главнее её: у АЛРОСЫ метка `meyer` по ОКВЭД, а новость и
потребность — компрессорные. По направлению ПИСЬМА раскладывается очередь,
подбирается ящик и подставляется бренд подписи («Компрессор Центр» /
«Руспром Мейер»).

### 8.4. Генерация — `sender/ai_letter.py`

`gen_prompt` → правила направления (`RULES_KC` / `RULES_MEYER`) + факты
(`kb/`) + блок получателя с НАЗНАЧЕННОЙ механикой захода (ротация по партии).

Ключевое из правил (полностью — в файле):
* правило 19 «КАНОН РЕДАКТОРА» (28.07, выведено из правок редактора на
  реальных отправленных письмах): тема «Вопрос по …», заход-пересказ новости
  с названием компании, связка без страшилок, открытый вопрос об
  актуальности, предложение помощи первым шагом, плотные абзацы;
* запрет длинных тире, «мы», канцелярита, чисел не из фактов, слова
  «хозяйство» в сочетании с компрессорным/воздушным/энерго;
* NEWS против GENERIC: без данных новости имитировать событие запрещено.

`best_of` (дефолт 3, конфиг `ai_quota.best_of`): N независимых вариантов
письма разными механиками → судья-редактор выбирает ближний к канону. Сбой
варианта или судьи не роняет письмо — остаётся вариант №0.

Дальше цикл: механический `gate()` → LLM-верификатор (`vf_prompt`) → фикс
нарушений, до `rounds` кругов; что не починилось — в брак.

### 8.5. Очередь подтверждений

Письмо ложится в `confirm_reviews` (pending) вместе с инфо-панелью
(`infopanel.build_panel`: скоринг, сигнал, контакт, комплаенс, история).
Оператор правит и подтверждает — только тогда идёт SMTP. Правка сохраняется
как золотая пара (диф) — источник для будущих правок промпта.

При отправке: подпись по направлению ящика, согласование рода с полом
менеджера (`sender/gender_agree.py`), пиксель открытий, копия в IMAP-папку
«Отправленные», запись фактического текста в `messages.body_rendered`.

## 10. Грабли (проверено, не наступать заново)

1. **Модель.** `extract_event` — только fable. haiku ломает капекс-детект.
2. **Дедуп.** `seen_news` не даст переобработать новость; для пересборки —
   режим `re_enrich`, а не повторный скан.
3. **hairpin-NAT.** Сервер, качая со своего же публичного адреса, рвётся
   примерно на 384 КБ. Большие файлы — из локального хранилища дропа
   (`C:\seostat\drop\drop-storage`) или Range-кусками.
4. **Конфиг отдаёт `mappingproxy`.** `isinstance(x, dict)` на секциях
   конфига — False. Проверять через `collections.abc.Mapping`, иначе настройка
   молча игнорируется.
5. **Живой конфиг перебивает дефолты кода.** Выдуманные адреса API постмастера
   в `sender.yaml` полгода давали 404, хотя в коде дефолт был уже правильный.
6. **`body_rendered`** до 28.07 писал только `confirm_decide`; ручная отправка
