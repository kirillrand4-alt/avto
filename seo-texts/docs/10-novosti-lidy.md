## 1. Что это и зачем

### 1.1. Задача

Найти компании, которым **скоро понадобится промышленное оборудование** «Руспрома»
(компрессоры / генераторы азота-кислорода — направление `kc`; фотосепараторы /
рентген-инспекция — направление `meyer`), поймав их **в момент капитального
события**: стройка завода, запуск цеха или линии, модернизация, расширение,
инвестпроект, займ ФРП, резидентство ОЭЗ/ТОР, всплеск найма под расширение.

Логика простая: компания, которая только что объявила о новом цехе, через несколько
месяцев будет закупать компрессорное хозяйство. Попасть к ней письмом до тендера —
и есть ценность этого пайплайна.

Результат работы — строки в `signals` таблицы `enrich.db` (система-источник-истины
всего обогащения, см. `seo-texts/docs/08-obogashchenie-yadro.md`): «у компании с
ИНН X произошло событие Y, вот ссылка-первоисточник Z, горячесть 1-5». Дальше
сигналы читают скоринг (`lead_scoring.py:175`) и лид-деск инфопанели
(`sender/infopanel.py:80-88`), а генератор письма вставляет конкретику события
в текст.

### 1.2. Два разных запуска — не путать

В области ДВА независимых исполнителя, и это главное, что надо понять первым:

| | `news_scan.py` | `news_schedule/news_cron.py` |
|---|---|---|
| Кто запускает | служба-раннер `job_runner.py` по заданию с дропа | **планировщик Windows, ежедневно 07:00** |
| Как параметризуется | JSON на stdin | аргументы командной строки (`argparse`) |
| Источники | 9 коллекторов (ВК, xmlriver, zakupki, hh, ФРП, RSS-каталог, Google News, браузер, доноры) | ТОЛЬКО доноры из таблицы `donors` |
| Режим | разовые кампании и самочейнящиеся свипы по каталогу запросов | инкрементальная ежедневная подпитка «обновить всё» |
| Обогащение контактов | опционально (`enrich:true`) | **нет, никогда** |
| Записан ли в `job_runner.ALLOW` | да (`job_runner.py:67`) | **нет** — раннер его запускать не умеет |

`news_cron` переиспользует `news_scan` **импортом**, а не копипастой
(`news_cron.py:50`, реюз `_get`/`_rss_items`/`fresh`/`_news_key`/`_CAPEX_KW`/
`extract_event`/`dadata_suggest`/`division_of`). Тонкая склейка (запись события)
дублируется, потому что в `news_scan` она живёт замыканиями внутри `main()`
(`enrich_ev` на `news_scan.py:1394`, `_persist_event` на `news_scan.py:1452`)
и импортом не достаётся — это прямо объяснено в `news_cron.py:17-19`.

### 1.3. Где заканчивается эта область

Эта область **порождает лиды и сигналы**. Она НЕ ищет контакты (это
`enrich_contacts.py`, раздел 08), НЕ считает скоринг (`lead_scoring.py`) и НЕ
шлёт письма (`sender/`, раздел 09). Единственное исключение — `news_scan` умеет
позвать `enrich_contacts.enrich_one` инлайн, если ему передали `enrich:true`
(`news_scan.py:1499-1518`).

## 2. Точки входа и как запустить

### 2.1. `news_scan.py` — через раннер (боевой путь)

Скрипт **не запускается руками из песочницы**: он читает JSON со stdin и рассчитан
на исполнение на сервере владельца (РФ-IP, CapMonster, доступ к РФ-сайтам). Канон
запуска — `run_on_server.py` (`seo-texts/server/run_on_server.py:86-91`):

```bash
python run_on_server.py news_scan '{"collectors":["zakupki","hh","frp"],"days":90}'
```

`run_on_server.py` подписывает задание HMAC-ом (`JOB_SECRET`), кладёт
`job-<id>.json` на дроп и ждёт `result-<id>.json`. Раннер проверяет подпись и
allowlist и запускает **ровно** `news_scan.py`, аргументы уходят через stdin
(`job_runner.py:62-73`, `job_runner.py:295-303`).

> **Запрещено текущей сессии.** По правилам задачи `run_on_server.py`,
> submit заданий раннеру, `drop_client.sh up/del` и вызовы провайдерского API
> не выполняются. Команды ниже — справочные.

Разово, локально на сервере, тот же скрипт можно кормить и через pipe:

```
echo '{"collectors":["frp"],"days":30}' | python news_scan.py
```

(`news_scan.py:1036-1039` — `json.load(sys.stdin)`, при ошибке разбора `args={}`.)

### 2.4. `news_cron.py` — ежедневная задача Windows (главное в этой области)

**Это единственная часть репозитория, работающая по расписанию сама, без участия
человека и без раннера.** Ни один другой документ репозитория её не описывает.

#### Что именно и когда запускается

`setup-news-schedule.ps1` (запускается **на сервере**, владельцем/оркестратором,
не сессией — прямо сказано в `setup-news-schedule.ps1:4`):

1. проверяет наличие питона `C:\Program Files\Python311\python.exe` и скрипта
   `C:\sender\server\news_cron.py`, иначе падает (`:29-30`);
2. генерирует обёртку `C:\sender\server\news_cron_task.cmd` в кодировке ASCII
   (`:35-39`) со строкой:
   `"C:\Program Files\Python311\python.exe" -X utf8 "C:\sender\server\news_cron.py" --days 30 >> "C:\sender\server\news_cron.out" 2>&1`
3. регистрирует задачу планировщика (`:42`):
   `schtasks /Create /F /TN RuspromNewsScan /SC DAILY /ST 07:00 /RU SYSTEM /TR "<обёртка>"`

Итого: **задача `RuspromNewsScan`, ежедневно в 07:00 по локальному времени сервера
(МСК), от имени `SYSTEM`, с окном свежести 30 дней, лог дописывается в
`C:\sender\server\news_cron.out`.** `/F` делает пересоздание идемпотентным,
`/RU SYSTEM` — прогон не зависит от логина владельца.

Обёртка `.cmd` нужна, потому что `schtasks` калечит вложенные кавычки и
перенаправление вывода в `/TR`; `-X utf8` — чтобы русская сводка не падала на
кодировке консоли службы (`:32-34`).

Сам файл `.ps1` лежит в **UTF-8 с BOM** и это не случайность: PowerShell 5.1
читает `.ps1` в системной кодировке, без BOM кириллица разваливалась и ломала
парсер на амперсанде (сообщение коммита `b45c472`). **Не пересохраняйте его без
BOM.**

## 3. Как устроено внутри

### 3.1. Общий конвейер `news_scan`

```
коллекторы -> дедуп в прогоне -> капекс-предфильтр (regex) ->
кросс-прогонный дедуп (seen_news в БД) -> fable: extract_event ->
фильтр «только РФ» -> dadata: имя -> ИНН -> запись СРАЗУ (jsonl + enrich.db) ->
[опц.] контакты -> сортировка -> JSON на stdout
```

Ключевая идея — **дешёвые фильтры раньше дорогих**. Провайдерский API (fable) —
самое дорогое звено, поэтому до него стоят три бесплатных отсечки: дедуп по
канон-URL, regex-предфильтр `_CAPEX_KW`, и дедуп по таблице `seen_news`
(«эта ссылка уже обрабатывалась когда-либо»).

### 3.2. Коллекторы (`collect_all`, `news_scan.py:945-1012`)

Их **девять**, не восемь (в `NEWS-LEADS-PIPELINE.md` §2 перечислено восемь —
там нет `rss`):

| Ключ | Тир | Функция | Что это |
|---|---|---|---|
| `google` | 4 | `col_google` (`:432`) | Google News RSS, 5 потоков, джиттер |
| `regional` | 1/4 | `col_regional` (`:452`) | RSS-каталог из `news-sources.json`, 6 потоков |
| `xmlriver` | 4 | `col_xmlriver` (`:480`) | выдача Google **и** Яндекса через xmlriver.com |
| `zakupki` | 3 | `col_zakupki` (`:583`) | ЕИС `zakupki.gov.ru` RSS расширенного поиска |
| `hh` | 5 | `col_hh` (`:598`) | `api.hh.ru/vacancies` — вакансии как маркер расширения |
| `frp` | 2 | `col_frp` (`:626`) | новости ФРП (frprf.ru), скрейп ссылок |
| `vk` | 1 | `col_vk` (`:674`) | `newsfeed.search` ВК — гиперлокал, районные паблики |
| `browser` | 1 | `col_browser` (`:772`) | конкретные URL через `browser_probe` (Playwright + CapMonster) |
| `rss` | 2 | `col_rss` (`:732`) | опрос RSS-лент доноров из `enrich.db` (`donors.rss!='' AND status='live'`) |

Единица данных на выходе коллектора — `{title, link, pubDate, source, tier,
collector, query}` (+`company_hint`/`equipment` у hh, `captcha_type` у browser).

Про xmlriver стоит знать отдельно (`:480-580`): это платный шлюз, который делает
поисковый запрос **своими** серверами, поэтому DPI-блокировка Google на сервере
владельца не мешает. Свежесть задаётся по-разному: узкие окна нативно
(`tbs=qdr:d|w|m` у Google, `within` у Яндекса), широкие (> 31 дня) — точным
диапазоном `cdr:1,cd_min..cd_max` у Google и оператором `date:>YYYYMMDD` в самом
запросе у Яндекса, при этом `within` для Яндекса выключается (`within=0`), иначе
он режет до 30 дней и конфликтует с `date:>` (`:498-504`). Каналы аккаунта
раздельные: 10 Google + 10 Яндекс, поэтому два независимых пула потоков
(`:560-579`).

ВК чистится **четырьмя** слоями ещё до конвейера (`:697-706`): только сообщества
(`owner_id<0`), не реклама и не репост, обязателен капекс-сигнал `_CAPEX_KW`,
минус-словарь мусора `_VK_TRASH` (`:650-653`) и детектор дайджест-подборок
`_vk_is_digest` (`:658-668`).

### 3.3. Фильтры до провайдера

1. **Дедуп в прогоне** (`:993-1001`) по `_news_key` (`:238-246`): канон-URL из
   `_norm_url` (`:229-235`) — без схемы, `www`, якоря, `utm_*`/`yclid`/`gclid`/
   `from`/`ref`/`_openstat`, хвостового слэша, в нижнем регистре. Если пути нет —
   фолбэк «домен + нормализованный заголовок» (ловит републикации).
2. **Капекс-предфильтр** (`:1002-1011`): для шумных коллекторов
   (`regional`, `google`, `xmlriver-*`) заголовок обязан матчить `_CAPEX_KW`
   (`:45-49`) — большой regex про завод/цех/запуск/стройку/инвестиции/ФРП/ОЭЗ.
   `zakupki`/`hh`/`frp`/`vk` уже таргетированы, их пропускают без фильтра.
3. **Кросс-прогонный дедуп** (`:1397-1400`): `db.seen_add(_news_key(it))` —
   `INSERT OR IGNORE` в `seen_news`, атомарно, под локом. Возвращает `False`, если
   ссылку уже видели когда-либо → провайдер не вызывается вообще.

### 3.4. Капекс-классификация (`extract_event`, `news_scan.py:793-822`)

Один вызов провайдерского API на заголовок. Промпт короткий (~400 токенов),
требует СТРОГИЙ JSON:

```
{"is_capex":true/false,"company":"...","event_type":"новый завод|модернизация|
запуск линии|расширение|инвестиции|тендер|найм|прочее","what":"1-2 полных
предложения с конкретикой","region":"...","country":"РФ если в России",
"sum":"...","hotness":1-5}
```

Явные отсечки в промпте: жильё, дороги/мосты, школы/больницы/соцобъекты, парки,
офисы/ТЦ, анонсы без компании-инвестора, рекламные посты. `company` требуется
**в именительном падеже как в ЕГРЮЛ** — это правка, без которой ломался следующий
шаг (dadata не понимает склонений).

Модель **только `claude-fable-5`**. В коде это зафиксировано дважды с одинаковым
объяснением (`news_scan.py:1377-1381`, `news_cron.py:192-194`): haiku на этой
задаче ставил `is_capex=false` на явные капекс-события и терял ~99% событий
(инцидент чанка №1). Менять модель — только осознанно через `extract_model` /
`--extract-model`.

Транспорт вызова — `verify_company._provider_call_stdlib`
(`verify_company.py:167-217`): stdlib, стриминг SSE, тело gzip-ом мелкими кусками
по 1200 Б с паузами 0.15 с. Причина не косметическая: маршрут сервера до шлюза
душит большие однокусковые POST (> ~2 КБ → `RemoteDisconnected` через ~60 с).
Фолбэк — обычный одиночный POST.

Сразу после модели — фильтр «только РФ» (`:1404-1407` и `news_cron.py:86-89`):
если `country` заполнена и не содержит `рф`/`росс`/`russia`, событие выбрасывается
(в лентах регулярно мелькают Казахстан и Беларусь).

### 3.5. Имя компании → ИНН (`dadata_suggest`, `news_scan.py:891-941`)

Самая хитрая часть, и она такая из-за эмпирики: **dadata не понимает склонений**
(«Северстали» → пусто). Поэтому:

1. `_name_variants` (`:839-870`) строит до 6 вариантов имени: как есть; ядро из
   кавычек; без ОПФ и контекст-слов (`_OPF_WORDS`, `:826-830`); расклонка по
   суффиксам `_DECL_SUF` (`:834-836`, «Северстали»→«Северсталь»,
   «Уралмаше»→«Уралмаш»).
2. Каждый вариант уходит в `suggestions.dadata.ru/.../suggest/party` с `count=3`,
   с ретраями и бэкоффом на 429/500/502/503 (`:904-918`).
3. Ответы ранжируются `_match_score` (`:873-888`): сколько содержательных токенов
   запроса нашлось в предложении, сравнение по префиксу в 5 символов (переживает
   падежи), длинный редкий токен (≥9 символов) даёт двойной вес.
4. **`score = 0` → ИНН не приклеивается вообще** (`:929-930`). Лучше лид без ИНН,
   чем чужой ИНН тёзки. `confidence`: `high` при `score ≥ 2`, `low` при 1.
5. При `score ≥ 2` перебор вариантов прерывается — не жжём лимит dadata (`:925-926`).

Возвращается также `okved`, полное имя, `region`, `status` и **email из ЕГРЮЛ**
(`egrul_emails`, до 3 штук) — dadata отдаёт его в том же ответе, раньше
выбрасывали.

По ОКВЭД считаются два поля:
* `icp_fit` — попадает ли 2-значный префикс в `ICP_OKVED` (39 разделов, реально
  присутствующих в обзвон-базе, `:55-60`);
* `division` — `division_of` (`:249-266`): сначала точный маппинг владельца
  (`enrich_db.OKVED_DIRECTIONS`, 77 кодов), при промахе — 2-значный фолбэк с
  дефолтом `kc` (сжатый воздух нужен почти любому производству). Значения:
  `kc` | `meyer` | `kc+meyer`.

### 3.6. Запись: дуал-сток, мгновенно (`_persist_event`, `news_scan.py:1452-1487`)

Каждое событие пишется **сразу**, не дожидаясь конца задания — иначе таймаут
раннера (30 мин, `job_runner.py:58`) съедал бы результат целого чанка.

1. `news_stream.jsonl` — append + `flush` + `os.fsync`. Туда идёт **всё, включая
   события без ИНН** (лид на ручной резолв).
2. `enrich.db`:
   * `bump_donor(домен источника)` — **безусловно**, даже без ИНН. Так копится
     durable-частота доноров;
   * при наличии ИНН: `upsert_company` + `add_signal` (+ `add_email` для
     ЕГРУЛ-адресов).

`add_signal` — `INSERT OR IGNORE` с `UNIQUE(inn, source, what)`
(`enrich_db.py:32-34, 321-329`), поэтому повтор события не плодит дубли.
`seen_add` — `INSERT OR IGNORE` в `seen_news`, возвращает `True` только если
ключ новый (`enrich_db.py:331-341`).

Одно соединение SQLite на весь пул потоков, доступ сериализован внешним локом
(`_ns_lock`, `news_scan.py:1435`; `lock` в `news_cron.py:142`), БД в режиме WAL.

### 3.7. Что делает ежедневный `news_cron.run` (`news_cron.py:138-220`)

```
migrate(db)                       # добить колонки/таблицы, идемпотентно
donors_to_poll(db)                # кого опрашивать
--- фаза 1: опрос доноров, ПОСЛЕДОВАТЕЛЬНО (вежливость важнее скорости) ---
  донор с rss  -> _poll_rss_donor  (просто читаем ленту)
  донор без rss-> no_rss.poll_donor (запомненный способ, иначе лестница)
  каждая ссылка -> seen_add -> новая? -> _CAPEX_KW -> в очередь на извлечение
--- фаза 2: извлечение, ПАРАЛЛЕЛЬНО (8 потоков) ---
  _extract_one: fable -> фильтр РФ -> dadata -> jsonl + enrich.db
record_run(...)                   # строка метрик в scan_runs
печать JSON-сводки + текстовой сводки свежести
```

Идемпотентность держится на `seen_news`: ссылка обрабатывается **один раз за всю
жизнь системы**, поэтому повторный запуск честно показывает нули и не тратит
провайдера (`news_cron.py:21-23`, тест
`tests/test_news_cron.py:85-101`).

Устойчивость: каждый донор в своём `try/except` (`:162-166`), падение одного идёт
в лог и в `fail_streak`, прогон продолжается (тест
`tests/test_news_cron.py:115-134`).

Метрика «новых сигналов» считается **дельтой** `COUNT(*) FROM signals` до и после
(`:149`, `:211`) — честно не учитывает схлопнутые дубли.

### 3.8. Лестница для доноров без RSS (`no_rss.py`)

Проблема, ради которой всё писалось: 145 доноров (56% от 260) не имели
объявленной RSS-ленты и **не опрашивались вообще**, из-за чего сигналы протухали
(«моложе 30 дней было 77 из 861» — `news_cron.py:5-6`, `no_rss.py:4-5`, и то же
число в сообщении коммита `b45c472`).

Лестница `probe_ladder` (`no_rss.py:333-360`), от дешёвого к дорогому:

| Шаг | Метод | Что пробуем | Когда считаем рабочим |
|---|---|---|---|
| а | `rss-path` | `/rss`, `/feed`, `/rss.xml`, `/feed.xml` | структура распарсилась хотя бы в один item |
| б | `sitemap` | адреса из `Sitemap:` в robots.txt, затем `/sitemap.xml`; у sitemapindex берём до 3 дочерних карт, предпочитая с `news`/`post` в имени | есть URL **с датами** `lastmod`; заголовок берём из `<h1>`, иначе `<title>` |
| в | `listing` | `/news`, `/novosti`, `/press`, `/press-centr` | в HTML нашлось ≥ 2 ссылок-заголовков |
| — | `none` | — | ничего не сработало |

Сработавший метод и URL запоминаются durable в `donors.probe_method/probe_url/
probed_at` (`schedule_db.set_probe`, `:85-92`), и следующий прогон идёт **сразу**
рабочим способом (`poll_known`, `no_rss.py:363-380`). Если способ сломался
(редизайн/переезд) — честная передискавери всей лестницей (`poll_donor`, `:383-406`).

Возврат `poll_donor` различает три исхода — это важно для метрик:
* `err=''` — успех (даже если 0 новостей);
* `err='fetch'` — хост не отдал ни байта → растёт `fail_streak`;
* `err='no-source'` — сайт **жив**, но раздела новостей нет → `fail_streak`
  НЕ растёт, лестница повторится не раньше чем через `none_retry_days=7`.

Парсинг листинга без DOM-библиотек (в `server/` только stdlib): новость = `<a>` с
текстом ≥ 20 символов на том же хосте, дата ищется в окне ±200 символов, но не
дальше соседних `<a>` — чтобы не «приклеить» дату соседней новости
(`parse_listing`, `:180-230`). Ссылка **без** даты не выбрасывается — «свежесть
неизвестна» трактуется как свежее, одноразовость гарантирует `seen_news`.

Даты понимает три формата (`parse_date`, `:154-169`): `21.07.2026`,
`2026-07-21(T…)`, `21 июля 2026`; русские месяцы по первым трём буквам, с явным
разведением `мая`/`май` и `мар` (`:138-139`).

### 3.9. Вежливость (`PoliteFetcher`, `no_rss.py:50-132`)

* `robots.txt` уважается (`User-agent: *`), кэш на прогон; пустой/недоступный
  robots = разрешено всё (стандарт краулеров); HTML вместо robots (SPA отдаёт
  index на любой путь) — игнорируется (`:92-107`).
* Пауза ≥ 3 с между запросами к **одному** хосту, разные хосты друг друга не ждут
  (`_wait`, `:71-78`).
* Жёсткий кап 25 HTTP-запросов на хост за прогон (`get`, `:125-132`).
* Исключение из фетча не пробрасывается — один упавший запрос не роняет ни
  донора, ни прогон (`_raw`, `:80-90`).
* Различаются «сайт лежит» и «сайт жив, новостей нет» — через `_alive`
  (`host_alive`, `:122-123`).

Тесты на robots-запрет и кап страниц: `tests/test_no_rss.py:138`, `:152`.

### 3.10. Схема-расширение БД (`schedule_db.py`)

Отдельный модуль, а не правка `enrich_db.py`, потому что `enrich_db` — общая
библиотека всех конвейеров, а задача разрешала писать только в свой каталог
(`schedule_db.py:5-10`). Миграция накатывается на уже открытую `EnrichDB` тем же
приёмом `ALTER TABLE` под `try/except` (`migrate`, `:62-71`), зовётся на каждом
старте `news_cron` (`news_cron.py:141`, и в `--report`-ветке `:258`).

Новые колонки `donors`:

| Колонка | Смысл |
|---|---|
| `probe_method` | `rss-path` / `sitemap` / `listing` / `none` |
| `probe_url` | конкретный рабочий URL |
| `probed_at` | когда лестница гонялась последний раз |
| `fail_streak` | ошибок доступности **подряд** |
| `last_ok` | последний успешный опрос (даже с 0 новых ссылок) |
| `last_new` | последний раз, когда донор дал НОВЫЕ ссылки |

Новая таблица `scan_runs(ts, donors_polled, donors_ok, new_links, new_signals,
errors, took_sec, note)` (`:36-40`) — журнал каждого прогона.

`donors_to_poll` (`:116-140`) выбирает кого опрашивать: сортировка по
`event_count DESC` (продуктивные первыми — если прогон оборвётся, ценное уже
собрано), исключаются:
* `SKIP_DOMAINS` (`:46-49`) — `vk.com`, `m.vk.com`, `ok.ru`, `t.me`, `hh.ru`,
  `news.google.com`, `zakupki.gov.ru`, `yandex.ru`, `dzen.ru`, `youtube.com`,
  `rutube.ru`: это не доноры, а домены собственных коллекторов `news_scan`;
* «мёртвые» — `fail_streak >= max_fail` (реанимация вручную:
  `UPDATE donors SET fail_streak=0 WHERE domain=…`);
* «none»-доноры, у которых лестница гонялась меньше 7 дней назад.

### 3.11. Метрики свежести (`freshness.py`)

`metrics(db)` (`:26-56`) считает одним набором SQL: всего сигналов, свежее 7 и 30
дней, всего доноров, с RSS, без RSS но с рабочим способом, «молчащих», «мёртвых»,
и последние 5 строк `scan_runs`. `report(db)` (`:59-78`) рендерит это 5 строками
текста — их печатает `news_cron` в конце прогона и отдельно по `--report`.

Важная деталь: свежесть меряется по `signals.updated_at` (момент записи в БД,
единый ISO-формат), а **не** по `signals.ts` — там сырой `pubDate` источника, где
форматы вразнобой (RFC2822/ISO/пусто) и SQL-сравнение строк бессмысленно
(`freshness.py:9-11`).

Пороги: «молчащий» — нет новых ссылок > 30 дней **или ни разу** (`SILENT_DAYS`),
«мёртвый» — 5+ ошибок подряд (`DEAD_STREAK`, `:22-23`). Обратите внимание: порог
«мёртвого» в метрике (5) и порог отключения донора от опроса (`--max-fail 10`) —
**разные числа**. Донор может числиться «мёртвым» в отчёте и при этом ещё
опрашиваться.

### 4.2. `news-sources.json` — что внутри и КТО его читает

Структура (проверено разбором файла): ключи `_note`, `feeds` (14 элементов),
`xmlriver_queries` (85 элементов), `_note_xmlriver`, `_note_donors`.

`feeds` — 8 федеральных firehose-лент tier 4 (lenta, rbc, tass, interfax,
vedomosti, kommersant, izvestia, finmarket) + 6 доноров tier 3 (abireg —
Черноземье, vz-nn — Нижний, vestidv — ДВ, pharmprom, fomag, glush).

`xmlriver_queries` — 85 запросов: 74 региона × один общий OR-блок из 8 капекс-фраз
(«новый завод» OR «запуск производства» OR «новый цех» OR «модернизация
производства» OR «строительство завода» OR «инвестпроект» OR «резидент ОЭЗ» OR
«займ ФРП»), плюс отраслевые (обогатительная фабрика, рентген-инспекция,
маслозавод/мясокомбинат/молокозавод…) и запросы под малые НП (моногород/ТОСЭР,
село/посёлок/райцентр).

**Грабля номер один по этому файлу: код читает его НЕ отсюда, а с дропа.**
`_load_feeds_catalog` (`news_scan.py:1025-1032`) и `_load_xmlriver_queries`
(`:1015-1022`) обе идут по `DROP_URL + '/news-sources.json'` с заголовком
`X-Drop-Token`, локального фолбэка на файл в репозитории **нет** — при недоступном
дропе обе возвращают `[]`, то есть коллекторы `regional`/`xmlriver` молча
отработают вхолостую. Файл в репозитории — это исходник, который надо
**выложить на дроп**, чтобы правки доехали.

| `DROP_URL`, `DROP_TOKEN` | каталоги, самочейнинг, дирижёр | да |
| `JOB_SECRET` | подпись джобов-преемников | да |
| `PROVIDER_API_KEY`, `PROVIDER_BASE_URL` | `extract_event` через `verify_company` | да |
| `DADATA_TOKEN` | резолв ИНН (`news_scan.py:1368`, `news_cron.py:195`) | да |
| `ENRICH_DB`, `SENDER_DIR` | путь к БД (`enrich_db.py:21-22`) | нет |
| `XMLRIVER_USER`, `XMLRIVER_KEY` | коллектор `xmlriver` (`news_scan.py:485-486`) | **нет** |
| `VK_TOKEN` | коллектор `vk` (`news_scan.py:983`) | **нет** |
| `VK_SLEEP` | пауза ВК, дефолт 0.5 (`news_scan.py:671`) | нет |
| `PROXY_URLV2/V3`, `PROXY_URL` | пул прокси в `verify_company` | нет |

Отсутствие `XMLRIVER_*` и `VK_TOKEN` в примере-ключнице проверено grep-ом по
всему репозиторию: эти имена встречаются **только** в трёх .py-файлах
(`news_scan.py`, `enrich_contacts.py`, `browser_probe.py`) и ни в одном .md.
Если ключи потеряются, коллекторы просто вернут `[]` без всякой диагностики
(`news_scan.py:487-488`, `:680-681`).

`news_cron` подхватывает секреты сам: он импортирует `job_runner` **ради
побочного эффекта** — тот при импорте читает `runner-secrets.env` из своей папки
в `os.environ` (`news_cron.py:41-48`, `job_runner.py:35-52`). Импорт обёрнут в
`try/except`: в песочнице модуля может не быть, это не ошибка. Порядок важен —
секреты должны попасть в окружение **до** `import news_scan`, потому что
`verify_company` читает часть env на импорте.

## 5. Ограничения и грабли

### 5.1. Деньги и квоты

* Каждая новая ссылка, прошедшая regex-предфильтр, = **один вызов fable**.
  Ограничители: `--max-links` (40 на донора), `--max-donors`, `max_items`,
  и главное — `seen_news` (ссылка оплачивается один раз навсегда).
* Чистка `seen_news` (`seen_clear_after`) заставит переспросить провайдера за
  весь период. Делать осознанно.
* xmlriver — платный (по `ENRICH-ROADMAP.md:189` владелец оценивал ~25 ₽/1000
  запросов) и лимитирован каналами аккаунта (10 Google + 10 Яндекс).
* dadata — бесплатно 10k/день по `runner-secrets.env.example`. Перебор вариантов
  имени тратит до 6 запросов на одну компанию, но прерывается на уверенном матче.

### 5.2. Время прогона

`news_cron` опрашивает доноров **последовательно** (`news_cron.py:154`), с паузой
3 с на хост и лестницей до 25 запросов на донора. Общего бюджета времени или
таймаута в скрипте **нет** — ни аргумента, ни проверки. Порядок «продуктивные
первыми» задуман как страховка «если прогон оборвётся», но обрывать его никто не
будет: `schtasks` по умолчанию не убивает задачу. На 260 донорах первый прогон
(когда у 145 гоняется полная лестница) может идти очень долго.

**ПРЕДПОЛОЖЕНИЕ (не измерено):** порядок нескольких часов. Если следующий запуск
в 07:00 наступит раньше окончания предыдущего, `schtasks` по умолчанию
(`/MULTIPLE` не задан) новый экземпляр не запустит — но это поведение планировщика
Windows, а не кода, и я его не проверял.

### 5.3. Реальный дефект: `.lstrip('www.')`

`str.lstrip` принимает **набор символов**, а не префикс. Проверено запуском
Python:

```
'world.ru'.lstrip('www.')  ->  'orld.ru'
'wz.ru'.lstrip('www.')     ->  'z.ru'
'lenta.ru'.lstrip('www.')  ->  'lenta.ru'   # тут повезло
```

То есть любой домен, начинающийся на `w` (или `.`), калечится. Места:

* `news_scan.py:233` — внутри `_norm_url`, то есть **в ключе дедупа новостей**;
* `news_scan.py:1467` — домен для `bump_donor` в `_persist_event`;
* `news_cron.py:115` — домен для `bump_donor` в `_extract_one`;
* `news_scan.py:518` — `source` элемента из xmlriver;
* `news_scan.py:1128` — фолбэк-подсчёт доменов в `rss_discover`.

Последствие: в таблице `donors` может появиться битый домен (`orld.ru` вместо
`world.ru`), и тогда `news_cron` будет ходить лестницей по несуществующему хосту,
накручивать `fail_streak` и в итоге пометит его мёртвым. В `no_rss.parse_listing`
(`:192`, `:205`) тот же `lstrip` применён к **обеим** сторонам сравнения, поэтому
там сравнение остаётся согласованным и вреда нет.

**Масштаб я оценить не могу** — нужен живой `SELECT domain FROM donors` на
сервере. В локальном `news-sources.json` доменов на `w` нет.

### 5.4. Метрика «молчащих» доноров завышена

`freshness.metrics` (`:33-36`) считает молчащими всех доноров с
`fail_streak < 5` и пустым/старым `last_new`, **не исключая** `SKIP_DOMAINS`.
А `donors_to_poll` (`schedule_db.py:131`) эти домены никогда не опрашивает, значит
у них `last_new` останется пустым навсегда. `vk.com`, `hh.ru`, `zakupki.gov.ru` и
ещё 8 доменов будут вечно числиться «молчащими». Ошибка косметическая (до 11
единиц), но при чтении сводки об этом надо помнить.

### 5.5. Расхождение порогов «мёртвого» донора

`--max-fail 10` (перестаём опрашивать) против `DEAD_STREAK = 5` (показываем как
мёртвого в сводке). Числа независимы и намеренно ли они разные — из кода не видно.

### 5.6. Кап страниц и robots

`PoliteFetcher.get` проверяет кап перед запросом, а `robots()` дёргает `_raw`
напрямую (`no_rss.py:96`), минуя проверку. То есть robots.txt всегда получит свой
запрос, даже когда кап уже исчерпан, и сам этот запрос кап увеличивает. Мелочь,
но кап де-факто «25 + robots».

### 5.7. `news_cron` не обогащает контакты

В `news_cron` нет ни импорта `enrich_contacts`, ни вызова `enrich_one` — проверено
чтением всего файла. Ежедневный прогон производит сигналы и (если dadata дала ИНН)
карточки компаний, но контактов у этих компаний может не быть вовсе. Контакты
добираются отдельно — заданиями `enrich_contacts` через раннер.

### 5.8. `news_cron` не доставляется автообновлением раннера

`PULL_ALLOW` в `job_runner.py:145-148` перечисляет 11 файлов, которые раннер может
скачать с дропа поверх себя. Среди них есть `news_scan.py` и `enrich_db.py`, но
**нет** `news_cron.py`, `no_rss.py`, `schedule_db.py`, `freshness.py`. Значит,
обновление ежедневного прогона — только ручная доставка в `C:\sender\server\`
(это же написано в `setup-news-schedule.ps1:9-11`). Легко забыть и получить
расхождение: `news_scan.py` на сервере свежий, а импортирующий его `news_cron.py`
— старый.

### 5.9. Данные сигналов от `news_cron` беднее, чем от `news_scan`

`_extract_one` (`news_cron.py:90-102`) не заполняет `icp_fit` и `status`, не
пишет `tier`/`query`/`equipment`, и в `signals.source` кладёт **домен донора**
(`rec['source_name']`, который равен `it['source']`, а тот выставлен как имя
домена в `news_cron.py:176`), с фолбэком на строку `'news-cron'`. У `news_scan`
там имя источника или коллектор. Для `UNIQUE(inn, source, what)` это означает, что
одно и то же событие, пойманное разными путями, может лечь двумя строками.

### 5.10. Прочее

* Обёртка задачи пишет в `news_cron.out` через `>>` — файл растёт бесконечно,
  ротации нет (`setup-news-schedule.ps1:38`).
* Время задачи — 07:00 **локального** времени сервера; в комментарии сказано, что
  сервер в МСК (`:18-19`). Если зону поменяют, `/ST` надо пересчитать вручную.
* `_get` (`news_scan.py:323-334`) ходит **в обход системного прокси и с
  выключенной проверкой TLS** (`CERT_NONE`, `:316-318`). Причина задокументирована
  (системный SOCKS режет хосты, госсайты отдают Russian-Trusted-CA), но это
  сознательный отказ от валидации сертификатов на всём фетче новостей.
* `_proxied_get` (`:369-373`) сейчас — просто обёртка над `_get`; ротация мобильных
  IP отключена, `_build_openers` (`:344-366`) остался, но вызывается только в
  диагностическом режиме `probe_urls` (`:1297`).
* В `parse_listing` ссылка без даты считается свежей. На сайте с плохой разметкой
  это протащит архив в конвейер — один раз (дальше `seen_news`), но провайдеру
  заплатить придётся.

### 6.1. Google News на сервере мёртв (документировано, коллектор оставлен)
