## 1. Что это и зачем

Внутри одной «области» лежат четыре разные истории, объединённые только тем, что они
про **клиента и продажу**, а не про SEO-тексты. Держите это различие в голове — иначе
скрипты кажутся случайным набором.

### 1.1. КП-конвейер (`kp_pipeline.py` → `merge_kp.py` → `kp_cleanup.py`)

У владельца на файловом обменнике (drop) лежали ~тысяча реальных коммерческих
предложений, презентаций, каталогов и прайсов в pptx/pdf/docx/doc/xlsx/xls. Задача:
превратить эту кучу в машинную базу фактов о брендах и моделях — что за модели, какая
мощность/давление/производительность, какая гарантия, какие обещания давались клиентам.
Итог — `kb/kp-base-all.json`: **99 брендов, 1588 моделей**, слито из **1117** документов
(`kb/kp-base-report.md:3`, цифры перепроверены чтением JSON).

Эта база — не для SEO-текстов. Её читает почтовый ассистент: `email-assistant/build_kb.py:8`
берёт `kb/kp-base-all.json` и собирает из него `answer-kb.json` — компактную базу цифр,
против которой факт-чекер рассыльщика сверяет каждую цифру в письме.

### 1.2. Клиентская аналитика (`match_clients.py` → `client-revenue-index.json`)

На сайте опубликовано 1018 кейсов («проекты») с названиями заказчиков. Отдельно есть
база обзвона `obzvon_all_2026-07-16.csv` (679 МБ, 161 761 юрлицо, у 104 861 известна
выручка). `match_clients.py` сопоставляет одно с другим по нормализованному названию и
даёт индекс «заказчик кейса → ИНН, выручка, регион».

Зачем: чтобы в холодном письме писать не «мы работаем с производствами», а «в вашем
регионе у нас 34 проекта, среди клиентов — КАО «Азот»». Логика заходов расписана
в `email-assistant/SEGMENTATION.md`.

Поверх индекса стоят два агрегатора (формально они в области доков 04, но без них
`client-revenue-index.json` бессмыслен): `region_aggregate.py` → `region-index.json`
и `segment_master.py` → `segment-master.json`.

`brands-pricelist.json` — из той же серии «факты для писем»: точный подсчёт брендов
в прайсе поставщиков, **66 брендов, из них свой один (ENGER), 65 дилерских**
(`brands-pricelist.json`, ключи `total`/`own`/`dealer_count`; producer — `count_brands.py:84-87`).

### 1.3. Аудит внутреннего поиска сайта (`search_test.py` → `search_eval.py`)

Разовое исследование: прогнали 1000 поисковых фраз через `/catalog/?q=` живого сайта,
выдачу оценил LLM-аудитор, результат — отчёт для разработчика Битрикса о том, почему
внутренний поиск теряет горячих покупателей. Итоги — в `paket-poisk/` и `paket-poisk-v2/`.

### 1.4. Ночная автономность (`night_orchestrator.py`, `heartbeat.py`)

Два одноразовых скрипта одной ночи 2026-07-20 (коммит `777293f`): пока сессия Claude
спит/упирается в лимит, фоновый процесс должен был досидеть до конца генерации вариаций
письма, отревьюить их, отобрать 100 и запустить рассылку на сервере владельца.
Сейчас это **исторические артефакты**, см. раздел 6.

### 1.5. Каталоги `paket-*/` — что это вообще

`paket-*` — это **пакеты-поставки владельцу**, не код и не входы конвейера. Каждый
каталог = «вот результат этапа, забирай и внедряй». Все семь пришли одним первым
импортом `3614fef` (2026-07-16), то есть это снимок работы за 14-16 июля 2026, а не
живые выходы. Подробная таблица различий — в разделе 4.3.

## 2. Точки входа и как запустить

> **Важно.** Скрипты `kp_pipeline.py`, `search_test.py`, `search_eval.py`,
> `night_orchestrator.py`, `heartbeat.py`, `kp_cleanup.py` ходят в сеть — на drop,
> на живой сайт prokompressor.ru и/или в провайдерский API. `kp_cleanup.py` ещё и
> **удаляет файлы с drop**. Не запускайте их «просто посмотреть».

### 2.1. КП-конвейер

```bash
cd /home/user/avto/seo-texts
python3 kp_pipeline.py                # все 4 фазы: скачать → извлечь → дедуп → LLM
python3 kp_pipeline.py --limit 20     # ограничить ТОЛЬКО фазу D (LLM) первыми 20 кластерами
```

Единственный аргумент — `--limit N` (`kp_pipeline.py:222-224`). Он режет не число
документов, а число кластеров, отправляемых в LLM (`kp_pipeline.py:194-197`).
Фазы A-C всегда выполняются целиком.

Конвейер **резюмируемый**: скачивание пропускает уже скачанное (`:44`), извлечение —
уже извлечённое (`:127-128`), LLM — уже структурированное (`:195`). Повторный запуск
безопасен и дёшев.

Требования:
* файл `seo-texts/.env` с `DROP_TOKEN` (**обязательно именно файл**, см. грабли 5.1);
* `curl`, `pdftotext` (poppler), `soffice` (LibreOffice — только для legacy `.ppt/.doc/.xls`),
  python-модули `anthropic` и `openpyxl`;
* `PROVIDER_API_KEY` для фазы D.

Слияние (LLM не используется, сеть не нужна, дёшево):

```bash

python3 merge_kp.py                   # kp-work/struct/*.json -> kb/kp-base-all.json + kb/kp-base-report.md
```

Аргументов у `merge_kp.py` нет.

Уборка на drop (**необратимо удаляет с сервера**):

```bash
cd /home/user/avto/seo-texts
python3 kp_cleanup.py
```

Аргументов нет. Порядок: сначала кладёт архив производных `kp-derived.tar.gz` на drop,
и **только при подтверждённом успехе заливки** удаляет с drop те документы, у которых
локально есть и raw, и text (`kp_cleanup.py:26-45`). Если заливка не удалась — печатает
«СТОП» и выходит с кодом 1, ничего не удалив (`:30-31`).

## 3. Как устроено внутри

### 3.1. `kp_pipeline.py` (235 строк) — 4 фазы

**A. Скачивание** (`:37-61`). `drop_list()` дёргает `GET {DROP_URL}/list` через curl
с заголовком `X-Drop-Token`. Фильтр: имя начинается на `kp` И расширение в
`DOC_EXT = {pptx, pdf, docx, doc, xlsx, xls}` (`:225-226`, `:20`). Качает в 6 потоков
в `kp-work/raw/`, атомарно через `.tmp` + `os.replace` (`:49-54`). Ошибка одного файла
глушится (`:55-56`) — файл просто докачается следующим запуском.

**B. Извлечение текста, 0 токенов** (`:64-144`) → `kp-work/text/<имя>.txt`:

| Формат | Как | Строка |
|---|---|---|
| pptx | распаковка zip, регексп `<a:t>…</a:t>`, слайды по порядку | `:64-74` |
| docx | zip → `word/document.xml`, `</w:p>` → перевод строки, срез тегов | `:77-81` |
| pdf | внешний `pdftotext -layout` | `:84-86` |
| xlsx | `openpyxl`, первые 5 листов, максимум ~800 строк | `:106-120` |
| ppt/doc/xls | `soffice --headless --convert-to` во временный каталог, потом как выше | `:89-103` |

Ошибки не роняют конвейер: в файл пишется `[extract fail: ...]` / `[legacy convert fail]`
(`:99`, `:120`, `:139-140`).

**C. Дедупликация шинглами** (`:147-179`). Тексты короче 400 символов отбрасываются
как мусор (`:156`). Шингл = 5 слов, шаг 2 (`:147-149`). Пара считается дублем,
если пересечение множеств шинглов делённое на размер меньшего > **0.7** (`:170`).
Кластеры склеиваются union-find'ом с path compression (`:160-171`). Представитель
кластера — **самый длинный текст** (`:175`). Карта кластеров пишется в
`kp-work/clusters.json`. Сложность — O(n²) по парам, при ~1200 документах это заметно,
но терпимо.

**D. LLM-структуризация** (`:182-218`). Каждому представителю кластера отправляется
`SCHEMA_PROMPT` (`:182-191`) + первые 24 000 символов текста (`:200`). Модель
`claude-fable-5`, `effort='low'`, 4 потока (`:203-204`, `:213`). Схема ответа:
`doc_type` (КП/презентация/каталог/прайс/сертификат/другое), `brand`, `series[]`,
`models[]` (модель, кВт, бар, л/мин, ресивер, осушитель, винтовой блок, цена),
`warranty`, `delivery_terms`, `seller`, `company_claims[]`, `client`, `date`.
Максимум 30 моделей на документ. Результат — `kp-work/struct/<имя>.json`, в него
дописываются служебные `_source` и `_tokens` (`:206-207`); при ошибке — `_error` (`:209`).

### 3.2. `merge_kp.py` (63 строки) — слияние с приоритетом

Читает все `kp-work/struct/*.json`, отбрасывает файлы с `_error` (`:16-23`).
Приоритет источника: **презентация (3) > каталог/прайс (2) > КП (1)**, всё остальное 0
(`:9`). Документы сортируются по возрастанию приоритета (`:28`), поэтому более
надёжный источник обрабатывается позже и перетирает менее надёжный (`:42-44`).

Бренды нормализуются: нижний регистр, срез небуквенного, плюс словарь алиасов
кириллица→латиница `атлас копко → atlas copco`, `кросс эйр → cross air`,
`энгер → enger` (`:11-14`). Документ без распознанного бренда идёт в счётчик
`skipped` (`:30-31`) — в отчёте это «без бренда: 84».

На выходе по каждому бренду: `models` (словарь модель → характеристики),
`series` (топ-15 по частоте), `screw_blocks` (топ-8), `warranties` (топ-4),
`company_claims` (топ-10), `docs` (сколько документов дало этот бренд) (`:54-57`).
Служебное поле `_prio` из моделей вычищается перед записью (`:53`).

Пишет два файла: `kb/kp-base-all.json` и `kb/kp-base-report.md` (`:60-61`).

### 3.3. `kp_cleanup.py` (45 строк)

Импортирует `drop_list, RAW, TXT, WORK, U, TOK, DOC_EXT` прямо из `kp_pipeline`
(`:9`) — то есть тянет за собой и его `.env`-требование, и импорт `gen_provider`.

Шаг 1: собирает `/tmp/kp-derived.tar.gz` из `kp-work/text/`, `kp-work/struct/`,
`clusters.json`, `kp-manifest.csv`, `kp-manifest-enger.csv` (`:16-25`) и кладёт
на drop через `curl -T`. Проверка успеха — грубая: строки `"ok"` и `true` в ответе
(`:28`).

Шаг 2: удаляет с drop только те `kp*`-файлы, у которых расширение в `DOC_EXT`
И локально есть и `raw/<имя>`, и `text/<имя>.txt` (`:34-44`). Медиа (jpg/png/mp4/psd/cdr),
манифесты и необработанное **не трогает** — это заявлено в докстринге и подтверждается
кодом.

### 3.4. `match_clients.py` (112 строк)

Нормализация названия (`:14-22`): нижний регистр, `ё→е`, снятие кавычек, вырезание
организационно-правовой формы по большому списку `OPF` (`:12`), срез небуквенно-нецифрового,
схлопывание пробелов. `ООО "Гранмото"` → `гранмото`.

Шаг 1 (`:28-49`): из `projects-index.json` собираются уникальные заказчики (поле `client`),
для каждого — множество городов и число проектов. Клиенты с нормой короче 3 символов
отбрасываются (`:37-38`).

Шаг 2 (`:52-81`): CSV базы обзвона читается из stdin, разделитель `;`, BOM снимается
с первого заголовка (`:56`), лимит поля поднят до 10 МБ (`:10`). Колонки ищутся **по имени**:
`База`, `ИНН`, `Краткое`, `Полное`, `Регион`, `Выручка, руб.` (`:58-59`). Для каждой
строки нормализуются `Краткое` и `Полное`; при совпадении с целевой нормой строка
кладётся в кандидаты и цикл по именам прерывается (`:67-81`).

Шаг 3 (`:84-104`): среди тёзок выбирается строка с **максимальной выручкой**, при
отсутствии выручки — первая (`:91-92`). Число тёзок сохраняется в `n_candidates`
(бывает 52, см. пример ниже) — это честный маркер «матч мог быть не тот».

Фактический результат в репозитории: **937 заказчиков, 324 с матчем, 301 с выручкой**
(посчитано по файлу). Коммит `687446e` говорит «сматчилось 315 (33%), с выручкой 292» —
разница в 9 записей появилась позже (раздел 5.2).

### 3.5. `search_test.py` (32 строки) и `search_eval.py` (52 строки)

`search_test.py`: берёт `inventory/search-test-phrases.json` (список объектов с
`phrase` и `source`), для каждой фразы дёргает `https://prokompressor.ru/catalog/?q=<urlencode>`
через curl с браузерным User-Agent (`:6`, `:14-17`), вытаскивает карточки товаров
регекспом по `class="item-title"` + `<span itemprop="name">` (`:10`), пишет построчный
JSONL: `phrase`, `source`, `found`, `empty_marker` (есть ли на странице «ничего не найдено»),
`top` (до 10 первых результатов). Флаш после каждой строки — резюмируемо по факту,
но перезапуск начинает файл с нуля (`open(..., 'w')`, `:8`).

`search_eval.py`: батчи по 15 записей, 8 потоков, модель `claude-fable-5`, промпт
просит по каждой фразе `relevance` 0/1/2, `should_have`, `fail_type` из фиксированного
списка (`ok, empty_but_should, wrong_top, too_few, model_not_found, category_not_found,
out_of_scope`) и короткую заметку (`:10-25`). Ответ вытаскивается регекспом `\[.*\]`
(`:36-37`). Упавший батч не роняет прогон, просто теряется (`:47-48`).

### 3.6. `night_orchestrator.py` (67 строк) и `heartbeat.py` (19 строк)

Оркестратор, по шагам: ждёт до 45 минут, пока в `variations-cache/` не наберётся
≥20 из 26 бакетов (`:20-27`) → собирает пул из всех бакетов в `variations-pool.json`
и проставляет `id` (`:29-39`) → если нет `variations-100.json`, запускает
`review_variations.py` подпроцессом с таймаутом 5400 с (`:42-46`) → кладёт
`variations-100.json` на drop через `run_on_server._req` (`:51-54`) → отправляет
на боевой раннер задание `spawn_campaign` без ожидания (`:58`) → через 40 с читает
`campaign-progress.json` и печатает статистику (`:61-66`).

`heartbeat.py`: спит **4 часа** (`:9`, `time.sleep(14400)`), затем печатает одну
строку `HEARTBEAT {json}` со статусом: число бакетов, наличие `variations-100.json`,
наличие `server/news_scan.py`, статистика кампании с сервера (`:10-19`).

## 5. Ограничения и грабли

### 5.1. `kp_pipeline.env()` требует именно ФАЙЛ `.env`, переменные окружения не спасут

`kp_pipeline.py:23-29` открывает `.env` **без проверки существования** и без фолбэка
на `os.environ`, затем `TOK = E['DROP_TOKEN']` (`:34`) на уровне модуля. Это отличается
от `gen_provider.env()` (`gen_provider.py:118-133`), который файл проверяет и
дополняет/переопределяет переменными окружения.

Следствие: **любой** `import kp_pipeline` без файла `.env` падает `FileNotFoundError`
(или `KeyError: 'DROP_TOKEN'`, если файл есть, а ключа нет). Под удар попадают также
`kp_cleanup.py:9`, `media_pipeline.py:9`, `media_sample.py:8` — они импортируют
`drop_list/U/TOK` из `kp_pipeline`.

В текущей песочнице `.env` отсутствует, и вдобавок не установлены модули `anthropic`
и `openpyxl` (проверено `python3 -c "import ..."`). Так что `kp_pipeline` тут
не импортируется вообще.

### 5.2. Повторный запуск `match_clients.py` УНИЧТОЖИТ ручное обогащение

`match_clients.py:106` перезаписывает `client-revenue-index.json` целиком, а в его
выходной записи (`:94-104`) **нет** полей `source`, `rating`, `note`, `bankrupt`.
Эти поля добавлены отдельно (коммит `d92c271`, «веб-добивка выручки (9 компаний) +
рейтинг A-G всем заказчикам»), и скрипта, который их воспроизводит, в репозитории нет.

Потеряется: 9 компаний, чья выручка добита из интернета (КАО «Азот» 65.4 млрд,
Шахта Сибирская 21.6 млрд, НЗНП Трейд 9.6 млрд и др.), рейтинги A-G у 324 записей
и флаг банкротства у «Трест Запсибгидрострой», из-за которого его нельзя
name-dropать в письмах.

Практика: перед запуском `cp client-revenue-index.json client-revenue-index.bak.json`,
после — руками перенести `source/rating/note/bankrupt` по ключу `client`.

### 5.3. Отсутствующая колонка CSV даёт индекс `-1` и молча читает последнюю колонку

`match_clients.py:58-59`: `col()` возвращает `-1`, если колонки нет. Дальше
`row[I_REV]` при `I_REV == -1` вернёт **последний столбец строки**, а не пустоту.
Проверка длины строки (`:65`) от этого не защищает: `max(...)` с `-1` в наборе
всё равно даёт положительное число, и строка проходит. Тот же паттерн — в
`extract_segments.py:15-20`.

Следствие: если у новой выгрузки базы обзвона переименуют колонку «Выручка, руб.» —
в индекс попадут молча неверные числа. При смене формата базы **сначала сверьте
заголовок**.

### 5.4. Матч по названию — это эвристика, `n_candidates` надо смотреть

Нормализация срезает орг-форму, поэтому «ООО Спецтех» из кейса матчится с 52
тёзками в базе (`n_candidates: 52`), и берётся тот, у кого выручка больше
(`match_clients.py:91-92`). Для ИП (флаг `ip`) нормой становится одна фамилия
(«ип носорев» → «носорев») — матч по такой норме почти наверняка мусорный.
Правило чтения индекса: `n_candidates > 3` — повод не использовать компанию
для name-drop без ручной проверки.

### 5.5. Порог дедупа 0.7 несимметричен

`kp_pipeline.py:170` делит пересечение на размер **меньшего** множества шинглов.
Короткое КП, целиком вошедшее в длинную презентацию, склеится с ней в один кластер,
и в LLM уйдёт только презентация. Для целей базы это скорее плюс (приоритет
презентации и так выше), но численные детали конкретного КП при этом теряются.

### 5.6. `search_test.py` перезаписывает результаты с нуля

`search_test.py:8` открывает `inventory/search-results.jsonl` на `'w'` до начала
работы. Прерванный прогон = потерянные предыдущие результаты. Резюмируемости, в
отличие от `kp_pipeline.py`, тут нет.

### 5.7. Парсер выдачи привязан к вёрстке сайта

`search_test.py:10` — регексп по `class="item-title"` и `<span itemprop="name">`.
Любая правка шаблона Битрикса превратит все выдачи в «found: 0», и это будет
выглядеть как катастрофа поиска, а не как поломка парсера. Перед доверием
результатам — проверьте на паре заведомо рабочих запросов.

### 5.8. `night_orchestrator.py`: условие «уже сделано» всегда истинно

`night_orchestrator.py:30`: `if not os.path.exists(f'{D}/variations-pool.json') or True:` —
`or True` делает проверку бессмысленной, пул пересобирается всегда. При частичном
кэше это перезапишет полный пул урезанным. Похоже на отладочный хвост, оставленный
в коде.

### 5.9. `heartbeat.py`: докстринг врёт про интервал

`heartbeat.py:2` обещает «спит ~55 мин», `heartbeat.py:9` спит `14400` секунд = 4 часа.
Верить надо коду.

### 5.10. `kp_cleanup.py` удаляет с боевого drop

Проверка успеха заливки архива — подстроки `"ok"` и `true` в теле ответа
(`kp_cleanup.py:28`). Это не строгая валидация JSON: теоретически возможен ответ,
где обе подстроки есть, а заливки не было. Плюс сам скрипт под текущими правилами
сессий запрещён (он делает `up` и `DELETE` на drop).
