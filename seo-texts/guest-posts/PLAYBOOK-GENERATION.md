# Плейбук: генерация статьи для донора (от акцептора до готового текста)

Операционная дока конвейера гост-постов. Написана 04.08.2026 по итогам волны 1 и
пилота в тон-каноне владельца. Выполнять по шагам; всё тяжёлое - через провайдерский
API (правило владельца), токены сессии - только оркестрация.

Результат конвейера: `ready/gp-<slug>.final.html` - статья, прошедшая мех-QA и
10 линз, в формате поставки площадке (TITLE + Description + Анонс в meta + тело).

---

## 0. Предпосылки (один раз на сессию)

- Env уже в песочнице: `PROVIDER_API_KEY`, `PROVIDER_BASE_URL` (+ drop). Зависимости:
  `pip install anthropic httpx openpyxl` (в свежей песочнице их нет).
- Смоук шлюза: короткий вызов из README кластера §3. Состояние шлюза переменчиво -
  текущие обходы см. README §4.10 и докстринг `gen_wave.py`.
- Ключевые файлы: `gen_wave.py` (генерация), `finalize_gp.py` (приёмка),
  `STYLE-GUIDE-GUEST.md` (тон-канон, уходит в каждый промпт целиком),
  `FINAL-ACCEPTORS.md` (приоритет закупок), `PLACEMENTS-LOG.md` (журнал),
  `../frog/acceptor-top100.xlsx` (пул акцепторов + живые запросы).

## 1. Выбор акцептора и донора (правило раскладки - обязательно)

1. Открыть `FINAL-ACCEPTORS.md` - шапка задаёт правило: вес квотами (№1-10 по 2 ссылки,
   №11-15 по 1), очередь непрерывная по журналу (новая закупка НЕ начинает с №1),
   финальный выбор - от донора (матрица донор-фита там же).
2. Открыть `PLACEMENTS-LOG.md` - сколько ссылок какой акцептор уже получил и где
   стоит очередь. Запись в журнал делается ДО закупки.
3. Известен донор -> кандидаты из матрицы донор-фита -> ближайший к месту очереди
   с неисчерпанной квотой и без нарушения лимитов темпа (≤1 ссылка на URL в 2 недели,
   ≤2 новых домена на сайт/нед, пара «Enger+прокомпрессор» ≤1 статьи из 3-4).
   Никто из матрицы не подходит - донора отложить, тему не натягивать.
4. Ссылок на статью: 1-2. Два URL одного сайта (категория + подкатегория) - можно;
   пара разных наших сайтов - только «производитель + каталог» и не чаще 1 раза на волну.

## 1.5. Как рождается угол статьи (предмет × призма)

Угол НЕ выдумывается свободно - он пересечение трёх входов:

1. **Предмет** - тема страницы-акцептора (что качаем): дизельные, азотные, сервис...
2. **Призма** - аудитория донора (кто читает): промгород -> стройка/цех; агро ->
   хранение урожая, рыбоводство, мехдвор; техно-площадка -> данные и экономика.
   Заготовки углов - в медиаплане владельца (donors-v2.xlsx, колонки «Угол статьи»
   и «Пример названия») и в матрице донор-фита FINAL-ACCEPTORS.md.
3. **Слова** - живые запросы акцептора из Вебмастера (шаг 2): какими фразами
   аудитория ищет предмет.

Один акцептор на разных донорах = разные углы (азотная страница: для агро - «азот
при хранении зерна», для промгорода - «азот в цеху»). Если пересечение предмета
с аудиторией пустое - донора откладываем (правило: тему не натягивать).

**Пакетное планирование (N статей за раз):** идти ОТ ДОНОРОВ - каждому донору пула
назначить лучший допустимый акцептор (матрица фита × очередь × квоты из
FINAL-ACCEPTORS), из пары вывести угол, раскладку по неделям сделать под лимиты
темпа. Так релевантность размещения максимальна у каждой пары, и топ-акцептор
не забирает все размещения.

## 2. SEO-семантика из живых данных (не из головы)

Живые запросы каждой страницы лежат в `../frog/acceptor-top100.xlsx`, колонка
«Топ-запросы» (выгрузка Вебмастера с позициями). Извлечение:

```python
import openpyxl
ws = openpyxl.load_workbook('../frog/acceptor-top100.xlsx').active
rows = list(ws.iter_rows(values_only=True))
iu, iq = [i for i,h in enumerate(rows[0]) if h in ('URL','Топ-запросы')]
print([ (r[iu], r[iq]) for r in rows[1:] if r[iu] and 'НУЖНЫЙ-СЛАГ' in str(r[iu]) ])
```

Из запросов собрать `seo`-поле джобы: главный ключ (самый частотный/близкий к теме),
3-5 живых фраз для вплетения в H2/текст, LSI-термины предметки. Правила вхождений
уже зашиты в PROMPT (естественные словоформы, ключ в TITLE и первых двух абзацах,
переспам хуже недоспама).

## 3. Заполнение джобы в `gen_wave.py` (JOBS)

Поля (образец - джоба `dizel-na-strojke`):

| Поле | Что писать | Грабли |
|---|---|---|
| `slug` | латиница-с-дефисами | имя файлов gp-<slug>.* |
| `donor` | домен площадки | |
| `links` | [(URL, инструкция по якорю)] | точный URL акцептора (гейт сверяет префикс); тип якоря по анкор-политике стайлгайда (ротация: брендовый / навигационный / разбавленный; коммерческий ключ в якоре на регионалке - жёлтая зона) |
| `angle` | тема/угол с конкретикой | без обещаний фактов, которых нет в каноне/kb |
| `case` | обезличенный кейс | БЕЗ юрлиц клиентов, брендов и артикулов (нативная модель) |
| `skeleton` | деловая структура | «постановка задачи -> разбор -> подбор -> практическое резюме»; сцены-репортажи и «звонки читателей» ЗАПРЕЩЕНЫ тон-каноном |
| `donor_note` | профиль аудитории площадки | + «без выдуманных местных фактов» |
| `seo` | главный ключ + живые запросы + LSI | из шага 2; поле опциональное, но без него SEO-линза судит вслепую |

Тон-канон (важное, полный - в `STYLE-GUIDE-GUEST.md`): спокойный инженерно-деловой
разбор с цифровой конкретикой; образная фраза ≤1 на статью; списки `<ul>/<ol>` и `<h3>`
разрешены (2-3 списка, не три параллельные нумерации подряд); без байлайна и наших
компаний в тексте (бренд - только внутри текста-якоря); объём 6000-13000 знаков.

## 4. Генерация

```bash
cd seo-texts/guest-posts
PROVIDER_FIRST_TOKEN_SEC=300 PROVIDER_STREAM_DEADLINE_SEC=900 python3 gen_wave.py <slug>
```

Что происходит: промпт = стайлгайд целиком + джоба + SEO-блок + нативная модель;
контракт ответа БЕЗ JSON (TITLE: / DESCRIPTION: / ANONS: / голый HTML - JSON-ответы
шлюз не отдаёт, см. README §4.10); черновик - gemini-3.6-flash -> haiku -> gemini-3.1-pro,
доводки по мех-QA - opus-4-8 (цепочки в `DRAFT_MODELS`/`FIX_MODELS`); до 3 раундов.
Выход: `gp-<slug>.html` + `gp-<slug>.meta.json` (title/description/anons/модель/QA).

Мех-QA (`qa_multi`): объём 5200-14000, стоп-слова BANNED, длинное тире, инженерные
детекторы (refinement), белый список ссылок + позиции (не в первом/последнем абзаце),
целостность `<a>`-тегов, разрешённые теги p/h2/h3/a/strong/ul/ol/li.

Сравнение моделей (если нужно): `--model openai:<id> --tag <suffix>` - файлы
`gp-<slug>.<suffix>.html`, оригинал не перетирается.

## 5. Приёмка: 10 линз

```bash
PROVIDER_DEAD_MODELS='' PROVIDER_FIRST_TOKEN_SEC=240 python3 finalize_gp.py <slug>
```

Линзы (порядок в `finalize_gp.LENSES`): link (якорь/посадочная), platform (редактор
донора), engineer (техника+безопасность), neutral (анти-реклама), logic (цепочка
читателя), seo (вхождения/H2), seo_yandex (Баден-Баден), seo_google (Helpful
Content/E-E-A-T), antiai (LLM-маркеры), language (корректор+филолог).

Механика: каждая линза возвращает `ВЕРДИКТ: PASS|FAIL` + правки «"цитата" -> "замена"»;
правки применяются детерминированно кодом; до 3 кругов, FAIL-линзы перепроверяются
с пометкой «подтверждающий круг». Судьи: fable-5 -> opus-4-8 -> gemini-3.6-flash.

Линза link дополнительно ставит БАЛЛЫ РАЗМЕЩЕНИЯ ССЫЛКИ: «МЕСТО: n/10» (позиция и
окружение) и «РЕЛЕВАНТНОСТЬ: n/10» (якорь -> абзац -> посадочная); ниже 7 по любой
шкале = FAIL до исправления. Баллы пишутся в finalize-лог.

Выход: `ready/gp-<slug>.final.html` (ГОТОВ К ПУБЛИКАЦИИ) либо
`ready/gp-<slug>.NEEDS-REVIEW.html` + лог `ready/gp-<slug>.finalize-log.md`
(все применённые правки и сырые вердикты несошедшихся линз).

При NEEDS-REVIEW: смотреть лог - чаще всего это либо реальная проблема (битый тег,
структурный дефект), либо цитата линзы не нашлась в тексте (правит человек руками),
либо линза-перфекционист (решает человек).

## 6. Поставка площадке и журнал

Пакет для площадки: TITLE + Description + Анонс (из `gp-<slug>.meta.json`) + тело
из `ready/*.final.html`. Перед отправкой:
- запись в `PLACEMENTS-LOG.md` (дата, слой/№, акцептор, донор, статья, якорь, статус);
- уточнить у площадки допустимый объём (наша норма 6000-13000, но у бирж бывают капы);
- **отправка на площадку = действие вовне: только по явному ОК владельца.**

## 7. Стоимость и время (ориентиры волны 1 + пилота)

Генерация: ~1-3 вызова (gemini-черновик ~16с, доводки opus) - десятки центов.
Приёмка: 10-20 вызовов линз по ~4k токенов - ~$1-2 на статью. Полный цикл статьи
~10-20 минут фонового времени. Пустые thinking-ответы шлюза биллятся - порядок
моделей в драйверах уже оптимизирован под это, не менять без замеров.

## 8. Известные грабли

1. Шлюз не отдаёт длинные JSON-ответы и «думает в пустоту» на тяжёлых промптах у
   opus/sonnet/fable - контракт plain-text и цепочки моделей это обходят (README §4.10).
   Состояние шлюза дрейфует - при странных пустых ответах перечитать §4.10 и перемерить.
2. fable-5 жив на ревью-задачах (~4-9 КБ промпт), мёртв на генерации. Для линз -
   первым судьёй, для генерации не использовать.
3. Судьи протаскивают в правки длинное тире и цитируют HTML с кавычками - санитизация
   и бэктик-парсер уже в `finalize_gp`, но новые форматы цитат возможны: NEEDS-REVIEW
   с «НЕ НАЙДЕНА цитата» - признак такого случая.
4. Gemini норовит добавить ссылку на ГОСТ/ISO (docs.cntd.ru) - гейт режет по белому
   списку. Если владелец разрешит нейтральные ссылки - расширить `allowed` в qa_multi.
5. Правки линз может сломать HTML (прецедент: битый <a> тег) - целостность тегов
   теперь в мех-QA, но при ручных правках прогонять qa_multi повторно.
6. Кейсы в статьях - только обезличенные; юрлицо клиента в покупной статье = согласие
   клиента + рекламный след.
7. Норма объёма 6000-13000 - внутренняя; потолок площадки уточнять при согласовании.
