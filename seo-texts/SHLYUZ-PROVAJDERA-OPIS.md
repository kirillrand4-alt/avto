# Шлюз провайдера с сервера владельца: что рвётся, на каком шаге и как обойти

Замер 17.09.2026, сервер владельца (внешний адрес 91.206.14.169, Windows Server, python
3.11.9, OpenSSL 3.0.13). Приборы: `seo-texts/shlyuz_diagnoz_servera.py`,
`seo-texts/novosti_vskrytie_servera.py`. Полные логи выложены на дроп
(`3s-shlyuz-log-*.txt`, `3s-vskrytie-novostey.txt`).

Значения ключей нигде не печатались: только «есть/нет» и длина.

---

## 1. Короткий ответ владельцу

Шлюз не сломался и нас не блокировал. **Имя `router.cheap` разъезжается на ДВА адреса
Cloudflare, и с этого сервера один из них мёртв, а второй полностью рабочий.** Клиент
идёт туда, куда его пошлёт порядок DNS, а порядок меняется сам собой. Отсюда и «всегда
работало, а тут не работает»: работает волнами по несколько минут, и никакой правки на
шлюзе для этого не требовалось.

| адрес | что с ним с сервера владельца |
|---|---|
| `172.67.173.181` | РАБОТАЕТ полностью: рукопожатие 10/10, `/v1/messages` с ключом даёт 200, восемь реальных вызовов подряд - 8 ответов из 8 за 2,0-4,5 с |
| `104.21.64.2` | МЁРТВ: 10 обрывов из 10. Сперва RST на рукопожатии (`WinError 10054`), через 15 минут - уже полный таймаут даже на порт 80 |

Лечится это не перепиской со шлюзом, а тремя строками в клиенте: обойти ВСЕ адреса
имени, а не умереть на первом. Готовый патч - в разделе 6.

## 2. На каком именно шаге рвётся

Прибор проходит связь по шагам и печатает последний УСПЕШНО пройденный:
`dns → tcp → tls → заголовки → тело → первый байт ответа`.

```
TLS по умолчанию + GET /      tcp   ConnectionResetError: [WinError 10054] ...
TLS 1.2 принудительно         tcp   ConnectionResetError: [WinError 10054] ...
TLS 1.3 принудительно         tcp   ConnectionResetError: [WinError 10054] ...
только ECDHE-RSA-AES128-GCM   tcp   ConnectionResetError: [WinError 10054] ...
```

Из трёх версий, которые надо было различить, подтверждается **вторая: разрыв на
TLS-рукопожатии.**

- Это НЕ «блокировка по IP сервера шлюзом». Блокировка по IP - это ОТВЕТ (403 от
  Cloudflare с телом). Тут ответа нет вовсе: ни одного байта, ни одного `cf-ray`.
- Это НЕ «обрыв после отправки тела». До тела и до заголовков дело не доходит: шаг
  `tls` не пройден ни разу, HTTP-запрос не уходил в сеть.
- TCP при этом ОТКРЫВАЕТСЯ, причём за 0,02 с. Двадцать миллисекунд до Хельсинки или
  Франкфурта не бывает: SYN-ACK нам отдаёт что-то на полпути, а не край Cloudflare.
  Это характерный почерк промежуточного фильтра - он принимает соединение и рвёт его,
  когда видит содержимое.

Через 15 минут тот же адрес перестал даже принимать соединение (таймаут 15 с на 443 и на
80). Поведение фильтра плавает, но всегда в одну сторону: этот адрес с этого сервера
непроходим.

## 3. Проверки, которые сняли ложные версии

**Дело не в имени (SNI) - дело в адресе.** Одно и то же рукопожатие к двум адресам с
тремя разными SNI:

```
адрес 104.21.64.2      SNI router.cheap         {"TimeoutError": 5}
адрес 104.21.64.2      SNI www.cloudflare.com   {"TimeoutError": 5}
адрес 104.21.64.2      SNI example.com          {"TimeoutError": 5}
адрес 172.67.173.181   SNI router.cheap         {"tls-ok": 5}
адрес 172.67.173.181   SNI www.cloudflare.com   {"tls-ok": 5}
адрес 172.67.173.181   SNI example.com          {"tls-ok": 5}

порт 80:  104.21.64.2 -> TimeoutError      172.67.173.181 -> HTTP/1.1 404 Not Found
```

Если бы резали имя `router.cheap` (DPI по SNI, WAF шлюза, бан аккаунта), второй адрес
рвался бы ровно так же. Он не рвётся. Если бы дело было в шлюзе, чужие SNI на плохом
адресе проходили бы. Они не проходят. Остаётся адрес.

**Дело не в User-Agent, не в версии TLS и не в наборе шифров.** Все эти пробы к рабочему
адресу дают 200: UA `curl/8.5.0`, `Python-urllib/3.11`, браузерный Chrome и вовсе без UA;
TLS 1.2 и TLS 1.3 принудительно; узкий набор `ECDHE-RSA-AES128-GCM-SHA256` и широкий
`DEFAULT:@SECLEVEL=1`. К мёртвому адресу ни одна из них не проходит. Заголовок
`curl/8.5.0` в `gen_provider.py`/`verify_company.py` менять не нужно - он по-прежнему
нужен против WAF самого шлюза, но к нынешней поломке отношения не имеет.

**Дело не в ключе.** `POST /v1/messages` БЕЗ ключа через рабочий адрес возвращает
`401 Unauthorized` с телом `{"error":{"message":"Invalid token ..."}}`. Это ОТВЕТ, то
есть путь до шлюза цел и шлюз с нами разговаривает. Ключ на сервере есть, длина 51.

**Дело не в сети сервера вообще.** Контроли в те же секунды, с того же сервера:

```
www.cloudflare.com        200 (10 соединений из 10)     - Cloudflare как таковой доступен
parsercompressor.online   401 (6 из 6)                  - дроп владельца отвечает
api.anthropic.com         403 "Request not allowed"     - ОТВЕТ, канал цел
ya.ru                     302
api.ipify.org             200, внешний адрес 91.206.14.169
```

Прокси в окружении сервера нет вовсе (`HTTPS_PROXY` пуст, `urllib.getproxies()` пуст),
так что запрос идёт напрямую - это и видно в трассировке (`_BEZ_PROXY.open`).

## 4. Почему «всегда работало, а тут перестало»

Порядок, в котором `getaddrinfo` отдаёт два адреса, меняется сам (ротация DNS плюс кэш
Windows с временем жизни порядка пяти минут). Замеры одного и того же дня:

| время | что отдавал DNS первым | что делал штатный клиент |
|---|---|---|
| 03:16 | рабочий адрес | 30 соединений по имени - 30 ответов, 8 вызовов модели из 8 |
| 03:26 | `104.21.64.2` в 20 запросах из 20 | - |
| 03:40 | `104.21.64.2` в 10 запросах из 10 | `_provider_call_stdlib` - **3 сбоя из 3**, `WinError 10054` за 37,9 с каждый |

И вот главное, из-за чего питон не выкарабкивается сам. `socket.create_connection`
перебирает адреса имени, но переходит к следующему **только если не удался TCP-connect**.
Здесь TCP-connect удаётся (фильтр отвечает SYN-ACK за 0,02 с), а рвётся всё позже, на
рукопожатии, - там перебора уже нет. Клиент умирает на первом адресе и до живого второго
не доходит НИКОГДА. Поэтому сбой выглядит как «шлюз лежит», хотя рядом лежит рабочий
адрес того же имени.

Цена: `_provider_call_stdlib` возвращает ошибку через 37,9 с (внутренние ретраи бьются в
тот же мёртвый адрес), а каждая новость съедает эти 38 секунд, чтобы дать `None`.

## 5. Почему из песочницы всё зелено (и почему это не доказательство)

Из песочницы тот же запрос отвечает 200 за 4,8 с - но сертификат в ответе выписан на
`Anthropic`, то есть исходящий трафик песочницы перевыпускает прокси агента и выпускает
в сеть со СВОЕГО адреса. Песочница просто не ходит маршрутом сервера. «В песочнице
работает» означает «другой путь цел», а не «шлюз здоров».
