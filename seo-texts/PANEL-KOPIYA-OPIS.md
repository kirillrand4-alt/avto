# Копия панели обзвона на отдельном порту + админская статистика

Задание владельца: «сделать копию, но на другом порту другая база будет (позже скину,
сначала просто копию сделай) и у админа возможность просматривать статистику по всем
пользователям и всем компаниям (как общая статистика, так и видеть очереди юзеров)».

Сделано и проверено. Боевая панель на 8012 **не тронута ни одной строкой** — продавцы
работают там прямо сейчас.

## Изоляция от боевых баз — была дыра, закрыта

**Что было не так с самого создания копии.** Модуль `app/api/routes_park.py` (страницы

процесса, причём под **своими** именами и с **боевыми** путями по умолчанию:

| переменная | что в ней | по умолчанию было |
|---|---|---|
| `CENTRO_SALES_DB` | продажи, чтение (список, блок) | `C:\seostat\data\centro_sales.db` |
| `CENTRO_DB` | каталог, чтение | `C:\seostat\data\centrifugal.db` |
| `PARK_OCHERED_SALES_DB` | продажи, **запись** («в обзвон», «мусор» на «Парке») | `C:\seostat\data\centro_sales.db` |
| `PARK_OCHERED_DB` | каталог, **запись** (добавление компании) | `C:\seostat\data\centrifugal.db` |
| `PARK_PANEL_DB` | база «Парка», чтение | `C:\seostat\data\park_panel.db` |

`.env` копии читает только pydantic-настройка, в окружение процесса он не попадает. Итог:
карточка, вход и основная статистика (модуль `centro_sales`, он считает путь от корня
приложения) читали базу копии, а «Список», «Парк» и календарный блок — **боевую**.
Кнопки «в обзвон» и «мусор» на «Парке» записали бы в боевую панель.

Обнаружилось по скриншоту: блок на «Статистике» показал user1..user3 действующими, а в базе
копии они отключены. Все прежние проверки этого не видели, потому что сами делали
`load_dotenv(.env)` — то есть проверяли окружение, которого у настоящего сервера нет.
Утверждение «копия прочитала именно свои пути», которое раньше стояло в этом файле, было
верно только для половины кода.

**Ущерба нет.** Замер боевой `centro_sales.db`: с 07.10 ноль записей в журнале, ноль
назначений, ноль состояний, комментариев и скрытий; файл последний раз менялся 24.08. До
и после починки отпечаток базы (размер, журнал 156, назначений 1 638, состояний 94) один и
тот же.

**Как закрыто.**

1. В `.env` копии прописаны **все** имена из таблицы выше — с путями копии.
2. `park_panel.db` (60.7 МБ) скопирована в копию через `sqlite3.backup` — файл может быть
   открыт боевым процессом, простое копирование поймало бы его на середине записи.
3. Сервер запускается через `C:\centro2\zapusk.py`: он кладёт **весь** `.env` в окружение
   процесса до импорта приложения, с перезаписью (глобальная переменная сервера не должна
   перебить путь копии), и **отказывается стартовать**, если хоть одна переменная с `DB` в
   имени смотрит в `C:\seostat\data`.
4. Проверка — в процессе, поднятом тем же загрузчиком, без `load_dotenv`: `zapusk.py
   --proverka` обходит все загруженные модули `app.*` и ищет строковые переменные с
   боевым путём. Результат: **0**. Все пять путей `routes_park` — в `C:\centro2\data`.
5. Решающая проверка — живой сервер через публичный адрес: блок на «Статистике» и на
   «Списке» показывает Беляева, Волкова, Ерохина и Пяткову, а не user1..user3.

## Путь «обзвон-мейер» и публикация наружу

Копия живёт на **`/obzvon-meyer`**, боевой обзвон остался на `/obzvon`.

Префикс задаётся одной переменной — код не правился ни в одной строке:

```
OBZVON_ROOT_PATH=/obzvon-meyer      в C:\centro2\.env
```

В `app/config.py` свойство `obzvon_path` считается из поля `obzvon_root_path`, а все 103
вхождения `/centro` в коде и шаблонах написаны как `{{ base_path }}/centro` или
`BP + "/centro"`. Поэтому меняется префикс — и уезжают все ссылки сразу. В боевом `.env`
этой переменной нет вовсе, там работает значение по умолчанию `/obzvon`.

**Почему не `/obzvon/meyer`.** Этот путь занят. В `app/services/callbase.py` есть реестр
`BASES = {"kc": "Компрессор Центр", "meyer": "Meyer"}`, и старый обзвон отдаёт их по
адресам `/obzvon/kc` и `/obzvon/meyer` — замер показал на обоих 401 обзвонной
авторизации, то есть страницы живые. Поставить копию туда значило бы затенить
работающее.

### Публикует Caddy, а не nginx

На 80/443 висит `C:\caddy.exe run --config C:\Caddyfile` — один процесс на все сайты
владельца. Файлы `C:\seostat\deploy\nginx-*.conf` это устаревшая документация, в работе
они не участвуют. Добавленный блок:

```
        handle /obzvon-meyer {
                redir * /obzvon-meyer/centro
        }
        @obzvon_meyer path /obzvon-meyer/*
        handle @obzvon_meyer {
                reverse_proxy 127.0.0.1:8016
        }
```

Точный путь стоит **первым**: блоки `handle` взаимоисключающие и идут по порядку, и если
первой поставить звёздочку, она поймает и короткий адрес, а редиректа не случится.
Матчер `path /obzvon /obzvon/*` боевого обзвона `/obzvon-meyer` не ловит: следующий знак
дефис, а не слэш.

Порядок правки, который менять нельзя: **бэкап → правка → `caddy validate` → только потом
`caddy reload`**. Caddy тут один на `parsercompressor.online`, `zernosort.ru`,
`sort-inspection.ru`, панель и редиректы доменов-двойников — битый конфиг уронил бы их
все. Проверка это уже окупила: первая версия блока была написана с фигурной скобкой в
одну строку, `validate` дал `Unexpected next token after '{'`, файл автоматически вернулся
из бэкапа и перезагрузки не произошло. Бэкапы: `C:\Caddyfile.bak-ГГГГММДД-ЧЧММСС`.

Пароли в Caddy не задаются: у копии своя обзвонная авторизация из `OBZVON_USERS`, тех же
пользователей, что и у боевой.

### Проверка, что продавец не уедет на боевую панель

Это главный риск переноса на другой префикс: одна забытая ссылка на `/obzvon/…` — и
продавец Мейера, кликнув, оказывается в центробежной базе чужой смены, причём страницы
выглядят одинаково и подмену он не заметит. Поэтому проверялись не исходники, а готовые
страницы: шесть страниц копии отрендерены, собраны все `href`, `src`, `action`, адреса
`fetch` — **2 968 адресов, ссылок на `/obzvon/…` ноль**.

Боевые адреса после публикации отвечают как раньше: `/obzvon/centro` → 303 на логин,
`/obzvon/meyer` → 401, `/obzvon/kc` → 401, `/stat` → 401.

## Аккаунты панели Мейера

Заведены пять: `meyer_admin` (роль `admin`) и `meyer1` … `meyer4` (роль `sales`).
**Пароли в этом файле и вообще в репозитории не записаны** — в базе лежат только
bcrypt-хеши, открытые значения переданы владельцу в переписке. Если потерялись, пароль
не восстанавливается, а задаётся заново (см. ниже).

### Два слоя входа, и почему хватило одного

У панели их два, и это легко перепутать:

1. `BasicAuthASGI` с парами из `OBZVON_USERS` — браузерное окно «Нужен логин и пароль
   обзвона», отвечает 401.
2. Своя форма входа с куками и таблицей `users` в `centro_sales.db`.

Страницы продаж освобождены от первого слоя: в `app/obzvon.py` метод
`BasicAuthASGI._is_centro_path` пропускает всё, что кончается на `/centro`, содержит
`/centro/`, кончается на `/centro1`, `/centro2` или на `/static/css/centro.css`. Поэтому
новым людям обзвонный пароль НЕ нужен — достаточно аккаунта панели. Замер это
подтверждает: `/obzvon-meyer/centro` даёт 303 на форму входа, а `/obzvon-meyer` (без
`/centro`) — 401 от первого слоя.

### Как заведено и как добавить ещё

Хеши не сочинялись: зовётся `app/services/centro_sales.py` → `upsert_user(username,
password, role, path=...)`, то есть тот же код, которым панель заводит людей. Выдуманный
формат хеша дал бы аккаунты, которые выглядят правильно и в которые нельзя войти.

```python
from app.services import centro_sales as sales
sales.upsert_user("meyer5", "пароль", "sales", path=r"C:\centro2\data\centro_sales.db")
```

`upsert_user` работает и как смена пароля: при существующем логине он перезаписывает хеш.
Роль проверяется базой — `CHECK(role IN ('admin','sales'))`, третьего значения не бывает.
Пароли генерировались из алфавита без пар, которые путают при наборе и диктовке: без
`0`/`O`/`o`, `1`/`l`/`I`, `5`/`S`, `2`/`Z`.

### Проверено входом, а не видом таблицы

Хеш может совпадать, а вход не работать: не та роль, `is_active=0`, своя проверка в
маршруте. Поэтому каждый аккаунт проверялся POST-ом на настоящую форму и попыткой
открыть страницу — сначала тестовым клиентом на сервере, потом сквозным HTTP через Caddy
по публичному адресу:

| кто | главная | статистика |
|---|---|---|
| `meyer_admin`, верный пароль | 200 | 200 |
| `meyer1`, `meyer4` | 200 | 403 |
| `meyer_admin`, неверный пароль | 303 на форму | 303 |
| отключённый `admin` | 303 на форму | 303 |

Тут была ловушка в моей же проверке: маршрут входа отвечает **303 и при успехе, и при
отказе** — при отказе он бросает обратно на форму. Если считать успехом код 303, то
«вошёл» покажется даже на неверном пароле. Признак входа один: после него главная
отдаёт 200.

Контролей два, на обе стороны: неверный пароль и несуществующий логин обязаны не
пускать, иначе пять успехов выше выглядели бы так же и при вовсе неработающей проверке
пароля. Запрет по `is_active` проверен отдельно на одноразовом аккаунте с известным
паролем (включён → 200, отключён → 303), который сразу удалён.

### Унаследованные аккаунты боевой панели отключены

В копию вместе с базой приехали `admin`, `user1`, `user2`, `user3` — аккаунты боевой
смены с ИХ паролями. Панель Мейера открыта из интернета, поэтому они отключены:
`is_active=0`. Строки и их 1 638 назначений сохранены, удалять я не стала — отключение
обратимо одной строкой SQL, удаление нет:

```sql
UPDATE users SET is_active=1 WHERE username IN ('admin','user1','user2','user3');
```

Порядок был именно такой: сперва новый админ проверен входом, и только потом отключение.
Наоборот — это шанс запереть владельца снаружи собственной панели.

## Блок статистики на «Списке компаний»

В пустом месте полосы счётчиков `/obzvon-meyer/centro/spisok`: календарь, выбор продавца
и таблица «взял в работу / не понравилась / дубль / в очереди» — за выбранный день и за
всё время, строкой «Все продавцы» и по каждому. Продавец видит только свою строку и без
выбора; подставленный в адрес `stat_user=` чужой логин ему не помогает (проверено).
Фильтры списка и дата блока друг друга не сбрасывают: форма блока несёт фильтры списка
скрытыми полями, форма фильтров — дату блока, ссылки сортировки и страниц — обе.

### Как считается

**За день** — по журналу `activity_log` (`action='call_saved'`, результат в
`payload_json`), а не по `company_state.last_contact_at`. Последнее — это время
ПОСЛЕДНЕГО действия, и если компанию тронули сегодня, вчерашняя отметка по ней пропала бы
задним числом. За день берётся последняя отметка по каждой компании, поэтому «сперва не
понравилась, потом взял в работу» не считается дважды. Отметка засчитывается владельцу
компании (`state_user`), даже если звонок сохранил админ. День — **по Москве**: продавцы
звонят по Москве, база пишет UTC.

**В очереди на конец дня** — назначено к концу дня (`assigned_at`), видно продавцу (есть
в каталоге и не скрыто) и ещё не отмечено к концу дня.

**За всё время** — нынешний статус. Результаты — по всем компаниям продавца, включая
скрытые позже: сделанная работа остаётся сделанной. Очередь — только видимое, то есть
ровно то, что продавцу ещё предстоит обзвонить.

На этой же карточке есть старый счётчик «в работе» — он считает **все обработанные**
(любой результат), а «взял в работу» в блоке — только этот статус. В снимке это 87 против
53, поэтому под таблицей стоит пояснение: иначе на одной карточке два разных «в работе».

### Сверено независимым подсчётом

Цифры блока сравнивались не с той же логикой второй раз, а с прямым SQL: оконная функция
`row_number() over (partition by владелец, ИНН, московский день order by created_at desc)`
и `json_extract` вместо питоновского прохода по журналу.

| | блок | SQL |
|---|---|---|
| взял в работу, всё время | 53 | 53 |
| не понравилась, всё время | 18 | 18 |
| дубль, всё время | 22 | 22 |
| в очереди, всё время | 517 | 517 |
| взял в работу, 11.08.2026 | 5 | 5 |
| не понравилась, 11.08.2026 | 7 | 7 |
| дубль, 11.08.2026 | 4 | 4 |

Строки продавцов складываются в итог; видимых назначений 604 = «компаний найдено» на
этой же странице. Все страницы обеими ролями отдают ожидаемый код: 200, а продавцу на
статистике и распределении 403.

**Отключённые пользователи убраны из всех сводок** (по просьбе владельца). Это user1..user3
и `admin`, унаследованные с боевой панели. Их нет в блоке на «Списке» (ни в строках, ни в
итоге, ни в выборе), в таблице продавцов на статистике, в таблице «Распределения» и в
фильтре «Продавец». «Последний день с отметками» тоже считается только по действующим —
иначе ссылка вела бы на день, где в таблице одни нули. «Распределение» теперь строится от
действующих продавцов, а не от назначений: раньше новые четыре продавца там не были видны
вовсе, потому что у них нет назначений.

**Из базы ничего не удалено** — на старых аккаунтах 1 638 назначений, 94 состояния,
комментарии и журнал; скрытие обратимо, удаление нет.

**Что осталось и почему.** В строках самого списка колонка продавца по-прежнему показывает
user1..user3 (на первой странице — у всех 100 строк): все компании снимка назначены старой
команде, и это факт назначения, а не сводка. Подменять его в показе значило бы врать о
данных. Уйдёт, когда приедет база Мейера или когда компании перераспределят на новых
продавцов. Плитки общей статистики («назначений всего 1638», «обработано 94») тоже
считают всю базу — они про компании, а не про продавцов.

Поэтому сейчас у всех четверых нули: ни назначений, ни звонков. Блок оживёт, когда
приедет база Мейера и её распределят.

На телефоне блок встаёт под счётчиками, таблица прокручивается в своей рамке. Страница
на телефоне всё равно шире экрана, но это было и до блока: старый выпадающий список ОКВЭД
с пунктами до 144 знаков.

## Одна шапка на все страницы

Владелец: «когда переходишь между вкладками появляется куча новых шапок. Нужны только
“Вся очередь, Взял в работу, Компания не понравилась, Дубль”, а у админа ещё
Статистика; кроме статистики остальное админ видит всю базу; никаких новых шапок».

Шапок было шесть разных: у карточки, статистики, распределения, списка и трёх страниц
парка — каждая со своим набором ссылок. Теперь шапка одна — `app/templates/_shapka.html`,
и все семь страниц её подключают (`{% include "_shapka.html" %}`). Поправить каждую по
отдельности было бы быстрее, но они разъехались бы при первой же следующей правке.

| кто | вкладки |
|---|---|
| продавец | Вся очередь · Взял в работу · Компания не понравилась · Дубль — уже работают |
| админ | то же + Статистика |

«Список компаний», «Парк машин» и «Распределение» из шапки убраны; страницы живы по
прямому адресу. Активная вкладка подчёркнута. Проверено на 9 страницах у админа и 7 у
продавца: шапка одна и та же с точностью до отметки активной вкладки, все её адреса
начинаются с `/obzvon-meyer/`.

**Ловушка, пойманная проверкой.** Первая версия шапки брала префикс так:
`base_path if base_path is defined else bp`. На «Списке» и «Парке» шаблону передают `bp`,
но `base_path` там тоже «определён» — это **глобальная** переменная общего окружения Jinja
от другого приложения, и она пустая. Шапка на этих страницах вела на `/centro` вместо
`/obzvon-meyer/centro`, а через Caddy такой адрес ушёл бы на совсем другой сервис. Теперь
шапка берёт только `obzvon_bp` — своё имя, его задаёт `routes_centro_sales` и больше никто.

**Админ видит всю базу** — проверено числом: на вкладках у админа «взял в работу» 53, «не
понравилась» 12, «дубль» 21 — ровно столько этих статусов по базе у всех продавцов вместе
(без скрытых и вне каталога). У продавца без назначений — 0.

**Календарный блок переехал на «Статистику»** — «Списка компаний» в шапке больше нет, и
иначе до блока не дойти. Блок вынесен в `_statblok.html` и стоит на обеих страницах одним
файлом; дата и выбранная очередь продавца друг друга не сбрасывают.

## Очередь списком, карточка по клику

Владелец: «вся очередь списком с основными данными в списке, когда проваливаешься в
компанию — тогда открывается карточка».

**Было.** `/centro` без `inn` подставлял первую компанию страницы и сразу рисовал её
полную карточку; список из 20 компаний жил в самом низу, под всеми блоками карточки.

**Стало.**

* Все вкладки (`/centro`, `?call_status=v_rabote|ne_ponravilas|dubl`) без `inn` — **список**:
  те же фильтры, тот же порядок, что у очереди (`_queue_rank`), по 20 / 50 / 100 на
  странице. Колонки: №, компания (ИНН · регион, статус ЕГРЮЛ если не ACTIVE), ОКВЭД,
  выручка, машины (+ «под замену», состояния), приговор, контакты (тел · тех · закуп,
  «телефон с ролью»), статус звонка с датой, балл, у админа — продавец. Строка кликается
  целиком; если выделяли текст (скопировать ИНН), переход не срабатывает.
* `?inn=…` — карточка, как была, плюс «← к списку» (на ту страницу списка, где эта
  компания) и место в очереди «Компания 21 из 518» вместо «Компания 1–20».
* **«Сохранить и перейти дальше»** ведёт на **следующую компанию очереди** в той же
  вкладке и с теми же фильтрами. Раньше «дальше» значило «первая компания страницы», и
  после сохранения карточка открывалась сама — в режиме списка без этой правки продавец
  падал бы в список после каждого звонка. Последняя в очереди — возврат в список.
* «← Предыдущая» / «Пропустить →» — соседние компании очереди, а не страницы по 20.
  «↩ Вернуть в очередь» возвращает в список: вернутая компания уходит из текущей вкладки.

Обёртка списка — не `main.page-wrap`: на ней висит скрипт «⚙ Вид» для блоков карточки,
и он сам выходит, если такой обёртки нет. Проверено в браузере: в списке кнопки «Вид»
нет, в карточке есть, ошибок скриптов ноль на обеих страницах.

Проверено: вкладки списком дают 518 / 53 / 12 / 21 — ровно как карточный режим до правки;
`size=50` — 50 строк; из 21-й компании «к списку» ведёт на 2-ю страницу; во вкладке
«Взял в работу» «дальше» остаётся во вкладке; продавец без назначений видит «Компании не
найдены», страница не падает. Сквозная проверка через публичный адрес — та же.

### Комментарий в списке, под статусом

Владелец про вкладку «Компания не понравилась»: «сюда выводится комментарий, который был
бы оставлен?» — раньше нет: под статусом стояла только дата, комментарий был виден лишь
внутри карточки. Теперь под статусом — **последний комментарий** по компании (обрезан до
120 знаков, целиком — при наведении). У админа рядом автор, а если комментарий оставлен в
другой день, чем последний звонок, — и его дата. Видимость как в карточке: админ видит
все, продавец — только свои (проверено: продавец без своих комментариев видит ноль).

Комментарии берутся отдельным запросом по ИНН строк текущей страницы, а не из «последних
1000», которые маршрут грузит для карточки: на большой базе старый комментарий к компании
в эту тысячу не попал бы и пропал из списка молча.

Сверено с базой: «не понравилась» — 12 компаний, с комментарием 12, показано 12;
«взял в работу» — 53, с комментарием 4, показано 4; «дубль» — 21, с комментарием 19,
показано 19.

## Причины «Компания не понравилась»

Владелец: «при наведении в “компания не понравилась” выпадал подсписок причин (5
причин)» — из списка Битрикса, лишние зачёркнуты. Остались: неверно указан номер; нету
ФТС и не надо (для хол); клиент не выходит на связь (3 звонка/2 письма); уже купили у
конкурентов. Пятую, «дубль», владелец затем убрал — «чтобы не плодить очереди»: для
дублей есть отдельный результат «Дубль — уже работают» со своей вкладкой, и вторая
дорога туда же разводила бы дубли по двум очередям. Сохранений с ней до правки не было. Список — одна константа `PRICHINY_NE_PONRAVILAS` в
`routes_centro_sales.py`: из неё строится меню и по ней же проверяет сервер.

Родной `<select>` подменю при наведении не умеет, поэтому «Результат» в карточке — своя
менюшка с теми же пунктами; у «Компания не понравилась ▸» подменю (наведение мышью, на
телефоне — тап; у правого края экрана раскрывается влево). Значение уходит в те же поля
формы. Причина пишется **первой строкой комментария** — «Причина: уже купили у
конкурентов. …» — и без новой схемы видна там же, где комментарии: под статусом в списке
и в истории карточки. «Не понравилась» без причины или с причиной не из списка сервер не
принимает (422); обязательность выбора даёт и скрипт.

Проверено: в браузере — наведение раскрывает подменю, выбор причины ставит оба поля,
обычный пункт причину сбрасывает, без результата форма не уходит; на сервере — 422 без
причины и с чужой, 303 с причиной, комментарий записан, причина видна в списке. Запись
шла во **временную копию** базы продаж: на рабочей с сегодняшнего дня работает команда.

## Фильтры под базу Meyer

Владелец: «есть техЛПР, выручка диапазоном, сегмент, ЛПР мобильный, ОКВЭД по основным и
дополнительным». Диалог «Все фильтры» перестроен:

* **Компания** — поиск, регион, **ОКВЭД — основной и дополнительные** (несколько через
  запятую: «10.3, 01.25»), сотрудник (по ФИО), результат звонка. «Статус ЕГРЮЛ» — только
  если у базы он есть.
* **Сегмент и ЛПР** — сегмент (с числом компаний), «Есть техЛПР», «ЛПР с мобильным»,
  «Закупщик / снабжение». Сегмент вынесен и в основную строку фильтров.
* **Выручка и приоритет** — выручка **в млн ₽** (раньше — рублями целиком, девять нулей).
* «Центробежное оборудование», «Новостной повод», «Известна модель» — только если у
  базы есть такие данные; у Meyer их нет, у центробежной базы они бы остались.

**ОКВЭД сравнивается по началу каждого кода**, а не подстрокой. Старый фильтр искал
подстроку и только в основном коде; подстрокой «10.» находит и 01.10.4, и 24.10. Новый
находит втрое больше, чем по основному: «10.3» — 19 компаний (по основному было бы 6),
«10.8» — 30 (было бы 10), «52.10» — 21 (было бы 7). Старый параметр `okved` оставлен
работать как раньше — на него могут вести ссылки.

Все фильтры сверены с независимым подсчётом по исходному файлу: сегменты 2 / 12 / 63 /
19 / 3 / 10, техЛПР 16, ЛПР с мобильным 64, выручка 100–1000 млн — 36, от 1 млрд — 8,
до 50 млн — 9, «ягоды + техЛПР» — 1.

**Попутно:** кнопка «Результат» была шире колонки формы и наезжала на соседнюю;
«Сохранить и перейти дальше» обрезалась и раньше (высота кнопки была зашита в 42px);
**со «Статистики» ссылки на уже обработанные компании давали 404** — «Вся очередь»
показывает только необработанные, а карточка ищется в текущей вкладке. Теперь ссылка
ведёт в вкладку статуса компании (проверено: 200).

## Как подменить базу, когда владелец её пришлёт

Код менять не нужно: пути к базам читаются из переменных окружения. **Но одна база
указана под несколькими именами** (разные модули ищут её по-разному), и менять надо
все — иначе часть страниц останется на старой базе:

```
каталог компаний:  CENTRIFUGAL_DB, CENTRO_DB, PARK_OCHERED_DB
продажи:           CENTRO_SALES_DB, PARK_OCHERED_SALES_DB
база «Парка»:      PARK_PANEL_DB
```

Порядок: положить присланный файл в `C:\centro2\data\`, поправить **все** строки нужной
группы в `C:\centro2\.env`, перезапустить `start-centro2.bat`, затем
`zapusk.py --proverka` — он покажет, куда смотрит каждый путь. Если новый путь окажется в
`C:\seostat\data`, загрузчик откажется стартовать.

Важно понимать разделение: `centrifugal.db` — это каталог (компании, факты, контакты,
люди, источники), `centro_sales.db` — работа продавцов (кому что назначено, результат
звонка, комментарии, журнал действий). Если присланная база это новый **каталог**, меняется
первая строка; если это новая **раскладка по продавцам** — вторая.

Базы в копии это снимок на момент копирования. Действия в копии в боевую панель **не
попадают**, и наоборот.

## Грабли, оплаченные этой сменой

* **`str.replace` без совпадения молчит.** Скрипт печатал «ссылка добавлена» по факту
  записи файла, а не по факту замены. Теперь каждая правка печатает `внесено N из M`, а
  якорь сперва ищется в настоящем тексте файла.
* **Раннер запускает системным питоном.** Любой скрипт, которому нужны `fastapi`,
  `jinja2` или `bcrypt`, должен сам перезапуститься под `C:\seostat\.venv\Scripts\python.exe`

  есть. Рендер проверяется запросом с подменённой через `dependency_overrides`
  авторизацией — пароль админа для этого не нужен.
* **`create_app()` возвращает обёртку `BasicAuthASGI`,** у неё нет `.routes`. Приложение
  FastAPI лежит внутри; моя первая проверка маршрутов из-за этого упала, а вторая считала
  маршруты не того объекта и печатала «stats: НЕТ» при работающей странице. Верить надо
  запросу, а не подсчёту атрибутов.
