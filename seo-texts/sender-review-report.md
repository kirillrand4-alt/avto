## ✅ Подтверждённые (состязательная проверка: реальные)

### `seo-texts/sender/sender.py` [high] — suppression проверяется один раз до отправки, но между проверкой и _deliver recipient мог попасть в suppress (IMAP-ридер добавил bounce)
- **Чем грозит:** письмо уйдёт suppressed адресату → жалобы/bounce
- **Как чинить:** переместить suppress-check в критическую секцию перед _deliver или сделать suppress check+send атомарным
- **Верификатор:** Классический TOCTOU: suppression.is_suppressed() в шаге (3), а _deliver — в шаге (7); между ними идут несколько синхронных вызовов store (get_campaign, build_headers→get_recipient) плюс can_send_now→get_mailbox_state, итого реальный зазор в десятки–сотни мс при DB-бэкенде; конкурентный IMAP-bounce-reader вполне успевает добавить запись в suppression за это время; никакой повторной проверки или блокировки перед _deliver в коде нет.

### `seo-texts/sender/gates.py` [critical] — Параметр since никогда не передаётся ни одним публичным методом — события считаются за всё время существования БД. Большой исторически «чистый» объём разбавляет знаменатель и делает порог недостижимым при свежем всплеске баунсов.
- **Чем грозит:** Домен можно сжечь полностью: гейт не сработает, пока накопленный исторический sent не будет перевешен свежим bounce в достаточной доле. Прямое нарушение требования'не жечь домен'.
- **Как чинить:** Добавить в GatesCfg поле window_days (например, 14). В _domain_metrics, check_mailbox, check_global передавать since=datetime.utcnow()-timedelta(days=cfg.window_days) в каждый вызов _count.
- **Верификатор:** since параметр есть в _count, но нигде не передаётся—все check_* методы вызывают _count без since, метрики считаются за всё время БД. Исторический объём разбавляет свежий всплеск, порог недостижим.

### `seo-texts/sender/gates.py` [high] — Для каждого домена из _active_domains() вызывается _domain_metrics() →3 вызова count_events (sent/bounce/complaint). При 500 доменах — 1500 отдельных SQL-запросов плюс полный скан recipients.
- **Чем грозит:** evaluate_all становится O(N_domains ×3) запросов; при росте базы блокирует event loop / scheduling thread на секунды. В production сротацией ящиков раз в 5 минут — неприемлемо.
- **Как чинить:** Заменить на один агрегирующий запрос: SELECT domain, event_type, COUNT(*) FROM events WHERE event_type IN ('sent','bounce','complaint') [AND ts >= :since] GROUP BY domain, event_type. Аналогично для mailbox и provider.
- **Верификатор:** Подтверждено: _active_domains() делает полный скан iter_recipients(), затем для каждого домена _domain_metrics() выполняет 3 отдельных COUNT-запроса (sent/bounce/complaint). 500 доменов → 1500 SQL +2 полных скана recipients (ещё один для _active_providers()). N+1 не замаскирован нигде в модуле.

### `seo-texts/sender/imap_watcher.py` [high] — письма никогда не помечаются \Seen после обработки; каждый poll возвращает одни и те же UNSEEN-сообщения; dedup на уровне БД защищает от двойного действия, но fetch50 писем и полный цикл classify выполняются при каждом тике
- **Чем грозит:** O(batch) лишних IMAP-fetch + DB-запросов на каждый poll; на загруженном ящике быстро исчерпывается rate-limit IMAP-сессий; нарастающий лаг при росте числа необработанных писем
- **Как чинить:** после успешного _process_event вызывать imap.store(uid, '+FLAGS', '\\Seen') (или imap.uid('store',...) при переходе на UID-команды)
- **Верификатор:** imap.store с флагом \Seen отсутствует; каждый poll делает fetch+classify всех UNSEEN писем заново; БД-dedup блокирует только _process_event, но не расход ресурсов на fetch/parse

### `seo-texts/sender/validation.py` [high] — RCPT-проба открывает порт-25-соединение с целевым MX прямо с отправляющего IP; probe_from='probe@localhost' нарушает RFC (invalid MAIL FROM).
- **Чем грозит:** Целевой MX логирует входящее SMTP-соединение без последующей доставки — это сигнатура зондирования; IP может попасть в блок-лист до начала кампании, уничтожив репутацию домена.
- **Как чинить:** smtp_probe уже False по умолчанию — сохранить. Документировать жёстко: не включать на IP кампании; если нужно, запускать с отдельного disposable IP с валидным probe_from (реальный домен ИНН-отправителя).
- **Верификатор:** Баг реален, но спящий: smtp_probe=False по умолчанию защищает прод, однако дефолтный probe_from='probe@localhost' — невалидный MAIL FROM по RFC 5321 (localhost не является допустимым доменом вне скобочной нотации). При включении smtp_probe=True без явного переопределения probe_from код немедленно отправляет RFC-нарушающие SMTP-соединения с IP кампании, что является сигнатурой зондирования для любого современного фильтра. Это неложное срабатывание: небезопасный дефолт+отсутствие валидации значения probe_from в __init__ — программная ошибка, а не только gap в документации.

### `seo-texts/sender/auth.py` [high] — отсутствует защита от перебора — нет счётчика неудачных попыток / lockout
- **Чем грозит:** offline или online brute-force пароля и TOTP-кодов неограниченничем кроме TLS latency
- **Как чинить:** добавить failed_login_count + locked_until в users или Redis; экспоненциальная задержка / блок после N попыток
- **Верификатор:** в Auth.login нет ни счётчика failed-попыток, ни проверки locked_until, ни rate-limit — store-методы (get_user_by_username, create_session, append_audit) не затрагивают никакой защиты от перебора; единственная «защита» — constant-time compare и единое сообщение обошибке, что лишь скрывает причину отказа, но не ограничивает число попыток; баг реален и воспроизводим в проде без каких-либо обходных механизмов в модуле

### `seo-texts/sender/auth.py` [high] — update_user + revoke_user_sessions — два отдельных вызова без транзакции
- **Чем грозит:** если revoke_user_sessions упадёт после смены пароля, старые сессии остаются валидными с уже изменённым паролем — bypass безопасности
- **Как чинить:** обернуть оба вызова в одну транзакцию через store.transaction() или отдельный метод store.change_password_and_revoke()
- **Верификатор:** resolve() проверяет только sess.revoked и expires_at — пароль не перепроверяется; если update_user() прошёл, а revoke_user_sessions() упал (DB-таймаут, connection-drop, любое исключение), старые токены остаются валидными навсегда; исключение из второго вызова не перехватывается и всплывёт к вызывающему, который увидит ошибку, но смена пароля уже зафиксирована — состояние БД несогласованное; сценарий воспроизводим в проде при любом частичном сбое слоя хранилища
