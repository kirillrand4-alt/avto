## А вот дошла ли слепота до продавца — проверил отдельно, и ответ разный

Само число невидимых строк ещё ничего не говорит о карточке. Взял ТЕ САМЫЕ
пострадавшие строки и посмотрел, стоит ли у них признак технаря.

    центробежка: невидимых для SQL 222 — С ПРИЗНАКОМ ТЕХНАРЯ 222 (все)
    P25:         невидимых для SQL   3 — с признаком технаря   0

**На центробежке цена находки равна ошибке в отчётах, и только.** Признак ставит
`EnrichDB._canon_role`, он питоновский, фильтр продавца идёт через `casefold()` —
«ГЛАВНЫЙ ИНЖЕНЕР» доезжает до карточки наравне с «Главный инженер». То есть числа
в моих сводках были занижены, а данные у продавца целы.

**В P25 — не целы, но причина другая, и это важно не спутать.** Ваша находка
привела меня к дыре, которая к кириллице отношения не имеет: моя приёмка ставила
`is_tech` по словам роли ИЗ ФАЙЛА («1 круг», «2 круг»), а ваша заливка писала роль
словом «техническая». Слово другое — человек тот же, признак не встал.
`Чучкалов Владимир Юрьевич, Главный инженер` лежал без признака, то есть в
главную меру продавцу не попадал.

Это моя ошибка целиком: заслон обязан смотреть на должность, а слова из входного
файла принимать как подсказку, не как источник истины. Починил обоими путями —
канон должности (тот же, что на центробежке) плюс слова роли; признак только
доставляю, ни у кого не снимаю.

## Что беру из этого в правило

Раньше у меня уже было `panel_contains` — питоновская UDF ровно от этой болезни,
написанная для панели обогащения. То есть класс был известен и закрыт в одном
месте, а в отчётных запросах продолжал жить. Правило: **колонку нормализуем при
записи, а на чтении сравниваем питоном; SQL `LIKE` по русскому слову считать
сломанным по умолчанию.**
