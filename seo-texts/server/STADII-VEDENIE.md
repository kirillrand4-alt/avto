## 1. Зачем это, коротко

Сейчас событие снимается один раз и не обновляется: в `signals` нет ни стадии,
ни ключа объекта, ни истории. Увидели «анонс» — и к проекту больше не
вернулись. Для работы от события нужно обратное: объект **ведётся**, и переход
`проект -> стройка` сам по себе повод позвонить. Плюс поле `ts` разнородное, и
свежесть в скоринге считается по грязному полю.

## 2. Что лежит в боевом `ts` (замер, а не память)

| форма | строк | пример |
|---|---|---|
| пусто | 2 848 | |
| RFC-822 со смещением | 329 | `Wed, 22 Jul 2026 20:36:01 +0300` |
| RFC-822 с `GMT` | 151 | `Sun, 28 Jun 2026 03:18:57 GMT` |
| ISO-дата | 144 | `2026-07-26` |
| обрезка до месяца | 129 | `2026-07` |
| `DD.MM.YYYY` | 118 | `13.07.2026` |
| ISO с временем | 6 | `2026-07-29 17:00:16` |
| RFC-822 с двузначным годом | 12 (внутри первых двух) | `Wed, 08 Jul 26 08:00:28 +0300` |

`updated_at` заполнен у **3 725 из 3 725** в виде `YYYY-MM-DDTHH:MM:SS`, но это
дата ЗАПИСИ, а не события.

Результат разбора нашими функциями:

* непустых `ts` — 877 (23,5%), разобрано **877 (100,0%)**: 748 с точностью до
  дня, 129 до месяца;
* `event_date` заполнится у **3 725 из 3 725 (100%)**, но честно это выглядит
  так: 877 (23,5%) — дата источника, 2 848 (76,5%) — подставленная дата записи.
  Поэтому рядом с `event_date` заведена колонка **`event_date_src`**
  (`ts` | `published` | `updated_at`): без неё дату записи невозможно отличить
  от даты события, а по свежести звонят.

Кто не отдаёт дату: vk.com 1 056 строк, zakupki.gov.ru 66, dzen.ru 56,
kommersant 51, neftegaz 43. Это задача коллекторов (в `rec` уже есть поле
`published`), а не парсера: разбирать нечего, когда поле пустое.

Чего `normalize_date` НЕ делает сознательно:

* не понимает «вчера», «на прошлой неделе» — их смысл зависит от момента
  разбора, а не от источника;
* не подставляет год в «12 августа» — новость может быть трёхлетней;
* не пересчитывает часовой пояс: `29 Jul 2026 23:40 +0500` -> 29 июля. Для
  «сколько дней назад» это ничего не меняет, а перевод в UTC сдвинул бы половину
  вечерних новостей на день назад;
* месячная обрезка `2026-07` якорится на 1-е число и помечается точностью
  `month` — это огрубление (самая ранняя точка месяца, то есть консервативная
  оценка возраста), а не выдуманный день;
* год вне диапазона 1990..(сегодня+6) — не дата, а мусор (id лота, сумма).

## 3. Стадии

```
0 не определена   1 проект/анонс   2 стройка   3 пуск   4 действующее/расширение
```

`stage_of(event_type, what)` решает так:

1. **текст `what`** по списку `TEXT_RULES` (сверху вниз, первое совпадение);
2. если текст молчит — **тип события** по `TYPE_RULES` (по префиксу);
3. иначе **0**. Ноль честный: пустая стадия лучше красивой и неверной.

Текст сильнее типа, потому что тип ставит классификатор одним словом, а в
тексте стоит факт: тип `новый завод` + текст «строительство завода» — это
стройка, а не анонс. Первыми в `TEXT_RULES` идут маркеры будущего
(`планирует`, `намерен`, `будет построен`), иначе «планирует запустить в 2028»
уехало бы в «пуск». Составной тип (`новый завод|модернизация`) разбирается по
`|`, берётся максимальная стадия: если объект уже модернизируют, он работает.

Оба словаря лежат **наверху `stadii.py`** плоскими списками, правятся без
чтения кода. Там же `NEW_PLANT_DEFAULT = 2` — куда падает `новый завод` без
текстовых маркеров (855 строк базы, самый спорный тип; ставим стройку, потому
что новость про новый завод почти всегда выходит, когда стройка уже идёт).

Раскладка на всей боевой базе:

| стадия | строк | доля |
|---|---|---|
| 1 проект/анонс | 1 010 | 27,1% |
| 2 стройка | 683 | 18,3% |
| 3 пуск | 790 | 21,2% |
| 4 действующее/расширение | 1 160 | 31,1% |
| 0 не определена | 82 | 2,2% |

В стадии 0 почти всё — `поставляет госзаказчикам` (63) и `прочее` (18): стадии
объекта в них действительно нет, там речь про саму компанию.

Расхождение с ЧАСТЬЮ 2 ТЗ (там было: действующее 36%, пуск 24%, стройка 21%,
проект 14%, не определена 5%) — не ошибка замера, а другое правило: у нас
маркеры будущего и типы `инвестиции` / `резидентство` / `разработка` уходят в
стадию 1, поэтому «проект/анонс» вырос с 14% до 27%. Общий вывод ТЗ это не
меняет: 70% потока по-прежнему стройка и позже.

## 4. Ключ объекта и правило схлопывания

`object_key(region, what, inn=None)` -> `регион|ИНН|стем1-стем2-стем3-стем4`,
например `челяб|7451234567|комбик`. Слова режутся до 6 букв (падежи и род
съедаются), служебные выкидываются, берутся до 4 штук в алфавитном порядке —
перестановка слов в заголовке ключ не меняет.

**Правило схлопывания дубля:** новое событие считается тем же объектом, если
совпал `object_key`. Тогда НЕ заводим вторую карточку, а дописываем строку в
`signal_history` и поднимаем `hotness` объекта. Сам дубль-сигнал по-прежнему
режется на уровне `signals` ключом `UNIQUE(inn, source, what)`.

Что это даёт на боевой базе: 3 725 строк -> 3 581 ключ; в группы больше одной
строки схлопнулись 123 ключа (267 строк), из них **25 ключей уже сейчас содержат
разные стадии** — это готовые переходы, которые видны только после миграции.
Например `санкт|7805104870|обогат`: «завершено строительство обогатительной
фабрики» (стадия 2) и две новости «запуск обогатительной фабрики» (стадия 3) —
раньше это были три отдельных сигнала.

**Где схлопывание рискует склеить разные объекты** (называю прямо, обе стороны):

* **пустой `what`** -> хвост `obj`, и все события компании в регионе попадают в
  одну карточку. В базе таких ключей 27, из них с двумя и более строками — 2.
  Именно так выглядит единственный подозрительный «переход» 4 -> 1
  (`влади|3316008403|obj`): это не движение объекта, а склейка двух разных
  новостей без текста;
* **два разных объекта одной компании в одном регионе, описанные общими
  словами** («строительство цеха» и «строительство цеха» на разных площадках) —
  один ключ. Цена мала: карточка одной компании, звонок всё равно один, в
  истории лежат оба `source_url`;
* **широкие закупочные тексты**: `астра|3006006420|автога-автотр-агнкс-бло`
  объединил «Строительство блочной автогазонаполнительной станции» и «Тендер на
  выполнение строительно-монтажных работ» — по смыслу это один объект, но
  проверять приходится по ссылкам;
* обратная ошибка — **расщепление**: другая формулировка («комбикормовый завод»
  -> «производство кормов») даёт другой ключ, и вместо перехода появится вторая
  карточка. У 715 ИНН из 1 382 больше одного ключа — в основном законно (у
  крупных закупщиков вроде ИНН 7709329253 45 ключей, это 45 разных лотов), но
  часть — именно расщепление. Это «лишняя карточка», а не потеря: событие
  никуда не делось. Лечится только сличением по смыслу, то есть вызовом модели —
  в детерминированную бесплатную библиотеку мы его не тащим;
* **ИНН в ключе** — намеренно: без него разные компании со словом «завод» в
  одном регионе слились бы в кучу. Обратная сторона: безымянное событие
  (задача 4 ТЗ, ИНН ещё нет) не сойдётся с тем же объектом после доопределения
  имени. Такие карточки сшивает повторный проход, а не этот ключ.

## 5. Что считается переходом стадии и почему это повод позвонить

**Переход** — смена `stage` у строк с одним `object_key`. Различаем три случая:

| случай | что делаем | почему |
|---|---|---|
| ключа раньше не было | первая строка в `signal_history`, в `rec` метка `stage_karta='новая'` | это заведение карточки, а не переход |
| стадия ВЫШЕ известной (1->2, 2->3, 3->4) | строка в `signal_history`, `hotness` ВСЕХ строк объекта +1 (потолок 5), метка `stage_perehod` | объект сдвинулся по лестнице |
| стадия НИЖЕ известной | строку в историю пишем, `hotness` НЕ трогаем, метка `stage_nazad` | вниз объекты не ездят: это либо склейка двух объектов в один ключ, либо поздно доехавшая старая новость. Повод перепроверить ключ, а не звонить |
| та же стадия ещё раз | в историю НЕ пишем ничего | подтверждение, а не переход. Новость всё равно лежит в `signals` с тем же `object_key` |

Разделение обязанностей между таблицами: `signal_history` — **только переходы**
(по строке на пару «объект + стадия», с датой и ссылкой-основанием),
`signals` — все события со своими ссылками. `stage_ts` в `signals` — датировка
стадии ЭТОЙ строки (равна её `event_date`, если она разобралась); «когда у
объекта сменилась стадия» берётся из `signal_history`, а не из `stage_ts`.

Почему переход — повод позвонить, а список — нет:

* компрессор покупают между «стройкой» и «пуском» (часть 2 ТЗ). Отдельная
  новость говорит, где объект был в момент публикации; переход говорит, что он
  **движется**, и даёт дату, от которой считается окно;
* переход — это законный повод для второго касания по той же компании:
  «в марте вы анонсировали, сейчас пошла стройка» звучит как внимание к клиенту,
  а не как второе письмо из той же рассылки;
* переход `1 -> 2` — наш главный момент: выбор оборудования ещё впереди.
  Переход `3 -> 4` — почти всегда поздно, но полезен для сервиса и второй
  очереди;
* это ровно то, что продаёт investprojects: не список, а карточка во времени.

Карточка объекта для лид-деска собирается из тех же полей:

```sql
-- карточки объектов одной компании
SELECT object_key,
       MAX(stage)      AS стадия_сейчас,
       MAX(event_date) AS последнее_событие,
       COUNT(*)        AS событий
FROM signals WHERE inn = ? AND object_key IS NOT NULL
GROUP BY object_key ORDER BY последнее_событие DESC;

-- лестница одной карточки: когда сменилась стадия и чем подтверждено
SELECT stage, ts AS сменилась,
       CAST(julianday('now') - julianday(ts) AS INT) AS дней_назад,
       source_url
FROM signal_history WHERE object_key = ? ORDER BY stage;
```

Делает: `ALTER TABLE signals ADD COLUMN stage/object_key/event_date/
event_date_src/stage_ts`; `CREATE TABLE signal_history(object_key, inn, stage,
ts, source_url, event_type, what, created_at)` с `UNIQUE(object_key, stage,
source_url)`; индексы `ix_sig_objkey`, `ix_sig_evdate`, `ix_sig_stage`,
`ix_hist_objkey`, `ix_hist_inn`, `ix_hist_ts`; простановку задним числом по
3 725 строкам и сборку истории (по строке на пару «объект + стадия», основание —
самое раннее событие этой стадии).

Идемпотентность: колонки через try/except, таблица и индексы через
`IF NOT EXISTS`, бэкфилл по умолчанию трогает только пустые поля, история —
`INSERT OR IGNORE`. Проверено на копии схемы: второй прогон обновляет 0 строк и
добавляет 0 строк истории. Приёмка задачи 5 на той же проверке: завод в трёх
новостях разных месяцев дал **одну** карточку `челяб|7451234567|комбик` с тремя
переходами (2 -> 3 -> 4), а не три сигнала.

## 7. Подключение к `news_scan._persist_event` (сам файл НЕ трогали)

### Шаг 1. Функция — на уровень модуля `news_scan.py`

Положить рядом с другими вспомогательными функциями (0 отступов), например
перед функцией, внутри которой живёт `_persist_event`:

```python
def _vedenie(db, rec, inn, source, what):
    """Задачи 5-6 ТЗ: стадия, ключ объекта, нормальная дата, история переходов.
    Зовётся СРАЗУ после db.add_signal(...) — сигнал уже записан, тут только
    надстройка. Любая ошибка проглатывается: ведение объекта не имеет права
    ронять запись события."""
    try:
        import stadii as ST
    except Exception:  # noqa: BLE001  библиотеки нет — работаем как раньше
        return
    try:
        cx = db.cx
        et = rec.get('event_type') or ''
        st = ST.stage_of(et, what)
        key = ST.object_key(rec.get('dd_region') or rec.get('region') or '', what, inn)
        date, src = ST.event_date_of(rec.get('published') or '', db.now)
        url = rec.get('source_url') or ''
        # 1. поля у самой строки сигнала (она уже вставлена add_signal)
        cx.execute('UPDATE signals SET stage=?, object_key=?, event_date=?, '
                   'event_date_src=?, stage_ts=COALESCE(stage_ts,?) '
                   'WHERE inn=? AND source=? AND what=?',
                   (st, key, date, src, date or db.now,
                    str(inn), source or '', what or ''))
        rec['stage'], rec['object_key'], rec['event_date'] = st, key, date
        if not st:                      # стадия не определена — вести нечего
            cx.commit()
            return
        # 2. что об этом объекте знали раньше
        r = cx.execute('SELECT MAX(stage) FROM signal_history WHERE object_key=?',
                       (key,)).fetchone()
        bylo = r[0] if r else None
        # 3. дубль по object_key НЕ плодит карточку. В историю пишем только
        #    НОВУЮ для объекта стадию: повтор той же стадии — подтверждение, а
        #    не переход, и его source_url и так лежит в signals рядом.
        if not cx.execute('SELECT 1 FROM signal_history WHERE object_key=? AND stage=?',
                          (key, st)).fetchone():
            cx.execute('INSERT OR IGNORE INTO signal_history'
                       '(object_key,inn,stage,ts,source_url,event_type,what,created_at) '
                       'VALUES(?,?,?,?,?,?,?,?)',
                       (key, str(inn), st, date, url, et, what, db.now))
        if bylo is None:
            rec['stage_karta'] = 'новая'
        elif st > bylo:                 # объект сдвинулся по лестнице — греем
            cx.execute('UPDATE signals SET hotness=MIN(5, MAX(hotness,?)+1) '
                       'WHERE object_key=?',
                       (int(rec.get('hotness') or 0), key))
            rec['stage_perehod'] = '%d->%d' % (bylo, st)
        elif st < bylo:                 # вниз объекты не ездят: проверить ключ
            rec['stage_nazad'] = '%d->%d' % (bylo, st)
        cx.commit()
    except Exception:  # noqa: BLE001
        pass
```
