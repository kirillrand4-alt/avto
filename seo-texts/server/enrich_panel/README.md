# Панель обогащения (задача #49-а)

Отдельная веб-панель на сайте владельца: загрузить список компаний (CSV/XLSX)
ИЛИ выбрать компании прямо из базы обзвона (страница «База»), выбрать конвейеры
обогащения, запустить, следить за прогрессом, выгрузить CSV.

Стек — как у панели продажников `C:\seostat\app`: FastAPI + Jinja-шаблоны +
свой CSS (без React и внешних CDN). Порт **8013**, за Caddy — путь `/enrich/*`.

## Как это работает (архитектура)

- Панель **НЕ вызывает** `enrich_contacts.py` напрямую и **не имеет своей
  очереди**: она кладёт подписанные HMAC задания `job-*.json` на дроп — их
  исполняет существующая служба `rusprom-runner` (`job_runner.py`). Формат и
  подпись байт-в-байт как у `run_on_server.py` (проверено тестом против
  настоящего `job_runner.sig_ok`). Задача `enrich_contacts` уже в allowlist
  раннера — **менять job_runner.py не нужно**.
- Прогресс считается **только по `stage_log`** в `C:\sender\enrich.db`
  (канон: туда пишутся только успешно завершённые стадии). Рестарт панели,
  раннера или сервера картину не теряет.
- Своё состояние панель держит там же, в enrich.db (таблицы создаёт сама):
  - `enrich_runs` — журнал прогонов (id, created, файл, конвейеры, всего,
    батчей, статус, отчёт валидации);
  - `enrich_run_rows` — принятые строки прогона (для join со stage_log);
  - `enrich_run_batches` — поставленные задания и их статусы.
- «Запустить» и «Докинуть недоделанные» — один и тот же код: отбираются только
  строки **без нужной стадии** в stage_log (идемпотентно), а конвейеры с ещё
  незавершёнными батчами блокируются от повторной постановки.

## Страница «База» (роут /base)

Требование владельца: «изначально обогащается база обзвона — там уже должны
быть (с пагинацией) вся база и возможность обогащать, выбирая числом сколько
и каким типом данных». Страница показывает **весь** индекс обзвона
(`C:\sender\obzvon-index.db`, 161 761 юрлицо; env `OBZVON_INDEX`) постранично:
ИНН, название, регион, выручка (млн ₽), направление, есть ли почта/сайт и
какие стадии stage_log уже пройдены (одним батч-запросом на страницу, без N+1).

Фильтры — комбинируются (AND):

- **выручка от/до, млн ₽** — в индексе выручка лежит строкой («123 456 789»
  в `revenue_rub`, «55,3 млрд руб.» в `revenue`), поэтому разбор — канонный
  `parse_money` (скопирован из sender-patches/obzvon-pagination/callbase),
  зарегистрированный SQL-функцией: пересборка индекса не нужна;
- **хвост списка** — последние N строк в порядке базы;
- **регион** (подстрока, кириллица регистронезависимо), **направление**
  (kc/meyer), **почта есть/нет**, **сайт есть/нет**.

«Обогатить выбранное» = чекбоксы стадий + «сколько компаний взять» (от начала
выборки, кап 5000 — больше без явного числа не берём). По submit панель создаёт
ОБЫЧНЫЙ прогон (enrich_runs/rows/batches) и ставит задания через существующий
`submit_run` — та же идемпотентность (строки со стадией из stage_log повторно
не ставятся) и та же HMAC-очередь раннера, никакой отдельной механики.

Приёмочный сценарий владельца кликами: «обогатить каждым видом обогащения
компании с выручкой от 100 до 150 млн и все компании из хвоста» =
(1) /base → выручка от 100 до 150 → все чекбоксы → «Обогатить выбранное»;
(2) /base → хвост N → все чекбоксы → «Обогатить выбранное». Каждый клик —
отдельный прогон со своей страницей прогресса.

## Конвейеры и фактические операции

| Чекбокс | Задание раннеру (`task=enrich_contacts`) | Батч | Стадия «сделано» |
|---|---|---|---|
| Базовое обогащение (сайт+краул+роли+почты+телефоны) | `args={companies:[{inn,name}], workers, smtp_check, resume, write_db, stream_file: enrich_panel_run<id>.jsonl, source: panel-run<id>}` | 8 | `site` / `site_cand` / `email` |
| ЕИС-закупки | `args={op:'etp_fit', inns:[...], limit:<размер батча>, max_cards:3}` | 8 | `etp` |
| ОКВЭД-классификация | `args={op:'checko_okveds', inns:[...]}` | 8 | `checko` |
| Пере-выбор лучшего адреса | `args={op:'promote_named_email', inns:[...]}` | 1000 | `best_email_v2` |
| Вакансии hh | `args={op:'hh_signals', pages:3}` | вся выборка = 1 job | `hh` |
| ОПО Ростехнадзора | `args={op:'opo_batch', companies:[{ogrn,inn,name}], out_file:panel-opo-run<id>-<инн>.csv}` | 40 | `opo` (см. оговорку) |
| Закупки ЕИС массово | `args={op:'zakupki_mass', cap:<размер выборки>, max_cards:3}` | вся выборка = 1 job | `zakupki` (см. оговорку) |

Почему батчи 8 (6-10, как в news-драйверах): маленький job предсказуем по
таймауту раннера (30 мин) и пишется в БД сразу; `promote_named_email` — чисто
БД-операция без внешних запросов, поэтому её дробить на 8 нет смысла.
`zakupki_check` в базовом конвейере выключен: ЕИС — отдельный чекбокс, иначе
двойная работа по тем же карточкам закупок.

Оговорки по hh/opo/zakupki (фактические ограничения ops, сверено по
enrich_contacts.py, подписи есть прямо в чекбоксах):

- **hh_signals** списка ИНН НЕ принимает: это глобальный скан выдачи hh.ru по
  компрессорным запросам с матчем работодателей на всю базу (+dadata-добор).
  Выборка задаёт только учёт прогресса; если у всех выбранных стадия `hh` уже
  есть — job не ставится вовсе.
- **opo_batch** ходит на checko по ОГРН (панель подтягивает его из индекса
  обзвона по ИНН; без ОГРН op вернёт «нет OGRN»), результат кладёт CSV на дроп
  и **стадию `opo` не пишет** — прогресс по стадии не растёт, а «Докинуть»
  пере-проверит те же компании (дельфин-время!). Не жать повторно без нужды.
- **zakupki_mass** списка ИНН НЕ принимает: идёт по ВСЕЙ базе сверху вниз по
  выручке со своим durable-резюмом (`.zk_done.txt` на сервере); выборка задаёт
  только объём (cap). Стадию `zakupki` тоже не пишет (контакты/сигналы — пишет).
  Адресный ЕИС по списку ИНН — это чекбокс «ЕИС-закупки» (etp_fit).

## Установка на сервер (Windows, C:\sender)

1. **Файлы**: каталог `enrich_panel\` целиком → `C:\sender\enrich_panel\`
   (доставка по канону PANEL-DEPLOY.md: сессия собирает `enrich-panel.zip` с
   путями `enrich_panel\...` → на дроп → владелец, по одной команде):

   ```powershell
   cd C:\sender
   $tok=(Select-String -Path C:\sender\server\runner-secrets.env -Pattern 'DROP_TOKEN=').Line.Split('=',2)[1].Trim()
   Invoke-WebRequest -Uri "https://parsercompressor.online/drop/enrich-panel.zip" -Headers @{'X-Drop-Token'=$tok} -OutFile C:\sender\enrich-panel.zip
   Expand-Archive -Path C:\sender\enrich-panel.zip -DestinationPath C:\sender -Force
   ```

2. **Зависимости** (системный Python 3.11 — тот же, что у панели/раннера;
   `py` без версии = 3.12, НЕ использовать):

   ```powershell
   & "C:\Program Files\Python311\python.exe" -m pip install fastapi uvicorn jinja2 python-multipart openpyxl
   ```

3. **Каталог загрузок**: `mkdir C:\sender\enrich_uploads` (панель создаст и
   сама, но пусть будет явно).

4. **Служба NSSM** (порт 8013, слушает только 127.0.0.1 — наружу только через
   Caddy):

   ```powershell
   nssm install EnrichPanel "C:\Program Files\Python311\python.exe" "C:\sender\enrich_panel\enrich_panel.py"
   nssm set EnrichPanel AppDirectory C:\sender\enrich_panel
   nssm set EnrichPanel AppEnvironmentExtra ENRICH_USERS=<логин>:<пароль>
   nssm start EnrichPanel
   ```

   Переменные окружения (всё, кроме `ENRICH_USERS`, имеет боевые дефолты):
   - `ENRICH_USERS` — **обязательно**; формат как `OBZVON_USERS`:
     `логин:пароль,логин2:пароль2`. Не задано → панель отвечает 503 всем.
   - `ENRICH_DB` — путь к enrich.db (дефолт `C:\sender\enrich.db`).
   - `ENRICH_UPLOADS` — куда класть загруженные файлы
     (дефолт `C:\sender\enrich_uploads`).
   - `RUNNER_ENV` — ключница раннера (дефолт
     `C:\sender\server\runner-secrets.env`): оттуда панель берёт
     `DROP_URL`/`DROP_TOKEN`/`JOB_SECRET` — свои секреты ей не нужны.
   - `OBZVON_INDEX` — путь к индексу базы обзвона для страницы «База»
     (дефолт `C:\sender\obzvon-index.db`; открывается read-only). Индекса
     нет — страница честно говорит об этом, остальная панель работает.
   - `ENRICH_ROOT_PATH` — префикс за прокси (дефолт `/enrich`).
   - `ENRICH_PORT` — порт (дефолт 8013).

5. **Caddy** — сам конфиг НЕ трогаем; блок для владельца (добавить в сайт
   `parsercompressor.online` и перезагрузить Caddy):

   ```
   redir /enrich /enrich/ 308
   handle_path /enrich/* {
       reverse_proxy 127.0.0.1:8013
   }
   ```

   `handle_path` срезает префикс `/enrich`; приложение добавляет его обратно
   в ссылки через `root_path` (как `app.obzvon` для `/obzvon`).

6. **Смоук**:

   ```powershell
   # напрямую (ссылки в HTML будут с /enrich — это нормально, ходить через Caddy)
   curl -u логин:пароль http://127.0.0.1:8013/
   # боевой путь
   curl -u логин:пароль https://parsercompressor.online/enrich/
   ```

   Дальше: загрузить маленький CSV (2-3 компании) → выбрать один конвейер →
   «Запустить» → на странице прогона батч должен уйти в «в очереди», затем
   «выполняется» → «готов», а в «Прогрессе по стадиям» появятся строки.

   Смоук страницы «База»: `curl -u логин:пароль
   https://parsercompressor.online/enrich/base` — должна показать первую
   страницу базы (или честное «индекс не найден», если obzvon-index.db ещё
   не собран). Мини-прогон: фильтр «хвост 3» → один чекбокс (например ОКВЭД)
   → «Обогатить выбранное».

## Безопасность

- Basic-auth на всё приложение; пользователи не заданы → 503 (не открытая панель).
- CSRF: POST принимаются только same-origin (паттерн обзвона, Sec-Fetch-Site).
- Из формы в систему не попадает ни один путь и ни одна команда: файл
  сохраняется под сгенерённым именем в `ENRICH_UPLOADS`, исполняются только
  4 захардкоженных конвейера, и то через allowlist-очередь раннера с
  HMAC-подписью (два независимых рубежа job_runner сохраняются).
- Панель слушает 127.0.0.1 — наружу только через Caddy (TLS + путь /enrich).

## Риски и ограничения (честно)

- **Стадия «сделано» для базового конвейера** — эвристика (`site`/`site_cand`/
  `email`): строка, по которой обогащение прошло, но не нашло НИ сайта, ни
  почты, останется «недоделанной» и попадёт в докидку. Защита от вечного
  ретрая — resume-кап попыток в самом enrich_contacts (`max_attempts=3` на
  stream-файл прогона).
- **`promote_named_email`** пишет стадию только при фактической замене адреса,
  поэтому его «готово N/M» на странице занижено, а докидка переотправляет
  строки без замены. Это дёшево (операция только по локальной БД) и
  идемпотентно, но выглядит как «вечно недоделанный» конвейер — подпись об
  этом есть прямо в чекбоксе.
- **Статусы батчей** обновляются при открытии страницы прогона (панель сама не
  поллит дроп фоном). Если результат job'а забрал кто-то другой (сессия Claude
  руками), батч останется «выполняется» до следующей докидки; прогресс по
  stage_log при этом всё равно корректен.
- **Конкуренция за enrich.db**: панель пишет свои таблицы в ту же SQLite (WAL,
  busy_timeout 30s). Теоретически долгая запись раннера может задержать ответ
  панели на секунды — на практике записи раннера короткие.
- **Большой прогон** (5000 строк, базовый конвейер) — это 625 батчей; тяжёлые
  enrich-job'ы раннер исполняет серийно (heavy-пул = 1), т.е. прогон может
  идти много часов. Это осознанный трейдоф: маленькие батчи переживают
  рестарты и таймауты. ЕИС/ОКВЭД-батчи идут параллельно в общем пуле.
- **Одновременные операторы**: защита от дублей — на уровне конвейера прогона
  (незавершённые батчи блокируют повторную постановку), но два РАЗНЫХ прогона
  с одинаковыми ИНН друг про друга не знают. Стадии в stage_log общие, так что
  второй прогон пропустит уже сделанное — расход задублируется только если оба
  запущены до появления первых стадий. Это же относится к повторным кликам
  «Обогатить выбранное» на /base: каждый клик = новый прогон, и пока стадий
  нет, повторный клик по той же выборке продублирует работу.
- **hh/opo/zakupki**: `opo_batch` и `zakupki_mass` НЕ пишут стадию в stage_log
  (см. оговорки выше) — их «готово N/M» на странице прогона всегда занижено,
  а докидка пере-запускает работу. У `zakupki_mass` есть свой durable-резюм
  (`.zk_done.txt`), у `opo_batch` — нет: повторная постановка ОПО = повторный
  дельфин-прогон по тем же ОГРН. Если понадобится честная докидка — надо
  добавить mark_stage в сами ops (enrich_contacts.py), не в панель.
- **Скорость /base**: фильтр по выручке считает `parse_money` питоном на каждую
  строку (SQL-функция) — полный проход 161k строк занимает доли секунды-секунды.
  Приемлемо для страницы; станет медленно — при пересборке индекса добавить
  числовую колонку `revenue_num` (как в callbase) и заменить `_REV_SQL`.
