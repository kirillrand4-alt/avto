### 1.1. `find_zakupki_contacts` / `zakupki_mass` — обогащение КОНТАКТОВ уже известных компаний, не поиск новых

`seo-texts/server/enrich_contacts.py`, функция `find_zakupki_contacts(inn)`
(строка 3144) и CLI-операция `zakupki_mass` (строка 8980). Механика: по ИНН
компании, которая **уже есть в нашей базе**, идёт RSS-поиск её извещений
`zakupki.gov.ru/epz/order/extendedsearch/rss.html?searchString=<ИНН>&fz44=on
&fz223=on&af=on&ca=on&pc=on&pa=on`, открывается карточка каждого извещения,
из блока «Контактная информация» тянется ФИО+email+телефон снабженца.
Попутно, если предмет закупки матчит `ZK_HOT`-regex — а туда **уже вписаны**
`фотосепаратор|рентген\w*\s+инспек` наравне с компрессорными словами — пишется
«горячий» сигнал через `db.add_signal(..., source='zakupki:eis', ...)`.

**Это инструмент обогащения контактов существующей базы, а не разведки новых
компаний**: вход — ИНН компании из наших 166 620/32 646, выход — email/сигнал
для НЕЁ ЖЕ. Компанию, которой в базе ещё нет, этот путь никогда не найдёт.

Фактическое состояние в `enrich.db`:

| метрика | значение |

| писем с `source='zakupki:eis'` | **765** всего, из них **92** у meyer-компаний |

встречается источник `zakupki:eis`» в `signals`). Это верно для `emails` и

### 1.5. `park/` — параллельный проект, целиком КЦ, но с готовыми, проверенными техническими приёмами

Отдельная поддиректория `seo-texts/park/` (150+ скриптов) — это ИНСТРУМЕНТЫ
разведки парка компрессорного оборудования, полностью про КЦ, к Meyer прямого
отношения не имеет (её `park_vlit_obogashchenie.py` — это «вливание
обогащения», т.е. стандартного конвейера enrich_contacts, а не «обогащения
руды» — ложный друг в названии). Но там **уже решены три технические
проблемы, с которыми столкнётся и Meyer-разведка**, и решения стоит взять
готовыми, а не изобретать заново:

1. **ЕИС отдаёт сертификат от НУЦ Минцифры** — обычный `urllib`/`requests`
   рвётся на TLS. Решение (`park_gaz_eis.py`, `park_brendy_eis.py`): Playwright
   с `ignore_https_errors=True`, headless Chromium на сервере.
2. **ЕИС рвёт слова пробелами при подсветке совпадений** («жидк ого азот а») —
   любой regex на целые слова промахивается мимо реальных совпадений.
   Решение — сравнивать по строке БЕЗ пробелов вовсе (`_bez_probelov`).
   Замер: первая версия фильтра без этого приёма **зря выбросила 3704 строки
   из 7157**.
3. **Потолок выдачи ЕИС — 1000 записей на один поисковый запрос** (20 страниц
   по 50). Общие запросы (по коду ОКПД2, а не по узкому бренду) нарезаются по
   окну публикации: год, а где карточек больше 900 — по месяцам.
4. Готовый паттерн «код ОКПД2 или бренд как ПОИСКОВАЯ СТРОКА в
   `extendedsearch/rss.html`/`results.html`, затем строгий текстовый фильтр по
   ОБЪЕКТУ закупки своей регуляркой» — то есть код ОКПД2 используется не как
   структурный фильтр (у него в самой ЕИС узкая и капризная логика), а просто
   как одна из ключевых фраз в общем текстовом поиске, с дальнейшей строгой
   отбраковкой на своей стороне. Именно этот паттерн стоит скопировать под
   Meyer (см. §2 ниже) — `park_gaz_eis.py` целиком годится как шаблон, меняя
   только список запросов и regex-фильтр.
5. Формат бренд-ориентированного скана уже существует как ОТДЕЛЬНЫЙ,
   дата-драйвенный скрипт: `park_brendy_eis.py` читает список запросов из
   `park_brendy_zaprosy.json` (лежит на сервере, не в репо) — то есть
   механизм «просканировать ЕИС по списку БРЕНДОВ» для КЦ уже есть и
   отделён от механизма «просканировать по ОКПД2/родовым словам»
   (`park_gaz_eis.py`, `park_okpd2_eis.py`). Для Meyer нужно то же самое,
   только с списком брендов-конкурентов вместо компрессорных.

| нет отдельного кода | Оптическая сортировка пластика/стекла/вторсырья (сегмент «сортировка вторсырья») | — | Чистого совпадения НЕ нашёл: ближайшие кандидаты — 28.92.4 (не про пластик), 28.96.10 («оборудование для производства резины и пластмасс» — тоже не то, это ПРОИЗВОДСТВО, а не сортировка отходов), либо 38.32 — но это ОКВЭД (вид деятельности переработчика), не ОКПД2 (вид продукции). **Рекомендация: для этого сегмента искать по тексту («оптический сепаратор», «сортировочный комплекс ТКО», названия брендов), а не по коду ОКПД2** |

Общая методологическая оговорка, важная и подтверждённая опытом `park/`
(см. §1.5, пункт 4): в самой ЕИС узкий структурный фильтр по ОКПД2 в
расширенном поиске работает не всегда предсказуемо (участники грузят карточки
с неточным/устаревшим кодом, код указывается «с запасом» по родительской
группе). Проверенный в этом же репозитории рабочий приём — **гнать код ОКПД2
как ПОИСКОВУЮ СТРОКУ вперемешку с родовыми словами** (`'28.93.20'`,
`'фотосепаратор'`, `'оптический сортировщик'`, `'рентген инспекция'` —
как уже сделано в `news_scan.col_zakupki`), а не полагаться на структурный
параметр — и затем ОБЯЗАТЕЛЬНО фильтровать по объекту закупки на своей
стороне (см. предупреждение из `park_gaz_eis.py`: первая версия такого
фильтра без учёта разрыва слов пробелами ЕИС выбросила 52% валидных строк
зря).

### 2.2. Доступ к данным ЕИС: API, открытые данные, объём

**Ключевая новость, меняющая план: свободный FTP-архив XML-выгрузок ЕИС
(`ftp.zakupki.gov.ru`) ЗАКРЫТ с 1 января 2025 года.** Раньше это был самый
дешёвый путь массово скачать реестр контрактов/извещений целиком; сейчас его
нет. Актуальная замена — SOAP-интеграционные сервисы:

- Эндпоинт сменился в марте 2026: было `int44.zakupki.gov.ru`, стало
  **`int.zakupki.gov.ru/eis-integration/services/...`** — старый адрес просто
  перестал отвечать после релиза ЕИС, у многих интеграторов это сломало
  прод без предупреждения.
- Доступные методы: `getDocsByReestrNumberRequest` (документы по рег.номеру),
  `getDocsByOrgRegionRequest` (документы по региону+типу заказчика),
  `getDocSignaturesByUrlRequest`, `getNsiRequest` (справочники). **Поиска
  «по ОКПД2» или «по ключевому слову» среди этих методов нет** — это не
  поисковый API, а API ВЫГРУЗКИ пакетов по уже известным реквизитам
  (номер/регион/период), рассчитанный на интеграцию учётных систем заказчиков,
  а не на разведку рынка.
- Токен для физлица получается БЕСПЛАТНО через `zakupki.gov.ru/pmd/auth/welcome`
  → вход через Госуслуги → выбор «Физическое лицо» → токен в формате UUID, без
  ЭЦП. Это не заблокировано, но и не даёт того, что нужно: массив документов
  без встроенного отбора по продукту.
- `zakupki.gov.ru/epz/opendata/search/results.html` — отдельный раздел
  «Открытые данные» (заявлено >3400 наборов) существует и общедоступен, но по
  доступным описаниям это, как правило, СПРАВОЧНИКИ/реестры (участников,
  жалоб, банковских гарантий и т.п.), а не построчная выгрузка контрактов —
  **не проверял вживую в этой сессии, наличие там датасета уровня «все
  извещения по ОКПД2 X за период» не подтверждено и не опровергнуто.**
- Отдельно подтверждено (веб-поиск), что раздел **планов закупок 223-ФЗ**
  (`zakupki.gov.ru/epz/orderplan/search/results.html`) поддерживает параметры
  фильтра по ОКПД2 и `fz223=on` прямо в URL расширенного поиска — то есть
  структурный поиск по коду продукта там, в отличие от поиска извещений,
  реально есть. Это, вероятно, источник того самого сигнала «ЕИС план
  223-ФЗ» (129 строк в `signals`), происхождение кода которого не
  восстановлено (см. §1.4) — но сама точка входа рабочая и стоит
  использовать для Meyer напрямую.

**Вывод по доступу**: открытого «скачай всё одним архивом» пути больше нет.
Прагматичный путь — тот, что уже проверен в `park/`: браузер (Playwright,
`ignore_https_errors`) по расширенному поиску `extendedsearch/results.html`/
`rss.html` и по плану-закупок `orderplan/search/results.html`, с кодом ОКПД2
и родовыми словами как поисковой строкой, постранично (до 1000 карточек на
запрос), с окном по году/месяцу при переполнении. Вкладываться в SOAP-токен
имеет смысл только если понадобится тянуть контракты ПАЧКАМИ по уже известному
номеру реестра (например, «допрокрутить» карточку, найденную в выдаче) — для
первичной разведки НОВЫХ компаний он не даёт нужного отбора.

## 3. Сигнал «купили конкурента» — кто уже приобрёл фотосепаратор/рентген-инспекцию другого производителя

Это горячий лид — вероятность апгрейда/второй линии выше, чем у холодного
контакта, а иногда прямая замена (конкурент подвёл по сервису/качеству).
Три канала, отсортированы по ожидаемой отдаче:

### 3.1. ЕИС/коммерческие площадки — по БРЕНДАМ, ре-используя `park_brendy_eis.py`

Технически — прямая копия уже работающего механизма (см. §1.5, п.5): список
брендов-запросов в JSON, тот же браузерный обход `extendedsearch/rss.html` +
`results.html`, тот же фильтр без пробелов. Список брендов из задания:
**Bühler/Buhler/Бюлер, Satake/Сатаке, TOMRA/ТОМРА, СиСорт, Zenith, Anzai**.

Честная находка сверху задания (стоит подсветить владельцу, не молча
подменять): при попытке проверить бренд «Zenith»/«Anzai» как производителей
фотосепараторов веб-поиск их НЕ подтвердил как известные бренды на российском
рынке зерновых фотосепараторов — возможно, это бренды из смежного сегмента
(руда/пластик/промышленная сортировка) или устаревшее/неточное написание,
нужно уточнение у владельца. Зато нашлись реальные, часто фигурирующие в
тендерах бренды, которых в задании нет: китайские **Sortex/SORTDEK, AMD
(Anhui Zhongke), TAIHO, Anysort** — дешёвый сегмент, массово ставится на
элеваторах и крупозаводах среднего размера именно там, где закупки идут через
ЕИС/тендерные площадки (а не напрямую у европейского вендора). Их стоит
добавить в список запросов — по объёму упоминаний в тендерах они, вероятно,
дадут БОЛЬШЕ карточек, чем Bühler/TOMRA (те чаще проходят прямыми контрактами
без публичного тендера).

**Ограничение по закону, которое снижает отдачу именно в 44-ФЗ**: конкурентные
процедуры 44-ФЗ по закону не должны называть бренд в объекте закупки (кроме
формулировки «...или эквивалент», которая тоже не всегда называет исходный
бренд прямо) — значит прямое упоминание бренда конкурента чаще найдётся в
223-ФЗ (госкомпании/госхолдинги закупают более вольно) и в КОММЕРЧЕСКИХ
тендерах на площадках типа b2b-center/bicotender/zakupki360 (частный бизнес,
подобные ограничения не действуют). Это те же площадки, что уже дают сигналы
в `signals` (см. §1.4) — то есть источник частично уже подключён (через
неизвестный код прошлой сессии), просто без Meyer-брендов в запросах.

- **Оценка объёма**: по аналогии с КЦ (park: несколько сотен карточек на
  бренд-группу за прогон, после фильтра — заметно меньше) и по факту, что
  bicotender/zakupki360 уже отдают Meyer-совпадения на ОБЩИХ, не
  брендовых запросах (см. §1.4) — **прикидка: сотни карточек на входе,
  десятки-низкие сотни новых ИНН после фильтра и дедупа с базой**, это
  ОЦЕНКА, не измерение.
- **Трудоёмкость**: низкая-средняя — воспроизвести существующий скрипт,
  собрать список брендов+транслитераций, прогнать.

### 3.2. Новостной сигнал «запустили линию с оборудованием <бренд>» — расширить существующий news_scan

`col_google`/`col_xmlriver` в `news_scan.py` уже ищут капекс-новости по
Meyer-отраслям (§1.6), но НЕ по названиям брендов конкурентов. Добавить
запросы вида `"фотосепаратор Bühler" элеватор` / `"рентген-сканер TOMRA"
завод` в набор `queries`/`xmlriver_queries` — дёшево (это конфигурация
существующего вызова, не новый код), но отдача ниже, чем у тендеров: пресс-
релизы про конкретный установленный бренд оборудования — редкий жанр
(обычно пишут «модернизировали линию», без марки).

### 3.3. Фото на сайтах/в соцсетях (шильдик оборудования на фото цеха) — идея верная, но НЕ построена, дорогая

В задании упомянуто как канал — в репозитории для Meyer НЕ реализовано
нигде (в `park/` для КЦ тоже нет аналога — там ставка на текстовые
источники). Технически это означало бы: скачать фото со страниц «о
производстве»/групп VK компаний из нашей же базы (частично уже кэшируются
через `pagecache`, см. `vk_slug_from_site` в `enrich_contacts.py`) и прогнать
через мультимодальный вызов провайдера с вопросом «виден ли на фото
шильдик/логотип фотосепаратора и какой бренд». Технически осуществимо
(провайдер уже используется мультимодально нигде явно не видел, но
`gen_provider.py` — Anthropic-совместимый клиент, значит vision-запрос
пройдёт тем же путём). **Дорого по деньгам и по времени на компанию**
относительно двух каналов выше — тысячи фото, большинство без полезного
шильдика. **Оценка: низкий приоритет**, стоит делать точечно (по компаниям,
уже отмеченным горячими другим сигналом), а не как отдельный массовый скан.

  сигнал, чем обычный тендер. Не реализован как отдельный систематический
  прогон под Meyer-коды — стоит сделать в первую очередь, точка входа
  подтверждена рабочей.
