## 3. Новые источники: разведка и оценка

### 3.1. 2ГИС (карточки организаций)

**Что даёт.** Название, адрес, 1–3 телефона (часто мобильные — актуальнее
реестровых), режим работы, рубрика, статус «открыто/закрыто» (фильтр мёртвых
лидов), изредка сайт. **Email почти никогда**, ФИО и должность — практически
никогда (2ГИС не публикует ЛПР на карточке юрлица).

**Как получать.** Два пути: (а) официальный API «2ГИС Платформа» —
коммерческий, тарификация по калькулятору объёма запросов, точная цена только
по запросу к 2ГИС (публичного прайса на 2026 год нет); (б) браузерный рендер
карточки через Dolphin — код уже написан (`source='dir'`/2gis в
`enrich_contacts.py`), но **по факту дал 0 строк** ни в `emails`, ни в
`phone_contacts` за всю историю базы, ни у КЦ, ни у Meyer. Значит путь (б)
существует только в коде, не в данных — совпадает с честным примечанием в
`ENRICH-ROADMAP.md` («⏸ Отложено — ждём ключи»/«внедрено, живого замера нет»).

**Ограничения и риски.** ToS 2ГИС формально запрещает автоматический сбор без
API-доступа; браузерный обход завязан на тот же хрупкий Dolphin-транспорт, что
уже флапал весь июль на VK. Юридический риск умеренный (агрегированные бизнес-
данные, не персональные), но конфликт с ToS платформы есть.

**Оценка на 1000 компаний**: телефон ~850–950 (карточка почти у каждой
действующей компании), email ~40–80, ФИО ~0.

### 3.2. Яндекс.Карты / Яндекс.Справочник

Симметрично 2ГИС по полям и по статусу: API организаций у Яндекса платный
(квоты, ключ), геосаджест недостаточен для тысяч точных запросов. Браузерный
путь (`maps:yandex`) тоже в коде, тоже **0 живых строк** в базе. Отличие от
2ГИС — Яндекс.Карты чуть чаще показывают сайт компании и рейтинг/отзывы
(в отзывах B2B-контакты почти не встречаются).

**Оценка на 1000**: телефон ~800–900, email ~50–90, ФИО ~0.

**Вывод по 3.1–3.2**: оба канала «отложены, ждём ключи» владельца — решение
уже принято раньше, здесь только подтверждение: без официального API это
хрупкий 0-выхлопной путь (год подтверждён замером), с API — предсказуемый
источник телефонов (не email/ФИО), стоит того при регулярной необходимости
актуализировать телефоны, но не как основной канал имён.

### 3.3. Rusprofile / список организаций

**Что даёт.** ФИО и должность руководителя (обычно «генеральный директор»),
дата регистрации, статус, учредители — всё это **данные ЕГРЮЛ**, просто в
другой обёртке. Email и телефон Rusprofile **не публикует** — он не собирает
контакты компании, только реестровые факты.

**Ключевой вывод**: раз это ЕГРЮЛ-данные, они **дублируют** то, что уже
теоретически доступно через dadata (уже глубоко интегрирован в конвейер) —
см. находку в разделе 1.4: `ЕГРЮЛ/dadata` как источник ФИО в `people` покрывает
лишь 0,3 % Meyer, хотя директор в ЕГРЮЛ есть у ~100 %. Дешевле проверить и
дожать существующий dadata-канал (нужно свериться, входит ли поле руководителя
в текущий подключённый тариф `findById`, или требуется более дорогой отчёт),
чем подключать отдельно платный Rusprofile (от 940 ₽/мес база, доступ к
массовому/API — дороже) ради того же самого факта.

**Оценка на 1000**: ФИО директора ~950–990 (почти у всех действующих юрлиц),
email/телефон — 0.

### 3.4. hh.ru (вакансии → ФИО отдела кадров и сигнал «расширяется»)

**Важный факт 2026 года**: с апреля 2026 hh.ru закрыл публичный
`GET /vacancies` для неавторизованных запросов (403) — ключ теперь выдаётся
только верифицированным работодателям/рекрутинговым сервисам с модерацией.
Легального публичного способа автоматически собирать вакансии по API для
аналитики **больше нет**. Это значит, что рабочий путь, который уже даёт
результат (`stage_log`: `hh` — 127 компаний Meyer / 324 КЦ, `hh_inversion` —
50 / 394), идёт **не через API**, а через браузерный рендер публичной страницы
hh.ru (Dolphin, как описано в `ENRICH-ROADMAP.md`) — то есть именно тот
скрейпинг, ради прекращения которого hh закрыл API. Умеренный ToS-риск,
хрупкая JS-отрисовка.

**Что даёт по полям.** Вакансия почти никогда не публикует прямой email/телефон
кадровика (кнопка «откликнуться» без контакта) — но **в 10–20 % описаний**
работодатель сам вписывает в текст телефон/почту отдела кадров или снабжения
(тот же паттерн «контакт в свободном тексте», что уже отработан на tender.pro).
Главная ценность — не контакт, а **сигнал**: вакансия по профилю оборудования
= компания расширяет производство прямо сейчас.

**Ключевой пробел именно для Meyer**: `hh_inversion` (вакансия → компания)
запускался с компрессорными ключевыми словами («машинист компрессорных
установок» и т.п.) — под Meyer нужны свои: «оператор фотосепаратора»,
«оператор/инженер рентген-инспекции», «контролёр рентгеноскопии», «оператор
сортировки/весового дозатора». Код тот же, только список запросов новый —
это буквально бесплатное расширение уже готового механизма.

**Оценка на 1000 вакансий по профилю**: именных HR/снабженец-контактов
~100–200 (текст описания), горячих сигналов «расширяется» ~800–950 (почти
каждая релевантная вакансия — сигнал).

### 3.5. Telegram-каналы отраслей

Не использовался прежде ни разу (не найдено ни в коде, ни в `ENRICH-ROADMAP.md`).
Публичные каналы (отраслевые СМИ, организаторы выставок, региональные
пищепром-паблики) читаются без авторизации через веб-превью `t.me/s/<канал>` —
низкий юридический риск (публичный контент, стандартная техника, не требует
логина/токена). Дают **не структурированные карточки контактов, а упоминания**:
«завод X запустил линию/расширяет производство» — тот же тип сигнала, что уже
собирает `news_scan` (donors/signals), просто из Telegram, а не с сайтов СМИ.
ФИО/email/телефон встречаются редко — только когда пост цитирует директора
по имени в связи с открытием/инвестицией (оценка 1–3 % постов).

**Оценка на 1000 постов профильного канала**: капекс-сигналов ~30–80, именных
цитат с ФИО ~10–30, прямых email/телефон ~0–5.

Технически это расширение уже существующей инфраструктуры `news_scan`
(donors-таблица уже поддерживает произвольные домены-доноры) — Telegram
просто ещё один тип источника для той же трубы, не новый конвейер.

### 3.6. ВКонтакте-страницы предприятий

Частично реализовано (см. `ENRICH-ROADMAP.md`, июль 2026) — но с важной
поправкой по факту базы: сигнал «ВКонтакте» (упоминание в постах, капекс) уже
даёт 71 компанию Meyer / 319 КЦ (сопоставимо пропорции — не главный разрыв).
А вот **вытяжка контактов со страницы группы «Контакты» (`source='vk-group'`)
даёт 0 строк в `emails` и `phone_contacts` по всей базе целиком** — не только
по Meyer, это общая недоделка, упомянутая в `ENRICH-ROADMAP.md` как
«транспорт флапает» (тот же хрупкий Dolphin/токен-к-профилю механизм). Чинить
транспорт нужно один раз для всей базы, а не отдельно под Meyer.

**Оценка на 1000 групп** (когда транспорт заработает): телефон ~300–500,
email ~100–200, ФИО (в постах «наш директор Иванов И.И. поздравляет...») ~20–40.

### 3.7. Отраслевые СМИ и пресс-релизы

Инфраструктура уже есть и уже касается Meyer: в `signals` по Meyer видны
`meatindustry.pro` (6 компаний), `prodindustry.com` (7), `bbgl.ru` (8) — то
есть пищепром-доноры **подключены**, это не белое пятно источников. Пробел —
в **объёме**: суммарно топ-12 сигналов у Meyer дают 261 запись, у КЦ — 1 560,
при том что компаний у Meyer в 4,1 раза меньше — то есть сигналов на компанию
у Meyer примерно **вдвое реже**, чем у КЦ. Это говорит не об отсутствии
источника, а о более редком/неполном скан-проходе именно по пищепром-донорам.
**Оценка**: досканировать существующих доноров под Meyer-ключевые слова
(«фотосепаратор», «рентген-инспекция», «сортировка», плюс пищепром-капекс
«запустил линию/модернизировал цех») — почти бесплатно, код готов, нужен
только отдельный проход.

## 4. Почта по шаблону домена (info@/sales@/zakupki@ + SMTP-проверка)

**Размер задачи.** 4 151 мейеровская компания (12,7 % от 32 646) имеет сайт
или кандидата на сайт, но **ни одного чистого email в `emails`** (после
отсева ловушек/общих ящиков холдингов). Ещё 6 358 компаний (19,5 %) не имеют
вовсе ни сайта, ни почты — для них шаблон неприменим, это отдельная задача
поиска сайта.

**Метод.** MX-проверка (домен принимает почту вообще) — дёшево и безопасно,
частично уже делается (`mx_ok` в схеме). RCPT-проверка (конкретный ящик
существует) — отдельная, более тяжёлая операция: SMTP-диалог до команды
`RCPT TO:<адрес>` без реальной отправки письма, смотрим код ответа
(250 = похоже на существующий, 550 = нет, 4xx = временно).

**Что это реально даст.** При 4–5 шаблонах на домен (`info@`, `sales@`/
`otdel-prodazh@`, `zakupki@`, `mail@`, `office@`) — это ~17–21 тыс. SMTP-
транзакций. Ключевая проверка перед тем, как верить ответу — **тест на
catch-all**: если домен отвечает 250 даже на заведомо случайный несуществующий
адрес того же домена, весь результат по нему недостоверен (сервер принимает
всё подряд). По опыту индустрии catch-all настроен у 15–30 % доменов малого
и среднего бизнеса — эту долю результатов придётся выбросить. С поправкой на
catch-all и на то, что многие малые сайты вообще не держат почтовый сервер,
реалистичная **грубая** оценка: confirmed-ответов после фильтра — порядка
800–1 500 доменов из 4 151 (не «адресов у Meyer», а именно тех, где хоть один
шаблон подтвердился). Из них **общие ящики** (`info@`), которые сама база уже
считает низкоотдачными (см. `OBOGASHCHENIE-PROVAYDER.md`, п.4: «модель
регулярно ставила info@ при живом sales@/zakupki@») — то есть даже подтверждённый
ящик по шаблону хуже персонального/ролевого адреса, снятого с сайта.

**Риск для репутации домена-отправителя.** SMTP-проверка сама по себе не
отправляет письмо, но она *создаёт SMTP-трафик* с почтового сервера/IP,
который потенциально пойдёт в боевую рассылку. Массовые пробные `RCPT TO` с
одного IP/домена интерпретируются многими провайдерами (особенно
Microsoft/Exchange-хостинг) как поведение харвестера — это может привести к
занесению **самого нашего** IP/домена в чёрные списки ещё до старта прогрева,
то есть прямо навредить будущей боевой рассылке. Плюс у части провайдеров
(в первую очередь Microsoft-хостинг) RCPT-ответы недостоверны в принципе —
они принимают всё на SMTP-уровне и отбраковывают позже фильтром содержимого,
так что для доменов на Exchange/M365 проверка часто просто не работает.

**Рекомендация**: если делать — только с отдельного, не боевого IP/домена
(не с того, что пойдёт в реальную рассылку), с низким темпом запросов и
обязательным catch-all-фильтром; трактовать результат как низкодостоверный
и приоритет ниже, чем прямой контакт с сайта/справочника. Это оценка «что
получится», реального запуска в рамках этой сессии не делали и делать не
планируем без отдельного решения владельца — тема соседствует с активным
холдом на прогрев/рассылку, хоть сама SMTP-проверка формально не является
отправкой.

## 5. ФИО из уже собранного контекста (`D:\razbor-nahodki.db`, поле `ctx`)

**Что это за база.** Отдельный накопитель (100,9 МБ), куда параллельный
проект (`razbor_stranic.py`) складывает находки при повторном разборе уже
скачанных страниц (сырьё Зенки на D: + кэш конвейера) — **без единого нового
обхода сайта**. У каждой найденной почты хранится `ctx` — ±80 символов вокруг
адреса на странице, специально «чтобы потом доставать фамилию и должность
провайдером, не перечитывая страницы» (комментарий в коде — то есть это
задумано, но ещё не выполнено, шаг ниже как раз про это).

**Замер по Meyer.** Из 119 438 находок в базе на Meyer приходится 23 083 (доля
почти пропорциональна размеру направления — разбор идёт не предвзято).
Применил к `ctx` два простых паттерна прямо в замере (без вызова провайдера):

| Паттерн | Совпало | Доля от 23 083 |
|---|---:|---:|
| «Фамилия И.О.» / полное ФИО с отчеством | 2 219 | **9,6 %** |
| ключевое слово должности рядом (директор, снабженец, инженер, отдел кадров…) | 3 702 | 16,0 % |
| хотя бы один из двух | 4 866 | **21,1 %** |

Примеры из выборки (реальные строки `ctx`, не выдумано): «Главный врач Булатов
Шамиль Энгельсович Телефон: +7 (347) 228-45-14 E-mail: med@simai.ru»; «Начальник
отдела +7 (347) 218-13-23 arslanov.fi@bashkortostan.ru Галиуллина Альбина
Рамил[евна]» — то есть ФИО и должность физически стоят в тех же 80 символах,
что и email, регулярно.

**Честная оговорка**: жёсткий regex-паттерн (9,6 %) — нижняя, надёжная оценка;
провайдер с промптом «извлеки ФИО+должность из контекста» возьмёт больше —
разумная верхняя оценка **около 20 %** (по совпадению с «ФИО или должность
рядом»), но это уже требует прогона через провайдерский API
(`gen_provider.py`), а не чистый regex.

**Масштаб задачи, которую это решает без обхода.** Разбор `razbor_stranic.py`
по Meyer выполнен только на **33,5 %** (10 936 из 32 646 ИНН для сырья Зенки,
и всего 273 — для кэша конвейера, при 1 000 разобранных по всей базе). Это
означает, что расчёт выше (21,1 % на 23 083 находках) сделан **на трети**
потенциального объёма — довести разбор сырья/кэша до 100 % по Meyer (тот же
код, тот же принцип «один проход») пропорционально утроит число доступных
`ctx`-окон, а затем прогон через провайдера по готовому `ctx` (без единого
нового обращения к сайту) — и есть самый дешёвый путь добрать ФИО+должность
для 1–2 тысяч мейеровских компаний. Смежная находка `01-voronka-stadiy.md`
(3 733 компании — «почта есть, но только из обзвонной базы, с сайта не
сняли» — плюс 3 713 «кэш есть, разбор не касался») — это тот же самый backlog
с другой стороны: страницы уже физически скачаны, просто не домыты.
