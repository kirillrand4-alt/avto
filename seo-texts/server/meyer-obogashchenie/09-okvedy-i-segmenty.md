## 3. Пересечение kc/meyer и ошибка разметки

- **kc+meyer** (двойная метка): **801** компания (0,48% всей базы `companies`).
- Разметка `companies.division` (79 970 обзвона) vs `division` в 166 620 companies:
  kc=130 369 (78,2%), meyer=31 845 (19,1%), kc+meyer=801 (0,5%), пусто=3416 (2,1%),
  `-`=169, `КЦ` (опечатка/легаси-метка)=20.

### 3.1. Расхождение между исходным `obzvon.division` и рабочим `companies.division`

Сверка по 161 799 общим ИНН: **160 998 совпадают (99,5%)**, **801 расходятся** —
и это ровно та же цифра, что и общее число `kc+meyer` (совпадение по величине не
означает тождество множеств: примеры ниже показывают разные типы расхождения). Разобрано
12 случайных примеров расхождения — три типа:

1. **companies шире, чем obzvon** (companies=`kc+meyer`, obzvon=`meyer`) — компания
   довооружена меткой kc сверх исходной. Пример: ИНН 5262341310, ОКВЭД 10.61
   (мукомольная промышленность), в обзвоне был чистый `meyer`, в companies стал
   `kc+meyer`. 3 из 12 примеров такого рода.
2. **companies уже, чем obzvon — потеря meyer**: companies=`kc`, obzvon=`meyer`, при
   этом ОКВЭД компании (43.99, 42.21, 43.12, 10.31, 10.84) не поменялся. 6 из 12 примеров.
   Показательно: ИНН 7705034202 (ОКВЭД 10.31 «Переработка и консервирование картофеля» —
   код, который в словаре ЯВНО помечен `meyer`!) в companies стоит `kc` — прямая потеря
   при переносе между базами, не объяснимая словарём вообще.
3. **companies пуст, obzvon заполнен**: companies=`-` (заглушка), obzvon=`kc`. 2 из 12.

Если пропорция (≈половина расхождений — потерянный meyer) сохраняется на всех 801,
это означает **порядка 300–450 компаний, у которых meyer-метка была в исходной выгрузке
обзвона, но не дошла (или была стёрта) до рабочей таблицы `companies`**, которой
пользуется панель рассылки. Это самая конкретная, легко проверяемая «утечка» сегмента —
не гипотеза по смыслу ОКВЭД, а прямое расхождение двух баз по одному и тому же ИНН.

### 3.2. Устарела ли разметка относительно ТЕКУЩЕГО словаря

Пересчитал `division` заново по действующему словарю `OKVED_DIRECTIONS`, используя
собственные поля компании (`okved` + `okved_all`), и сравнил с тем, что реально стоит в
`companies.division`:

| Показатель | Значение |
|---|---:|
| Пересчёт даёт `meyer`, а факт — НЕ meyer | **173** |
| Из них примеры с точным попаданием в meyer-код словаря (10.31, 10.84), но факт = kc | видно в п. 3.1 |
| Словарь даёт только `kc`, а факт — содержит `meyer` | 27 |
| Факт содержит `meyer`, а по текущим кодам компании словарь meyer вообще не даёт | 27 |
| Словарь не даёт НИЧЕГО (коды компании пустые/не распознаны), а факт `division` заполнен | 1138 |
| **Полное несовпадение факта с пересчётом по всей базе (companies)** | **18 132 из 161 799 (11,2%)** |
| То же для `obzvon.division` | 18 819 из 161 799 (11,6%) |

⚠️ Методологическая оговорка про последние две строки: пересчёт сделан упрощённым
Python-скриптом вне сервера (регэксп-парсер кодов, копия словаря), а не вызовом боевой
`division_for_okveds()` из `enrich_db.py` на самих данных сервера — часть 11,2%/11,6%
может быть шумом моего парсера (например, злоупотребление 2-значным fallback-паттерном
кода на произвольных цифрах в тексте), а не реальным дрейфом. Числа 173/27/27/801 —
надёжные (получены прямым SQL по обеим базам, без регэксп-догадок). Для точной цифры
дрейфа нужен реальный прогон `division_for_okveds()` по всей `companies` на сервере —
это стоит сделать отдельным шагом.

**Оценка ошибки разметки одним числом**: как минимум **173 компании** заведомо
недомечены под meyer при пересчёте по действующему словарю, ещё **порядка 300–450**
потеряны при переносе obzvon→companies (п. 3.1), и есть более широкий (но менее точно
измеренный без боевого прогона) сигнал **до ~18 тыс. строк (≈11%)**, где `division`
не совпадает со свежим пересчётом по текущей версии словаря — вероятно, потому что
метка была проставлена раньше, чем словарь дополнялся.

## 5. Что делать (с числом компаний на каждый пункт)

1. **Долить потерянный meyer из obzvon в companies** — прямая сверка по ИНН находит
   до **~300–450 компаний**, где исходная выгрузка (`obzvon.division`) содержала meyer,
   а рабочая карточка (`companies.division`) — нет. Это самый дешёвый и самый надёжный
   прирост: данные уже есть в базе, нужен только перенос. *(seo-texts/server/okved_iz_obzvona.py
   как образец скрипта-переливателя, но писать только в ПУСТЫЕ поля, как он и делает.)*

2. **Пересчитать division по текущему словарю боевым `division_for_okveds()`** (не моим
   упрощённым парсером) по всей `companies` — минимум **173 подтверждённых** компании
   железно недомечены, потенциально до **~18 тыс.** (требует точного боевого прогона,
   не оценки). Это самый крупный по потенциальному объёму пункт, но с оговоркой:
   реальное число может быть заметно меньше 18 тыс. — нужна точная проверка, не догадка.

3. **Починить сопоставление кодов с усечённым нулём** (71.20 хранится как «71.2»,
   36.00 как «36.0» и т.д. — сопоставление по префиксу `code.startswith(k+'.')` не ловит
   более короткую, «родительскую» форму кода). Задевает **≈918 компаний** по базе в целом
   (не только meyer): крупнейший случай — 353 компании с кодом «71.2» вместо «71.20».
   Технический фикс в `division_for_okveds`, без потребности в новых данных.

4. **Новая внешняя выгрузка** — если нужен РОСТ объёма (не чистка) — по кодам,
   которых в текущей базе физически почти нет: пластмассы 22.21/22.22/22.23/22.29,
   стекло 23.13/23.14/23.19, отходы шире текущего 38.32 (38.11/38.12/38.21/38.31/39.00),
   корма 10.91/10.92, опт. торговля профильным сырьём 46.21/46.31/46.36/46.37/46.38,
   уголь/руды/алмазы 05.10/05.20/08.99/32.12. Внутри существующих 161 761 строк по этим
   кодам максимум **7 компаний на код** — довыборка бессмысленна, нужен новый экспорт
   у поставщика данных.

5. **Ревизия «размытых» кодов meyer** (не удаление, а метка на проверку — конверсии по
   ним у меня нет данных): код **10.89** «прочие пищевые продукты, не включённые в
   другие группировки» — самый растяжимый по смыслу код сегмента, **1142 компании
   (3,5% meyer)** под общей формулировкой без конкретики. Три двойных kc+meyer-кода
   (07.10, 10.61, 10.89) вместе дают все **801** компании с двойной меткой — стоит
   решить, как их приоритезировать в очереди (кому звонить первым, КЦ или Meyer),
   чтобы отдел продаж не путался.

6. **Пересмотреть вес «непрофильного первичного ОКВЭД»**: не менее **7043 компаний
   (≥21,6% meyer-сегмента, по данным только топ-40 кодов — реально больше)** получили
   метку meyer исключительно по ВТОРИЧНОМУ коду, а первичный вид деятельности —
   строительство, металлообработка, аренда техники, вода, больницы, НИОКР. Это компании
   повышенного риска ложного попадания (по аналогии с уже пойманным паттерном
   28.13-как-вторичный-код у конкурентов) — кандидат на понижение приоритета обзвона,
   а не на исключение без проверки.
