## 0. Механика: как вообще исполняется шаг

Три разных способа запуска, их важно не путать — от этого зависит ответ «работает ли по одному ИНН».

```

```

**B. Ветка `op` внутри `enrich_contacts.py`** (9049 строк, 61 уникальная ветка `args.get('op')`). Едет той же задачей `enrich_contacts`:

**C. Скрипты `ops/*.py` — их в allowlist НЕТ.** Мост к ним — ветка `op: panel_py`: запускает любой скрипт под `C:\sender` питоном панели 3.11 с `argv`, таймаут по умолчанию 900 с:

Всё, что ниже про `ops/*.py` с флагами `--inn` / `--targets`, исполняется именно так.

**Куда всё стекается.** `enrich_db.py` (902 строки) — единственный источник истины: `companies`, `people`, `phone_contacts`, `emails`, `signals`, `stage_log`, `donors`, `seen_news`. Правило durability из CLAUDE.md соблюдают не все модули — исключения помечены ниже.

## Шаг 5. Надзор и экспертиза промбезопасности

Здесь самая большая дыра, и её надо назвать прямо.

**Что есть — ветки ОПО внутри `enrich_contacts.py`:**

- `{"op":"opo_probe","inn":"…","name":"…"}` (строка 5758) — разведка по одному ИНН: `eo.nadzor-info.ru/search?q={inn}`, checko, rusprofile, list-org + до 5 ссылок из SERP; браузер + CapMonster, дельфин-профиль. **Помечено в коде как РАЗВЕДКА.**
- `{"op":"opo_serp","companies":[…]}` (строка 5705) — тест: хватает ли одних сниппетов xmlriver, чтобы увидеть номера ОПО (`А\d{2}-\d{4,6}`) и контекст «опасный производственный объект / Ростехнадзор». **Помечено как ТЕСТ.**
- `{"op":"opo_licenses","companies":[{"ogrn":"…"}]}` (строка 5508) — лицензии Ростехнадзора через `checko.ru/company/{ОГРН}/licenses/data?source=07`. Ловит маркеры: взрывопожароопасные, химически опасные, **оборудование под давлением более 0,07 МПа**, нагрев воды выше 115 °C, номера лицензий вида `ВХ-\d{2}-\d{5,6}`. ## 3. Нет вовсе, надо написать

1. **Оркестратор «один ИНН → все шаги».** В описи такого модуля нет. Нужен один вход, который по ИНН последовательно дёргает: `dadata` → `checko_okveds` (отсев) → поиск сайта → `dept_directory` → `eis_archive` → `eis_protocols` + `utverzhdayu` → ОПО → hh по названию → новости → и складывает всё в `enrich.db` с `stage_log`. Сейчас это 10+ ручных вызовов раннера, каждый со своей формой аргументов.
2. **Экспертиза промышленной безопасности (ЭПБ).** Реестра заключений ЭПБ в конвейере нет ни в каком виде. Для компрессорной темы это самый прямой квалификационный сигнал после ОПО: заключение ЭПБ на сосуд/компрессор прямо называет объект и часто — ответственное лицо.
3. **ЕРКНМ.** Реестр контрольных (надзорных) мероприятий как канал не реализован. `ops/tel_dlya_erknm.py` только выгружает телефоны по чужому списку ИНН.
4. **ОПО как durable-канал.** Ветки `opo_*` есть, но `opo_batch` пишет только CSV на дроп; в `enrich.db` (`signals` + `stage_log`) признаков ОПО и лицензий РТН нет, в `lead_scoring.py` они не участвуют.
5. **Парсер `pub.fsa.gov.ru`.** `{"op":"fsa_probe"}` — только разведка формы API по тестовому ИНН `4205000908`; самого парсера аттестованных лиц нет.
6. **Целевой поиск по одному ИНН на hh.** Все hh-модули идут либо от ключевых слов, либо от вакансии к компании. Нужен модуль «имя компании с шага 1 → работодатель на hh → его вакансии → техслужба → сигнал», собранный из уже существующих кусков (`hh_probe`, `hh_bez_tehlpr`, `hh_tehsluzhba`).
7. **Целевой поиск новостей по одному ИНН.** `news_scan.py` идёт от новости к ИНН, `newsco_op.py`/`news_from_company.py` — от файла целей. Модуля «дай ИНН — верну ленту поводов» нет; `people_from_news.py` — ближайший, но он про людей и ограничен сайтом компании плюс SERP по должностям.
8. **Боевой 2ГИС.** Единственный модуль — `_ops_map_2gis3.py` (218 строк), состояние **`замер`**: карточки и филиалы по ИНН из зашитого `sales_base.json`, результат только в stdout, ничего не пишет. В задачнике это пункт «пять замеров и ни одного рабочего прохода».
9. **Промышленное применение `_ops_company_card.py`.** Сборщик карточки существует, но не описан, не в allowlist и режет вывод на 12 000 символов.
