# Проверочный VPS (89.22.169.2): что там стоит и как этим рулить

## Зачем отдельная машина

Массовые вопросы «есть ли такой ящик» для антиспама неотличимы от перебора
адресов. Боевой IP у нас один (91.206.14.169, Selectel), и на нём висит всё:
панель, дроп, сервер отписки, раннер. Заменить его дорого. Поэтому проверки
унесены на дешёвый VPS со своей обратной записью — решение владельца 07.08,
«безопасность в первую очередь». Сгорит этот IP — меняется он один, рассылка
не замечает.

Технический домен машины: `probe.compressor-pro-systems.ru`, обратная запись
(PTR) настроена. Письма с неё НЕ отправляются: разговор с сервером получателя
обрывается на команде RCPT TO, получатель ничего не видит.

## Что на ней работает

Один процесс — `vps_runner.py`, задача планировщика `VpsRunner`, поднимается
при старте системы. Делает две вещи:

1. **сам гоняет проверку адресов** каждые 10 минут (`probe_worker.проход`);
2. **разбирает задания сессии** с дропа — файлы `vjob-*.json`.

Раньше проверка жила отдельной задачей `ProbeWorker` в планировщике. Так было
хуже: про такую задачу невозможно узнать, жива ли она, пока не появится работа.
Установщик удаляет её и оставляет один процесс, который отмечается на дропе
файлом `vps-runner-zhiv.json` — по нему и видно состояние машины.

## Установка (одной командой на сервере)

```powershell
powershell -ExecutionPolicy Bypass -File C:\install-vps-runner.ps1
```

Скрипт лежит на дропе (`install-vps-runner.ps1`), скачивается туда же, куда
всё: `C:\probe`. Спросит `DROP_TOKEN` и `JOB_SECRET` — оба есть на боевом
сервере в `C:\sender\server\runner-secrets.env`. Ставит Python и dnspython,
качает раннера и работника, прописывает ключи, регистрирует задачу и делает
пробный круг.

## Как сессия рулит машиной

```bash
# короткая проверка связи
python3 seo-texts/server/run_on_vps.py ping '{"hi":1}'

# проверить адреса прямо сейчас, не дожидаясь своего часа
python3 seo-texts/server/run_on_vps.py probe '{"limit":40}'

# любая команда PowerShell
python3 seo-texts/server/run_on_vps.py shell '{"cmd":"Get-Service VpsRunner*"}'

# выполнить свой скрипт (заливает файл на дроп и запускает там)
python3 runvps.py мой_скрипт.py
```

Права намеренно широкие — прямое указание владельца 07.08: «полные права себе
сделай там и рули». Риск ограничен тем, ЧТО на этой машине есть: ни базы, ни
почтовых ящиков, ни ключей рассылки — только проверка адресов.

Задание принимается, только если сходится HMAC-подпись (`JOB_SECRET`): одного
`DROP_TOKEN` подсунуть работу недостаточно.

**Префикс `vjob-`, а не `job-`.** На дропе живут ДВА раннера — боевого сервера
и этой машины. Общий префикс означал бы, что они растаскивают задания друг
друга, кто первый успел.

## Как замкнута петля с панелью

Прямого доступа между машинами нет, обе ходят на дроп:

```
панель  --> probe-zadanie.json    --> VPS   (кого проверить)
панель  <-- probe-rezultat.jsonl  <-- VPS   (вердикты)
```

Со стороны панели этим занимается цикл `sender/probe_sync.py` (раз в 10 минут,
включён по умолчанию). Он же прогоняет заслон ловушек. Ручки:
`GET/POST /api/probe-sync`, `POST /api/probe-sync/run`.

Собственная проба панели (`addr_probe_enabled`) выключена СОЗНАТЕЛЬНО: она
ходила бы к чужим почтовым серверам с боевого IP. Включать её не надо.

## Правило, которое нельзя ослаблять

Адрес хоронится ТОЛЬКО по явному «такого пользователя нет» (`no such user`,
`user unknown`, `5.1.1`). Отказ САМОЙ пробе — «нужно шифрование», «нет
PTR-записи», серый список — это про нас, а не про адрес. 07.08 из восьми
ответов 5xx четыре были про пробу, и выброс «по коду» убил бы четыре живых
контакта.

## Если что-то не работает

* **на дропе не обновляется `vps-runner-zhiv.json`** — процесс не идёт:
  `schtasks /Run /TN VpsRunner` на машине, либо переустановка одной командой;
* **вердикты «нет MX» по всем адресам** — так было, когда MX искали через
  `dig`, которого в Windows нет. Сейчас ищется через dnspython, запасной
  путь — `nslookup` с разбором, не привязанным к языку вывода;
* **панель пишет «дроп не настроен»** — служба панели не видит переменных
  раннера; `probe_sync` читает их из `C:\sender\server\runner-secrets.env`,
  проверьте, что файл на месте.
