## 1.3 От события к компании и контактам

**Решение владельца 17.09: контакты обогащать не надо, нужны только поводы.**
Прогоны сканера запускаются с `enrich: false`. Причина проста: контактная база у
нас и так 335 тысяч адресов по 124 тысячам ИНН, а обогащение занимает часы на
каждый прогон — вчерашний скан потратил на него пять часов из шести. Событие

# ЧАСТЬ 2. Почему текущий поток — поздний

Разбор 3 725 событий по стадиям:

| стадия | доля |
|---|---|
| действующее, расширение | 36% |
| запуск | 24% |
| строительство | 21% |
| проект / анонс | 14% |
| резидентство | 0,6% |
| не определена | 5% |

Шесть событий из десяти приходят, когда стройка уже идёт или завод запущен.
Причина в устройстве, а не в невезении: мы читаем новости, а новость выходит,
когда режут ленточку. Компрессор покупают между «стройкой» и «пуском», то есть
к моменту нашей новости выбор часто сделан.

Цепочка сигналов от раннего к позднему:

```
намерение → земля и подключение → финансирование → проектирование →
разрешение на строительство → стройка → закупка → пуск
```

Мы стоим на трёх последних. Задача — встать на три-четыре шага раньше.

## Задача 3. Федресурс — СДЕЛАНО 16.09, но не тем способом, что задумывался

**Что оказалось на деле.** Читать Федресурс можно **бесплатно**: у сайта есть
JSON-API `fedresurs.ru/backend/...` без ключей и договора, и даже опубликована
спецификация (`/backend/swagger/v1/swagger.json`, OpenAPI 3.0.1, 129 путей).
Договорной API оператора стоит 50 100 ₽ + НДС в квартал (≈240 тыс. ₽ в год) —
**платить сейчас не за что**, всё нужное отдаёт открытый.

**Главное ограничение, определившее конструкцию: сквозной ленты сообщений в
открытом API нет** — только в разрезе конкретной компании. Единственная сквозная
лента (`/backend/encumbrances`) отвечает, но стоит в `Disallow` robots.txt,
поэтому она вынесена в отдельный режим и по умолчанию выключена. Рабочий режим —
опрос по НАШИМ ИНН из `enrich.db`: компания → её публикации → карточка
сообщения (предмет лизинга, суммы, все стороны с ИНН).

**Замеры на сервере.** 150 ИНН по целевым ОКВЭД за 90 дней: найдены 150 из 150,
капекс-сообщения у 37 (24,7%), всего 182 сообщения, скорость 57 компаний в
минуту. Темп источник держит: 120 запросов подряд с паузой 0,3 с — ни одного
отказа. Попутно снята страшилка: код 451 у них означает не бан, а недопустимое
значение `Limit`.

**Честно про качество.** Разбор 90 карточек лизинга и залога: прямых попаданий

Ценность источника не «он купил компрессор», а «он прямо сейчас оснащает цех».

**Поправка к ТЗ:** типа сообщения «намерение совершить крупную сделку» в

## Задача 4. Доопределение компании перед отсевом

**Зачем.** Ранняя новость часто безымянная: «инвестор построит завод в ОЭЗ»,
«подписано соглашение с резидентом». Сейчас такое событие отсеивается сразу и
попыток нет. Требование «есть компания» владелец сохранил — значит, надо
дожимать имя, а не смягчать правило.

**Что сделать.** В `extract_event` при `company=null`, но `is_capex=true`,
событие не выбрасывать, а отправлять в доопределение по шести путям:

1. реестр резидентов ОЭЗ/ТОР по площадке и дате — резидент там назван;
2. ЕГРЗ по объекту — в заключении стоят заказчик и застройщик (задача 1);
3. инвестпортал региона — «приоритетные проекты» ведутся с юрлицом;
4. Федресурс — сообщение о крупной сделке привязано к ИНН (задача 3);
5. более поздняя новость про тот же объект — там имя обычно появляется;
6. поиск по связке «объект + район + отрасль» нашим xmlriver.

Не дало юрлица ни одно — событие уходит **в отдельную кучу, а не в удаление**:
имя может появиться через месяц. Куча = таблица `signals_bez_imeni` (или
`suspect=2` в `signals`) с текстом, ссылкой, регионом и датой, чтобы по ней
можно было повторно пройтись задачей 5.

**Сделано 16.09:** `doopredelenie.py` (семь стратегий, единый интерфейс, ранний
выход), `kucha_bez_imeni.py` (таблица `signals_bez_imeni` + durable-дубль в
jsonl, миграция идемпотентна и по умолчанию сухая), `DOOPREDELENIE.md`.

**Приёмка пересмотрена по замеру.** Требование «≥30%» было написано на глаз и на
сегодняшних источниках недостижимо — вот измеренное: путь по нашему же корпусу
даёт 3,1% (23 из 735) при точности матчера 88%; ЕГРЗ — 3% от кандидатов; ОЭЗ/ТОР
оценочно 2–4%; платные пути (SERP, xmlriver) не проверялись, оценка 5–10% каждый.
Итого бесплатными путями 8–13%, с платными 15–25%. Новая приёмка: доопределение
не выдумывает имён (точность на отложенной выборке не ниже 85%), а отсев ложится
в кучу и переразбирается повторным прогоном без потери.

**Две грабли, найденные при замере.** Наивный матч давал 57% «попаданий»,
которые оказывались совпадением названия издания и фамилии журналиста. И ЕГРЗ
как определитель имени слаб, хотя как источник событий отличен: в реестре объект
назван канцелярски («Строительство СИКН № 516 ЦПС»), в новости житейски («завод
картонной упаковки»), так что порог «одно общее слово» даёт мусор.

## Задача 5. Стадия объекта и ведение во времени

**Зачем.** Сейчас событие снимается один раз и не обновляется: в `signals` нет
ни поля стадии, ни истории, ни ключа объекта. Увидели «анонс» — и к проекту
больше не возвращаемся. Для работы от события нужно обратное: объект ведётся, и
переход «проект → стройка» сам по себе повод позвонить. Это и есть то, что
продаёт investprojects — не список, а карточка во времени.

**Что сделать.**

* Добавить в `signals` поля `stage` (1 проект / 2 стройка / 3 пуск / 4
  расширение), `object_key` (регион + объект + отрасль, нормализованно) и
  `stage_ts`.
* Завести `signal_history(object_key, stage, ts, source_url)` — по строке на
  каждый переход.

## Задача 6. Нормализованная дата события

**Зачем.** Поле `ts` в `signals` разнородное: там и RFC-822 из RSS

участвует в скоринге.

**Что сделать.** Добавить `event_date` (ISO `YYYY-MM-DD`), парсить при записи,
одноразово проставить задним числом по существующим 3 725 записям. `ts`
оставить как есть — это сырьё источника.

**Приёмка.** У ≥95% записей непустой `event_date`; скоринг свежести считает по
