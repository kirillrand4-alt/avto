# ЧАСТЬ 2. Почему текущий поток — поздний

Разбор 3 725 событий по стадиям:

| стадия | доля |
|---|---|
| действующее, расширение | 36% |
| запуск | 24% |
| строительство | 21% |
| проект / анонс | 14% |
| резидентство | 0,6% |
| не определена | 5% |

Шесть событий из десяти приходят, когда стройка уже идёт или завод запущен.
Причина в устройстве, а не в невезении: мы читаем новости, а новость выходит,
когда режут ленточку. Компрессор покупают между «стройкой» и «пуском», то есть
к моменту нашей новости выбор часто сделан.

Цепочка сигналов от раннего к позднему:

```
намерение → земля и подключение → финансирование → проектирование →
разрешение на строительство → стройка → закупка → пуск
```

Мы стоим на трёх последних. Задача — встать на три-четыре шага раньше.

# ЧАСТЬ 3. Что сделать

Задачи отсортированы по отношению «польза / трудозатраты». Каждая — с
приёмкой, чтобы следующая сессия могла закрыть её и проверить себя.

## Задача 1. ЕГРЗ — заключения экспертизы проектной документации

**Зачем.** Единственная точка, где проект виден до закупки: объект, заказчик,
застройщик и **сметная стоимость**. Стадия «проектирование» — ровно та, где
оборудование ещё не выбрано.

**Что сделать.** Новый коллектор `egrz` в `news_scan.py` по образцу `frp`:
`egrz.gov.ru`, реестр заключений, фильтр по типу объекта (производственные,
промышленные) и региону. Поля на выходе те же, что у остальных коллекторов:
`{title, link, pubDate, source, tier, collector, query}`, плюс в `what` —
объект и смета, в `sum` — сметная стоимость.

**Особенности.** Заказчик и застройщик в заключении названы юрлицами — это
готовый источник имени для доопределения компании (см. задачу 4). ИНН может не
быть, имя есть → dadata v2 отработает.

**Приёмка.** Прогон за последние 90 дней даёт ≥100 заключений по промышленным
объектам, у ≥70% определяется ИНН, в `signals` появляется `source='ЕГРЗ'` с
непустым `sum`.

## Задача 2. Реестр займов ФРП вместо новостей ФРП

**Зачем.** Работа сделана наполовину: коллектор `frp` читает
`frprf.ru/press-tsentr/novosti/` — это пресс-релизы, а реестр займов даёт **все**
профинансированные проекты структурно, с суммой, регионом и сроком. Заём — это
подтверждённый бюджет до стройки.

**Что сделать.** Переключить коллектор с новостной ленты на реестр займов,
новости оставить вторым источником (они дают детали). В `lead_scoring.py` уже
есть признак `budget_confirmed` — он должен зажигаться от реестра, а не от того,
что про заём написали новость.

**Приёмка.** Число событий с `source` ФРП растёт кратно; у каждого есть сумма
займа; `budget_confirmed` проставлен.

## Задача 3. Федресурс

**Зачем.** Обязательные сообщения юрлиц: намерение совершить крупную сделку,
залоги, лицензии. Публикуются **по закону и с привязкой к ИНН** — то есть
сразу без задачи угадывания компании. У нас источника нет вовсе.

**Что сделать.** Коллектор `fedresurs`: сообщения выбранных типов, фильтр по
ОКВЭД/региону, ИНН берём прямо из сообщения (это единственный источник, где
шаг dadata не нужен).

**Приёмка.** События появляются с `inn_conf='high'` без обращения к dadata.

## Задача 4. Доопределение компании перед отсевом

**Зачем.** Ранняя новость часто безымянная: «инвестор построит завод в ОЭЗ»,
«подписано соглашение с резидентом». Сейчас такое событие отсеивается сразу и
попыток нет. Требование «есть компания» владелец сохранил — значит, надо
дожимать имя, а не смягчать правило.

**Что сделать.** В `extract_event` при `company=null`, но `is_capex=true`,
событие не выбрасывать, а отправлять в доопределение по шести путям:

1. реестр резидентов ОЭЗ/ТОР по площадке и дате — резидент там назван;
2. ЕГРЗ по объекту — в заключении стоят заказчик и застройщик (задача 1);
3. инвестпортал региона — «приоритетные проекты» ведутся с юрлицом;
4. Федресурс — сообщение о крупной сделке привязано к ИНН (задача 3);
5. более поздняя новость про тот же объект — там имя обычно появляется;
6. поиск по связке «объект + район + отрасль» нашим xmlriver.

Не дало юрлица ни одно — событие уходит **в отдельную кучу, а не в удаление**:
имя может появиться через месяц. Куча = таблица `signals_bez_imeni` (или
`suspect=2` в `signals`) с текстом, ссылкой, регионом и датой, чтобы по ней
можно было повторно пройтись задачей 5.

**Приёмка.** На контрольной сотне безымянных событий доля доопределённых ≥30%;
остальные лежат в куче и переразбираются повторным прогоном без потери.

## Задача 5. Стадия объекта и ведение во времени

**Зачем.** Сейчас событие снимается один раз и не обновляется: в `signals` нет
ни поля стадии, ни истории, ни ключа объекта. Увидели «анонс» — и к проекту
больше не возвращаемся. Для работы от события нужно обратное: объект ведётся, и
переход «проект → стройка» сам по себе повод позвонить. Это и есть то, что
продаёт investprojects — не список, а карточка во времени.

**Что сделать.**

* Добавить в `signals` поля `stage` (1 проект / 2 стройка / 3 пуск / 4
  расширение), `object_key` (регион + объект + отрасль, нормализованно) и
  `stage_ts`.
* Завести `signal_history(object_key, stage, ts, source_url)` — по строке на
  каждый переход.
* При записи нового события искать существующий `object_key`; совпал — не
  плодить дубль, а дописать переход и поднять `hotness`.
* В лид-деск вывести не «сигнал», а карточку объекта: стадия сейчас, когда
  сменилась, сколько прошло.

**Приёмка.** Один и тот же завод, упомянутый в трёх новостях разных месяцев,
даёт одну карточку с тремя переходами, а не три сигнала.

## Задача 6. Нормализованная дата события

**Зачем.** Поле `ts` в `signals` разнородное: там и RFC-822 из RSS
(`Wed, 29 Jul 2026 23:40:41 +0500`), и обрезки вроде `2027-04`. Сортировать по
свежести и считать «сколько дней назад» по такому полю нельзя, а свежесть
участвует в скоринге.

**Что сделать.** Добавить `event_date` (ISO `YYYY-MM-DD`), парсить при записи,
одноразово проставить задним числом по существующим 3 725 записям. `ts`
оставить как есть — это сырьё источника.

**Приёмка.** У ≥95% записей непустой `event_date`; скоринг свежести считает по
нему.

Общий критерий, по которому меряем результат всей работы: доля событий стадии
«проект/анонс» в новом потоке. Сейчас 14%. Цель — не меньше 40% при сохранении
требования «у события есть компания».
