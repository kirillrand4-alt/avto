## Что НЕ работает и требует решения

### 1. Срывы модели в рассуждение — главная дыра по деньгам

Вызов отдаёт 8–19 тысяч токенов выхода при почти пустом тексте. Стоит
$0.28–0.58. Доля — **15% вызовов**.

Что проверено и НЕ помогло:
* уровень рассуждения: срывы идут и на `low`, и на `medium`;
* `max_tokens`: **шлюз его не соблюдает**. Ставил 16000 — приходило 18414.
  Ставил 4000 — приходило 11386. Ограничить выход нельзя.

Что стоит в коде: детектор (выход ≥70% потолка при тексте короче выхода)
переспрашивает на `low` и считает срывы в журнал. Он не предотвращает
срыв, только не даёт принять мусор за ответ.

**Не проверено:** привязаны ли срывы к конкретным компаниям, длине карточки
или стадии. Учёт пишется, данных хватит после сотни писем.

### 2. РАБОТНИК VPS МЁРТВ С 12 АВГУСТА — это блокирует всю отправку

Проверено по файлам дропа 17.08:

| | |
|---|---|
| адресов в задании `probe-zadanie.json` | 400 |
| из них проверено | **0** |
| строк в `probe-rezultat.jsonl` | 2485 |
| **последний вердикт в файле** | **2026-08-12T12:17:09** |

Файл вердиктов накопительный, и свежее 12.08 в нём НЕТ НИ ОДНОЙ СТРОКИ.
Ни один адрес, выложенный сегодня (828 штук двумя порциями), не тронут.

**Осторожно с проверкой «жив ли он» по базе панели.** В `addr_probe` есть
строки с сегодняшним `ts` — это время ЛОКАЛЬНОГО СОХРАНЕНИЯ при повторном
чтении накопительного файла, а не время пробы. Я на этом ошибся и заявил
владельцу «работник жив, 2485 вердиктов за час»; на деле это весь архив за
7–12 августа. **Живость работника проверять ТОЛЬКО по `probe-rezultat.jsonl`
на дропе: есть ли строки свежее сегодняшней даты.**

Следствия:

* 48 писем, одобренных «по проверенной почте», опираются на данные

  свежей проверкой не является);
* `partiya_proba_adresov.py` написан и работает правильно (кладёт наши
  адреса в голову задания, будит работника), но бесполезен, пока будить

**Первое, что надо сделать следующей сессии: поднять работника на VPS.**

## Дроп: как им пользоваться

Дроп — файловый обменник на сервере владельца. Через него ходят тяжёлые
файлы (выгрузки, отчёты, задания работнику VPS) и забираются результаты,
которые не влезают в стандартный вывод серверного задания.

Адрес и токен — в окружении: `DROP_URL`, `DROP_TOKEN`. Токен передаётся
заголовком `X-Drop-Token`. **В чат ни то, ни другое не печатать.**

### Из песочницы сессии — готовый клиент

```
bash seo-texts/server/drop_client.sh list          # что лежит
bash seo-texts/server/drop_client.sh up ФАЙЛ       # положить
bash seo-texts/server/drop_client.sh down ИМЯ      # забрать
bash seo-texts/server/drop_client.sh del ИМЯ       # удалить
```

`down` кладёт файл в ТЕКУЩИЙ каталог под тем же именем и печатает
«скачан: ИМЯ» — самого содержимого в вывод не даёт.

### С сервера, изнутри своего скрипта

```python
import os, urllib.request
def дроп(метод, имя, data=None):
    req = urllib.request.Request(
        os.environ["DROP_URL"].rstrip("/") + "/" + имя,
        data=data, method=метод,
        headers={"X-Drop-Token": os.environ["DROP_TOKEN"]})
    with urllib.request.urlopen(req, timeout=120) as r:
        return r.read()
```

### Зачем это нужно на практике

**Стандартный вывод серверного задания обрезается по объёму, и режется он с
НАЧАЛА — остаётся хвост.** Большой отчёт через `print` не доедет: я так
дважды потерял выгрузку писем. Правильный порядок:

1. скрипт пишет отчёт в файл на сервере (`C:\sender\_ops\ОТЧЁТ.md`);
2. тем же или следующим заданием кладёт его на дроп методом `PUT`;
3. из песочницы `drop_client.sh down ОТЧЁТ.md`.

### Файлы работника VPS (проверка адресов)

* `probe-zadanie.json` — список адресов на проверку. **Плоский JSON-массив**
  строк. Работник берёт из него по `limit` за раз (его потолок — 100).
* `probe-rezultat.jsonl` — накопительный файл вердиктов, по строке на адрес.
  Приём (`probe_sync.забрать`) перечитывает его целиком каждый круг.
* `probe-zadacha-<id>.json` — разовая задача «проверь сейчас», ею работник
  будится (`probe_sync._толкнуть`), иначе он ждёт своего круга.

Имена констант — `ЗАДАНИЕ`, `РЕЗУЛЬТАТ`, `ЗАДАЧА` в `sender/probe_sync.py`.
Я потерял час, гадая имена файлов вместо того чтобы посмотреть туда.

## Скрипты партии — в репозитории

Лежат в `seo-texts/server/ops/`, запускаются через
`seo-texts/server/zapusk_svoego_skripta.py` (он же `runop3.py` в песочнице):
заливает файл на сервер и запускает питоном панели.

```
python3 zapusk_svoego_skripta.py ops/partiya_gen.py 900 1650 --timeout=1700
```

Аргументы после имени файла — **позиционные, уезжают в argv как есть**;
`--timeout=N` разбирается драйвером отдельно.

| скрипт | что делает |
|---|---|
| `partiya_zavesti.py` | заводит кандидатов в панель, дедуп по ИНН |
| `partiya_proba_adresov.py` | держит адреса партии в голове задания работнику |
| `partiya_gen.py` | генерация писем (25 потоков, без пачек) |
| `partiya_hod.py` | ход: сколько сделано, срывы, цена |
| `partiya_skolko_progonov.py` | сколько прогонов живо на сервере |
| `partiya_ubit_dubli.py` | убить лишние прогоны |
| `partiya_proverka_mehanika.py` | адрес в кеше страниц, бренды, числа, гейт |
| `partiya_proverka_smysl.py` | смысловая проверка через провайдера |
| `partiya_v_avtootpravku.py` | одобрить письма с проверенной почтой |
| `partiya_dolozhit_iz_zhurnala.py` | вернуть в очередь письма из журнала |

**Порядок запуска любого прогона:** `partiya_skolko_progonov.py` → если не
ноль, `partiya_ubit_dubli.py` → только потом свой запуск. Правку скрипта
заливать ТОЛЬКО когда прогонов ноль: питон читает файл при старте процесса.
