# Проверка адресов без отправки писем: что настроить

Задача: узнавать, существует ли ящик, ДО того как отправить письмо. Сейчас мы
узнаём это по отбивке — то есть ценой репутации домена рассылки.

Проверка идёт так: сервер получателя спрашивают «примешь письмо для такого-то
адреса?» и разговор обрывают, не отправляя. Ящик отвечает «приму» или «нет
такого пользователя». Само письмо не уходит, получатель ничего не видит.

## Почему сейчас не работает

Прогон 07.08 по 242 адресам очереди: подтверждено 200, «нет такого
пользователя» 4, а **37 остались без ответа — и 20 из них из-за нас**:

```
cannot find your hostname / cannot find your reverse / IP name lookup failed for 91.206.14.169
```

Почтовые серверы обрывают разговор, не дойдя до адреса: у нашего IP нет
обратной записи (PTR). Плюс проба представлялась боевым доменом рассылки —
так делать нельзя, для антиспама сотни неудачных подключений с безымянного
IP выглядят как перебор адресов.

## Что уже есть (проверено на сервере 07.08)

```
сервер            Maxwell, Windows, Selectel
внешний IP        91.206.14.169
PTR-запись        НЕТ  <- главная проблема
порт 25 наружу    открыт (проверено живым соединением с mx.yandex.ru)
```

## Не сожжём ли IP сервера

Проверено 07.08 по конфигу: **письма уходят не с нашего IP**, а через SMTP
Яндекса (11 ящиков, smtp.yandex.ru:465) и Mail.ru (6 ящиков,
smtp.mail.ru:465). В доставке писем `91.206.14.169` не участвует вообще, и
его репутация на неё не влияет.

Что реально можно потерять, если проверять адреса с этого IP:

* сам IP попадёт в чёрные списки (Spamhaus и подобные) — для антиспама
  массовые вопросы «есть ли такой ящик» неотличимы от перебора адресов;
* после этого проверка перестанет работать с него: серверы начнут отказывать
  ещё на подключении;
* веб-панель, дроп и сервер отписки от этого не пострадают — списки касаются
  почтового трафика, не HTTP.

Отсюда простое правило:

| объём проверок | откуда проверять |
|---|---|
| сотни адресов, раз в несколько дней (текущая очередь) | можно с этого сервера, с паузами и лимитом на домен |
| вся база (161 тыс. адресов) | **только отдельный дешёвый VPS**, и лучше два-три с ротацией |

Отдельный VPS под это стоит 200–400 ₽/мес. Требования к нему ровно два:
белый IP и возможность поставить PTR (Selectel, Timeweb, Aeza — дают все).
Плюс отдельного сервера в том, что сожжённый IP не жалко: меняем адрес и
продолжаем, ничего не теряя. Панель и рассылка при этом не задеты.

**Моя рекомендация:** раз база 161 тысяча, взять отдельный VPS сразу — на
текущем сервере проверять только текущую очередь (200–300 адресов), пока VPS
не появился. Инструкция ниже одинаково годится для обоих: меняется только IP.

## Технический домен

Берём **compressor-pro-systems.ru** — у него есть близнецы среди боевых
(kompressor-pro-expert, kompressor-pro-trade), так что как домен рассылки он
всё равно избыточен. После настройки **письма с него не отправляем никогда**:
его задача — только представляться при проверке адресов.

# Шаг 1. PTR-запись (Selectel) — САМОЕ ВАЖНОЕ

Нужно, чтобы `91.206.14.169` резолвился в `probe.compressor-pro-systems.ru`.

**Облачный сервер:** панель my.selectel.ru → Облачная платформа → Сеть →
Плавающие IP-адреса → нужный адрес → меню (⋯) → «Настроить PTR» → вписать
`probe.compressor-pro-systems.ru` → сохранить.

**Выделенный сервер (bare metal):** Серверы и оборудование → нужный сервер →
вкладка «Сеть» → у адреса «Изменить PTR».

**Если поля нет — тикет в поддержку**, текст целиком:

```
Здравствуйте. Прошу настроить обратную DNS-запись (PTR) для IP-адреса
91.206.14.169:

    91.206.14.169  ->  probe.compressor-pro-systems.ru

Прямая A-запись probe.compressor-pro-systems.ru -> 91.206.14.169 уже создана
на нашей стороне. Спасибо.
```

Порядок важен: сначала сделайте шаг 2 (A-запись), потом просите PTR — иначе
поддержка попросит сделать прямую запись и придётся писать второй раз.

# Шаг 2. DNS в RU-CENTER (домен compressor-pro-systems.ru)

Добавить три записи:

| тип | имя | значение |
|---|---|---|
| A | `probe` | `91.206.14.169` |
| TXT | `@` | `v=spf1 ip4:91.206.14.169 -all` |
| MX | `@` | как у остальных доменов (Яндекс 360: `mx.yandex.net.`, приоритет 10) |

MX нужен для шага 3: серверы получателей перезванивают и проверяют, что наш
обратный адрес существует.

# Шаг 3. Ящик postmaster@compressor-pro-systems.ru

Завести домен в Яндекс 360 (как остальные) и создать в нём ОДИН ящик:
`postmaster@compressor-pro-systems.ru`. Пароль приложения — в переменную
окружения сервера, как у боевых ящиков.

Зачем: при проверке мы называем этот адрес обратным. Часть серверов делает
встречный звонок — существует ли он. Сейчас такого адреса нет, и отсюда
отказ `550 Verification failed for <postmaster@...>` (07.08 — один случай).

# Шаг 4. Проверка, что всё встало

На сервере в PowerShell, по одной команде:

```
nslookup -type=PTR 91.206.14.169
```
Ожидаем: `169.14.206.91.in-addr.arpa name = probe.compressor-pro-systems.ru`

```
nslookup probe.compressor-pro-systems.ru
```
Ожидаем: `Address: 91.206.14.169` (прямая и обратная записи должны сходиться —
это и проверяют почтовые серверы).

```
nslookup -type=TXT compressor-pro-systems.ru
```
Ожидаем строку с `v=spf1`.

Как только PTR появился — скажите, я перезапущу проверку по тем 37 адресам,
что сейчас сняты с очереди, и верну живые обратно.

## Что делает наша сторона (уже в коде)

* проба обрывается до передачи письма — получателю ничего не приходит;
* «нет ящика» принимается ТОЛЬКО по явному ответу сервера («no such user»,
  «user unknown», «5.1.1»); отказ нашей пробе (нет PTR, нужен TLS, greylist)
  адрес не хоронит — 07.08 это спасло 4 живых контакта из 8;
* результат каждой пробы пишется в durable-журнал на дропе
  (`proba-adresov.jsonl`), повторный прогон её не повторяет.

## Что добавим после настройки

* STARTTLS в пробе (один сервер сегодня потребовал шифрование);
* контрольная проба заведомо несуществующего ящика того же домена — так
  ловятся catch-all серверы, отвечающие «есть» на что угодно;
* повтор через 20 минут на временный отказ (серые списки);
* лимит: не больше 2-3 проб на домен подряд, пауза между ними.
