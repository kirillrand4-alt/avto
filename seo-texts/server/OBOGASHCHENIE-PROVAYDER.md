## 1. Транспорт: почему он такой странный

`verify_company.py::_provider_call_stdlib` — единственная дверь к провайдеру.

```
адрес     PROVIDER_BASE_URL, по умолчанию https://router.cheap, путь /v1/messages
формат    Anthropic-совместимый: x-api-key + anthropic-version: 2023-06-01
тело      max_tokens 1500, stream: true, одно сообщение role=user
```

Две неочевидные вещи, обе оплачены инцидентами и записаны в комментариях кода:

**`User-Agent: curl/8.5.0`.** Cloudflare-WAF самого шлюза отклоняет дефолтные заголовки
anthropic-SDK — без подмены приходит 403 от WAF. Это вход в оплаченный сервис, а не сокрытие.

**Стриминг + gzip + chunked мелкими кусками по 1200 байт с паузой 0,15 с.** Диагноз от
2026-07-24: маршрут сервера до шлюза душит большие однокусковые POST-тела — свыше ~2 КБ
получаем RemoteDisconnected примерно через 60 секунд, причём содержимое не важно
(воспроизведено и на latin, и на gzip). Проходит только сжатое тело, отданное по частям.
При любом сбое — фолбэк на прямой одиночный POST, на случай если маршрут выздоровел.

`ensure_ascii=False` в теле — не косметика: кириллица в `\uXXXX`-эскейпах занимает 6 байт на
символ вместо 2, а тело и так душат по размеру.

## 2. Модель: какая и почему

```python
VC._PROVIDER_MODEL = args.get('extract_model') or (
    'claude-haiku-4-5' if (args.get('mass_base') or args.get('news_enrich')) else 'claude-fable-5')
```

```
обычный прогон      claude-fable-5
массовый прогон     claude-haiku-4-5   (mass_base или news_enrich)
```

зашит на `claude-fable-5`, когда идёт через `gen_provider`.

## 3. Где вызывается: два места, не больше

### 3.1. `extract_roles` — основной, на каждую компанию с текстом сайта

`enrich_contacts.py`, вызов `VC._provider_call_stdlib(prompt)`.

**Условие вызова:**

```python
if key and EMAIL_RE.search(text):
```

Есть ключ И в скачанном тексте сайта найден хоть один email. Нет сайта, не скачался, нет
почты в тексте — провайдер не зовётся вовсе.

**Сколько раз:** один вызов на компанию, до 3 попыток при сбое (пауза 1,5 с). Не удалось

перепроверяются отдельно: пометка отличает «провайдер лежал» от «сайта не было».

**Выключается** флагом `skip_provider` — тогда только краул и regex, роль у всех «общий».
Это режим быстрого сбора текстов, не боевой.

**Что просит промпт вернуть:**


## 4. Что код ДЕЛАЕТ с ответом: где верит, где перебивает

**Перебивает — выбор лучшего адреса.** Модель возвращает `best_for_outreach`, но код его
пересчитывает своим `_best_by_role`, а ответ модели идёт лишь подсказкой при равенстве
ролей. Причина в комментарии: «она регулярно ставила info@ (общий) при живом
sales@/zakupki@ (пример: БРОКС 3705011046)».

**Перебивает — роли.** Список ролей в промпте не захардкожен, он собирается из канона
(`_ROLES_FOR_PROMPT`), а пришедшее значение всё равно прогоняется через `_canon_role` с 39
правилами. Модель не может выдумать роль вне шкалы.

**Чистит — junk-адреса.** Платформенные и служебные (`help@creatium.io`, noreply, support@)
выбрасываются ДО выбора лучшего; если junk оказался в `best_for_outreach`, он заменяется.

**ВЕРИТ — принадлежность сайта.** Единственное место, где слово модели решает:

```
ИНН на странице        -> verified='inn'       жёстко
ОГРН на странице       -> verified='ogrn'      жёстко
телефон из базы совпал -> verified='phone'     средне
owner_match=true       -> verified='provider'  МЯГКО, это мнение
owner_match=false      -> verified='mismatch', сайт не пишется вовсе
```

**ВЕРИТ — конкурент.** `is_compressor_maker` — вторая ступень отсева (первая — основной
ОКВЭД 28.13/28.12). Ошибка сюда стоит выброшенного клиента, поэтому в промпте прямо сказано
ставить false при сомнении.

## 9. Ответы на четыре вопроса владельца (11.08)

### 9.1. Определяется ли сайт, если его не было в базе, и жёстко ли по ИНН

Определяется. Каналов три, и **по ИНН работает только один, и он фолбэк**:

```
find_site_via_xmlriver   ОСНОВНОЙ. Запрос «<имя без ООО> <город> официальный сайт» —
                         ПО ИМЕНИ И ГОРОДУ. Один запрос с additional=knowledge_graph_y
                         тянет и органику, и карточку компании справа; сайт из карточки
                         берётся первым — органика бывает агрегатором или конкурентом
find_site_via_listorg    ПО ИНН ЖЁСТКО: list-org.com/search?type=inn&val=<ИНН> ->
                         карточка -> внешняя ссылка-домен (не агрегатор)
find_site_via_search     DuckDuckGo по имени+городу, последний фолбэк
```

Плюс кэш ИНН->сайт из прошлых прогонов (`site_source='cache:enrich-db'`) и, если своего
сайта нет, — карточка Яндекса, Я.Карты, ЕГРЮЛ-почта, VK-группа, бизнес-справочники.

Привязка к ИНН возникает НЕ при поиске, а при проверке найденного: ищем ИНН/ОГРН в тексте
сайта. Жёстко подтверждено 1 025 сайтов из 5 001 (см. раздел 5).

### 9.2. Сохраняются ли ВСЕ страницы, откуда достался контакт — нет, по одной

`crawl_contacts` собирает `csrc['emails'][email]`:

```python
per[e] = {'src': srcmap[e],        # метод извлечения (mailto, текст, js-render…)
          'local': e.split('@')[0],
          'ctx': ctx,              # контекст ±70 знаков вокруг адреса
          'url': url_first.get(e, ...)}   # страница, где найден ВПЕРВЫЕ
```

То же для телефонов: `phone_url_first`, контекст ±90 знаков (в нём обычно и стоит должность —
«Главный энергетик — Иванов И.И. — +7 …»).

**Хранится ПЕРВАЯ страница, остальные теряются.** Требование владельца — хранить все.
Правка локальная: `url_first` (dict email->url) заменить на накопление списка, и то же для
телефонов; в `emails.source_url` писать основную, а полный список — отдельным полем или
строками. Заодно это даёт то, чего сейчас нет: видно, что контакт подтверждён НЕСКОЛЬКИМИ
страницами сайта, а не одной.

### 9.3. Как именно получается описание (activity)

Не с главной, а со СКЛЕЙКИ страниц, причём урезанной в пользу контактов:

```
texts = главная + контактные страницы + страницы руководства + найденные поиском
   ↓ склейка
_contact_cap(txt, 24000) — УМНАЯ обрезка: head страницы + окна ±130 знаков вокруг
   каждого email / телефона / «доб. N»; приоритет окон: email и «доб.» (0),
   реквизиты (1), телефоны без контекста (2)
   ↓
text[:24000] -> промпт -> activity (одна фраза)
```

Обрезка писалась ради контактов: в комментарии назван случай robotech.digital, где тупое
`t[:28000]` съело таблицу телефонов с добавочными в конце `/contacts/` — вытянут был только
`info@`, потеряны `sales@` и все добавочные.

**Побочный эффект, который надо знать:** текст «о компании» режется ПЕРВЫМ, потому что в нём
нет ни email, ни телефонов. То есть `activity` строится на том, что уцелело после отбора в
пользу контактов. Если описание нужно надёжным — его надо брать отдельным окном (первые
N знаков главной страницы) и передавать в промпт своим полем, а не надеяться на остаток.

### 9.4. Что именно отдаётся провайдеру

Один текст и один промпт на компанию:

```
на входе   text[:24000] — склейка страниц после умной обрезки (см. 9.3)
           + имя компании, ИНН, город — подставляются в текст промпта
промпт     «Из текста сайта компании извлеки контакты С РОЛЯМИ и ПОДТВЕРДИ, что сайт
            принадлежит именно этой компании… Также определи по тексту главной, ЧЕМ
            занимается компания, и НЕ является ли она нашим КОНКУРЕНТОМ…»
на выходе  СТРОГО JSON: owner_match + owner_reason · activity · is_compressor_maker ·
           emails[{email, role, person}] · phones[] · best_for_outreach
```

Определение конкурента в промпте намеренно УЗКОЕ: конкурент — тот, кто сам производит,
продаёт или сдаёт в аренду компрессоры, генераторы азота/кислорода, мембранные и
адсорбционные установки, фотосепараторы, рентген-инспекцию. Все прочие — клиенты, даже если
делают котлы, трубы, насосы, станки: они сжатый воздух ПОТРЕБЛЯЮТ. При сомнении —
`is_compressor_maker=false`, потому что «ложный флаг = выброшенный клиент».
