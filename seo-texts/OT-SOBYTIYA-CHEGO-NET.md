# Вход от СОБЫТИЯ, а не от компрессора: чего у нас нет

Разворот задачи меняет не список источников, а устройство работы. Раньше вход был
«машина»: парк 12 840 фактов, словарь 986 серий, реестр ЭПБ, предметы закупок с
компрессорными словами. **При входе от события весь этот аппарат молчит** — событие про
машину не говорит ничего, оно говорит «здесь будет стройка».

Ниже — чего нет, по трём разделам: нет источников ранних стадий, нет объекта «проект» в
данных, нет людей ранней стадии. Всё померено сегодня на живой базе.

## 2. Нет объекта «проект». Это главная дыра, и она в данных, а не в источниках

Замер по живой `enrich.db`:

```
таблиц про проект/стадию/событие ....... НЕТ НИ ОДНОЙ   (stage_log — это лог панели, не проектов)
таблица signals, колонки ............... inn, source, event_type, what, sum, source_url,
                                          hotness, ts, updated_at, suspect, inn_conf
НЕТ полей ............................... стадия · проект · регион · адрес · кадастр ·
                                          дата события · срок · застройщик · проектировщик ·
                                          подрядчик
```

Что из этого следует практически — по пунктам, каждый с числом:

**2.1. «Раннюю стадию» сейчас нечем измерить.** У сигнала нет даты события, а дата
взятия пуста у **2 848 строк из 3 725 (76,5 %)**. У остальных она в формате RSS
(`Sun, 28 Jun 2026 03:18:57 GMT`), то есть даже сортировка по строке не работает. Нельзя ни
отобрать «свежие», ни посчитать, на сколько раньше конкурентов мы пришли.

**2.2. Сшивка идёт по ИНН, а не по проекту.** Сигналов 3 725 на 1 382 предприятия,
в среднем 2,7 на ИНН; у **718** предприятий больше одного сигнала, из них **364**
подтверждены двумя и более источниками. Звучит хорошо, но один завод ведёт три разных
проекта — и все они склеиваются в одну кучу под одним ИНН. Разделить их нечем: нет ни
названия объекта, ни адреса, ни кадастрового номера.

**2.3. Дедуп работает против нас.** `seen_news` — **139 030 ключей**, и он дедуплицирует
НОВОСТИ: кто первым взял ключ, тот новость забрал, остальные получают ноль. Для события
нужно ровно обратное — одно событие, найденное пятью источниками, должно давать **один
проект с пятью доказательствами**. Это же и правило владельца «источники накапливаются, а
не заменяются», и именно здесь оно нарушено.

**2.4. Уверенность привязки не проставлена у половины.** `inn_conf`: пусто у **1 900**
из 3 725, `high` 1 028, `low` 575. То есть по половине сигналов неизвестно, чей это проект,
а помечено это молчанием, а не признаком.

**2.5. Приоритет считается не «ранностью».** Есть `hotness` 1–5 (4: 1 293, 3: 1 270,
2: 712, 5: 303, 1: 147), но чем он считается — я не разбирала и не выдаю за известное.
Поля «насколько рано мы пришли» нет вовсе.

## 3. Нет людей ранней стадии. Это проверено поимённо

На стадии проекта решает не тот, кто чинит машину. Замер по `people` (11 434 строки):

```
директор по развитию .......................... 0
капитальное строительство / УКС ............... 0
руководитель проекта / ГИП .................... 0
инвестиции .................................... 0
технический заказчик, служба заказчика ........ 0
                                   для сравнения:
главный энергетик ............................ 612
снабжение и закупки .......................... 571
КОНТРОЛЬ: выдуманная роль ...................... 0
```

**Ни одного человека ранней стадии во всей базе.** Контроль чист, значит это свойство
данных, а не поиска. База собрана под эксплуатацию: энергетик, механик, снабженец. Под
стройку нужны другие: служба заказчика, УКС, директор по развитию, ГИП проектировщика.

Отдельно: **нет самого понятия «покупатель ≠ завод».** На ранней стадии оборудование часто
берёт генподрядчик или EPC-подрядчик, а у нас вся привязка идёт к ИНН эксплуатанта.
Справочника проектных институтов и генподрядчиков нет; связи «проект → проектировщик →
снабженец подрядчика» нет.

## 4. Нет возврата к проекту во времени

Событие ранней стадии — это не повод звонить сегодня, это повод поставить будильник.
После заключения экспертизы до закупки оборудования обычно проходят месяцы.

```
таблицы «проект → ожидаемая следующая стадия → когда вернуться» .... НЕТ
подписки на проект (следить за изменениями по объекту) .............. НЕТ
повторного прохода по старым сигналам ............................... НЕТ
```

Сейчас сигнал живёт один раз: попал в ленту — либо отработали, либо он утонул.

## 6. Порядок починки, если идти от события

```
1. Завести объект ПРОЕКТ: ключ (объект + адрес/кадастр + застройщик), стадия, дата стадии,
   регион, ссылки-доказательства списком. Без него всё остальное будет копить кашу.
2. ЕГРЗ в конвейер. Единственный готовый источник ранней стадии: ИНН застройщика есть у
   397 записей из 420, регион лежит прямо в записи (SubjectRf), ключ не нужен.
3. Дата события отдельным полем, в ISO. Пока 76,5 % строк без даты, слово «ранняя» ничего
   не значит.
4. Роли ранней стадии в справочник ролей и в промпт разбора: служба заказчика, УКС,
   директор по развитию, ГИП. Сейчас их ноль.
5. Будильник по проекту: «заключение экспертизы → вернуться через N месяцев».
6. Подрядчик как покупатель: тянуть из проекта проектировщика и генподрядчика.
7. Стройнадзор/ГИСОГД и слушания — самое дорогое, 85 региональных систем; браться после.
```

Чего я НЕ мерила и не выдаю за известное: как считается `hotness`, как проставляется
`event_type`, работает ли `col_browser`. Это отдельная проверка.
