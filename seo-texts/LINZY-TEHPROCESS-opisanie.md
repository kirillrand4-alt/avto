# Две инженерные линзы техпроцесса — описание для переноса (на статьи и куда угодно)

Обкатано 06.08 на 274 письмах рассылки, встроено в конвейер генерации писем
(`ai_letter.py`, этап `_teh_lens_stage` в конце, после гейта и верификатора).
Забирайте промпты дословно, меняйте только рамку «что проверяем».

## Зачем они, одной фразой

Механический гейт и штатный верификатор проверяют ПРАВИЛА ТЕКСТА (объём, тон,
запрещённые слова). Эти две линзы проверяют ИНЖЕНЕРНУЮ ПРАВДУ утверждений о
технологии: «в гальванике воздухом не сушат детали», «под плазменную резку —
воздух, не азот», «опрессовку делают водой». Такое не ловится регулярками
в принципе.

## Почему их ДВЕ, а не одна

Одно мнение на инженерный вопрос — не проверка. Линзы зовутся НЕЗАВИСИМО
(два отдельных вызова, друг о друге не знают):

* **технолог** — установка «оцени честно»;
* **скептик** — установка «найди неправду; не нашёл — так и скажи».

Расхождение вердиктов — само по себе сигнал: на прогоне 274 писем линзы
разошлись на 44 (16%), и это ровно та серая зона, которую надо показывать
человеку, а не решать автоматом.

## Промпт 1: ТЕХНОЛОГ (дословно)

```
Ты инженер-технолог машиностроительного профиля. Проверь письма поставщика
компрессорного оборудования (винтовые компрессоры, осушители, генераторы
азота/кислорода, МКС, бустеры). В каждом письме есть технологическая связка:
утверждение, где в производстве получателя используется сжатый воздух / азот /
кислород. Проверь ЭТО утверждение на инженерную правду для производства с
данным профилем. verdict: "верно" | "сомнительно" | "ошибка". Ошибка - только
когда утверждение инженерно НЕВЕРНО для такого производства. Общие фразы без
конкретики - "верно".
```

## Промпт 2: СКЕПТИК (дословно)

```
Ты придирчивый инженер-технолог. Установка: НАЙТИ инженерную неправду в
технологической связке письма поставщика компрессорного оборудования. Ищи:
операции, которых в таком производстве не бывает; неверную роль
воздуха/азота/кислорода в названных операциях; перевранные параметры (точка
росы, давление, чистота). Нет неправды - честно скажи "верно", выдумывать
претензию нельзя. Общие фразы без конкретики - "верно".
verdict: "верно" | "сомнительно" | "ошибка".
```

## Вход и выход

На каждый проверяемый текст подаётся:

```
=== ПИСЬМО <id>
Получатель: <имя>
Профиль производства (с их сайта): <activity или «неизвестен»>
ОКВЭД: <код>
ТЕМА: <тема>
<тело целиком>
```

Ответ — строго JSON:

```
{"verdicts":[{"idx":N,"verdict":"верно|сомнительно|ошибка",
              "chto_ne_tak":"пусто или конкретная претензия одной фразой"}]}
```

## Технические грабли (наступлено, не повторяйте)

1. **Партии не больше 3 текстов** — шлюз router.cheap обрезает длинные ответы
   («Unterminated string» на ~1400 знаках). 3 письма × 2 линзы = стабильно.
2. **Профиль обязателен.** Без строки «Профиль производства» технолог слеп и
   судит по ОКВЭДу, а ОКВЭД врёт (у завода чугунных ванн основной код —
   «разборка и снос зданий»).
3. Каждый вердикт — сразу в durable jsonl с fsync, резюм по (id, линза).
4. Модель: claude-opus-4-8 через gen_provider (fable на шлюзе отдаёт пустой
   текст). Стриминг обязателен.

## Как трактовать вердикты (наша политика в комбайне писем)

```
оба «верно»                    пропуск
«сомнительно» у любой          НЕ брак: пометка человеку (след в rounds_json)
«ошибка» у любой               одна попытка починки с претензией дословно,
                               после — повторный мехгейт + повторная линза;
                               не помогло — брак с причиной
```

Резать «сомнительно» нельзя: их 16%, и половина претензий скептика сама
спорна (пневмораспыление в порошковых пистолетах существует, пневмоиспытания
газопроводов — норматив). «Ошибка» двух линз одновременно — почти всегда
настоящая.

## Цифры обкатки (274 письма, для калибровки ожиданий)

```
оба «верно»      179 (65%)
спорно            44 (16%)
ошибка ≥1 линзы   51 (19%)
```

Главный системный урок: ошибки кучковались НЕ в фантазии модели, а в нашем же
справочнике болей по ОКВЭД — модель честно писала из него. Линзы это вскрыли
за один прогон. То же ждите и на статьях: линза найдёт ошибки в исходных
данных (kb/, факты брендов), не только в генерации.

## Перенос на статьи — что поменять

* Рамку: «письмо поставщика» → «SEO-статья каталога prokompressor.ru о
  <бренде/типе машины>»; «технологическая связка» → «технические утверждения
  статьи: параметры, применение, принцип работы».
* Вход: вместо профиля получателя — карточка факта/бренда из kb/
  (`brand_facts_lib`), чтобы линза сверяла с НАШИМ каноном, а не с памятью.
* Скептику добавить ось: «числа и модельные ряды, которых нет в карточке
  бренда — ошибка» (у статей главный риск — выдуманные параметры моделей).
* Политику оставить ту же: ошибка → починка с претензией → повторная линза;
  сомнительно → пометка.
