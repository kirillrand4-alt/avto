# Как работает рассыльщик + автоответчик (сервис «Руспром»)

Полная схема потока: **база → кампания → отправка (с защитой доставляемости) →
получатель отвечает → автоответчик разбирает → тёплый лид → Bitrix → продажник
звонит → квал-лид → сделка.**

Люди-продажи (28 чел) только **звонят по тёплым телефонам**; переписку-
квалификацию ведёт робот — это снимает узкое место ёмкости (10-20 звонков/день/чел
против 2-7 email-диалогов).

---

## ЧАСТЬ 1 — РАССЫЛЬЩИК (исходящее)

### 1.1 База и очистка (`importer`, `suppression`, `validation`)
- Импорт `obzvon_all` (161k юрлиц) → таблица `recipients`. Дедуп по email/ИНН.
- **Suppression:** 39 ИНН конкурентов + корп-список → исключаются из базы.
- **MX-валидация:** классификация по провайдеру получателя (`provider_class`:
  mail.ru / yandex / google / прочее). Данные: **74% базы — Mail.ru+Яндекс**.
- Отсев: мёртвые MX (6 411), role-адреса (info@/sales@), disposable, catch-all.
  Upfront-проверка ящика на Mail.ru/Яндекс невозможна → защита = живой bounce-тормоз.

### 1.2 Кампания и цепочка (`store`, `cadence`, `personalize`)
- Кампания = сегмент получателей + **цепочка писем**: письмо 1 → пауза N дней →
  follow-up 2 → … Останавливается на ответе (`isStopSendingOnReply`).
- Каждое письмо собирается с:
  - персонализацией (имя, компания, ОКВЭД → релевантное оборудование);
  - **атрибуцией «ООО «Руспром», ИНН 2221239841» в КАЖДОМ письме** (ФЗ-38, не только в первом);
  - **List-Unsubscribe one-click** (RFC 8058, ФЗ-152);
  - **пикселем открытия** (open-tracking, справочно — см. §2.6).
- QA-гейт: письмо с незаполненным `{плейсхолдером}` НЕ уходит; числа — только из базы.

### 1.3 Прогрев (`warmup`) — ОБЯЗАТЕЛЬНО до боевых кампаний
- Новый домен/ящик = репутация ноль. Массовая отправка сразу = спам + смерть домена.
- Живой прогрев (НЕ пул-обмен): 2-3 письма/день/ящик → рамп до ~30-50/день за 3-4 нед,
  взаимопереписка + отметки «не спам». `reputation_floor` — пауза при просадке.

### 1.4 Отправка (`orchestrator.run()`, `sender`)
- Цикл: берёт запланированные письма, проверяет:
  - **окно отправки** (Пн-Пт 09:30-18:00 МСК, праздники переносятся);
  - **паузы** между письмами одного ящика (90-420с, jitter);
  - **провайдер-сплит**: mail.ru-получателям шлём с mail.ru-ящиков (репутация раздельная);
  - выбор наименее загруженного ящика в пуле.
- Инварианты: **идемпотентность** (sha256 + UNIQUE, не шлём дважды),
  **lease + recover_stale** (переживает рестарт контейнера/сервиса).

### 1.5 Защита доставляемости (`gates`, kill-switch)
- **Канареечная волна:** первые ~150 получателей → пауза 4ч на сбор DSN → замер bounce.
  Не прошла (>3%) → кампания стопится, пока волна целиком не «прозвонилась».
- **Гейты (пороги %):** bounce по домену/ящику/**провайдеру получателя**, complaint.
  Планка: complaint <0.1% (жёсткий глобальный стоп), bounce 2-3%.
- Превышение → **kill-switch**: пауза отправки + мгновенный алерт в Telegram.
- **Постофис Mail.ru / Постмастер Яндекс** — внешний сигнал репутации/спам-рейта
  (не только свой журнал).

### 1.6 Аутентификация домена
- `mail.parsercompressor.online`: SPF + DKIM + DMARC настроены, **smoke пройден**
  (Gmail: spf=pass, dkim=pass, dmarc=pass, инбокс). Каждое письмо подписывается DKIM.

## ЧАСТЬ 2 — АВТООТВЕТЧИК (входящее)

### 2.1 Приём (`imap_watcher`)
- Поллит ящики (каждые ~120с). Новое письмо → определяет тип (ответ / DSN / жалоба /
  автоответ) и классифицирует.

### 2.2 Классификация — 11 классов (`reply_classify`)
Выведены из РЕАЛЬНОЙ кампании Meyer (см. `REPLY-TAXONOMY.md`):
- **Служебные:** bounce/DSN, complaint (жалоба), auto_reply (отпуск/OOO), unsubscribe.
- **Бизнес (7):** `hot` (пришлите прайс/КП), `deferred` (позже/строим завод),
  `redirect` (я в декрете, пишите коллеге), `wrong_contact` (не тот адресат),
  `objection_tech` (технически не подходит), `objection_status_quo` (нас устраивает),
  `competitor_in_place` (уже стоит Bizerba/Mettler).
- AI-разбор через провайдер: извлекает **потребность / телефон / готовность 0-10**.
- Урок: coldy ошибся на 2 из 7 (redirect→auto, deferred→«не интересно») = потерянные
  сделки. Наш классификатор ОБЯЗАН их различать.

### 2.3 План действий по классу (`autoresponder.plan()`)
- `hot` (запрос КП/прайса) → **ГОТОВЫЙ лид сразу в Bitrix** (статус ready, высокая
  готовность) + алерт продажнику → **продажник готовит КП и звонит**. Робот его сам
  НЕ отрабатывает (запрос прайса = уже квалифицированный интент). Опционально шлёт
  короткое подтверждение получения («менеджер подготовит КП и свяжется»), которое
  проходит ревью-конвейер;
- `deferred` → вежливый ответ + **снуз на N мес** (вернуть в работу, не закрывать);
- `redirect` → переслать предложение на указанный адрес + благодарность;
- `wrong_contact` → пометить контакт битым + спросить верного адресата;
- `objection_tech` → черновик, честное закрытие, без дожима;
- `objection_status_quo` → черновик с 1 фактом «что металлодетектор не ловит»;
- `competitor_in_place` → учёт (низкий приоритет, длинный цикл);
- `auto_reply` → ничего (не стопит цепочку); `unsubscribe` → в suppression.

### 2.4 Ревью-конвейер — 8 ревьюеров (`REVIEW-CHAIN.md`) — ГЛАВНАЯ страховка
Каждое ответное письмо ПЕРЕД отправкой проходит ВСЕ 8 проверок (через провайдер):
1. **факт-чекер против базы** — каждая цифра/модель/срок сверяется с `answer-kb`;
2. **юрист ФЗ-38/152** — атрибуция, ПД, отписка;
3. **эскалация-гейт** — торг/рекламация/>1млн/госзакупки/юр-вопрос → сразу человеку;
4. **классификация-скептик** — не спутан ли класс входящего;
5. **продажник-квалификатор** — двигает ли к телефону по лестнице контакта;
6. **клиент-адвокат** — симуляция получателя (раздражает? риск жалобы?);
7. **тон-редактор** — инженер-практик, без канцелярита, 1 экран, без длинных тире;
8. **спам-техник** — спам-триггеры, ссылки, репутация.

**Критическое замечание → перегенерация (лимит 2 итерации) → если не прошло →
ЭСКАЛАЦИЯ человеку** с пояснением. Судья по умолчанию недоверчив: сомнение = не слать.

**Пилот-режим:** ВСЕ авто-ответы понижаются до **черновиков оператору** (человек
одобряет/правит/шлёт). Автоотправку на безопасных типах включаем, только когда на
живых данных убедимся, что классификация не врёт. Правки людей копятся → few-shot.

### 2.5 Выход: очередь тёплых лидов (`leaddesk`, `bitrix`, `notify`)
- Тёплый лид → **Bitrix24** (`crm.lead.add`): компания, ИНН, сегмент, потребность
  (задача/объём/давление/сроки), бюджет-сигнал, **телефон**, готовность 0-10,
  рекомендованное действие, ссылка на тред.
- Роутинг на продажника (28 чел). Алерт в **Telegram** (событие `warm_lead_created`).
- Продажник **звонит** по тёплому телефону → квал-лид → сделка. Атрибуция на ВП.

### 2.6 Open-tracking (`OPEN-TRACKING-SPEC.md`)
- Колонка «Открыл» как у coldy: пиксель 1×1 на трекинг-домене → событие `open`.
- **ЧЕСТНО:** в РФ (Mail.ru/Яндекс проксируют картинки) открытия ненадёжны —
  **справочный сигнал**, гейты каденции ведём по **клику/ответу**, не по открытию.

## Сквозное
- **Уведомления** (`notify`, Telegram): kill_switch, приближение к порогу жалоб,
  SMTP-сбой, **создан тёплый лид** + дневной дайджест.
- **Юр-слой:** `consent_log` (ФЗ-152, хранение ПД в РФ), атрибуция в каждом письме (ФЗ-38).
- **Резюмируемость:** lease + recover_stale, идемпотентность — переживает рестарт.
- **Панель** (`api` + SPA, `panel.parsercompressor.online`): дашборд, кампании,
  база/suppression, ящики/прогрев/DNS, лента лидов, аналитика (воронка
  отправка→ответ→тёплый→квал), настройки, аудит. Вход: логин+пароль+2FA.
