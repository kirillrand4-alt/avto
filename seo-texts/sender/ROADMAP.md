свой аналог coldy (движок + сайт-панель), на выходе тёплые квал-лиды в Bitrix24.

приоритизация), `OWNER-TODO.md` (доступы владельца), `CONTRACT.md` (интерфейсы),

- **Любой вывод модели/ревью — сверять фактчек-линзой против КОДА** до внесения (иначе

- **Deliverability-правила:** живой прогрев (не пул), канареечные волны, bounce × провайдер

  невозможна, защита = живой bounce-тормоз.

## ФАЗА 1 — операционный слой (движок → запускаемый сервис) · ~3-5 дней · ОБЯЗАТЕЛЬНО

Без этого движок = библиотека, ничего не поедет. Всё через провайдер, thinking=False, с тестами.

- **1.1 Импортёр базы.** CSV `obzvon_all` (648 МБ) → таблица `recipients`. Стрим, дедуп по
  email/ИНН, применить `suppression-final` (39 ИНН + корп-список конкурентов), MX-валидация
  → `valid_status`/`mx_provider`/`provider_class`. Скрипт + тест на выборке.
- **1.2 CLI / entry-point** (`python -m sender`): `init-db`, `import <csv>`, `campaign-create`,
  `campaign-add-step`, `validate`, `run`, `status`, `pause/resume`, `stats`. Тонкий argparse-
  слой над модулями (логику НЕ дублировать). Тесты.
- **1.3 HTTP-эндпоинт отписки.** one-click List-Unsubscribe-Post (RFC 8058) на трекинг-домене:
  stdlib `http.server`/wsgi → `unsub.handle_one_click`. Публичный URL. Без него отписки не
  приходят (юр-риск+жалобы). Тест.
- **1.4 YAML-конфиг** — заполнить реальными значениями (ящики, домены, провайдер-сплит, пороги
  gates, атрибуция Руспром+ИНН, окна/праздники). Валидация при старте.
- **1.5 Хостинг/деплой.** systemd/supervisor: `orchestrator.run()` + IMAP-поллинг +
  unsub-сервер 24/7. Логи, ротация, авто-рестарт. `RUNBOOK.md` деплоя.
- **1.6 Smoke доставляемости.** Реальный домен + 2 ящика + 2-3 сид-ящика (OWNER-TODO §4).
  SPF/DKIM/DMARC pass + попадание в инбокс. Первый живой прогрев боевого домена.

**После Фазы 1 система работает headless: кампании через CLI, лиды → Bitrix, алерты → Telegram,
аналитика — отчётами. Функционально как coldy-движок, но без веб-морды.**

## ФАЗА 2 — ВЕБ-ПАНЕЛЬ (сайт как coldy) · ~2-3 недели · для UX «мышкой»

Цель — управление как в coldy. **Дизайн сайта проектировать через мульти-модельную панель**
(правило проекта: не одна модель, а расхождение углов + судья + сверка с кодом):

- **2.0 Мульти-модельный дизайн сайта — ВЕСЬ прогон через провайдерский API**
  (`gen_provider`, `claude-fable-5`, `thinking=False`, effort high, в фоне, кэш по
  персонам/раундам, ретраи — как ревью движка в этой сессии). Токены сессии — только
  оркестрация (запуск скрипта, сбор выхлопа, коммит). НЕ гнать генераторы/судью/фактчек
  своими токенами:
  1. **Генераторы (6-10 непохожих персон-моделей):** UX для оператора-одиночки; UX для 28
     продажников; информационная архитектура/навигация; экран аналитики (воронка→квал-лид);
     редактор цепочек; управление ящиками/прогревом/репутацией; лента тёплых лидов;
     мобильный/адаптив; минимализм-vs-мощь; безопасность/роли. Каждый — конкретные экраны и
     потоки под НАШУ задачу (не «как у всех»).
  2. **Кросс-опыление:** каждый видит чужие идеи → гибриды, добивает пропущенное.
  3. **СУДЬЯ:** дедуп, кластеры, единый макет (экраны, роуты, компоненты), приоритет по
     «двигает квал-лид / скорость оператора».
  4. **ФАКТЧЕК-ЛИНЗА против КОДА (обязательно):** сверить КАЖДЫЙ предложенный экран/функцию
     с тем, что УЖЕ есть в движке (`store` API, `analytics.dashboard()`, `orchestrator`,
     `bitrix`, `notify` и т.д.). Вердикт: реально надо строить / уже есть в движке (только
     вывести в UI) / требует нового бэкенд-метода. Без этой линзы панель «нарисует» то, что
     уже реализовано, и продублирует. (Так фактчек уже ловил переоценки в ревью движка.)
  5. Итог 2.0 → `SITE-DESIGN.md` (проверенный макет: экраны + API-контракты + что переиспользуем).
- **2.1 Backend API** (FastAPI) поверх движка ✅ ЗАВЕРШЕНО 2026-07-19 (см. SENDER-STATE п.8) — REST для кампаний/базы/ящиков/аналитики/лидов/
  настроек. Auth (владелец + продажники, роли). Только вызовы движка, логику не дублировать.
- **2.2 Frontend** (React+Vite SPA) по `SITE-DESIGN.md` ✅ ЗАВЕРШЕНО 2026-07-19/20 (см.
  SENDER-STATE пп.9,11) — 21/23 экранов живые над реальными эндпоинтами: дашборд-светофор;
  кампании (список + Новая/Детали: цепочка-шаги, статус, воронка); ящики/домены (готовность,
  DNS-чек, прогрев); suppression/комплаенс/субъект-ПД; лента лидов+карточка (эпицентр, «Взять»
  с CAS-гонкой, PII-маскировка менеджеру); настройки+команда (users CRUD, аудит); профиль
  (смена пароля). Бэклог 2/23 — Цепочки/Шаблоны (отдельной сущности в движке нет).
- **2.3 Деплой сайта** ✅ ЗАВЕРШЕНО 2026-07-20 (см. SENDER-STATE п.12) — `make_site_app`
  (API под /api + SPA статикой с fallback), CLI `serve-api --static-dir`, `sender/deploy/`
  (nginx-panel.conf TLS+прокси, systemd-юнит, NSSM-скрипт, panel.env.example), RUNBOOK §7.
  Бэкапы БД — RUNBOOK §6. Панель — на localhost за обратным прокси, отдельно от доменов.

## ФАЗА 3 — пилот и масштабирование · ~1-2 мес календарно

- **3.1** Юр-линия финализирована владельцем (адресное B2B-предложение vs согласие).
- **3.2 Прогрев** ящиков живой микродозой (2-3/день → ~30-50/день/ящик, 3-4 нед) по чистейшему
  A-срезу; канареечные волны включены.
- **3.3 Пилот:** 200-500 конечников (не дилеров-конкурентов), 1 прогретый домен. Замер
  open/reply/bounce/complaint/тёплый лид. Гейты: complaint <0.1%/домен, bounce <2-3%.
- **3.4 Рамп** до 800-1000/день ТОЛЬКО при удержании метрик; kill-switch активен.
- **3.5 Замкнуть цикл** тёплый лид → Bitrix → продажник (28 чел, загрузка 60%) → квал-лид →
  сделка; атрибуция на ВП.
