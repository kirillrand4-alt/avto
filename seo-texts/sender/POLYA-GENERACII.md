# Какие поля берутся на генерацию письма и какие вообще заливаются

Записано 11.08.2026 по просьбе владельца: «запиши, какие столбцы берутся из
базы для генерации писем и какие заливаются в принципе, я скорее всего скоро
дополню столбцы и их значения».

Смысл документа один: показать **разрыв** между «что лежит в базе» и «что
доезжает до промпта». Разрыв есть, и он неочевиден — половина полей карточки
живёт для оператора и фильтров, а не для письма. Когда добавляете столбец,
надо знать, в какую из трёх колонок он попадёт.

---

## 1. Таблица получателей (`recipients`) — что вообще заливается

| столбец | чем заполняется | доезжает до промпта |
|---|---|---|
| `email` | загрузка партии, обогащение, ручной ввод | да — адресат |
| `inn` | то же | не в текст, но по нему собирается вся карточка |
| `domain` | вычисляется из адреса | нет (нужен пробе и стоп-листу) |
| `company_name` | партия, обогащение, база обзвона | **да** — «Компания:» |
| `okved` | партия, обогащение, чеко | **да** — «ОКВЭД/профиль:» и поиск боли |
| `contact_name` | обогащение сайта, ручной ввод | **да** — именное приветствие либо «Добрый день!» |
| `segment` | название группы при загрузке | косвенно: задаёт направление партии (kc/meyer) |
| `region`, `tz` | партия, база обзвона | нет в тексте; `tz` управляет окном отправки |
| `source` | откуда строка взялась | нет — след происхождения |
| `mx_provider` | проба почты | нет в тексте; значок в очереди и выбор ящика |
| `valid_status`, `catch_all`, `role_based`, `disposable` | проба адресов | нет в тексте; заслон отправки |
| `priority_max`, `priority_total`, `pxr` | скоринг | нет в тексте; порядок очереди |
| `bitrix_id` | привязка к CRM | нет |
| `extra_json` | свободное поле | **частично** — см. раздел 3 |

**Важно про ОКВЭД.** В `recipients.okved` лежит ОДИН код — основной. Все коды
компании (`okved_all`) живут в карточке и в обогащении. С 11.08 боль ищется по
ВСЕМ кодам: основной первый, дальше дополнительные (правило владельца «если
есть другой подходящий оквед — он возьмётся»).

## 2. Что собирается ВНЕ таблицы получателей

Перед генерацией по ИНН собирается карточка (`company_card.build_company_card`),
и оттуда берутся поля, которых в `recipients` нет вовсе:

| откуда | поле | зачем в письме |
|---|---|---|
| обогащение сайта | `activity` — чем компания занимается | **строка «ОКВЭД/профиль»** рядом с кодом |
| обогащение сайта | `role` контакта (снабжение, гл.инженер, директор) | **угол письма**: о чём говорить с этим человеком |
| база обзвона | `equip_categories` — категории оборудования | подсказка «оборудование по профилю» |
| отчётность | `revenue` | **тон письма** по размеру бизнеса |
| новости | `news_object`, `news_url`, месяц | режим NEWS: заход строится на событии |
| новости / карточка | `city` | склонение города в новостном заходе |
| файл болей | боль по ОКВЭД | **«зачем это ЕГО производству»** |
| линзы-генераторы | `idea` | идея захода у писем без новости |

## 3. Полный список того, что уходит в промпт

Блок получателя (`ai_letter._recipient_block`) печатает ровно это и ничего
больше:

```
=== ПОЛУЧАТЕЛЬ #N [режим: GENERIC|NEWS]
Компания: {company_name}
ОКВЭД/профиль: {okved} {activity}
Контакт: {contact_name} | либо «нет имени — приветствие строго Добрый день!»
РОЛЬ АДРЕСАТА: {role}. {угол под эту роль}
РАЗМЕР: {тон по выручке}
НОВОСТЬ: {news_object} | город: {city} | месяц:        (только режим NEWS)
МЕХАНИКА ЗАХОДА: {назначается ротацией по партии}       (только режим NEWS)
Оборудование по профилю: {equipment}
Зачем это ЕГО производству: {боль по ОКВЭД}
ИДЕЯ ЗАХОДА: {idea}                                     (только GENERIC)
```

Ключи `extra`, которые читает блок: `role`, `company_size`, `revenue`,
`news_object`, `news_month`, `city`, `city_source`, `equipment`, `idea`.
Всё остальное в `extra` до промпта не доходит.

## 4. Как добавить новый столбец, чтобы он попал в письмо

Одной записи в базу мало — поле само в промпт не приедет. Нужны три шага:

1. **залить** — колонка в `recipients` (или ключ в `extra_json`), заполнение
   в `import_bazy.применить`;
2. **донести** — добавить поле в `ai_quota._request` (в корень запроса или в
   `extra`), взяв его из получателя либо из карточки;
3. **напечатать** — строку в `ai_letter._recipient_block`, иначе генератор
   поля не увидит.

Пропуск любого шага даёт молчаливую потерю: данные в базе есть, письмо про них
не знает. Так было с `equipment` — слот в промпте существовал, а класть в него
значение забыли, и он был пуст ВСЕГДА.

Проверять правку надо на живом сервере, а не в репозитории: файл болей и код
панели лежат отдельно (`C:\sender\okved-pains.json` и `C:\sender\sender\`), и
репозиторная копия отставала от боевой на 44 боли.

## 5. Файл болей: четыре таблицы

`C:\sender\okved-pains.json` — на 11.08:

| таблица | сколько | когда берётся |
|---|---|---|
| `kc` | 102 | направление Компрессор Центр |
| `meyer_foto` | 27 | Meyer, фотосепаратор — сортировка по цвету и дефекту до фасовки |
| `meyer_rentgen` | 27 | Meyer, рентген — плотные включения в упакованном продукте |
| `meyer` | 35 | запасная, если своей градации у кода нет |
| `_meyer_gradaciya` | 27 | карта «код → какой станок уместен» |

Градация выбирается по коду автоматически; можно назвать её и прямо, передав
`meyer_foto` / `meyer_rentgen` вместо `meyer`. Карта лежит в самом файле болей,
рядом с текстами, — правка отрасли не требует правки кода.

Список целевых ОКВЭДов — `data/okved_directions.json` (75 кодов, 76 слотов:
КЦ 48, Meyer 26, оба 1). Поле `equip` в нём задаёт оборудование под код; если
код помечен `kc+meyer`, поле ОДНО на обоих, и для Meyer оно может врать — на
этом 10.61 получил боль про пневмотранспорт вместо сортировки зерна.
