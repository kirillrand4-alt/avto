# Сендер-сервис: состояние и как продолжить

Свой сервис холодной B2B-рассылки для ООО «Руспром» — замена coldy (SMTP-отправка
с наших Яндекс360/VK ящиков, IMAP-приём/ответы, свой живой прогрев, юр-гейты
ФЗ-38/152, стык с AI reply-desk). Причина «своего»: база не уезжает на сторону
(coldy — ИП Ахматзянов, база уходит к нему), контроль, экономия тарифа. Разбор coldy —
в `FEATURES-PLAN.md`.

## ТЕКУЩЕЕ СОСТОЯНИЕ (код в git, здесь же)

Код **уже в репозитории** (`seo-texts/sender/`), НЕ в scratchpad. Сгенерирован
изолированно по `CONTRACT.md` через провайдер (`claude-fable-5`), интегрирован.

- **13 модулей + `dtos.py`**: config, store, suppression, validation, personalize,
  gates, sender, imap_watcher, cadence, unsub, analytics, warmup, orchestrator.
- **Тесты: 269/275 pass** (`python3 -m pytest sender/tests/` из `seo-texts/`).
- Инварианты из контракта на месте: идемпотентность (sha256+UNIQUE+ON CONFLICT),
  резюм после рестарта (lease+recover_stale), гонка «ответил→не слать дубль»,
  hard/soft bounce, юр-гейт (List-Unsubscribe + RFC 8058), kill-switch с min_volume.

### Валидация + защита от bounce (ревью+сверка с кодом 2026-07-17)

Данные подтверждены на базе: **74.4% получателей Mail.ru/Яндекс** (51.1%+23.3%),
**6 411 мёртвых MX = 3.6%** (гарантированные баунсы). На 74% MX всегда резолвится →
проверить существование ЯЩИКА до отправки там нельзя; upfront-валидатор снимает лишь
мёртвый домен+синтаксис+role+disposable (единицы %). Значит основная защита — НЕ
upfront-чек, а тормоз по ЖИВОМУ bounce-rate.

**Тормоз по bounce у нас ЕСТЬ (`gates.py`), но слишком грубый — доработать, НЕ строить с нуля:**
- порог `domain_bounce_pct: 8.0` / `mailbox_bounce_pct: 6.0` → **опустить до 2-3%** (8% =
  новый домен-двойник уже сгорел, пока накопится);
- ключ rate сейчас домен/ящик → **добавить измерение × провайдер получателя** (репутация
  Mail.ru и Яндекс раздельная, считать баунсы отдельно);
- **канареечные волны** — слать сегмент малыми волнами, замерять live hard-bounce-rate,
  только потом остальное (сейчас пауза срабатывает ПОСЛЕ удара по первой полной волне).

**Дешёвые правки в `validation.py`/`imap_watcher` (проверены, валидны):**
- Null/dead-MX (RFC7505) → `hard-invalid` (те самые 6 411);
- офлайн typo-коррекция домена (mial.ru→mail.ru, yandx.ru→yandex.ru) — нулевой IP-риск;
- тег `recipient_provider` на строку результата → cadence делит темп consumer/корп;
- greylist 4.x → **ретрай** (переслать позже), НЕ suppress (RU часто гриллистят; сейчас
  soft уже не суппрессится, но и не ретраится);
- кэш MX-резолвов (не долбить 161к дважды).

**НЕ делать (скептик + сверка, подтверждено):** RCPT-проба со СВОИХ отправляющих IP
(74% accept-all/greylist → врёт + харвестинг-сигнал); живой disposable-фид (в B2B РФ ~0%);
IDN/.рф-нормализация (почти всё ASCII); эвристика спам-ловушек (не предсказуемы). Глубокая
mailbox-проверка — ТОЛЬКО на неопределённый сегмент (custom/корп) и ТОЛЬКО внешним
сервисом/с отдельных прогретых IP, не на весь 74% consumer.

⚠️ Урок про ревью-харнесс: прогон БЕЗ линзы-верификатора «сверь с текущим кодом» склонен
утверждать «у вас нет X», хотя X частично есть (так вышло с bounce-gating). Выводы любых
ревью сверять с кодом/данными до внесения — как здесь.

### Пробелы против coldy (проверка покрытия 2026-07-17)

Ядро рассылки воспроизведено (P0). Не воспроизведены (обвязка):
- **Коннектор CRM Bitrix24** — есть только интерфейс `ReplyDeskSink`, коннектора нет.
  Владелец на Bitrix — P1, важно.
- **Исходящие MIME-вложения** — sender их не строит (для холодной часто и не надо).
- **Глубокая валидация (спам-ловушки, полный анти-bounce)** — есть MX+провайдер+
  catch-all/role/disposable; deep-проход — внешним RU-валидатором.
- **API** — не построен (P2).
- **AI-предобработка базы** (реальное имя с сайта + проверка на ЦА) — частично: своя
  база уже с названиями/ОКВЭД.
- **Подписи ящиков** — проверить, реализованы ли полноценно (керворд есть в sender/config).
Сознательно пропущены (правильно): warmup-пул (Google-only), Leadbase 7М (своя база),
под-ключ/авто-оплата. Источник сравнения — `FEATURES-PLAN.md` + на drop
`coldy-parse-2026-07-17.tar.gz` (сырьё страниц coldy).

## Deliverability-контекст (почему модули так устроены)

Мягкое знание из разбора coldy и переписки с их саппортом — иначе не очевидно из кода:

- **Прогрев у нас ЖИВОЙ, не пул.** Warmup-пул coldy — только Google-ящики; для нашей
  базы (74% Mail.ru/Яндекс) почти бесполезен. Mail.ru забанил инструменты прогрева.
  Поэтому `warmup.py` = живая рассылка микродозами: рамп **2-3/день → ~30-50/день/ящик**
  за 3-4 недели по чистейшему A-срезу. Это и есть «прогрев» под RU-инбоксы.
- **Инфраструктура инбоксов (смета):** ~10 доменов-двойников `.ru` (~2 500 ₽/год) с
  301-редиректом на основной сайт (основной `prokompressor.ru` НЕ трогать); ~30-35
  ящиков = 20 Яндекс360 + 10-15 VK WorkSpace (~250 ₽/ящик/мес ≈ 7.5-9 тыс/мес).
  **Провайдер-сплит**: mail.ru-домены и yandex-домены — раздельными пулами.
  Западные (Google WS / M365 / Mailreef и т.п.) НЕ брать — иностранные IP плохо
  проходят Mail.ru/Яндекс. (Детали и вердикты — на drop: `coldy-inboxes.json`.)
- **Google-контур (опция):** в базе ~706 ценных компаний (100 млн+ выручки) на
  Google-хостинге — единственное место, где Google-пул coldy уместен. 2-3 отдельных
  ящика можно прогреть им под этот сегмент.
- **Юр-гейт письма-1 (ФЗ-38):** атрибуция ООО «Руспром» + ИНН обязательна уже в первом
  письме (3 ревьюера единогласно ПРОТИВ «бренд называем позже»); мягкая личная подпись
  менеджера — ок. Владельцу выбрать юр-линию (адресное B2B-предложение vs согласие).
- **Каденция engagement-gated:** касание 1 всем валидным → 2 не-отскочившим → 3-4
  только вовлечённым. Гейт complaint-rate <0.1%/домен (стоп при >0.3%), bounce <2-3%.
- **База уже чистится от конкурентов:** suppression 39 ИНН (на drop, `base-cleaning-
  2026-07-17.tar.gz`); ждём корп-список ИНН конкурентов от владельца.

## Извлечённые уроки (грабли) — чтобы новая сессия не наступала

1. **Баг шлюза router.cheap: при `thinking=adaptive` код иногда уходит в thinking-блок,
   а `text` пустой** (`stop=end_turn, thinking=26k, text=0`). НЕ защита, НЕ упор в
   max_tokens — вывод ушёл не в тот канал. Обход: кодоген с `thinking=False`.
2. **`gen_provider.call` хардкодит `max_tokens=16000`** — мало для крупных модулей.
   Для кодогена звать `gp._raw_stream(msgs, model, 32000-64000, thinking=False, effort=...)`.
3. **Шлюз НЕ отбраковывает большой `max_tokens`** (принял 200000). Потолок — у модели:
   Fable 5 — 128K вывода, Sonnet 5 / Opus — ~64K.
4. **Изолированной генерации нужен общий типовой модуль ПЕРВЫМ.** DTO собраны в `dtos.py`
   из §3 контракта механически (без API). Генерить его ДО остальных модулей.
5. **Экстрактор кода режет по маркерам `# FILE:`**, а не по числу ```-блоков (модель
   иногда склеивает impl+тесты в один блок).
6. **Устойчивость прогона:** ловить исключение помодульно, фолбэк effort/thinking,
   ретраи. Иначе один пустой ответ убивает весь прогон (так упало на imap_watcher).
7. **max-усилие Fable 5 работает** для качества — но только с `thinking=False`.
8. **Тесты бывают брителе кода:** чинить РЕАЛИЗАЦИЮ; тест править только если он
   противоречит контракту (см. unsub).
9. **Не называть типовой модуль `types.py`** — затеняет stdlib `types` (падает запуск
   из папки). У нас переименован в `dtos.py`.
10. **Провайдерский фикс-цикл не всесилен** — если 3 круга не сошлись (unsub), дешевле
    разобрать руками.
