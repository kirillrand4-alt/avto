# Сендер-сервис: состояние и как продолжить

Свой сервис холодной B2B-рассылки для ООО «Руспром» — замена coldy (SMTP-отправка
с наших Яндекс360/VK ящиков, IMAP-приём/ответы, свой живой прогрев, юр-гейты
ФЗ-38/152, стык с AI reply-desk). Причина «своего»: база не уезжает на сторону,
контроль, экономия тарифа. Разбор coldy и вывод — в `FEATURES-PLAN.md`.

## Что готово (в этом каталоге, [git])

- **`FEATURES-PLAN.md`** — все фичи coldy + наш модульный план P0/P1 + ответ по
  тест-домену (реальный домен нужен только на финальном smoke-тесте; разработка и
  автотесты — на локальном SMTP-песочнике).
- **`CONTRACT.md`** — контракт интерфейсов (820 строк): SQLite-схема (8 таблиц),
  публичный API 13 модулей, DTO, YAML-конфиг, инварианты безопасности. Проверен:
  идемпотентность (sha256-ключи, UNIQUE, ON CONFLICT), резюм после рестарта (lease
  + recover_stale), закрытая гонка «ответил→не слать дубль», hard/soft bounce,
  юр-гейт (List-Unsubscribe + RFC 8058 one-click), kill-switch с min_volume.

## Что генерится (13 модулей, изолированно по контракту)

Порядок: config, store, suppression, validation, personalize, gates, sender,
imap_watcher, cadence, unsub, analytics, warmup, orchestrator. Каждый — свежий
изолированный вызов провайдера (видит только CONTRACT + свой фокус), + pytest-тесты,
+ компиляционная проверка. Скрипт генерации: `scratchpad/gen_modules.py`
(резюмируемый по кэшу). Готовый код → `scratchpad/sender-build/sender/`, после
баг-ханта переносится СЮДА (`seo-texts/sender/`) и коммитится.

## Что дальше (план до результата)

1. Дождаться генерации всех 13 модулей (фон).
2. **Механический прогон pytest** на локальном SMTP/IMAP-песочнике (aiosmtpd +
   IMAP-mock): лимиты, рамп, стоп-на-ответ, bounce, дедуп, резюм после рестарта.
   Без API.
3. **Баг-хант через провайдера**: независимые линзы (корректность/гонки, логика
   делайверабилити, безопасность/ПД, edge-cases кодировок/заголовков,
   отказоустойчивость) × loop-until-dry с потолком; фиксы через провайдера;
   перепрогон тестов после каждого круга.
4. Перенести финальный код в `seo-texts/sender/`, закоммитить.
5. Финальный smoke-тест доставляемости на реальном домене с 2 ящиками (перед
   пилотом): SPF/DKIM/DMARC pass + попадание в инбокс.

## Как продолжить в НОВОЙ сессии

> Работаем над сендер-сервисом. Читай `seo-texts/sender/SENDER-STATE.md`,
> `CONTRACT.md`, `FEATURES-PLAN.md`. Код в `scratchpad/sender-build/` эфемерный —
> если новая сессия, сначала подними его из git/drop или перегенерируй
> `gen_modules.py`. Продолжай с шага <N>. Тяжёлое — через провайдер, фон.

⚠️ Код в scratchpad ЭФЕМЕРЕН. Перед закрытием сессии он должен быть либо
закоммичен сюда, либо залит на drop — иначе новая сессия его не увидит.

## Извлечённые уроки (грабли) — чтобы новая сессия не наступала

1. **Баг шлюза router.cheap: при `thinking=adaptive` код иногда уходит в
   thinking-блок, а `text` приходит пустой** (`stop=end_turn, thinking=26k, text=0`).
   Это НЕ защита и НЕ упор в max_tokens — модель пишет ответ, но в не тот канал.
   Обход: кодоген с `thinking=False` (текст гарантирован). Диагностика: ловить и
   thinking, и text; если код в thinking — извлечь оттуда или перегенерить без thinking.
2. **`gen_provider.call` хардкодит `max_tokens=16000`** — мало для крупных
   модулей+тестов. Для кодогена звать `gp._raw_stream(msgs, model, 32000-64000,
   thinking=False, effort=...)` напрямую.
3. **Шлюз НЕ отбраковывает большой `max_tokens`** (принял 200000). Физический потолок
   задаёт модель: Fable 5 — 128K вывода, Sonnet 5 / Opus — ~64K.
4. **Изолированная генерация требует общий типовой модуль ПЕРВЫМ.** Модули писались
   независимо, часть ждала `sender/types.py` (общие DTO), которого не было в списке →
   ImportError при интеграции. Раздел 3 контракта = готовые dataclass, `types.py` собран
   из него МЕХАНИЧЕСКИ (без API). Урок: генерить `types.py` из §3 контракта ДО остальных.
5. **Экстрактор кода должен резать по маркерам `# FILE:`, а не по числу ```-блоков** —
   модель иногда склеивает реализацию и тесты в один блок.
6. **Устойчивость прогона:** ловить исключение помодульно (сбой одного не рушит цикл),
   фолбэк effort high→medium и thinking on→off, ретраи. Иначе один пустой ответ убивает
   весь прогон (так упало на imap_watcher в первый раз).
7. **max-усилие Fable 5 работает** для качественного модуля — но только с
   `thinking=False` (иначе баг №1). imap_watcher так и сгенерён (24k символов, чисто).
8. **Тесты бывают брителе кода:** unsub падал на конкретном тексте ошибки, хотя
   безопасность (отвергать битый/подделанный токен) была цела. Правило фикс-цикла:
   чинить РЕАЛИЗАЦИЮ; тест править только если он противоречит контракту.

9. **`sender/types.py` затеняет stdlib-модуль `types`.** Под pytest ок (импорт как
   `sender.types`), но запуск `python3` ИЗ папки `sender/` роняет импорт (cwd в sys.path
   перекрывает стандартный `types`). Мина. Лучше переименовать модуль в `dtos.py`/`models.py`
   и обновить 6 импортов `from .types import` — отложено, чтобы не ломать перед коммитом.
10. **Провайдерский фикс-цикл НЕ всесилен.** unsub 3+3 круга не сошёлся — модель крутила
    impl↔тесты. Когда цикл зациклился, дешевле разобрать руками, чем жечь ещё круги.

## Прогресс тестов (на момент чекпоинта)

**269/275 pass.** cadence, imap_watcher, validation — зелёные после фикс-цикла.
unsub — 6 фейлов, но это **брителость ТЕСТОВ, не дыры безопасности** (проверено):
реализация верна (раздельное `payload.sig`, constant-time compare, подпись верна по
построению). Тесты кривые — напр. «разный секрет» меняет `os.environ`, но мок-конфиг

верифицируется → тест ждёт исключение и падает. Нужна отдельная чистка test_unsub.py
(env-мок, доступ к приватным методам, match= на тексте ошибки), НЕ трогая логику.
