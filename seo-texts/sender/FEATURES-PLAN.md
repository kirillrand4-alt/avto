## Чего у coldy НЕТ, а нам надо (наши дифференциаторы)

1. **База не уезжает** — всё на сервере владельца (parsercompressor.online). ИП-лицензиар coldy = риск для 131к контактов.
2. **Юр-гейты ФЗ-38/152 в ядре** — атрибуция ООО «Руспром» + ИНН в письме-1, List-Unsubscribe RFC 8058 one-click, лог отказов ≤1 день.
3. **Провайдер-сплит роутинг** под MX-распределение НАШЕЙ базы (mail.ru-домены / yandex-домены отдельными пулами).
4. **Сегмент-персонализация** из bitrix (чек/сегмент → конкретное оборудование под ОКВЭД).
5. **Стык с AI reply-desk** → очередь тёплых телефонов 28 продажникам.
6. **Google-контур на 2-3 ящика** — единственное, где прогрев-пул уместен (706 жирных google-хостед целей).

## Модульный план сервиса (папка `sender/`)

**P0 (ядро):**
- `config` — ящики/домены/лимиты/рамп/окна/провайдеры (YAML+env), валидация конфига.
- `store` — SQLite-схема + DAL (recipients, campaigns, messages, events, suppression, mailbox_state), резюмируемо, идемпотентно.
- `suppression` — check/add по email/домену/ИНН; загрузка конкурентов (готово) + отписки + жалобы.
- `validation` — MX + провайдер (моя логика) + catch-all/role/disposable детект.
- `personalize` — merge-поля + **гейт незаполненных `{}`** + рендер «от продажника» + AI-хук (per-recipient ОКВЭД→оборудование) через gen_provider.
- `sender` — SMTP пул ящиков, лимит/ящик + рамп-кривая (2-3→50/день), рандом интервалы, окна/праздники, провайдер-сплит, заголовки List-Unsubscribe, **dry-run в песочницу**.
- `imap_watcher` — поллинг IMAP: ответ→стоп цепочки + в reply-desk; DSN/NDR→авто-suppress; тред-линк; кастом-статусы.
- `cadence` — движок касаний, engagement-gated (1 всем→2 не-bounced→3 вовлечённым), праздники.
- `gates` — kill-switch: bounce%/домен, complaint%/домен, глобальный; пауза домена/ящика.
- `unsub` — one-click эндпоинт + List-Unsubscribe-Post (RFC 8058).
- `analytics` — по ящику/кампании/прогреву + отчёт-дашборд.
- `warmup` — свой живой микро-прогрев (рамп 2-3→50), не пул.
- `orchestrator` — главный цикл, dry-run, резюмируемость.

**P1:** `crm` (Bitrix24), reply-desk-стык, подписи/тест письма.

**Тесты:** юнит на каждый модуль + интеграционный прогон на локальном `aiosmtpd`-песочнике + симуляция сбоя (упал на середине волны → рестарт → без дублей).

## Тест-домен (ответ на шаг 3)

Для **сборки и автотестов реальный домен НЕ нужен** — гоняю на локальном SMTP/IMAP-песочнике (aiosmtpd + локальный IMAP-mock): проверяю всю логику (лимиты, рамп, стоп-на-ответ, bounce, дедуп, резюм после рестарта) без единого живого письма.
Реальный домен с 2 ящиками понадобится **только на финальном smoke-тесте доставляемости** (перед пилотом): отправить пару писем ящик→ящик, проверить SPF/DKIM/DMARC pass и попадание в инбокс. Это последний шаг, не блокирует всю разработку. Заведёшь его, когда вернёшься.
