# SENDER-ARCHITECTURE — как работает система холодной рассылки

Автодокументация всех модулей `seo-texts/sender/` (провайдер claude-fable-5) + ручная верификация ключевых узлов. Что делает, ОТКУДА берёт данные, логика обработки, где трогает БД, пересечения модулей.

**Покрытие: 29/29 модулей.** Единый писатель в БД (SQLite) — `store.py`; остальные ходят в БД только через него.

## Поток данных (tick-цикл оркестратора)

```
recover_stale → IMAP poll (reply/bounce) → gates (kill-switch) →
cadence.plan_campaign → enqueue → claim_due → personalize.render →
sender.pick_mailbox → sender.send → warmup.run_cycle → TickResult
```


## Слой: Ядро данных и конфиг

### `config.py` (645 строк)
**Загружает, парсит (собственным мини-YAML) и строго валидирует конфигурацию сервиса рассылки, отдавая иммутабельные типизированные структуры и секреты из env.**

- Обязанности: Чтение YAML-файла конфига и разбор его встроенным мини-парсером без внешних зависимостей (_load_yaml/_MiniYaml); Применение безопасных дефолтов: service.dry_run=True, tick_interval_sec=60, validation.check_mx=True, personalization.fail_on_unfilled=True, imap.auto_suppress_on_bounce/complaint=True; Построение и валидация типизированных структур: MailboxCfg, WindowCfg, GatesCfg, LegalCfg; Проверка инвариантов безопасности: непустые/положительные/неубывающие рамп-кривые с покрытием каждого провайдера ящика; окно отправки (ISO-дни 1..7, start<end); ссылочная целостность provider_split (пулы→ящики, routing→пулы, mailbox.pool→пулы); атрибуция (entity+ИНН 10/12 цифр); наличие секретов в env; Гарантия иммутабельности объекта Config после load() (запрет setattr/delattr при _frozen); Предоставление типизированного доступа к конфигу и точечного доступа get() с иммутабельным (_freeze) представлением
- **Источники данных:** YAML-файл конфига по пути в Config.load(path) (Path.read_text, encoding utf-8); Переменные окружения (os.environ или переданный env): секреты по именам из mailboxes[].password_env и legal.unsub_secret_env; Конфиг-ключи: service (dry_run, tick_interval_sec), validation (check_mx), personalization (fail_on_unfilled), imap (auto_suppress_on_bounce, auto_suppress_on_complaint), mailboxes[] (mailbox_id, provider, smtp_host, smtp_port, imap_host, imap_port, login, password_env, from_name, signature_ref/signature, pool, is_warmup_node), provider_split.pools, provider_split.routing, ramp_curves.<provider>, warmup.ramp_curve, window (days, start, end), timezone, holidays[], gates (domain_bounce_pct, domain_complaint_pct, mailbox_bounce_pct, global_complaint_pct, min_volume, provider_bounce_pct), legal (entity, inn, unsub_base_url, unsub_secret_env, refusal_log_max_lag_hours), attribution (entity, entity_inn)
- Логика обработки: Построчный препроцессинг YAML: _strip_comment убирает комментарии с учётом кавычек, пустые строки отбрасываются, вычисляется отступ; _MiniYaml рекурсивно строит map/list по отступам; _parse_scalar приводит к bool/int/float/None/str и flow-спискам [a,b]; _apply_safe_defaults делает поверхностную копию секций и подставляет консервативные значения по умолчанию; _build_mailboxes: проверка непустого списка, уникальности mailbox_id, provider ∈ {yandex,mailru,google,outlook}, наличия password_env в окружении; signature берётся из signature_ref, иначе signature; _build_pools: пулы ссылаются только на объявленные mailbox_id; routing ссылается только на существующие пулы; mailbox.pool должен быть определён; _validate_ramp_curves: _validate_curve проверяет непустоту, положительность и неубывание; каждый provider ящика обязан иметь кривую; warmup.ramp_curve валидируется при наличии; _build_window: дни ISO 1..7, HH:MM через _hhmm_to_minutes, start<end; timezone валидируется через zoneinfo.ZoneInfo (мягко, при отсутствии tzdata не блокирует); _build_holidays: парсинг ISO-дат через date.fromisoformat в set[date]; _build_gates: приведение к float/int, проверка процентов в диапазоне [0..100] и min_volume>=0; provider_bounce_pct опционален (дефолт 2.5)
- Наружу (I/O): Чтение файла конфига с диска (Path.read_text); Чтение переменных окружения процесса (os.environ); Локальная проверка таймзоны через zoneinfo/tzdata (без сети)
- Публичный API: Config.load(path, env) -> Config, Config.mailboxes() -> list[MailboxCfg], Config.provider_pools() -> dict[str, list[str]], Config.ramp_curve(provider) -> list[int], Config.sending_window() -> WindowCfg, Config.holidays() -> set[date], Config.gates() -> GatesCfg, Config.legal() -> LegalCfg

### `store.py` (1323 строк)
**Единственный писатель в SQLite: DAL со всеми таблицами, транзакциями и идемпотентными операциями сервиса холодной рассылки.**

- Обязанности: Инициализация схемы БД (init_schema через executescript) и настройка PRAGMA (WAL, foreign_keys, busy_timeout, synchronous); Потокобезопасный доступ к единственному соединению sqlite3 через RLock и ручные транзакции BEGIN IMMEDIATE/COMMIT/ROLLBACK; Определение всех DTO (RecipientIn/Recipient, CampaignIn/Campaign, SequenceStep, MessageIn/Message, EventIn/Event, SuppressionIn/SuppressionEntry, Lead, User, Session, MailboxState, WarmupState) и иерархии исключений (SenderError и наследники) внутри модуля; CRUD получателей с upsert по email без затирания непустых полей NULL-ами; запись результатов валидации (set_recipient_validation); Управление кампаниями и шагами последовательности (create_campaign, set_campaign_status, add_step, get_steps); Очередь сообщений: постановка (enqueue_message), атомарный захват due-сообщений с lease (claim_due_messages), пометки sent/failed/skipped, восстановление зависших (recover_stale); Журнал событий append-only с дедупом (append_event) и агрегирующие чтения (count_events, open_counts, last_event_ts, has_reply)
- **Источники данных:** SQLite-файл по пути db_path, переданному в конструктор Store(db_path); env/конфиг-ключи модуль напрямую не читает; Входные данные приходят исключительно через аргументы методов (DTO *In и параметры), а не из внешних источников
- Логика обработки: Соединение открывается с isolation_level=None и check_same_thread=False; все записи идут через contextmanager transaction() с BEGIN IMMEDIATE, реентерабельно по потоку через RLock; Идемпотентность через UNIQUE-индексы и ON CONFLICT DO NOTHING/DO UPDATE: email (recipients), idempotency_key (messages), dedup_key (events, leads), (scope,value) (suppression); claim_due_messages: SELECT статуса 'scheduled' с scheduled_at<=now, фильтром по mailbox_id (NULL или в переданном не-паузнутом наборе), NOT EXISTS reply по (recipient,campaign) и NOT EXISTS активной suppression (email/domain/inn), затем UPDATE в 'sending'+claimed_at — всё в одной транзакции (suppression-first + lease); recover_stale: 'sending' с пустым/старым claimed_at (порог = now - lease_ttl_sec) возвращается в 'scheduled', claimed_at=NULL; mark_failed: retryable → обратно в 'scheduled' со снятием lease и attempt_count+1; иначе финальный 'failed'; increment_sent: при совпадении day_key инкремент sent_today, при смене day_key сброс sent_today=1 и ramp_day+1, всегда sent_total+1; Время хранится как UTC ISO-8601 фиксированного формата (лексикографическая сортировка = временная); наивный datetime трактуется как UTC; JSON-поля сериализуются с ensure_ascii=False, sort_keys=True; suppression_lookup перебирает scope в порядке email→domain→inn, отбрасывая истёкшие (expires_at)
- **БД (через store):** recipients: INSERT/upsert по email, UPDATE валидации, SELECT (get/iter); campaigns: INSERT, UPDATE статуса/started_at/paused_at, SELECT; sequence_steps: INSERT, SELECT по campaign_id; messages: INSERT (enqueue), UPDATE claim/sent/failed/skipped/recover, SELECT (get, по rfc_message_id, join в count_events); events: INSERT append-only с дедупом, SELECT/COUNT/GROUP BY/MAX (count_events, open_counts, last_event_ts, has_reply); suppression: INSERT, SELECT lookup; mailbox_state: INSERT/upsert, UPDATE (increment_sent, set_mailbox_paused), SELECT; warmup_state: INSERT/upsert, SELECT
- Наружу (I/O): Файл SQLite на диске по db_path (WAL-режим); других сетевых/процессных обращений наружу нет — модуль на чистом stdlib
- Публичный API: Класс Store и его методы: init_schema, transaction, close, recover_stale, upsert_recipient, bulk_upsert_recipients, set_recipient_validation, get_recipient, iter_recipients, create_campaign, get_campaign, set_campaign_status, add_step, get_steps, enqueue_message, claim_due_messages, mark_sent, mark_failed, mark_skipped, get_message, find_message_by_rfc_id, append_event, count_events, open_counts, last_event_ts, has_reply, suppression_lookup, suppression_add, get_mailbox_state, iter_mailbox_states, upsert_mailbox_state, increment_sent, set_mailbox_paused, get_warmup_state, upsert_warmup_state, log_consent, consent_history
- Зависит от: Только stdlib (json, sqlite3, threading, contextlib, dataclasses, datetime, pathlib, typing); других модулей системы не импортирует — сознательно не зависит ни от кого

### `dtos.py` (230 строк)
**Единый источник типов (dataclass-DTO) для обмена данными между всеми модулями системы рассылки.**

- Обязанности: Определяет frozen-dataclass'ы входных DTO для записи в store: RecipientIn, CampaignIn, SequenceStepIn, MessageIn, EventIn, SuppressionIn; Определяет DTO сущностей, читаемых из store: Recipient, Campaign, SequenceStep, Message, SuppressionEntry, а также изменяемые (не frozen) MailboxState и WarmupState; Определяет runtime-DTO для обмена результатами между модулями: ValidationResult, RenderedMessage, SendResult, InboundEvent, CadenceDecision, GateDecision, UnsubResult, RateSnapshot; Определяет DTO отчётов analytics: CampaignReport, MailboxReport, WarmupReport, GlobalReport, TickResult, WarmupCycleResult; Определяет конфиг-структуры: MailboxCfg, WindowCfg, GatesCfg, LegalCfg; Фиксирует допустимые значения полей через комментарии-перечисления (valid_status: valid|invalid|risky|unknown; engagement_gate: all|not_bounced|engaged; scope: email|domain|inn; action: send|skip|stop и т.д.)
- **Источники данных:** Данных не берёт: модуль содержит только объявления типов (dataclass), без чтения файлов, БД, сети или env; Косвенно ссылается на имена env-переменных как строковые поля-указатели: MailboxCfg.password_env, LegalCfg.unsub_secret_env (сами значения читают другие модули)
- Логика обработки: Логики обработки нет: только описания структур данных; Использует @dataclass(frozen=True) для неизменяемых DTO и @dataclass (изменяемый) для MailboxState/WarmupState — состояния, обновляемые в рантайме; field(default_factory=dict) для полей extra/config/detail/detail, чтобы избегать общего мутабельного дефолта; Комментарии в коде задают контракт значений (например RenderedMessage.unfilled_fields: если непусто и не preview → gate падает) — правило исполняется в вызывающих модулях, не здесь
- Публичный API: RecipientIn, CampaignIn, SequenceStepIn, MessageIn, EventIn, SuppressionIn — входные DTO, Recipient, Campaign, SequenceStep, Message, SuppressionEntry, MailboxState, WarmupState — сущности, ValidationResult, RenderedMessage, SendResult, InboundEvent, CadenceDecision, GateDecision, UnsubResult, RateSnapshot — runtime-обмен, CampaignReport, MailboxReport, WarmupReport, GlobalReport, TickResult, WarmupCycleResult — отчёты, MailboxCfg, WindowCfg, GatesCfg, LegalCfg — конфиг-структуры
- Зависит от: Никакие модули системы не импортирует; зависит только от стандартной библиотеки: dataclasses, datetime, typing

### `errors.py` (67 строк)
**Единая иерархия исключений сендера — общий источник идентичности классов ошибок для кросс-модульных except.**

- Обязанности: Определяет базовый класс SenderError и всю иерархию наследуемых от него исключений; Обеспечивает единую идентичность классов ошибок для модулей, использующих паттерн try-import с фолбэком (gates, orchestrator, personalize, suppression, validation, sender); Экспортирует фиксированный публичный набор классов через __all__; Разделяет ошибки по семантике: конфиг, хранение, suppression, валидация, персонализация, отправка, rate-limit, kill-switch, временные (ретраибельные)
- **Источники данных:** Нет внешних источников данных — модуль содержит только определения классов, не читает файлы/БД/env/сеть
- Логика обработки: Строит дерево наследования от Exception: SenderError → {ConfigError, StoreError, SuppressedError, ValidationError, PersonalizationGateError, SendError, GateTrippedError, TransientError}; SendError имеет подкласс RateLimitExceeded (превышение темпа отправки); Семантика узлов иерархии задаёт правила обработки в вызывающих модулях: PersonalizationGateError — письмо не должно уйти (§5.4), TransientError — ретраибельно, GateTrippedError — kill-switch; Никакой исполняемой логики/алгоритмов внутри классов нет — только докстроки
- Публичный API: SenderError — базовый класс всех ошибок, ConfigError — невалидный конфиг/отсутствующие секреты, StoreError — ошибка слоя хранения, SuppressedError — получатель под suppression, ValidationError — невалидный вход (адрес/токен/аргумент), PersonalizationGateError — незаполненные плейсхолдеры, SendError — ошибка отправки, RateLimitExceeded(SendError) — превышен лимит темпа
- Зависит от: Не импортирует другие модули системы; зависит только от встроенного Exception. По докстроке предназначен для импорта модулями gates, orchestrator, personalize, suppression, validation, sender

### `validation.py` (605 строк)
**Проверяет качество и доставляемость e-mail адресов (MX, провайдер, catch-all/role/disposable) без отправки писем, возвращая ValidationResult.**

- Обязанности: Синтаксическая нормализация и валидация адреса (parseaddr, IDNA-кодирование домена, RFC-5321-ish regex, лимит длины 254); Резолвинг MX-записей домена с сохранением null-MX sentinel '.' (RFC 7505) и A/AAAA-фолбэком для доставляемости; Классификация почтового провайдера: yandex|mailru|google|outlook|vk|other|unknown — сначала по known consumer-домену, затем по подстроке MX-хоста; Определение сигналов: role-based локальная часть, disposable/temp-mail домен, catch-all (опциональный SMTP RCPT-probe); Присвоение итогового статуса valid|invalid|risky|unknown (invalid имеет приоритет); Вычисление provider_class (consumer|hosted|corp|unknown) для управления темпом каденции; Оффлайн-детекция опечаток домена с предложением исправления через detail['typo_suggestion'] (адрес сам не переписывается)

- **Источники данных:** Файл конфигурации: аргумент --config или env SENDER_CONFIG, дефолт ./sender.yaml (через Config.load с env=os.environ); Конфиг-ключи: service.db_path, orchestrator.active_campaigns; секции config.legal(), config.mailboxes(); SQLite-БД по пути service.db_path (default sender.db) через Store; CSV-файл получателей (аргумент csv_path); Файл suppress-списка (аргумент file_path); Файл с телом письма для шага кампании (--body-file, читается как UTF-8); env BITRIX_WEBHOOK_URL (включает BitrixSink), TELEGRAM_BOT_TOKEN (включает Notifier); env с паролем нового пользователя (имя задаётся --password-env, дефолт SENDER_NEW_USER_PASSWORD)
- Логика обработки: _load_config: путь конфига из --config/SENDER_CONFIG/дефолта → Config.load; _open_store: читает service.db_path из конфига → создаёт Store; import: парсит --map в словарь column_map (пары k=v через запятую), вызывает import_csv, печатает JSON-результат; campaign-add-step: проверяет наличие body-file, читает тело, формирует SequenceStepIn (include_legal=True, engagement_gate из --gate) и вызывает store.add_step; run: конструирует граф зависимостей (Suppression, Gates, Sender, Cadence, Personalizer, Warmup, Analytics, LeadDesk с опциональным BitrixSink, ImapWatcher, опциональный Notifier) и передаёт в Orchestrator; определяет active_campaign_ids из --campaigns или config; вызывает bootstrap(); затем tick(now) при --once либо run(interval, dry_run, stop) в цикле с обработкой KeyboardInterrupt через threading.Event; status: перебирает config.mailboxes() и печатает get_mailbox_state; кампании перебираются жёстко по ID 1..100 через get_campaign; pause: scope=global — пауза всех ящиков из конфига; scope=mailbox — пауза одного --target (обязателен); resume: --target — снять паузу с одного, иначе со всех ящиков конфига
- **БД (через store):** Store.init_schema() — создание схемы (init-db); store.create_campaign(CampaignIn) — создание кампании; store.add_step(SequenceStepIn) — добавление шага последовательности; store.set_campaign_status(id, 'active'|'paused') — статус кампании; store.get_campaign(id) — чтение кампаний (status); store.get_mailbox_state(mailbox_id) — чтение состояния ящика (status); store.set_mailbox_paused(mailbox_id, bool, reason) — пауза/возобновление ящиков (pause/resume); store.get_user_by_username(username) — чтение пользователя (rotate-2fa)
- Наружу (I/O): Файлы: чтение CSV, suppress-файла, body-файла; чтение YAML-конфига; SQLite-файл БД (через Store); HTTP-сервер: uvicorn.run для веб-панели на host:port (serve-api); Косвенно наружу через собранные объекты в run: SMTP (Sender), IMAP (ImapWatcher), HTTP-вебхук Bitrix (BitrixSink при BITRIX_WEBHOOK_URL), Telegram API (Notifier при TELEGRAM_BOT_TOKEN); stdout/stderr — вывод результатов и сообщений об ошибках
- Публичный API: main(argv) — точка входа CLI (вызывается из __main__/python -m sender), Приватные обработчики _cmd_* — внутренние, не предназначены для внешнего вызова
- Зависит от: config (Config), store (Store, CampaignIn, SequenceStepIn, ConfigError, StoreError, SenderError), importer (import_csv, import_suppression, validate_recipients), suppression (Suppression), gates (Gates), sender (Sender), cadence (Cadence), personalize (Personalizer), warmup (Warmup), analytics (Analytics), imap_watcher (ImapWatcher), notify (Notifier), orchestrator (Orchestrator), leaddesk (LeadDesk, ленивый импорт), bitrix (BitrixSink, ленивый импорт при BITRIX_WEBHOOK_URL), auth (Auth, ленивый импорт), api.app (make_app, make_site_app, build_deps, ленивый импорт)


## Где используется обработка данных из БД

- **analytics**: events — только чтение через count_events (COUNT по event_type + фильтрам campaign_id/domain/mailbox_id/sequence_step_id/since); дедуп по UNIQUE(events.dedup_key) на уровне БД, analytics не пересчитывает; messages — косвенно через фильтр sequence_step_id (join events.message_id -> messages.sequence_step_id) в per-step снимках; mailbox_state — только чтение: get_mailbox_state, iter_mailbox_states; warmup_state — только чтение: get_warmup_state; sequence steps (get_steps) — только чтение
- **auth**: store.get_user_by_username — чтение пользователя по имени (login, create_user); store.get_user — чтение пользователя по id (resolve, enable_2fa); store.create_user(username, password_hash, role, email, totp_secret) — запись нового пользователя; store.update_user(user_id, ...) — обновление password_hash / totp_secret; store.revoke_user_sessions(user_id) — отзыв всех сессий пользователя
- **bitrix**: store.append_event — запись/проверка события 'bitrix_lead_created' для дедупликации (SimpleNamespace с dedup_key, event_type, event_ts, recipient_id, detail={thread_id}); чтение результата (created) определяет, создавать ли лид
- **cadence**: Через StoreProtocol (не напрямую SQLite): чтение get_steps, has_reply, count_events (sent/bounce/canary_passed), iter_recipients, last_event_ts; Запись: append_event(EventIn) события canary_passed с dedup_key='canary_passed:{campaign_id}' (дедуп по ON CONFLICT), detail={sent, bounced, rate_pct}; Формирует MessageIn DTO, предназначенные для store.enqueue_message (по докстроке), но сам enqueue не вызывает
- **cli**: Store.init_schema() — создание схемы (init-db); store.create_campaign(CampaignIn) — создание кампании; store.add_step(SequenceStepIn) — добавление шага последовательности; store.set_campaign_status(id, 'active'|'paused') — статус кампании; store.get_campaign(id) — чтение кампаний (status)
- **gates**: count_events — чтение агрегированных счётчиков событий (sent/bounce/complaint) с фильтрами; iter_recipients — чтение получателей (домены, mx_provider); set_mailbox_paused(mailbox_id, True, reason) — запись паузы ящика; suppression_add(SuppressionIn scope='domain') — запись домена в suppression (идемпотентно, ON CONFLICT DO NOTHING)
- **imap_watcher**: find_message_by_rfc_id — чтение исходного сообщения по RFC Message-ID; get_recipient — чтение получателя по recipient_id; has_reply — проверка наличия ответа по (recipient_id, campaign_id); append_event — запись событий в журнал: типы reply/reply_auto/dsn/complaint/other, skip, suppress, retry_scheduled (идемпотентно по dedup_key); enqueue_message — постановка нового письма в очередь при soft-bounce ретрае (идемпотентно, ON CONFLICT)
- **importer**: store.bulk_upsert_recipients(batch) — запись/upsert получателей (import_csv); store.iter_recipients(valid_status=...) — чтение получателей для валидации; store.set_recipient_validation(id, valid_status, mx_provider, catch_all, role_based, disposable) — обновление результатов валидации; косвенно через Suppression: add_inn / add_domain / import_competitors — запись в таблицы подавления
- **leaddesk**: store.create_lead — запись нового лида (email, dedup_key, recipient_id, thread_id, company_name, inn, reply_kind, phone, need, sla_due_at); store.update_lead_cas — обновление с оптимистичной блокировкой (expected_version): actions taken/assigned/status_changed/synced, поля status/assigned_to/need/bitrix_lead_id; store.get_lead — чтение одного лида; store.list_leads — выборка очереди с фильтрами (status, assigned_to, unassigned, reply_kind, limit, offset); store.list_lead_events — история событий лида
- **notify**: store.append_event(event_in) — запись служебного события с event_type='notify_sent' и dedup_key для реализации дебаунса; полагается на возвращаемый флаг created для определения дубля (запись только, чтения нет)
- **orchestrator**: store.init_schema() — инициализация схемы (bootstrap); store.recover_stale(lease_ttl_sec) — чтение/апдейт зависших сообщений (bootstrap и каждый tick); store.get_mailbox_state(mailbox_id) — чтение состояния ящика; store.upsert_mailbox_state(MailboxState) — посев/апдейт mailbox_state; store.set_mailbox_paused(mailbox_id, paused, reason) — пауза/снятие паузы ящика
- **sender**: Через StoreLike (не прямой SQLite): читает get_recipient, get_campaign, get_message, get_mailbox_state; Пишет: mark_failed, mark_skipped, mark_sent (rfc_message_id, sent_at), increment_sent(mailbox_id) — обновление состояния ящика/счётчика; append_event(EventIn) с event_type='sent' и dedup_key='send:{message.id}'; log_consent (опционально, если метод есть у store) — журнал правового основания касания ФЗ-152
- **store**: recipients: INSERT/upsert по email, UPDATE валидации, SELECT (get/iter); campaigns: INSERT, UPDATE статуса/started_at/paused_at, SELECT; sequence_steps: INSERT, SELECT по campaign_id; messages: INSERT (enqueue), UPDATE claim/sent/failed/skipped/recover, SELECT (get, по rfc_message_id, join в count_events); events: INSERT append-only с дедупом, SELECT/COUNT/GROUP BY/MAX (count_events, open_counts, last_event_ts, has_reply)
- **suppression**: store.suppression_lookup(email, domain, inn) — SELECT/lookup по индексу; конкретная таблица определяется в store; store.suppression_add(SuppressionIn) — INSERT OR IGNORE / upsert; идемпотентность через UNIQUE(scope, value) в БД; store.count_suppression() — SQL-агрегация (COUNT + GROUP BY scope/reason + фильтр expires_at); опциональный метод; store.iter_suppression(limit=1_000_000) — SELECT * с лимитом для fallback-агрегации в Python; опциональный метод
- **tracking**: store.get_message(mid) — SELECT сообщения по ID (чтение sent_at, recipient_id, campaign_id, mailbox_id); store.append_event(EventIn(dedup_key='open:<mid>', event_type='open', ...)) — INSERT события; дедуп через dedup_key (предположительно UNIQUE-индекс в store), возвращает (id, created: bool)
- **unsub**: store.get_recipient(recipient_id) — чтение получателя по id; store.log_consent(...) — запись в журнал согласий/оснований (ФЗ-152), только при первом срабатывании токена, вызов защищён hasattr и try/except
- **unsub_server**: Напрямую SQLite не трогает; работа с БД инкапсулирована в Store, которую используют Unsub (запись отписок/подавления) и OpenTracker (фиксация открытий). Конкретные таблицы задаются в suppression/unsub/tracking, а не здесь.
- **warmup**: store.get_warmup_state(mailbox_id) — чтение состояния прогрева (warmup_state); store.upsert_warmup_state(WarmupState) — запись/обновление состояния прогрева (updated_at ставит store); store.append_event(EventIn) — append-only запись событий 'sent' и 'bounce' с warmup=True в detail

## Анализ пересечений модулей (нужны ли в коде)

_Синтез: Полностью лишних (удаляемых) модулей нет: warmup, cadence, gates, sender, bitrix, leaddesk, dns, validation, unsub/unsub_server, tracking, review_chain/review_lenses — все имеют самостоятельную зону ответственности. Ключевые пары, о которых был вопрос, разделены по сути корректно (warmup≠sender, cadence≠orchestrator, gates≠warmup — разные данные/скоупы/последствия), а не дублируют друг друга. Реальные проблемы — не архитектурные дубли, а расползание общих примитивов: (1) рамп-кривая/дневной лимит считаются в sender/warmup/orchestrator/config — нужен единый резолвер; (2) errors и dtos продублированы fallback-копиями по многим модулям — риск расхождения идентичности классов и схем; (3) DNS-резолвинг (dns/validation), HMAC-токен (tracking/unsub) и нормализация email/домена (suppression/validation) дублируются дословно — вынести в shared-хелперы; (4) DI-wiring дублируется между cli и композиционным корнем. Всё это РЕФАКТОР (консолидация общих частей), а не удаление модулей. Дублей уровня 'ДУБЛЬ-УДАЛИТЬ' не найдено._

| Модули | Что пересекается | Вердикт | Почему |
|---|---|---|---|
| warmup, sender | Отправной контур: warmup вызывает sender.send/can_send_now, но при этом сам формирует Message/RenderedMessage и локально переобъявляет DTO (EventIn, Message, SendResult, MailboxState) и всю иерархию исключений вместо переиспользования пайплайна sender/dtos/errors. | **РЕФАКТОР** | Как отдельный модуль warmup оправдан — у него своя доменная задача (рамп-объём, репутация, отбор peer-ящиков, ящик↔ящик внутри провайдер-контура), это НЕ дубль sender. Но сборка письма и локальные копии DTO/исключений — реальная дупликация. Нужно, чтобы warmup переиспользовал сборку/доставку sender и общие dtos/errors, а не держал параллельный мини-пайплайн. |
| cadence, orchestrator | Планирование и запуск волн: cadence считает время отправки (задержка/джиттер/окно/праздники), канареечную волну и engagement-гейты; orchestrator владеет 'now' и решает, когда запускать tick/волну. Границы 'кто владеет now и запуском волны' размыты по комментариям. | **ОК** | Разделение корректное по сути: cadence — чистая логика 'что и когда планировать' (без побочных эффектов запуска), orchestrator — исполнительный цикл и композиционный корень. Это не дубль, а слои. Стоит лишь явно зафиксировать контракт передачи now (orchestrator._now() → cadence), чтобы расчёт времени не расползался. |
| gates, warmup | Оценка здоровья/репутации: gates считает bounce/complaint по событиям и при превышении порогов ставит паузу (kill-switch); warmup держит собственный эвристический reputation_score (0..1) по факту доставок/провалов и свой гейт reputation_floor (phase=paused). | **ОК** | Измеряют разные вещи в разных контурах: gates — продакшн kill-switch по реальным bounce/complaint из журнала событий; warmup — внутренняя эвристика прогрева на синтетическом трафике ящик↔ящик. Совпадает только идея 'плохая репутация → пауза', но данные, скоуп и последствия разные. Слияние ухудшило бы обе задачи. |
| sender, warmup, orchestrator, config | Лимиты/рамп: sender.can_send_now применяет дневной лимит по ramp_curve(provider) + окно + пейсинг; warmup.daily_target считает целевой объём по своей рамп-кривой; orchestrator при посеве mailbox_state берёт daily_limit из config.ramp_curve[0]; config хранит и валидирует сами кривые (ramp_curves.<provider>, warmup.ramp_curve). | **РЕФАКТОР** | Знание о рамп-кривой и вычислении дневного лимита размазано по четырём модулям, и это уже приводит к параллельным веткам (боевой лимит sender vs прогревной target warmup vs стартовое значение orchestrator). Нужен единый резолвер лимита (например, в config или тонкий shared-хелпер), который отдаёт дневной лимит по (provider, ramp_day, warmup?) — тогда sender/warmup/orchestrator только потребляют, а не пересчитывают. |
| gates, analytics | Обе стороны вычисляют bounce_rate/complaint_rate по журналу событий через count_events; analytics отдаёт сырые проценты, gates применяет пороги и min_volume. | **ОК** | Разделение ответственности заявлено и оправдано: analytics — read-only отчётность, gates — принятие решения о паузе. Дублируется лишь арифметика rate. Слияние не нужно; при желании можно вынести общую формулу rate в маленький shared-хелпер, но модули должны остаться раздельными (разные последствия и права записи). |
| gates, suppression, orchestrator | Применение пауз/подавления: gates пишет домены в suppression (store.suppression_add) и ставит ящики на паузу, но на global-trip намеренно НЕ паузит всё сам, отдавая pause_all оркестратору. | **ОК** | Это осознанный safety-контракт, а не дубль: gates — 'только пауза, без resume', suppression владеет хранением/нормализацией правил, orchestrator транслирует global-решение в pause_all. Роли распределены. Дублирования логики нет, есть кооперация через store. |
| errors, store, cadence, warmup, analytics, sender, gates, personalize, suppression, validation, config | Иерархия исключений SenderError и наследников определена в errors, но множество модулей держат приватные fallback-копии (try-import с локальным классом), а store/cadence/warmup/analytics/config определяют свои классы без унификации. | **РЕФАКТОР** | Реальный риск: при расхождении определений except PersonalizationGateError в orchestrator не поймает исключение из personalize (разная идентичность классов). errors как отдельный модуль нужен, но fallback-копии нужно свести к единому импорту и гарантировать, что errors всегда доступен, иначе кросс-модульный except ненадёжен. |
| dtos, store, config, warmup, suppression, personalize | DTO-типы (Recipient, Campaign, Message, MailboxState, WarmupState, SuppressionIn, MailboxCfg/WindowCfg/GatesCfg/LegalCfg и др.) объявлены канонически в dtos, но продублированы внутри store, а также как fallback-dataclass'ы в warmup/suppression/personalize; config заполняет config-структуры, форма которых задана в dtos. | **РЕФАКТОР** | dtos как единый источник контракта оправдан, но фактически store и ряд модулей держат параллельные объявления — при рассинхронизации схем возможны тихие расхождения полей. Нужно сделать dtos реально единственным местом объявления и убрать локальные дубли (fallback оставить только для изолированного запуска, с явной пометкой). |
| dns, validation | Оба резолвят DNS одним и тем же паттерном: dnspython с фолбэком на subprocess nslookup; оба проверяют MX (dns — гигиену отправляющего домена SPF/DKIM/DMARC/MX, validation — доставляемость адреса получателя). | **РЕФАКТОР** | Назначение модулей разное и оба нужны, но низкоуровневый резолвинг (dnspython + nslookup-фолбэк, таймауты, парсинг) — буквальное дублирование кода. Стоит вынести общий DNS-резолвер в один хелпер, который используют и dns, и validation. |
| tracking, unsub | Идентичный формат HMAC-токена: base64url(payload).base64url(sig), sort_keys, одинаковые separators, один и тот же секрет из legal.unsub_secret_env; make_token/verify реализованы в обоих (в tracking — {mid,rid,cid,ts}, в unsub — {rid,cid,ts}). | **РЕФАКТОР** | Формат и криптопроцедура токена дублируются дословно (это даже задокументировано в docstring tracking). Нужно вынести генерацию/верификацию подписанного токена в общий утилитарный модуль, чтобы формат и секрет управлялись в одном месте; сами tracking и unsub остаются раздельными по назначению. |

## Слой: Веб-панель (HTTP + SPA)

### `api/app.py` (594 строк)
**Тонкий HTTP/JSON-слой (FastAPI) над движком системы холодной рассылки: каждый эндпоинт — обёртка над готовым методом компонента под Bearer-auth-гейтом.**

- Обязанности: Экспонировать REST-API веб-панели поверх компонентов движка (store/analytics/gates/sender/suppression/leaddesk/warmup/dns) без дублирования бизнес-логики; Аутентификация и авторизация запросов через Bearer-токен и ролевые гейты (principal — любой залогиненный, owner — только владелец); Собирать контейнер зависимостей движка из config+store (build_deps) как единую точку сборки для API; Обслуживать Lead-Desk («эпицентр»): очередь, карточка, взятие, смена статуса, назначение лидов; UI-only просмотр справочников: получатели, кампании, события, подавления, аналитика, гейты, готовность ящиков, ёмкость пулов; Управление кампаниями, шагами последовательности, статусами (owner); Управление командой/пользователями, настройками, аудитом, доменами/DNS, прогревом, комплаенсом, субъектами ПД (owner)
- **Источники данных:** Deps-контейнер с собранными компонентами движка (config, store, auth, leaddesk, analytics, gates, sender, suppression, warmup, dns); HTTP-заголовок Authorization (Bearer-токен) и User-Agent; Pydantic-модели тела запроса (LoginBody, StatusBody, AssignBody, CampaignBody, StepBody, CampaignStatusBody, UserBody, PasswordBody); Query-параметры фильтрации/пагинации (status, assigned_to, limit, offset, provider, domain_like, inn и т.п.); config.mailboxes()/legal()/gates()/provider_pools() — конфигурация ящиков, юрлица, порогов и пулов провайдеров; Каталог статики SPA (static_dir с dist/) в режиме make_site_app
- Логика обработки: make_app(deps) строит FastAPI-приложение и регистрирует эндпоинты; make_site_app оборачивает его в «сайт» с SPA; principal(): извлекает токен из заголовка Bearer, вызывает auth.resolve; None → HTTP 401; owner(): проверяет что principal.role == ROLE_OWNER, иначе HTTP 403; Маппинг доменных исключений в HTTP-коды: AuthError→401, LeadConflict→409 (конфликт версии/уже взят), прочие→400, отсутствие сущности→404; _leads_to_json: обогащает лиды справочным счётчиком открытий (opens) через store.open_counts (open-трекинг в РФ считается приблизительным, в гейты не входит); _clean: отбрасывает None-значения фильтров перед передачей в store; campaign_detail/campaigns: funnel-отчёт из analytics оборачивается в try/except чтобы не ронять карточку при сбое отчёта; domains: быстрая сводка по доменам ящиков без сетевого DNS; domain_dns: отдельный сетевой чек DKIM/SPF/DMARC (может быть медленным)
- **БД (через store):** store.open_counts — счётчики открытий по recipient_id; store.query_recipients / count_recipients — выборка и подсчёт получателей; store.list_campaigns / get_campaign / create_campaign / set_campaign_status — кампании; store.get_steps / add_step — шаги последовательности; store.list_events — события; store.iter_suppression / suppression_remove / suppression_lookup — подавления
- Наружу (I/O): Приём HTTP/JSON-запросов и выдача JSON-ответов через FastAPI/Starlette; Раздача статических файлов SPA (dist/) и index.html fallback в режиме make_site_app; Сетевые DNS-проверки (SPF/DKIM/DMARC/MX) через deps.dns.check в эндпоинте /domains/{domain}/dns; Эндпоинты health/healthz для nginx/systemd/docker
- Зависит от: fastapi (Depends, FastAPI, Header, HTTPException), pydantic (BaseModel), starlette (StaticFiles, HTTPException) — для SPA-fallback, sender.auth (Auth, AuthError, Principal, ROLE_OWNER, verify_password), sender.leaddesk (LeadDesk, LeadConflict), sender.analytics (Analytics), sender.gates (Gates), sender.suppression (Suppression), sender.sender (Sender), sender.warmup (Warmup), sender.dns (DnsHealth), sender.store (CampaignIn, SequenceStepIn) и переданный извне store, os (проверка каталога статики)
