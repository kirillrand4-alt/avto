## P1 — латентный баг: расхождение идентичности исключений/DTO

Из overlap-анализа: `errors.py` и `dtos.py` — канонические источники, но многие
модули держат **приватные fallback-копии** классов (`try import ... except:
class ...`). Реальный риск: если определения разойдутся, `except
PersonalizationGateError` в `orchestrator` НЕ поймает исключение из `personalize`
(разная identity классов) — молчаливый пропуск инварианта.

Задача: сделать `errors`/`dtos` жёстко импортируемыми во всём дереве (как пакет),
fallback-копии убрать или свести к единственному источнику. Проверить, что
`except`-ветки ловят реальные классы (тест на identity: raise из одного модуля,
catch в другом).

## P2 — консолидация общих примитивов (рефактор, не удаление модулей)

Полностью лишних модулей НЕТ (warmup ≠ sender: warmup вызывает sender.send;
cadence ≠ orchestrator; gates ≠ warmup). Но общие куски размазаны — вынести в
`shared`/утилиты:

1. **Рамп-кривая/дневной лимит** считаются в `sender.can_send_now`,
   `warmup.daily_target`, `orchestrator._seed_mailbox_states`, `config` — единый
   резолвер лимита по (provider, ramp_day), все четверо зовут его.
2. **HMAC-токен** (`tracking` и `unsub` — дословно одинаковый формат
   base64url(payload).base64url(sig), один секрет) → общий `sign_token/verify_token`.
3. **DNS-резолвинг** (`dns` и `validation` — dnspython + фолбэк nslookup) →
   общий резолвер MX/таймаутов.
4. **Нормализация email/домена** (`suppression` и `validation` — lower/strip/IDNA)
   → одна функция (иначе стоп-лист рассинхронится с валидацией).
5. **review_chain** дублирует вызов LLM-caller + парсинг JSON из `review_lenses` —
   судью собрать через тот же механизм линз.
6. **DI-wiring** графа зависимостей дублируется в `cli` и (частично) `api` —
   вынести композиционный корень (`build_deps`) и звать из обоих.

Каждый пункт — отдельный небольшой PR с тестами. P2 не блокирует запуск, делать
после P0/P1.
