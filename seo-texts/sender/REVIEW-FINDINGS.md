## КРИТИЧНЫЕ ДЫРЫ (CONFIRMED) — без них бизнес-выход не построен

1. **Bitrix24 коннектор [P1]** — есть только интерфейс `ReplyDeskSink`, реализации нет.
   Тёплый лид не доходит до продажников → pipeline «ответ→лид→продавец» обрывается.
2. **AI-извлечение лида** — заглушка: нет парсинга потребности/телефона/готовности из
   ответа. Продавец получает сырой текст. (Классификация reply/dsn/complaint ЕСТЬ; не
   хватает извлечения полей и скоринга готовности — см. также NEW #2.)
3. **Атрибуция ООО+ИНН в КАЖДОМ письме** [quick win ~2-3 дня] — сейчас `include_legal`
   только на письмо-1. ФЗ-38 ст.18: рекламодатель идентифицируем в каждом письме, штраф
   до 500к. Правка шаблонов.
4. **Consent_log отсутствует** [ФЗ-152] — нет истории согласий/отказов (источник, дата),
   нет защиты при жалобе в РКН.
5. **Интеграция Яндекс.Постмастер / Mail.ru Постофис** — доставляемость оптимизируется
   вслепую (gates считают bounce/complaint по своему журналу, но нет внешнего сигнала
   репутации/спам-рейта от провайдера).
6. **Суб-классификация ответов** — базовый классификатор reply/dsn/complaint есть, но не
   отделяет автоответ (OOO) / «не интересно» от живого горячего ответа → мусор в лиды.

## PARTIAL — ДОРАБОТАТЬ, не строить с нуля (базовое уже в коде)

- **gates bounce-тормоз:** есть (`domain_bounce_pct: 8.0`/`mailbox_bounce_pct: 6.0`), но
  → опустить до **2-3%**, добавить **× провайдер получателя**, добавить **канареечные

- **warmup:** пауза по низкой репутации есть (`reputation_floor`), не хватает real-time
  реакции на bounce-rate + rollback рампа.
- **дашборд:** агрегирующий `dashboard()` есть, не хватает real-time метрик/алертов.
- **AI-персонализация:** хук ОКВЭД→оборудование есть, не хватает парсинга сайта получателя.
- **engagement-каденция:** гейт по open — заменить на **click/reply** (open в RU часто
  не считается/накручивается).
- **пауза-ручки:** селективная по ящику/домену есть, не хватает API с scope.

## НЕ СТРОИТЬ — уже реализовано (9 ALREADY_EXISTS, verified в коде)

- **same-provider routing** — `sender._route_pool()` при `match_recipient_provider=true`;
- **greylist 4xx** — `validation._smtp_accepts` уже возвращает `None` (unknown), НЕ invalid
  → **корректирует претензию ревью «greylist трактуется как недоступность → ложные негативы»**
  (ретрай позже — валидный enhancement, но «мы жжём» неверно);
- **IDN/.рф/EAI** — `validation._norm_domain` уже делает IDNA (`encode("idna")`, стр.397) +
  `suppression.normalize_domain` → **корректирует претензию ревью «IDN режется синтаксисом»**.
  NB: это НЕ то же, что typo-коррекция (mial.ru→mail.ru) — та остаётся валидной отдельной правкой;
- **dynamic provider balancing** — `pick_mailbox` сортирует по наименее загруженному ящику;
- **базовая классификация** reply/dsn/complaint — `imap_watcher.classify`;
- **ОКВЭД→оборудование персонализация** — `personalize` + `GenProvider.suggest_equipment`.

## Метод-урок (важно для новой сессии)

Верификатор поймал **9 переоценок** («у вас нет X», а X есть) + **2 неточности в моих же
прежних заметках** (greylist, IDN). Правило: **любой вывод ревью-прогона сверять
фактчек-линзой против кода/данных до внесения в план.** Без этого модели уверенно
«находят» дыры, которые уже закрыты.
