# Сдача BASE-MERGE (объединение баз + гейт направлений) — dry-run приёмка

Дата: 2026-07-24. По ТЗ ENGINEER-TASKS-BASE-MERGE §5.
Прогон: `tools/dryrun_basemerge.py` на РЕАЛЬНЫХ данных — полный индекс обзвона
(161 761 юрлицо: КЦ 129 343 + Meyer 32 418, цифры сошлись с владельцем 1:1)
+ снапшот enrich.db с сервера (4370 компаний, 194 сигнала).

Холд соблюдён в актуальной формулировке владельца: **автоматика не шлёт
никогда; живая отправка — только ручной approve оператора** (live_send).
В dry-run live_send выключен — всё легло в очередь подтверждений.

## DoD-пункты

1. **Индекс обзвона + company_card(inn)** — `company_card.py` (коммит b5a30f6).
   Приоритеты ТЗ соблюдены: направление ТОЛЬКО из базы обзвона (enrich —
   «предположение»), контакты enrich приоритетнее, телефоны оба набора с
   источником, site по verified, cand_site с пометкой. Индекс строится стримом
   CSV с дропа без сохранения на диск: `tools/build_obzvon_index.py`
   (424 МБ SQLite, «ВсеОКВЭД» сжат до кодов).
2. **division в конфиге + гейт в трёх точках** — коммит e4d88c4, 12 тестов.
3. **Карточка → JSON панели, новые блоки** — коммит 2b3e5ed: news_events
   (ВСЕ события со ссылками + signal_match), company_full, очередь
   «дозаполнить данные» (needs_data), рендер CLI+веб, кнопка блокируется.
4. **Dry-run 20 писем** — этот отчёт.

## Итоги прогона 20 писем

- 20/20 легли в `pending` очереди подтверждений (оператор видит их в панели
  со всеми новыми блоками).
- **Новостных — 6** (норма ≥5): 2 КЦ + 4 Meyer, каждое событие в карточке
  с реальным source_url из enrich; матчинг имени подсвечен
  («имя в тексте» / «НЕТ имени — проверь»).
- Полная карточка компании собрана у всех 20 (реквизиты/ОКВЭД/продуктовая
  разметка из базы обзвона + контакты/сигналы enrich).
- Направление компании = направлению кампании у всех 20 (КЦ-письма — в
  КЦ-кампании, Meyer — в Meyer).

## Негативные кейсы гейта (§4, все отбиты)

| Кейс | Точка 1 (очередь) | Точка 2 (подтверждение) | Точка 3 (SMTP) |
|---|---|---|---|
| КЦ-кампания/ящик × Meyer-компания | ⛔ campaign_division_mismatch | ⛔ approve заблокирован | ⛔ division_mismatch |
| Ящик без division × КЦ-компания | н/п* | н/п* | ⛔ mailbox_without_division |
| Компания без division (ИНН не из базы) | ⛔ company_division_empty | ⛔ approve заблокирован | ⛔ company_division_empty |

\* На этапах очереди и подтверждения ящик ещё НЕ выбран (его выбирает
диспетчер при отправке), поэтому пара «ящик × компания» там не существует.
Кейс держат два рубежа: `pick_mailbox` вообще не выбирает ящик без division,
а точка 3 (последний рубеж перед SMTP) блокирует, даже если ящик подсунули
руками — что и показал прогон. Ручной approve в live-режиме тоже упирается в
точку 3 — живьём такое письмо не уйдёт.

Каждый блок записан событием **division_gate_block** (inn, email, mailbox,
причина, точка, ts) — 3 события в журнале, видны в панели «События».

## Контракт {news_object}/{city}

Письмо с незаполненными полями НЕ ушло и НЕ похоронено: статус
`needs_data`, причина `unfilled_placeholders:news_object,city`, лид виден в
`GET /messages/needs-data` (очередь «дозаполнить данные»). Оба пути закрыты:
рендер оркестратора и шаг (1) диспетчера.

## Находки для решения владельца

1. **139 из 145 новостных ИНН в enrich НЕТ в базе обзвона** → по правилу §4
   у них «направление не определено», отправка запрещена с любых ящиков.
   Это правильно по ТЗ, но означает: почти весь новостной поток стоит, пока
   эти ИНН не разметят (или не добавят в базу обзвона с направлением).
   Варианты: досыпать их в базу обзвона; или отдельная процедура разметки
   оператором. Решение за владельцем.
2. **DOMAINS-24-ASSIGN.md** (упомянут в ТЗ: «18 доменов КЦ») в репо
   отсутствует; маппинг ящик→направление зафиксирован в конфиге
   (`mailboxes[].division`) и согласован с реестром `config/domains.json`
   (9 КЦ + 5 Meyer доменов, 3 на hold). Если файл существует на сервере —
   прислать, сверю.
3. **Ответы клиентам (kind='reply') гейт направлений не режет** — осознанно:
   клиент сам инициировал диалог, и он может быть вне базы обзвона; блокировать
   оператору ответ нельзя. Отписка/жалоба/kill-switch на ответах остаются.
4. Скоринг в панели — из существующего блока (enrich+signals+выручка);
   отдельный вызов `server/lead_scoring.py` в карточку не вайрился (его
   контракт заточен под серверный enrich.db) — короткий хвост при деплое,
   если владелец захочет его цифры в карточке.

## Как повторить

```bash
# 1) индекс (один раз, ~5 мин, нужны DROP_URL/DROP_TOKEN):
python3 sender/tools/build_obzvon_index.py --out /opt/sender/obzvon-index.db
# 2) приёмка:
OBZVON_INDEX=/opt/sender/obzvon-index.db \
ENRICH_DB_SNAPSHOT=/opt/sender/enrich.db \
DRYRUN_WORKDIR=/tmp python3 sender/tools/dryrun_basemerge.py
```

Боевое включение: в config.yaml секция `obzvon` (index_path, enrich_db) +
`division: kc|meyer` у каждого ящика (в `mailboxes.kc.yaml` уже проставлено).
Без индекса гейт спит; с индексом — режет всё несовпадающее в трёх точках.
