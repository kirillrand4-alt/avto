# Аудит статей под категориями prokompressor.ru: план

Задача, как я её понял: пройти по всем категориям каталога и по каждой ответить на семь
вопросов - есть ли статья, про содержимое ли она страницы, помогает ли выбрать, оптимизированы
ли метатеги под содержимое, нет ли в статье бреда, нет ли битых ссылок, не каннибализирует ли
страница с другими разделами. Результат - таблица по всем страницам плюс очередь работ.

Ниже - то, что уже проверено фактически (не гипотезы), и то, как предлагаю строить прогон.

## 2. Как предлагаю прогонять

### Этап 0. Инвентаризация (без ИИ, ~2-3 часа машинного времени)

1. Обход каталога с живого сайта: от `/catalog/` вглубь по меню и по SmartSEO-тегам, плюс
   сверка с sitemap. На выходе новый реестр разделов с глубиной и родителем.
2. По каждому разделу скачиваем страницу и вырезаем: `title`, `description`, `H1`, блок статьи,
   все ссылки из статьи, наличие FAQ и микроразметки, счётчики фасетов фильтра, пагинацию.
   Полные HTML не храним - только вырезки, иначе 788 x 750 КБ съедят диск.
3. Сшивка с данными ПС: URL -> список запросов в Яндексе и Google с позициями и показами.
4. Построение индекса «запрос -> все наши URL с показами» для каннибализации.

Артефакт: `audit/inventory.jsonl`, одна строка на страницу, всё нужное внутри.

### Этап 1. Механические проверки (Python, без ИИ, без токенов)

Гоняются по всем страницам, дают жёсткие факты:

| Проверка | Как считается |
|---|---|
| Есть ли статья | наличие блока текста, число `<h2>`, объём в знаках, FAQ, байлайн, тип статьи (наша / легаси / нет) |
| Битые ссылки | обход всех уникальных ссылок, коды ответа, редиректы, ссылки на самих себя |
| Метатеги, формальная часть | длины title и description, дубли title и description по сайту, пустые, обрезанные, H1 = title |
| Стайлгайд | длинные тире, теги `<ul>`, запрещённые конструкции |
| Числа против выгрузки | `count`, `price_min`, `price_max`, диапазоны мощностей в статье против `payload-*.json` и выгрузки Битрикса |
| Соответствие ассортименту | состав раздела по фасетам и выгрузке против типов оборудования, упомянутых в статье |
| Каннибализация по данным ПС | запросы, где у нас 2+ URL с показами; отдельно - брендовые связки «каталог vs /info/brands/» |
| Каннибализация по FAQ | одинаковые вопросы FAQ на N страницах |
| Приоритет страницы | показы x потенциал сдвига позиции по CTR-кривой из `seo-effect-report.md` |

Эти проверки закрывают целиком пункты «есть ли статья» и «битые ссылки», и процентов на
семьдесят - «метатеги» и «каннибализацию».

### Этап 2. ИИ-ревью агентами (только то, что механикой не берётся)

Остаются три содержательных вопроса: про содержимое ли страницы статья, помогает ли она
выбрать, и нет ли в ней бреда. Их гоняем агентами батчами.

На вход каждому агенту по странице подаём:
- текст статьи и метатеги;
- `payload-*.json` этой страницы: H1, реальное число позиций, цены, модели, состав раздела;
- досье фактов бренда и категории из `kb/` и `brand_facts_lib.py` - это гейт достоверности,
  чтобы агент сверял утверждения с проверенной базой, а не с собственной памятью;
- топ-30 запросов страницы отдельно по Яндексу и Google с позициями и показами;
- список URL, с которыми страница делит запросы.

На выходе - строго структурированный JSON по семи блокам с вердиктом и цитатой-уликой на каждое
замечание. Формат - в образце отчёта.

**Спорные и критичные находки перепроверяем вторым проходом**, чтобы не плодить ложные
срабатывания. Пример из разведки: я чуть не записал в ошибки упоминание спиральных компрессоров
в description страницы Atlas Copco - а в фильтре раздела фасет «спиральный» показывает 35
позиций, то есть description прав. Одиночному проходу такие вещи доверять нельзя.

### Этап 3. Сводка

- `audit/results.csv` - строка на страницу: 7 статусов, вердикт, приоритет, ссылки на улики.
- `audit/OTCHET.md` - что нашли, сколько чего, топ проблем с деньгами.
- Три очереди работ: **написать с нуля** (страницы без статьи), **править** (мета, факты,
  ссылки, склейка каннибалов), **перегенерировать** (статья не про то или бред в основе).

## 3. Объём и чем платим

788 страниц, из них ИИ-ревью нужно примерно на 760 (у остальных статьи нет, там нечего читать -
только фиксируем факт и приоритет). На страницу уходит около 6-8 тыс. токенов входа
(статья + payload + факты + ключи) и 1-1,5 тыс. выхода. Итого порядка 6 млн токенов на прогон,
плюс перепроверка спорных.

**Вопрос, который надо решить до старта.** По вашему правилу тяжёлое гоняется через
`PROVIDER_API_KEY` на router.cheap, а квота сессии бережётся. Готов так и сделать. Отмечу
честно то, что записано в CLAUDE.md: у шлюза нет публичной оферты и юрлица, характер его
доступа к моделям не подтверждён. Альтернатива - гнать субагентами внутри сессии: дороже по
квоте, но без этого вопроса. **Скажите, каким путём идти.**

Приоритет прогона предлагаю такой: сначала 29 страниц без статьи (там чистый недобор трафика),
затем 269 страниц на позициях 11-30 с показами (там правки дают сдвиг быстрее всего), затем
остальные.
