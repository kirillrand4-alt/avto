(68 идей, сырьё: `seo-texts/data/confirm_screen_ideas.json`), ниже уже сведено.

## Правила сессии (обязательны)

- **⛔ Холд действует:** реальная отправка/прогрев НЕ запускаются. Всё ниже — код,
  dry-run и UI; «Отправить» в calibration-режиме до снятия холда пишет в лог/очередь,
  но реальный SMTP — только после команды владельца.
- **Тяжёлое — через провайдер** (`seo-texts/gen_provider.py`, `claude-fable-5`;
  массовое — `claude-haiku-4-5`): генерация, ревью, разбор модулей, любые LLM-прогоны.
  Сессионные токены — только оркестрация.
- Ветка инженера: `persona-prompt-seo-sender`. Не коммитить секреты/токены.

## Задача 1 — механизм confirm-send (ядро)

Активируемая опция конфига рассыльщика: `confirm_mode: off | all | sample`
(all = каждое письмо ждёт подтверждения — калибровка; sample = каждое N-е; off — как сейчас).

- Пайплайн: генерация письма → запись в очередь `pending_review` (письмо + JSON
  инфо-панели, см. Задачу 2) → решение оператора → `approved` уходит в отправочную
  очередь / `edited` (сохранить правку И диф — это золотые пары для дообучения
  промптов) / `skipped` (+причина) / `stoplist` (+причина: конкурент / нерелевант /
  плохие данные / по запросу).
- Решения durable (SQLite/jsonl, переживает рестарт), идемпотентны по (ИНН, email,
  campaign_id). Очередь не теряет письма при падении UI.
- **Один бекенд для CLI и веба** (Задача 5): очередь и решения — общий модуль/API,
  CLI и веб-панель — только представления над ним.

## Задача 2 — инфо-панель оператора (спека из 68 идей, 5 линз)

Порядок на экране (линза UX): стоп-флаги → скоринг-шапка → триггер → контакт →
компания → письмо → KB-провенанс → действия.

### MUST (без этого режим не сдаём)

1. **Красная полоса стоп-флагов** (до письма): `is_competitor` («КОНКУРЕНТ»),
   `verified='mismatch'` («сайт НЕ этой компании»), `mx_ok=false` («адрес мёртв»),
   бренд/серия из стоп-листа снятых (`kb/snyatye-verdict.json`, 17 серий),
   email/ИНН в базе отписавшихся. Любой флаг = «Отправить» требует
   доп-подтверждения (двойной клик/hold).
2. **Скоринг-шапка**: балл 0-100 крупно (цвет: <40 серый / 40-64 жёлтый / 65+
   зелёный) + мини-бары компонент (сигнал/40, выручка/20, verified/15, роль/15) +
   бейдж `buying_power` (micro…enterprise) + бейдж capex-окна («🔥 0-30 дн» зелёный /
   «⏳ 31-90» жёлтый / серый «нет триггера»). Источник: `server/lead_scoring.py`.
3. **Карточка новостного повода** (или явное «повода нет — холодный заход»):
   event_type, что именно (≤80 симв.), сумма, дата, hotness ★, **кликабельный
   source_url**. Несколько сигналов — самый горячий сверху, остальные под катом.
4. **Контакт**: email + роль (иконка; 🔴 приёмная/общий — вероятный роутер) +
   ФИО; **ЛПР-матч** (ФИО директора базы vs ФИО email: ✅ совпало / ⚠ разные /
   — безлично); mx_ok; verified-строка иконок (ИНН/ОГРН/тел/провайдер);
   расхождение домена email vs домена сайта — жёлтым.
5. **Компания-снипет** (1-2 строки): название, город/регион, выручка округлённо,
   основной ОКВЭД с расшифровкой, директор; `activity` из enrich.db («чем реально
   занимается») + **«зачем им компрессор/фотосепаратор»** — фраза-обоснование
   выбора направления (из ОКВЭД-маппинга + activity); бейдж направления
   КЦ (синий) / Meyer (фиолетовый).
6. **Письмо целиком** + подсветка подстановок (имя, город, кейс, цена, триггер-фразы).
7. **KB-провенанс**: какие данные KB использованы в письме — кейсы (id + город +
   что внедрили), ценовая связка бренд×категория и коридор по бюджет-баллу,
   гео-агрегат («в письме N внедрений» vs фактическое N из KB — завышение = жёлтый
   флаг), триггер-фраза ФРП/ОЭЗ с пометкой «подтверждено данными signals: да/нет».
8. **Комплаенс-флаги** (линза ФЗ-38/152): в письме есть полное «ООО «Руспром»» +
   ИНН/URL (нет = красный); механизм отписки присутствует (нет = красный);
   счётчик персданных в тексте (ФИО ×N, шкала 0/1/2/3+); regex-скан на
   «лучший/№1/дешевле чем/имена конкурентов» — жёлтая подсветка фрагментов.
9. **Панель действий** (фикс-низ, горячие клавиши): [Enter] Отправить, [E] Править,
   [S] Скип, [X] Стоп-лист (+причина). Калибровка сотен писем — мышь убивает темп.
10. **История контактов**: последняя отправка на этот ИНН/email (дата, тема,
    был ли ответ), красный флаг при <90 дн (см. Задачу 3).

### SHOULD (вторая итерация)

- Все ОКВЭД компании с подсветкой сматченных на направление.
- Deliverability-светофор (агрегат: 🟢/🟡/🔴 по прозрачной формуле, детали по клику).
- Доменная концентрация волны (N писем на один домен-получатель в текущей пачке).
- Возраст данных контакта (updated_at; >90 дн жёлтый, >180 красный).
- Ценовой разрыв: цена письма vs buying_power (enterprise-прайс для micro = жёлтый).
- Правовое основание обработки (метка: «публичный адрес с сайта», «ЕГРЮЛ» и т.п.).

### NICE

- Паттерн local-part (info@/sales@ generic — метка), бесплатный провайдер (mail.ru 🟡).
- Ссылка на политику ПД в письме (метка есть/нет).

### Чего сейчас НЕТ в данных (не изобретать, а завести/пропустить честно)

- catch-all-детект домена — НЕ реализован (беклог Фазы 0 валидации); поле в панели
  зарезервировать, показывать «не проверялось».
- История отправок — таблицы нет, создаётся в Задаче 3.
- Дельта выручки год-к-году — в базе одного года нет; пропустить.

## Задача 3 — send-log + suppression (пункт 7 владельца)

этапе подтверждения.

Требование владельца: **код (CLI на C:\sender) и веб-версия умеют одно и то же.**

- Инвентаризация: список возможностей CLI (send_campaign и др.) vs веб-панель —
  таблица расхождений.
- Закрыть расхождения через общий бекенд (Задача 1): очередь подтверждений,

- Тест паритета: один сценарий калибровки прогоняется в обоих интерфейсах с
  одинаковым результатом в очереди/логе.
