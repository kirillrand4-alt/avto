## 2. Объединённая карточка компании (view поверх, БЕЗ миграции баз)

Не сливать физически 161k-CSV в SQLite ради слияния — сделать **модуль
`company_card(inn)`**, который собирает карточку на лету (и кэширует):

1. строка из базы обзвона (36 полей) — грузится один раз в индекс по ИНН
   (в памяти или отдельная таблица `obzvon` в enrich.db, importer уже есть
   в C:\sender — переиспользовать);
2. + enrich.db: companies/emails/signals по этому ИНН;
3. + скоринг lead_scoring.

Правила приоритета при конфликте полей:

- **Направление (КЦ/Meyer): ТОЛЬКО из базы обзвона.** Это поле маршрутизации
  (см. §4), обогащение его не перебивает. Если ИНН нет в базе обзвона —
  направление считается ПУСТЫМ (не выводить из ОКВЭД молча; `division_for_okveds`
  из enrich_db.py можно показать как «предположение», но не как основание для отправки).
- Контакты: enrich.db приоритетнее базы (свежее, с ролями/верификацией);
  телефоны показывать ОБА набора с пометкой источника («база» / «сайт, с доб.»).
- Выручка/ОКВЭД/директор — из базы обзвона (первоисточник).
- site — из enrich.db только при `verified in (inn, ogrn, phone, provider)`;
  `cand_site` показывать с пометкой «не подтверждён».

Карточка отдаётся одним JSON — тем самым, который пишется в очередь
`pending_review` (Задача 1 в ENGINEER-TASKS-CONFIRM-SEND.md). CLI и веб рендерят
один и тот же JSON (паритет — Задача 4 там же).

## 3. Экран подтверждения: что добавляется к спеке инфо-панели

Спека панели (стоп-флаги → скоринг → триггер → контакт → компания → письмо →
KB → действия) — в `ENGINEER-TASKS-CONFIRM-SEND.md`, Задача 2. По слову владельца
«вся информация» дополняем:

- **Новостные события — ВСЕ по компании, каждое с кликабельным source_url**
  (не только самый горячий; остальные под катом). Поля карточки события:
  event_type, what/news_object, sum, hotness, ts, source_name, source_url,
  signal_match («имя в тексте» / «НЕТ имени — проверь» — жёлтый флаг).
- **Полная карточка компании** из §2 (раскрывающийся блок): все контакты с
  источниками-ссылками (all_contacts уже несёт страницу-источник по каждому
  email), телефоны с добавочными и метками отделов, ОПО (opo_object + opo_source),
  закупки (zakupki_contact со ссылкой на карточку закупки), продуктовая разметка
  из базы обзвона (категории + балл).
- **Контракт верстальщика писем:** `{news_object}` и `{city}` обязаны быть
  заполнены в данных news-батча (колонки news_object и city в выгрузках уже
  есть). Пустое поле = письмо НЕ генерируется, лид падает в отдельную очередь
  «дозаполнить данные» с причиной — а не уходит пустышкой.

## 4. ЖЁСТКИЙ гейт направлений (п.3 владельца)

**Правило: ящик направления КЦ может отправлять только компаниям с
направлением КЦ из базы обзвона. Симметрично для Meyer.**

- Маппинг «ящик → направление» уже существует на уровне ДОМЕНОВ:
  `DOMAINS-24-ASSIGN.md` (18 доменов КЦ, остальные Meyer). Зафиксировать его
  в конфиге рассыльщика (sender.yaml): у каждого ящика/домена поле
  `division: kc | meyer`. Домен без разметки = ящик не участвует в отправке.
- Проверка в **ТРЁХ точках**, все три обязательны:
  1. **Сборка очереди**: письмо не ставится в очередь, если
     `mailbox.division != company.division`;
  2. **Экран подтверждения**: несовпадение = красный стоп-флаг, кнопка
     «Отправить» ЗАБЛОКИРОВАНА (не «доп-подтверждение», а блок);
  3. **Диспетчер SMTP** (последний рубеж): отказ + запись в лог
     `division_gate_block` (inn, email, mailbox, ts) — на случай, если письмо
     попало в очередь до внедрения гейта или мимо UI.
- `company.division` пустой (ИНН не из базы обзвона, направление не размечено) =
  отправка запрещена С ЛЮБЫХ ящиков, пока владелец/оператор не разметит.
  В панели — отдельный флаг «направление не определено».
- Тест приёмки: dry-run очереди с намеренно перепутанными парами
  (КЦ-ящик × Meyer-компания, ящик без division, компания без division) —
  все три точки должны отбить каждую пару, лог фиксирует причину.

## 5. Порядок работ и приёмка (DoD)

1. Индекс базы обзвона по ИНН + модуль `company_card(inn)` (§2).
2. `division` в sender.yaml по DOMAINS-24-ASSIGN.md + гейт в трёх точках (§4).
3. Карточка → JSON очереди pending_review; панель рендерит новые блоки (§3).
4. Dry-run: 20 писем калибровки (как в DoD ENGINEER-TASKS-CONFIRM-SEND.md),
   из них минимум 5 новостных (карточка события с работающими ссылками) и
   3 негативных кейса гейта направлений.
