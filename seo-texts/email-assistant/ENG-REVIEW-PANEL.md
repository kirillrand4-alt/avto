## Ревью confirm.py

Файл **в целом чистый** по критическим и высоким приоритетам. Найдены две среднеприоритетные проблемы:

---

### **[MED] Рассогласование с интеграционной точкой**
**Где:** `_recent_contact()`, строка ~89  
**Суть:** Вызов `self._store.last_contact(email=..., inn=...)` предполагает наличие метода `last_contact` в store, но этот метод не упомянут в интеграционных точках. Если store его не реализует, код упадёт при первом вызове `_guard()` в production.

**Почему баг:** Безмолвный `except Exception` маскирует проблему в dev, но при реальных данных функция может возвращать `None` всегда (если метод отсутствует) или падать с AttributeError.

**Фикс:**
1. Добавить `last_contact(email, inn) -> Optional[dict]` в контракт store (если это интеграционная точка);
2. Либо явно проверить наличие метода и задокументировать, что без него защита "90 дней" не работает:
```python
if not hasattr(self._store, 'last_contact'):
    return None
last = self._store.last_contact(email=email, inn=inn)
```

---

### **[MED] Неполная обработка ошибок базы при идемпотентности**
**Где:** `submit()`, строка ~134 и ~150  
**Суть:** Вызовы `self._store.confirm_get_by_key()` и `confirm_submit()` не защищены от database-ошибок. Если БД недоступна или конкурентная запись создаёт UNIQUE-конфликт, метод бросит исключение вверх, нарушая идемпотентность (повторный submit может создать дубль при race condition).

**Почему баг:** ТЗ требует "идемпотентность по (ИНН, email, campaign_id)" и "без гонок (TOCTOU)". Текущий код полагается на то, что store корректно обработает UNIQUE-конфликт в `confirm_submit`, но не гарантирует это контрактом и не перехватывает возможные IntegrityError.

**Фикс:**
```python
existing = self._store.confirm_get_by_key(inn, email, campaign_id)
if existing is not None:
    return SubmitResult(existing["id"], False, existing["status"], ...)

try:
    rid, created = self._store.confirm_submit(...)
except IntegrityError:  # race: кто-то вставил между get_by_key и submit
    existing = self._store.confirm_get_by_key(inn, email, campaign_id)
    if existing is not None:
        return SubmitResult(existing["id"], False, existing["status"], ...)
    raise  # другая причина — пробрасываем
```

- ✅ Durable: все решения через store (SQLite).
- ✅ Стоп-лист: причины из whitelist, маппинг в suppression корректен.
- ✅ Безопасность: нет секретов, нет SQL-инъекций (store абстрагирует).

## **Severity: LOW** — потенциальная проблема с timezones (строка 475, `_history_block`)

**Где:** `_history_block()` — обработка `last["ts"]` для проверки `recent_90d`.

**Суть:** При `ValueError` в парсинге даты `recent` принудительно становится `True` (строка 493):

```python
except ValueError:
    recent = True  # дата не парсится → консервативно красный
```

Это означает "красный флаг блокирует отправку" даже если дата просто отсутствует или некорректна в логе (например, если `send_log` вообще пустой и `last=None`).

**Почему:** Если `last=None` (нет истории контактов), блок `if last:` не выполняется и `recent=False` остаётся. Но если `last` существует с битой датой, код консервативно блокирует. Это корректная стратегия для безопасности, но может быть излишне агрессивным в случае испорченного лога.

**Фикс:** Явно проверить `last is not None` перед блоком парсинга и оставить `recent=False` для случая битых данных, если это не считается риском. Либо логировать предупреждение для операторского внимания:

```python
if last:
    try:
        ts = datetime.fromisoformat(...)
        recent = (datetime.now(timezone.utc) - ts).days < 90
    except ValueError:
        # Вместо блокировки можно вернуть флаг "проверить вручную"
        recent = None  # или False с пометкой в note
```

Текущая логика безопасна (лучше ложноположительный блок, чем пропустить повтор), но может генерировать ложные стопы при проблемах с данными.

## **Severity: LOW** — недостаточная защита от injection в regex (строка 333, `_letter_block`)

**Где:** `add()` внутри `_letter_block()` — динамическая компиляция регулярки:

```python
m = re.search(rf"\b{re.escape(stem)}\w*", low_body)
```

**Суть:** `re.escape()` используется корректно для `stem`. Угрозы нет, но для ясности: если `stem` вдруг будет содержать управляющие последовательности (в нашем случае это основа слова из сигнала/ОКВЭД/названия компании), `re.escape()` их нейтрализует.

**Почему:** Строки из `signals` и `company` контролируются БД обогащения, которая берёт их из внешних источников (ЕИС, ЕГРЮЛ, RSS). Теоретически, если в названии компании окажется спецсимвол вроде `$` или `\`, это не сломает regex благодаря `re.escape()`. Текущий код безопасен.

**Фикс:** Не требуется. Для педантизма можно добавить assert или проверку, что `stem` — буквенный:

```python
if stem and stem.isalpha():
    m = re.search(rf"\b{re.escape(stem)}\w*", low_body)
```

Но учитывая, что мы работаем с русскими падежами (буквы), текущая реализация достаточна.

## Ревью `unsub.py`

Файл в целом **чистый** — основная логика корректна, интеграция с `Store`/`Suppression` выглядит разумно, RFC 8058 соблюдён. Нашёл **две находки**:

---

### 1. **[MED]** Неполная валидация `unsub_base_url` (конструктор `__init__`)

**Где:** строка 56 `self._base_url = legal.unsub_base_url.rstrip("/")`

**Суть:** Код проверяет наличие `unsub_secret_env` в окружении (строка 59–61), но **не проверяет** `unsub_base_url`. Если конфиг вернёт `None` или пустую строку, то `.rstrip("/")` либо упадёт с `AttributeError`, либо `self._base_url` станет `""`, и в `list_unsubscribe_headers` (строка 90) сформируется невалидный URL вида `?t=token`.

**Почему баг:** В продакшене неверный конфиг приведёт к тому, что заголовки `List-Unsubscribe` будут содержать битый URL. MTA могут проигнорировать такой заголовок или даже снизить репутацию. При запуске код упадёт только если `unsub_base_url` равен `None` (тогда `.rstrip` выкинет исключение), но пустая строка пройдёт молча.

**Фикс:** Добавить проверку после строки 56:
```python
self._base_url = legal.unsub_base_url.rstrip("/")
if not self._base_url:
    raise ValueError("unsub_base_url must be non-empty in config")
```

---

### 2. **[LOW]** Хардкод домена `mailto` в `list_unsubscribe_headers` (строка 91)

**Где:** строка 91
```python
mailto_url = f"mailto:unsub@{self._config.legal().entity.lower().replace(' ', '')}.ru?subject=unsubscribe"
```

**Суть:** Код генерирует `mailto` как `unsub@<entity>.ru`, где `entity` берётся из `config.legal().entity`, очищается от пробелов, приводится к нижнему регистру и добавляется `.ru`. **Проблема:** если `entity` в конфиге не совпадает с реальным доменом компании (например, `entity="ООО Руспром"` → `mailto:unsub@ооорупром.ru`, кириллица в домене), то адрес будет недоступен.

**Почему баг:** RFC 6068 требует кодирования не-ASCII в `mailto`, но тут `.lower()` применяется напрямую. Если в конфиге `entity` написан кириллицей, получится `mailto:unsub@ооорупром.ru`, что валидно только в IDN-форме (`xn--...`), но код этого не делает. Хуже: если `entity` содержит символы, недопустимые в доменном имени (например, кавычки, пробелы после `replace(' ', '')`), получится синтаксически битый адрес.

**Почему LOW, а не MED:** Согласно RFC 8058, `mailto` в `List-Unsubscribe` — fallback-механизм; основной путь — HTTPS. Большинство почтовиков игнорируют `mailto` при наличии HTTPS + `List-Unsubscribe-Post`. Но для полного комплаенса лучше исправить.

**Фикс:** Вынести домен отписки в явную настройку `config.legal().unsub_mailto_domain` (например, `"rusprom.ru"`) либо использовать `sender_domain` из конфига, если он есть. Если `entity` действительно должен формировать локальную часть (сомнительно), то нужно добавить валидацию/очистку по RFC 5321:
```python
# вариант 1 (рекомендуемый):
domain = self._config.legal().unsub_mailto_domain or "rusprom.ru"
mailto_url = f"mailto:unsub@{domain}?subject=unsubscribe"

# вариант 2 (если entity нужен):
import re
local_part = re.sub(r'[^a-z0-9._-]', '', self._config.legal().entity.lower())
if not local_part:
    local_part = "unsub"
mailto_url = f"mailto:{local_part}@rusprom.ru?subject=unsubscribe"
```

---

### Что **не** является багом (но отмечу для контекста):

- **Импорт `sender.tokens`** (строки 51, 77) — вызывается динамически в методах, а не на уровне модуля. Это допустимо, если `sender.tokens` живёт в том же пакете. Проверить наличие модуля — задача интеграционных тестов.

- **Логирование** (строка 134) правильное: `logger.exception` с контекстом, без PII в plaintext (email есть, но это допустимо в серверных логах при условии ротации и ограничения доступа, что выходит за рамки ревью кода).

**Итого:** 2 находки (1 MED, 1 LOW), основная логика без нареканий.

Файл в целом корректен по архитектуре и не нарушает жёстких инвариантов проекта. Нашёл одну потенциальную проблему средней серьёзности:

---

### **[MEDIUM]** Потенциальная гонка при обработке one-click POST

**Где:** `_handle_one_click_post()`, строки 150–155

**Суть:**  
Код вызывает `unsub.handle_one_click(token)`, который должен записать отписку в suppression-лист, затем проверяет `result.ok` и отвечает провайдеру. Если между `handle_one_click()` и проверкой `result.ok` произойдёт сбой (kill процесса, crash), провайдер не получит подтверждения, но запись в suppression может быть зафиксирована — повторный запрос провайдера получит 200 (корректно), но если запись НЕ успела зафиксироваться, то `result.ok=False` → 404, провайдер может повторить, но токен уже использован → идемпотентность нарушена.

**Почему баг:**  
Без явной транзакции или durable-флага между записью в suppression и ответом клиенту возможен TOCTOU:
- Если `handle_one_click()` коммитит в БД, но процесс падает до `self._send_response_text(200, "OK")`, провайдер не получит 200 и повторит запрос.
- При повторе токен уже использован (в `used_tokens`), `result.ok=False` → клиент получит 404 вместо 200.

**Фикс:**  
Убедись, что `Unsub.handle_one_click()` либо:
1. Использует транзакцию, которая коммитится только после успешной валидации и записи в suppression;
2. Либо помечает токен как use-once атомарно с записью в suppression (SQLite `BEGIN IMMEDIATE` / `UPDATE ... RETURNING`).

Если `handle_one_click()` уже реализует идемпотентность (проверяет used-токен и возвращает `ok=True` для повторного запроса того же токена), то это не баг. Проверь реализацию `Unsub.handle_one_click()` — если там нет защиты от повтора, добавь:

```python
# в sender/unsub.py
def handle_one_click(self, token: str) -> UnsubResult:
    recipient_id, campaign_id = self._validate_token(token)
    
    # Проверяем, не был ли токен уже использован
    with self._store.transaction():
        if self._is_token_used(token):
            # Идемпотентность: повторный запрос на уже обработанный токен → 200 OK
            return UnsubResult(ok=True, recipient_id=recipient_id, campaign_id=campaign_id)
        
        self._suppression.add(recipient_id, source="one-click", campaign_id=campaign_id)
        self._mark_token_used(token)
    
    return UnsubResult(ok=True, recipient_id=recipient_id, campaign_id=campaign_id)
```
