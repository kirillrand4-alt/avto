## Задача 1 (🔴 главная, требование владельца) — ПРЕ-ГЕНЕРАЦИЯ писем к подтверждению

**Требование:** при ручном подтверждении письма должны быть УЖЕ ВСЕ сгенерированы и
готовы к отправке. Оператор НЕ должен ждать, пока письмо сгенерируется — он только
смотрит готовое и жмёт «Отправить/Править/Скип».

Что сделать:
- Генерация писем per-lead выполняется **пакетно ЗАРАНЕЕ**, ДО попадания в confirm-очередь,
  а не лениво «на чтение» экрана подтверждения. К моменту, когда письмо в `pending_review`,
  у него уже готовы `subject` + `body` (все merge-поля подставлены, прогнан QA/линзы,
  снятые серии проверены).
- Явный триггер пре-генерации в вебе: `POST /campaigns/{cid}/generate` (или авто-запуск
  генерации при постановке шага в расписание) — сгенерировать письма для всех получателей
  шага в статус «готово к подтверждению». Кнопка «Сгенерировать письма» в `CampaignDetail`
  с прогрессом (как импорт базы).
- `GET /confirm/{rid}` и `GET /confirm/queue` возвращают уже готовое письмо **мгновенно**,
  без генерации на лету. Если письмо ещё не сгенерировано — оно НЕ должно показываться
  оператору как «на подтверждение» (показывать только `ready`).
- Тяжёлая генерация (LLM) — через провайдерский API (`gen_provider`, fable; массово — haiku),
  фоном, резюмируемо, с кэшем. Не блокировать веб-запрос оператора.

**Сколько генерировать (требование владельца):** НЕ всю базу, а ровно **на сегодняшний
лимит отправки**. Причина: если появятся правки (шаблоны / база знаний / промпты) —
заранее сгенерированная гора писем протухнет и её пришлось бы перегенерировать. Дневными
пачками правки применяются к СЛЕДУЮЩЕЙ пачке без потерь и без лишних трат LLM.

Объём = суммарная дневная ёмкость по всем активным ящикам с учётом прогрева:
`Σ по ящикам (ramp-лимит дня этого ящика − уже отправлено сегодня)` (из `ramp.py`/`warmup.py`).
- Пре-генерация берёт ТОП-N лидов (по скорингу/приоритету, `lead_scoring`) где N = сегодняшняя
  ёмкость, и генерит только их. Не жечь LLM на письма, которые сегодня всё равно не уйдут.
- Каждый день пул до-генерируется под ёмкость нового дня (по мере роста ramp-лимита).
- Если оператор за день не подтвердил весь пул — остаток переносится/регенерится по свежести
  на следующий день (не копить протухшие письма).

DoD: оператор открывает confirm-очередь — там ровно «сегодняшняя пачка» готовых писем
(= дневной лимит), каждое открывается и отправляется без ожидания; генерация прошла заранее
и видна отдельным прогрессом; за пределы дневной ёмкости генерация не уходит.

## Задача 3 (🟡, требование владельца) — ручной ответ на входящий лид из карточки (Шаг 7)

**Требование владельца:** «ответ сначала пишу сам, а только после автоответчику доверю».
Сейчас реплай-деск — **звонковый**: карточка лида (`web/src/screens/LeadCard.tsx`) умеет
только «Взять» / «Позвонить» (`tel:`) / сменить статус (Позвонил/Квалифицирован/…/в Bitrix);
«История переписки» — только чтение. Написать и отправить ответ по email из панели НЕЛЬЗЯ:
в `api/app.py` по лидам есть лишь `GET /leads`, `GET /leads/{id}`, `take`, `status`, `assign` —
ни одного `reply`/`send`. Единственная отправка email из веба — исходящая кампания (`Confirm.tsx`),
не свободный ответ на входящее. Это надо закрыть.

Что сделать:
- Новый эндпоинт `POST /leads/{lead_id}/reply` — тело `{text, subject?}`. Письмо уходит
  **через тот же ящик**, который принял тред, и **в тот же тред**: заголовки `In-Reply-To`
  и `References` из `message-id` входящего (иначе ответ оторвётся от цепочки), `From` = этот ящик.
  Оптимистичная блокировка по `version`, как у остальных lead-действий (409 при гонке).
- Экран `LeadCard.tsx`: блок «Ответить» — `textarea` + кнопка «Отправить ответ».
  Префилл `subject` = «Re: …». После отправки → запись в «Историю переписки» + refetch карточки.
  Доступно только когда лид **взят** этим оператором (как статус-действия).
- **Отправка сразу, без LLM-подтверждения/линз** — оператор пишет руками, он и есть проверяющий.
  Но оставить **механический комплаенс-гейт** перед отправкой:
  - блок, если получатель в suppression / отписке (ФЗ-38) — 409, как защита в `DELETE /suppression`;
  - автоподстановка байлайна «ООО «Руспром»» + футер/ссылка отписки (unsub) в тело;
  - лог отправленного ответа в историю лида + `events` (тип «исходящий ответ»).
- **Холд:** реальная SMTP-отправка — за общим hold-флагом / в `dry_run`, пока владелец не даст GO.
  UI-компоновку и эндпоинт можно собрать и прогнать в dry-run уже сейчас.

DoD: оператор в карточке взятого лида пишет ответ, жмёт «Отправить», письмо уходит тем же
ящиком в тот же тред, попадает в историю; отписавшимся отправка блокируется; автоподстановки
(байлайн + unsub) на месте; в dry-run видно готовое письмо без реальной отправки.
