# Аудит веб-версии рассыльщика: 6 шагов владельца

## Анализ 6 шагов рабочего процесса владельца в веб-версии

---

### Шаг 1 — Загрузка базы получателей

**СТАТУС:** ✅ полностью в вебе

**Эндпоинт(ы):**
- `POST /recipients/import` — принимает CSV сырым телом, `segment` в query, запускает фоновый поток, возвращает `import_id`
- `GET /recipients/import/{import_id}` — поллинг прогресса

**Экран:** `web/src/screens/Recipients.tsx` — блок «Загрузить CSV»: file-picker, поле сегмента, кнопка «Импортировать», прогресс-поллинг каждые 2 с, тост по завершению.

**Пробел:** отсутствует — реализация полная, включая прогресс и обработку ошибок.

---

### Шаг 2 — Генерация писем под лидов

**СТАТУС:** 🟡 частично

**Эндпоинт(ы):**
- `POST /campaigns/{cid}/steps` — создаёт шаг с `subject_tmpl` / `body_tmpl` и merge-полями
- `GET /confirm/queue`, `GET /confirm/{rid}` — отдают уже сгенерированные (персонализированные) письма с `panel.letter`

**Экран:** `CampaignDetail` (`admin.tsx`) — форма «Добавить шаг» (тема + тело вручную). `Confirm.tsx` — показывает финальное письмо с подстановками и подсветкой.

**Пробел:** нет веб-эндпоинта и кнопки «сгенерировать письма для кампании». Фактическая LLM/шаблонная персонализация per-lead происходит в движке автоматически, только когда кампания активна. Через веб можно создать шаблон и просматривать/редактировать результат в confirm-очереди — но явно инициировать генерацию нельзя.

---

### Шаг 3 — Добавление доменов и почтовых ящиков

**СТАТУС:** 🟡 частично

**Эндпоинт(ы):**
- `GET /domains` — список доменов из конфига
- `GET /domains/{domain}/dns` — DNS-чек (SPF/DKIM/DMARC/MX)
- `GET /mailboxes/readiness` — статус готовности ящиков

**Экран:** `Domains` (`admin.tsx`) — таблица доменов + кнопка «Проверить DNS». `DomainWizard.tsx` (`/domains/new`) — мастер: генерирует DNS-записи и YAML-сниппет для `sender.yaml`.

**Пробел:** нет `POST /domains` и `POST /mailboxes`. `DomainWizard` сам это оговаривает: «Мастер не меняет конфиг сервера». Фактическое добавление ящика требует ручного редактирования `config/sender.yaml` + задания env-переменных + рестарта сервиса. Это CLI/devops-операция, не веб.

---

### Шаг 4 — «Плохие» почты: bounce / невалидные / suppression

**СТАТУС:** ✅ полностью в вебе

**Эндпоинт(ы):**
- `GET /suppression` — список suppression с фильтром по scope/reason + агрегат stats
- `DELETE /suppression/{sid}` — удаление (с защитой на отписку ФЗ-38→409)
- `GET /recipients?valid_status=invalid` — невалидные адреса
- `GET /events?event_type=bounce` / `event_type=complaint` — лог событий
- `GET /analytics/dashboard` и `GET /analytics/rates` — глобальные bounce/complaint-rate
- `GET /gates/active` — активные kill-switch срабатывания

**Экраны:** `Suppression` (`views.tsx`) — таблица с фильтром + кнопка «удалить»; `Recipients` — фильтр по `valid_status`; `Logs` — лог с фильтром типа события; `Reputation` — активные гейты + динамика7дней; `Dashboard` — светофор + метрики.

**Пробел:** отсутствует — покрытие достаточное для понимания проблемных адресов.

---

### Шаг 5 — Отправка писем через веб + confirm-подтверждение

**СТАТУС:** ✅ полностью в вебе

**Эндпоинт(ы):**
- `POST /campaigns/{cid}/status` — `{"status": "active"}` — запуск; `"paused"` — пауза
- `GET /confirm/queue` — очередь на подтверждение
- `GET /confirm/{rid}` — детали письма с panel
- `POST /confirm/{rid}/decision` — действие: `approve` / `edit` / `skip` / `stoplist`

**Экраны:** `CampaignDetail` (`admin.tsx`) — кнопки «Запустить» / «Пауза». `Confirm` (`Confirm.tsx`) — полноценный confirm-workflow: стоп-флаги, скоринг, письмо с подсветкой, комплаенс-блоки, хоткеи Enter/E/S/X, edit-режим с сохранением золотой пары, hold-диалог при наличии стоп-флагов.

**Пробел:** отсутствует — confirm опциональна (кампания может работать без неё, если `confirm_hold = false`), веб поддерживает оба режима.

---

### Шаг 6 — Автоответчик (включить/выключить)

**СТАТУС:** ❌ нет в вебе (только конфиг/CLI)

**Эндпоинт(ы):** отсутствуют — в `api/app.py` нет ни одного роута типа `/autoresponder`, `/auto-reply`, `/settings/autoresponder` или аналогичного.

**Экран:** нет экрана —ни в `App.tsx`, ни в `screens.ts` нет ни маршрута, ни компонента для управления автоответчиком.

**Пробел:** система детектирует `reply_kind = "auto_reply"` у лидов (IMAP-парсинг входящих), но toggle «включить/выключить автоответчик» не реализованни как бэкенд-эндпоинт, ни как React-экран. Управление — только через конфиг-файл и/или CLI.

## ИТОГ — что доделать инженеру

| Приоритет | Задача |
|---|---|
| 🔴 высокий | **Автоответчик (Шаг 6):** добавить `GET /autoresponder` (статус), `POST /autoresponder/enable`, `POST /autoresponder/disable` + React-экран (или секцию в `/settings`) с toggle и статусом |
| 🟡 средний | **Добавлениеящиков (Шаг 3):** добавить `POST /mailboxes` (или `POST /domains`) для записи нового ящика в конфиг на лету (или в БД-override) — сейчас `DomainWizard` генерирует YAML-сниппет «на бумагу», но не применяет |
