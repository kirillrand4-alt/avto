# Решения по результатам проверки

## 1. Правки плана

### 1.1 Изменить порядок волн

**Было:** Волна 0 → Волна 1 (газ/МКС 6 доменов) → Волна 2 (центробежные пробные 10 доменов) → Волна 3 (фасетные) → Волна 4 (188 категорий)

**Стало:**
- **Волна 0-А (блокеры):** починка даты в gen_provider.py:65, свежая выгрузка каталога и запросов, проверка brands-allow.json против дилерских договоров, доработка payload (поле context для каждого числа), расширение qa_text.py проверкой "число упомянуто с контекстом"
- **Волна 0-Б (пилотная проверка фасетов):** три домена (prokompressor, enger-air, berg-kompressor) на предмет canonical/метатегов/ЧПУ. Если чисто - дальше. Если нет - волну 3 в конец, делаем сначала категорийные на доменах без фасетов
- **Волна 1-пилот:** 10 страниц газа/МКС на prokompressor и enger-air, замер через месяц, пересчёт прогноза
- **Волна 1-полная:** если реальная отдача 3+ клика со страницы - расширяем на остальные 4 домена. Если 1-2 - останавливаем, переходим к волне 4
- **Волна 4 (урезанная):** только домены с 8+ карточками в категории и пройденной волной 0-Б. Без этого - в отложенные
- **Волна 3:** после технической раскладки на всех задействованных доменах
- **Волна 2 и остаток волны 4:** по факту освобождения ресурсов

**Почему:** Пилот на 10 страницах стоит 15-20 часов, но спасает от ситуации "60 страниц газа дали треть ожидаемых лидов". Урезание волны 4 по наполненности освобождает инженера для проверки технических ограничений, а не для вычитки пустых категорий.

### 1.2 Заменить метрику "4,8 клика со страницы"

**Было:** "Клики со страницы в месяц (4,8) - множитель для планирования. 60 газовых × 4,8 = 290 кликов"

**Стало:** 
- Для prokompressor и enger-air: ожидаем 3-5 кликов со страницы через 3 месяца
- Для остальных доменов: ожидаем 1-2 клика через 3 месяца, 2-3 через 6 месяцев
- Общий прогноз волны 1: 100-150 кликов через 3 месяца при полной реализации на шести доменах

**Почему:** Экстраполяция 4,8 с домена в 29к URL на домен в 18 URL методологически неверна. Новая оценка консервативна, но реалистична.

### 1.3 Добавить в метрики

**Новое поле в таблице §4 PLAN-RABOT:**

| Метрика | Как считаем | Зачем | Порог действия |
|---|---|---|---|
| Матрица попарных пересечений доменов по кластерам | скрипт по выгрузке запросов, раз в месяц | видеть где каннибализация критична | пара доменов >15% по кластеру - пересмотр фасетной стратегии |
| Медиана кликов для страниц младше 6 месяцев | выгрузка по возрасту страницы | прогноз для новых текстов | обновляем после каждых 20 новых страниц |
| Конверсия лид→сделка по типам оборудования | CRM за последние 12 месяцев | проверка гипотезы "модуль = 6 компрессоров" | если у модулей в 3 раза ниже - пересчёт приоритета |

### 1.4 Изменить правило публикации партиями

**Было:** "Публиковать буду по очереди" (решение владельца 20.08)

**Стало:** Волна считается завершённой не после генерации, а через месяц после размещения последней страницы волны с проверкой индексации. Между волнами - пауза на замер, а не немедленный переход к следующей.

**Почему:** "По очереди" не определён как процесс. Через 3 месяца владелец забудет логику и будет публиковать хаотично. Проверка размещения должна быть встроена в конвейер, а не отдельным скриптом.

### 1.5 Урезать волну 4 по правилу наполненности

**Было:** "188 категорий на 16 сайтах"

**Стало:** Категория получает текст только при выполнении трёх условий:
1. В разделе 8+ карточек (было "меньше трёх - не генерируем", поднимаем до 8)
2. Домен прошёл волну 0-Б (починки и техническая раскладка)
3. Карта сайта содержит товарные страницы этого раздела (не только категории)

Если домен не соответствует - откладываем до второй итерации, после проверки гипотезы о газе.

**Почему:** Текст на категорию с 3-7 карточками не даёт ни SEO (слишком мало товара), ни конверсии (паралич выбора при малом ассортименте). Освобождает инженера на критичные проверки.

2. Для фото "бренд не определён" (128 из 351): ручная проверка перед первым использованием, затем пометка "годен для доменов X,Y,Z"

Альтернатива: использовать схемы/чертежи расстановки оборудования вместо фото - уникальны, не требуют согласия клиента.

### 2.2 Новый тип страницы: калькулятор подбора

**Минимальная версия для волны 1:**
- JS-виджет "Сколько воздуха нужно" на каждой категорийной странице
- Чекбоксы по типам инструмента (гайковёрт, краскопульт, пескоструй - из справочника расходов)
- Поля количества, автоматический расчёт с коэффициентом одновременности
- Кнопка "подобрать из каталога" → фильтрует листинг под результат
- Форма на выходе с email (данные калькулятора передаются в CRM)

**Разработка:** 2-3 дня фронтенда, один виджет на всю сетку, данные инструмента меняются по категории.

**Размещение:** после волны 1-пилот, если она подтвердит гипотезу о газе. Иначе - вместе с волной 4 на винтовые категории.

### 2.3 Технические ограничения в ТЗ-шаблон

Добавить в раздел 10 "Чего нельзя писать" новый подраздел "Технические ограничения" (5 пунктов из материала inzhener):

1. Не ставить центробежные компрессоры в МКС. Для ЗИФ-СЦЭ и ZH/ZR писать "компрессорная станция", не "модуль".
2. Различать генератор как товар (ЗИФ-ПАУ) и модуль на базе компрессора. Не писать "Berg выпускает азотные установки" - Berg выпускает компрессоры для них.
3. Производительность указывать с контекстом: "по паспорту при ISO 1217" либо "с учётом условий эксплуатации, требуется запас 15-20%".
4. Класс чистоты ISO 8573-1 не указывать без паспортных данных. Писать требование отрасли, не характеристику машины.
5. IP54 - про пыль и влагу, не про мороз. Климатическое исполнение и температурный диапазон не указывать до появления данных об исполнении У, УХЛ, Т.

В payload добавить три поля: `product_type` (compressor/generator/module), `pressure_context` (nominal/network/application), `performance_type` (rated/effective).

### 2.4 Версионирование payload

При генерации волны сохранять:
```json
// page_metadata.json
{
  "url": "https://berg-kompressor.ru/catalog/vintovye-kompressory/",
  "generated_at": "2026-08-20T14:23:00Z",
  "catalog_snapshot": "20260811",  // из какой выгрузки
  "catalog_source": "data/catalog/20260811_nash_katalog.csv",
  "payload_hash": "a3f2b9...",
  "cards_used": ["12345", "12346", "12347"],
  "exchange_rate_usd": 92  // курс на дату генерации
}
```

Через полгода при споре "почему у вас 598 позиций написано" открываем не текущую выгрузку, а ту, на которой генерировался текст.

Добавить скрипт `monitoring/staleness_check.py` (запускать раз в сутки):
```python
def check_page_freshness(page_url, page_payload_snapshot):
    current_catalog = load_catalog('data/catalog/latest.csv')
    
    for fact in page_payload_snapshot['facts']:
        card = current_catalog.get(fact['source_card_id'])
        
        if not card:
            yield Alert('CARD_REMOVED', fact['source_url'])
        
        if card['price'] != fact['value'] and fact['unit'] == '₽':
            drift_pct = abs(card['price'] - fact['value']) / fact['value']
            if drift_pct > 0.05:  # порог 5%
                yield Alert('PRICE_DRIFT', drift_pct, fact['source_url'])
```

Складывать в `monitoring/staleness_report_YYYYMMDD.json`. Через 3 месяца прогнать весь опубликованный контент и получить список "что переписать в первую очередь".

## 3. Что сознательно НЕ делаем

### 3.1 Групповые сравнения по тирам

**Идея (novye-idei):** Таблица "все бренды тира А в 15-30 кВт" с ценами и характеристиками. Одна таблица генерируется раз, переиспользуется на всех брендовых сайтах с акцентом на свой бренд.

**Не делаем, потому что:** Противоречит решению владельца "сетку не линкуем". Такая таблица на брендовом сайте Berg покажет конкурентов (Cross Air, IronMac), что размывает брендовый фокус. Плюс при обновлении цен одного конкурента придётся обновлять таблицу на всех 16 сайтах.

**Альтернатива:** Сравнительные таблицы только на prokompressor (мультибрендовый, там это естественно). На брендовых - честное позиционирование текстом ("Berg в начальном сегменте, аналог по цене - Cross Air"), но без явной таблицы конкурентов.

**Цена решения:** Потеря страниц типа "Berg или Cross Air: что выбрать" на брендовых сайтах. Но это восполняется категорийными описаниями с позиционированием.

### 3.2 Контрольная группа страниц без текстов

**Идея (analitik-effekta):** AB-тест: 10 категорий переписать, 10 оставить как есть, через 3 месяца сравнить. Если разница статистически значима, эффект доказан.

**Не делаем, потому что:** Владелец не согласует. Если известно, что тексты могут поднять конверсию, сознательно оставлять страницы без них - упущенная выгода. Отдел продаж видит разницу в качестве заявок (с переписанных страниц vs с не переписанных) и будет требовать переписать всё.

**Альтернатива:** Сравнение "до/после" на одних и тех же страницах. Фиксируем метрики за 90 дней до переписывания, через 90 дней после публикации - сравниваем. Не чистый AB (нет контроля на внешние факторы), но практически достижимо.

**Цена решения:** Нельзя доказать причинно-следственную связь "именно тексты дали рост". Но для владельца достаточно корреляции "после переписывания показатели выросли".

### 3.3 Указание владельца в футере девяти доменов

**Идея (komplaens):** На девяти сайтах нет указания на связь с владельцем. Либо указать ООО в футере, либо сильнее развести сайты, чтобы связь была неочевидна.

**Не делаем, потому что:** Это решение владельца, не исполнителя. Юридически не обязательно (сайт не СМИ), поисково - видимость сетки уже есть (10,1% пересечения). Указание владельца снизит риск санкций, но владелец может не захотеть светиться.

**Альтернатива:** Разведение запросов брендом (уже в плане, волна 3) + матрица попарных пересечений для контроля. Если после волны 3 пересечение не снизится - вернуться к вопросу об указании владельца.

**Цена решения:** Сохраняется риск, что Яндекс применит санкции к сетке. Но это риск, который владелец принял ещё при создании 18 доменов.

### 3.4 Гибридный FAQ

**Идея (BRIEF §5):** Два вопроса из вычитанного пула, два-три генерируются из payload страницы. Порог: не чаще трёх страниц домена и двух доменов. Проверка на 20 страницах через инженер-ревьюера до запуска серии.

**Делаем, но урезаем:** Пилот на 20 страницах остаётся. Но если качество не лучше, чем у пула - откатываемся к пулу без угрызений. Повтор FAQ не каннибализация, читатель страницы Berg не видел страницу Comaro.

**Цена решения:** Если откатимся к пулу - 38 повторов вопросов на 200+ страницах останутся. Но это меньшее зло, чем усложнение конвейера ради косметического улучшения.

### 3.5 Страницы применений (лазер, пескоструй, автосервис)

**Идея (novye-idei, konkurent):** Один шаблон, 5-7 страниц на сильный домен, длинный хвост "компрессор для лазерной резки". Конкурент назвал это "что украду первым".

**Не делаем в волне 1, делаем после:** Идея верна, но требует отдельного шаблона и фактуры (специфика отрасли, требования к воздуху, типичные ошибки). Это 20-30 страниц дополнительно. Делаем после подтверждения гипотезы о газе, иначе рискуем размазать усилия.

**Цена решения:** Конкурент может запустить такие страницы раньше. Но длинный хвост применений - низкочастотный, конкуренция там минимальна. Если конкурент успеет - не критично, места хватит.

## 4. Что нужно от владельца

### 4.1 Немедленно (блокеры волны 0-А)

1. **Свежая выгрузка каталога** (nash_katalog_YYYYMMDD.csv, дата не старше недели). Без неё генерация идёт на протухших ценах (+3,6% за 9 дней по факту).

2. **Свежая выгрузка запросов** (текущая до 12.07, прошло больше месяца). Без неё невозможен замер отдачи девяти газовых страниц prokompressor, а значит нельзя проверить экономическое обоснование приоритета газа.

3. **Список доменов под накруткой поведенческих.** Сейчас исключаем 65% кликов сетки (93% на berg-compressor.com), но если после запуска текстов на домене включится накрутка - рост кликов будет ложным. Нужен список ДО старта волны 1.

4. **Реестр дилерских договоров** (список брендов, по которым есть официальное право торговли). Для проверки brands-allow.json. Если в whitelist попал бренд без договора, текст выйдет с формулировкой "официальный дилер" и даст риск претензии.

5. **Частотность Wordstat по газовому кластеру** (генераторы азота, модульные станции, центробежные компрессоры). Без этого непонятен потолок темы. Если суммарный спрос 500 показов/мес - прогноз 290 кликов физически недостижим.

### 4.2 В течение недели (для волны 0-Б)

6. **Дата запуска девяти газовых страниц на prokompressor.** Для проверки гипотезы "газовых обращений мало потому что страницу завели недавно" нужно знать, когда именно "недавно". Если страница работает больше 60 дней - можно взять реальную конверсию клик→лид и пересчитать прогноз.

7. **Конверсия лид→сделка по типам оборудования** (CRM за последние 12 месяцев). Для проверки гипотезы "один модуль = 6-30 компрессоров". Если у модулей конверсия в 3 раза ниже - приоритет меняется.

8. **Загрузка карточек для волны 1** (центробежные Enger и ЗИФ, газовое ЗИФ и Atlas Copco на указанные домены). Статус "подтвердил", но нужна оценка объёма и срока. Если это ручная загрузка десятков позиций - волна 0 растянется на недели.

9. **Процедура публикации "по очереди"** (какая очерёдность, по какому правилу, кто принимает решение). Сейчас это намерение, не инструкция. Через 3 месяца владелец забудет логику и будет публиковать хаотично.

### 4.3 После волны 1-пилот (для решения о продолжении)

10. **Решение о бюджете на закупку ссылок** по месяцам. Если в декабре купят ссылок на 300 тыс., а в январе на 50 тыс. - рост трафика в декабре нельзя приписать текстам. Нужна фиксация до старта каждой волны.

11. **Согласие на калькулятор подбора** (2-3 дня фронтенда, данные калькулятора в CRM). Если "нет" - не делаем, если "да" - запускаем после подтверждения гипотезы о газе.

## 5. Порядок первых пяти шагов

### Шаг 1: Блокеры (1-3 дня)

**Что делаем:**
1. Починить `gen_provider.py:65` - дата = текущая, не константа (10 минут)
2. Запросить у владельца пункты 1-5 из списка выше (отправить запрос сегодня, дедлайн ответа - 3 дня)
3. Доработать payload: добавить поля `context`, `source_card_id`, `source_url` для каждого числа (1 день на payload-builder)
4. Расширить `qa_text.py`: проверка "число упомянуто вместе с контекстом в радиусе 200 символов" (4 часа)
5. Проверить `brands-allow.json` против полученного реестра дилерских договоров (1 час после получения данных)

**Критерий готовности:** Получены данные от владельца (п. 1-5), блокеры починены, qa_text.py пропускает только тексты с числами в контексте.

**Если владелец не даст данные за 3 дня:** Останавливаем работу до получения. Генерация на старых данных производит мусор.

### Шаг 2: Пилотная проверка фасетов (1-2 дня)

**Что делаем:**
1. Проверить три домена (prokompressor, enger-air, berg-kompressor) на canonical/метатеги/ЧПУ в фасетных подборках
2. Если найдена поломка типа п.10 реестра (склеенные дубли) - оценить объём работы по исправлению
3. Если поломка на всех трёх - проверить остальные 15 доменов выборочно (5 штук)

**Критерий готовности:** 
- Если три домена чисты - идём дальше
- Если поломка на 1-2 доменах - чиним их, откладываем волну 3 до починки остальных
- Если поломка на всех - ставим волну 3 в конец, делаем сначала категорийные (волна 4) на доменах без фасетов

### Шаг 3: Волна 1-пилот (2 недели генерация + месяц замера)

**Что делаем:**
1. Генерируем 10 страниц газа/МКС: 6 на prokompressor, 4 на enger-air (пропорционально весу доменов)
2. Публикуем сразу (не ждём полной волны)
3. Через месяц после публикации: выгрузка запросов, замер кликов по этим 10 страницам
4. Считаем реальную отдачу: клики/страница, CTR, время на странице, переходы в форму
5. Пересчитываем прогноз: если 3+ клика/страница - волна 1 работает, расширяем на 4 домена. Если 1-2 - останавливаем, переходим к волне 4

**Критерий готовности:** Замер через месяц дал данные для решения о продолжении волны 1. Если владелец не даст свежую выгрузку запросов через месяц - замер невозможен, решение принимаем по косвенным признакам (лиды в CRM по типу оборудования).

### Шаг 4: Решение о волне 1-полная или переход к волне 4

**Если волна 1-пилот подтвердилась (3+ клика/страница):**
1. Генерируем оставшиеся 50 страниц газа/МКС на шести доменах
2. Публикуем партиями по 10-15 страниц с интервалом неделя
3. Параллельно: запрашиваем у владельца согласие на калькулятор подбора (п.11)
4. Если "да" - 2-3 дня на фронтенд, затем размещение на всех категорийных

**Если волна 1-пилот НЕ подтвердилась (1-2 клика/страница):**
1. Останавливаем газ, фиксируем причину (слабые домены, низкий спрос, каннибализация)
2. Переходим к волне 4: категорийные описания на доменах с 8+ карточками и пройденной волной 0-Б
3. Газовые страницы возвращаем в план после усиления слабых доменов (загрузка карточек, набор истории)

### Шаг 5: Волна 4 (урезанная) или доработка волны 1

**Если делаем волну 4:**
1. Фильтруем домены по правилу: 8+ карточек в категории, прошли волну 0-Б, в карте сайта есть товарные страницы
2. Генерируем категорийные описания только для прошедших фильтр (ожидаем 80-120 вместо 188)
3. Публикуем партиями по 20-30 страниц, интервал 2 недели между партиями
4. Через месяц после публикации первой партии - замер, корректировка подхода для следующих

**Если дорабатываем волну 1:**
1. Анализируем, почему пилот дал 1-2 клика вместо 3+
2. Если причина в качестве текста - генерируем 5 страниц с другим набором блоков, повторяем замер
3. Если причина в слабости доменов - откладываем газ на 3 месяца, занимаемся усилением (карточки, внутренняя перелинковка, устранение техдолга)

---

**Главное правило первых пяти шагов:** Каждый шаг заканчивается решением о следующем на основе данных, а не плана. Пилот на 10 страницах стоит 15-20 часов, но спасает от месяцев работы в неверном направлении.
