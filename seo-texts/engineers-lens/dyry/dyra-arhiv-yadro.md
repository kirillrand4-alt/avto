# Критический анализ архива массового обогащения

## A. НАХОДКИ: ДАННЫЕ УЖЕ НЕВЕРНЫ

### A1. Баг `_domain()` портит все домены с `w` в начале

**Цитата:** 
> `lstrip` принимает **набор символов**, а не префикс. Проверено запуском самой функции... `http://water-service.ru/` → `ater-service.ru`, `http://wtc.ru/` → `tc.ru`

**Класс:** 3 (замер сломанным инструментом) + новый класс «Python API понят неверно».

**Проверка:** 
```sql
SELECT inn, site FROM companies WHERE site LIKE '%tc.ru' OR site LIKE '%ater-%' OR site NOT LIKE '%.%';
SELECT COUNT(*) FROM companies WHERE LENGTH(site) - LENGTH(REPLACE(site, '.', '')) = 0;
```
Первый запрос найдёт подозрительные обрезки, второй — домены вообще без точек.

**Масштаб не измерен** — документ это признаёт в §14 п.15, но данные УЖЕ в БД с испорченными доменами. Discovery-путь (лаунчеры) даёт полную потерю компании.

### A2. Тонкий `source` контакта потерян в 100% обогащений

**Цитата:**
> То есть **штатный конвейер** пишет в `emails.source` **тег задания** (`sales-base`, `centrifugal-core`, `mass`, `enrich`…), а не `own-site:staff`/`egrul:dadata`. Тонкий источник сохраняется только в jsonl-потоке.

**Класс:** 5 (пустое поле принято за отсутствие данных) — но наоборот: информативное поле затёрто техническим.

**Проверка:**
```sql
SELECT source, COUNT(*) FROM emails WHERE source IN ('enrich','sales-base','centrifugal-core','mass','core') GROUP BY 1;
SELECT source, COUNT(*) FROM emails WHERE source LIKE 'own-site%' OR source LIKE 'egrul%' GROUP BY 1;
```
Если первый запрос даёт тысячи, а второй — сотни, значит массовое обогащение потеряло провенанс у большинства контактов. Восстановление требует парсинга `source_url` + джойна к jsonl-потокам.

**Это хуже ошибки** — это архитектурное решение (:6754), принятое без комментария.

### A3. `division` не пишется для прогонов лаунчеров

**Цитата:**
> Лаунчеры `launch_sales_enrich`/`launch_core_chunked` передают только `inn/name/site/ogrn`... и не задают `division` в args... — значит для этих прогонов `division_for_okveds('', '')` вернёт `('', 0)`

**Класс:** 5 (пустое поле принято за отсутствие данных).

**Проверка:**
```sql
SELECT division, COUNT(*) FROM companies GROUP BY 1;
SELECT COUNT(*) FROM companies WHERE division IS NULL OR division = '';
```
Если NULL/пустых больше половины, а известно, что основной объём шёл через лаунчеры — подтверждение. Проверить: есть ли у этих компаний `okved` в той же таблице. Если есть — значит направление могли посчитать, но не посчитали.

### A4. Телефоны координат векторной графики PDF

**Цитата (из шапки):**
> Координаты векторной графики в PDF дают ровно десять цифр (`M8892 7.44042 1`) — 3 815 ложных телефонов за один прогон. ИНН прочитан как телефон.

**Класс:** 7 (формат случайно похож на данные).

**Проверка:** 
```sql
SELECT phone, COUNT(*) FROM phone_contacts GROUP BY 1 HAVING COUNT(*) > 50;
SELECT inn, phone FROM phone_contacts WHERE phone LIKE '8892%' OR phone LIKE '4042%';
```
Если одинаковый "телефон" у сотен компаний — это артефакт шаблона PDF. Координаты меняются плавно, поэтому будут кластеры похожих чисел.

### B6. Домены без `www` в AGGREGATORS блокируются широко

**Цитата:**
> `any(a in d ...)` — подстрочный матч. Например `'gis'` в списке заблокирует любой домен, содержащий `gis` (`registr-gis.ru`, `logistika-gis.ru`).

**Класс:** новый — «фильтр убивает валидные данные».

**Проверка:**
```python
AGGREGATORS = [строка из :288-329]
test_domains = ['registr-gis.ru', 'logistika-gis.ru', 'energo-servis.ru', 'wtc-moscow.ru']
for d in test_domains:
    blocked = any(a in d for a in AGGREGATORS)
    print(f"{d}: {'BLOCKED' if blocked else 'OK'}")
```
Если хотя бы один валидный домен блокируется — **неизвестно, сколько компаний потеряли сайт** из-за совпадения подстроки.

Граблю с `'gis'` документ называет прямо, но не считает. Проверить:
```sql
SELECT COUNT(*) FROM companies WHERE site IS NULL AND cand_site LIKE '%gis%';
```
