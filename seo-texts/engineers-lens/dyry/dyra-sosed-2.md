> "в `ops/mx_scan.py` числитель считает СТРОКИ (`sum(case when v>=1e9)`), а знаменатель — КОМПАНИИ (`count(distinct inn)`), из-за чего группа «своя» раздувалась с 572 до 788, а средняя выручка была взвешена по строкам. Не исправлено, помечено."

**Класс 3** (замер сломанным инструментом).

Все выводы из раздела 4.5 о фильтре "свой домен" держатся на этой арифметике. Написано "Не исправлено" — значит, любое использование mx_scan.py даёт неверные цифры.

**Проверить:** открыть `ops/mx_scan.py`, найти строки с `sum(case` и `count(distinct`, пересчитать правильно: числитель и знаменатель должны считать одно и то же (либо оба строки, либо оба компании).

**2. Подпись источника в графе роли: 2805 телефонов checko**

> "У 2805 телефонов checko в поле `role` лежит «контакты компании (чеко)», ещё у 159 — «общий (чеко)». Это подпись источника не в той графе... Любой отчёт с условием `role NOT IN ('','общий')` на этих строках врёт. НЕ ИСПРАВЛЕНО"

**Новый класс:** метаданные источника в графе данных. 

Состояние базы даёт "технических 18", но если среди 2805 есть хотя бы один технарь с подписью "чеко", цифра неверна. Написано "НЕ ИСПРАВЛЕНО" — значит, любой отчёт по ролям врёт.

**Проверить:**
```sql
SELECT role, COUNT(*) FROM phone_contacts 
WHERE role LIKE '%чеко%' OR role LIKE '%чек%' 
GROUP BY role;
```
Найти роли типа "гл.инженер (чеко)" — они войдут в подсчёт технических, хотя это просто "чеко".

**4. Реквизиты проходят мимо починки через прямой вызов add**

> "первая починка стояла в `add_phone`, а слои «реестр» и «база продажников» зовут `add` напрямую, и реквизит-телефон её пережил"

**Класс 3** (частично): починка в неполном месте.

Вето на реквизиты поставлено в `add_phone`, но часть телефонов записывается через `add` (минуя `add_phone`). Значит, реквизиты всё ещё могут попадать в базу.

**Проверить:**
```sql
SELECT phone, source FROM phone_contacts 
WHERE phone LIKE '3801006860' -- без +7, то есть не прошло форматирование
   OR phone LIKE '5001000066'
   OR LENGTH(phone) = 10 AND phone NOT LIKE '9%';
```
Если есть — проверить, совпадают ли они с ИНН/ОГРН самой компании.

**7. VK-путь блокируется наличием почты**

> "VK-путь закрыт условием `not r.get('best_for_outreach')` — работает только когда почты ещё нет, то есть фолбэк вместо прохода"

**Класс 5** (возможно): наличие одного контакта блокирует поиск другого.

ВК может дать телефон техдиректора даже если почта уже есть. Условие превращает ВК в фолбэк, хотя должен быть параллельным источником.

**Проверить:**
```sql
SELECT COUNT(DISTINCT e.inn) FROM email_contacts e
WHERE NOT EXISTS (
  SELECT 1 FROM phone_contacts p 
  WHERE p.inn = e.inn AND p.source LIKE '%vk%'
);
```
Сколько компаний имеют почту но не имеют ВК-телефонов? Это упущенный потенциал.

**8. Бренд компании перенесён с hh на 2ГИС без проверки**

**Класс 9:** правило перенесено без контрольного замера.

Функция `бренд_компании` написана для hh (где бренд = домен), перенесена на 2ГИС (где нужно название + город). Первый прогон дал 30% отказов, то есть функция не годится для 2ГИС в исходном виде.

**Проверить:** открыть определение `бренд_компании`, прогнать на 10 компаниях с известными карточками в 2ГИС, сравнить что функция возвращает с тем, что нужно передать в `catalog.api.2gis.ru`.

**10. Якорь для 2ГИС создаёт курицу-яйцо**

**Класс 1** (косвенно): проверяется не та карточка (тёзка).

Прогон по всей базе отложен. Но если якорь = "известный телефон", то компании без телефонов не пройдут через 2ГИС, хотя там могут быть телефоны. Замкнутый круг.
