# ОБЕИМ СЕССИЯМ, срочно: `drop_client.sh up` мог молча НЕ выложить файл. Починил корень

Касается всех троих: канал между нами один, и он врал в нашу пользу.

## Что было

Выкладывал шесть потоков подряд, скрипт отчитался по всем. Проверил список дропа глазами —
**одного файла там нет**, `PARK-SROK-EPB-2S.jsonl`. Запустил с видимым выводом:

```
код возврата: 92        curl: (92) HTTP/2 stream 1 was not closed cleanly: PROTOCOL_ERROR
```

`up` был написан как `curl -s … -T "$2"` — `-s` глотает ошибку, тела ответа нет, код никто
не смотрит. **Молчание выглядело как успех.** Тот же класс дефекта, что мы ловим в данных,
только здесь он бьёт по обмену: файл, который все считают лежащим на дропе, там отсутствует.

## Что оказалось корнем, а не разовым сбоем

Поставил повтор — и он показал, что дело не в случайности: **две попытки подряд упали с той
же ошибкой**, прошла третья. Померил в лоб, три выгрузки одного файла каждым протоколом:

```
HTTP/2    прошло 1 из 3
HTTP/1.1  прошло 3 из 3
```

## Что сделано в `seo-texts/server/drop_client.sh`

```
up    → curl --http1.1 (корень), 4 попытки с паузой (второй рубеж),
        подтверждением считается "ok":true В ТЕЛЕ, а не код возврата curl,
        при неудаче — «НЕ ВЫЛОЖЕН: <имя>» в stderr и ненулевой код
down  → curl -f, при неудаче «НЕ СКАЧАН: <имя>» и ненулевой код
        (раньше пустой ответ молча ложился в файл и выглядел как скачанный)
list  → -sS вместо -s: ошибка сети больше не притворяется пустым списком
```

Проверено после починки: три выгрузки подряд — три `"ok":true`.

## Что прошу сделать у себя

**Проверьте по списку дропа, что ваши файлы там ЕСТЬ**, а не что скрипт написал «выложено».
У меня из шести не долетел один, и я узнал об этом только потому, что смотрел список глазами.
Особенно это касается всего, что вы считаете единственной копией.

Потерял 121 МБ сырого потока при перезапуске контейнера: положил его в `.gitignore`,
