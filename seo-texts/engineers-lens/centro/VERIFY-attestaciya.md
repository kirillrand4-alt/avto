# VERIFY: реестр аттестации по промышленной безопасности (задача 16)

Проверка идеи 16 из `IDEI-NEPROVERENNYE.md`: даёт ли публичный реестр аттестации
Ростехнадзора третий путь к личности инженера — привязку человека к технической
области (Б8 — оборудование под избыточным давлением), а не к закупке.

Дата: 29.07.2026. Вся сетевая работа — через раннер на сервере владельца
(из песочницы `*.gosnadzor.ru` не открываются).

---

## Итог одной строкой

**Идея не работает. Доказанный отрицательный результат.** Публичный сервис есть,
но он умеет только одно: подтвердить подлинность протокола, **номер которого вы уже
знаете**. Поиска по организации, ИНН или фамилии нет; а в самой выдаче фамилия
обрезана до одной буквы и должности нет вообще. От «нашего предприятия» к людям по
нему пройти нельзя ни в одну сторону.

кабинеты для аттестующих организаций. Публичная точка одна: `qr.gosnadzor.ru`.

## Как устроен публичный сервис (разобрано по трём независимым срезам)

### 1. Форма поиска — одно поле

`browser_probe` по `qr.gosnadzor.ru/prombez`: http 200, заголовок «Сервис проверки
подлинности протоколов ИС ЕПТ», HTML 35 935 байт (не упёрся в `html_cap` 400 000).
На странице единственное поле ввода **«Введите номер протокола»** и кнопка «Поиск».
Счётчик «Запросов: 17 088 638, обновлено 28.07.2026» — сервис живой и массовый.

Никаких полей «организация / ИНН / ФИО / дата» на форме нет.

### 2. API фронтенда — только по номеру

Скачал и разобрал бандл `qr.gosnadzor.ru/main.e1fac6f1ba86a09baed8.js` (Angular,
482 КБ). Весь сервисный слой обращений к бэкенду — четыре метода:

```
fetchByProtocolNumber(number, AKType) -> GET /api/protocols/byProtocolNumber/{number}/{AKType}
fetchByID(id)                         -> GET /api/protocols/{id}
fetchLastProtocols()                  -> GET /api/protocols/findLastProtocols/1
fetchQueryCount(...)                  -> GET /api/protocols/fetchQueryCount/{...}
```

Метода «искать по организации / ИНН / фамилии» в коде **нет**. Единственный вход —
номер протокола (`AKType` — это раздел: `prombez` / `energybez` / `gts`).

### 3. Что реально отдаёт бэкенд — живой запрос

`fetch_url` по `qr.gosnadzor.ru/api/protocols/findLastProtocols/1` (последний
занесённый протокол), http 200, вернулась одна запись:

```json
{
 "applicant": "Александр Николаевич Ё.",
 "oa": "Б.9.3.",
 "protocolDate": "2026-07-27T21:00:00.000Z",
 "protocolNumber": "02-3307-3-1-26-41",
 "organizationINN": "5032137342",
 "ak": "Щелковский филиал АО 'Мособлэнерго' Отдельная-1",
 "city": "Московская область, Щелково",
 "AKType": "prombez",
 "disabled": false
}
```

Ключевое:
- **`applicant` = «Александр Николаевич Ё.»** — имя и отчество полные, а **фамилия
  обрезана до первой буквы**. Идентифицировать человека по такой записи нельзя.
- **Должности нет ни одного поля.** Роль (главный механик и т. п.) — та самая
  ценность идеи — в выдаче отсутствует.
- Название организации не отдаётся — только её ИНН.
- Область `oa` есть («Б.9.3.» в этом примере) — то есть техническая привязка в данных
  живёт, но без личности и должности она бесполезна для нашей задачи.

Скомпилированный шаблон карточки результата (тот же бандл) рендерит ровно эти поля:
`Протокол №`, заголовок = `applicant`, `Дата`, `Область`, `ИНН организации`,
`Аттестационная комиссия`, `Город`. Поля «Должность» и «Фамилия полностью» в шаблоне
**структурно отсутствуют** — это не обрезка на конкретной записи, а устройство сервиса.

### 4. Официальное подтверждение запрета поиска

Разъяснение Ростехнадзора (перепечатка nkprom.ru): «Поиск протокола аттестации по дате
сдачи, по Ф.И.О, наименованию организации, ИНН и пр. на Сервисе ЕПТ не предусмотрен» —
со ссылкой на 152-ФЗ. То есть закрытость поиска по организации — заявленная позиция
ведомства, а не наша недоработка запроса.

---

## Почему идея падает по двум независимым причинам

1. **Нет входа от предприятия.** Искать можно только по номеру протокола. У нас есть
   ИНН и названия 212 воздушных предприятий (задача просила снять 15–20 по
   `epb-vozdushnye.csv`) — но ни один из них нельзя превратить в список протоколов:
   поиска по ИНN/организации не существует. Снять данные по целевым предприятиям
   **физически нечем**, и это не ошибка выборки, а отсутствие функции.
2. **Даже с номером — нет личности.** Если бы номера у нас были, выдача всё равно даёт
   обрезанную фамилию и не даёт должности. Третьего пути к «человек → роль → предприятие»
   здесь нет.

Вывод для реестра идей: пункт 16 закрывается в раздел неудач. Область Б8 в данных
присутствует, но не соединяется с идентифицируемым человеком через публичный канал.

---

## Чему верить нельзя

- **Живая проба одна.** `findLastProtocols` отдаёт ровно одну запись, поэтому образец
  реальной выдачи у меня один (та самая «Александр Николаевич Ё.»). Систематичность
  обрезки фамилии подтверждается вторым, более сильным доказательством —
  скомпилированным шаблоном карточки, где полей «фамилия/должность» нет вовсе, — но
  «живьём» я видел один протокол, а не пять.
- **Реального целевого номера не проверял.** У нас нет ни одного номера протокола
  аттестации по нашим предприятиям (в `epb-vozdushnye.csv` лежат номера заключений ЭПБ —
  другой документ, другой формат), поэтому запрос «по нашему заводу» я не выполнял:
  выполнять его нечем.
- **`att`/`gasu` объявлены закрытыми по таймауту и косвенным данным**, а не по факту
  входа. Таймаут даже с РФ-адреса + характеристика систем из открытых источников
  (кабинет ЕСИА для аккредитованных) — сильный признак, но внутрь я не заходил и
  теоретическую возможность там полнотекстового реестра не опроверг «изнутри».
- **`oa` в примере — Б.9.3, а не Б8.** Это не противоречие (в реестре все области),
  просто последним занесённым оказался лифтовик; на структуру полей область не влияет.
- Счётчик 17 088 638 — это число запросов к сервису, а не число протоколов в реестре;
  объём базы отсюда не следует.
