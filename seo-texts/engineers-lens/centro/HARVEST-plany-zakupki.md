# Задача 1. Планы закупки 223-ФЗ

## Главная находка: в реестре есть режим поиска по ПОЗИЦИЯМ, а не по планам

Пункт А20/А29 стоял на поиске по планам: выдача отдаёт **план целиком**, а позиции надо было
доставать из печатной формы весом до 2,5 МБ. Из-за этого за две сессии разобрано пять форм.

В разметке карточки плана нашлась ссылка «Перейти к позициям» с вызовом
`goToPositionSearchWithPlanSearch('/epz/orderplan//search/results.html?...&searchType=true&fz223=on')`.
**`searchType=true` переключает реестр в режим позиций.** Карточка позиции отдаёт ровно то,
за чем шли:

| Поле карточки позиции | Пример |
|---|---|
| № позиции | 579 |
| Предмет договора | Поставка запчастей для компрессоров в 2026г |
| Начальная цена | 0,00 ₽ … 6 136 000 000,00 ₽ |
| Размещено / Обновлено | 22.12.2025 / 30.07.2026 |
| Способ размещения закупки | Анализ предложений |
| **Срок проведения закупки** | **09.2025** ← планируемая дата размещения |
| **Срок исполнения договора** | **12.2026** |

Это снимает печатные формы как основной путь: 50 позиций на страницу вместо одной формы
на 2,5 МБ.

## Рабочие адреса и параметры

Хост: `https://zakupki.gov.ru`. Сертификат подписан российским УЦ, поэтому
`fetch_url` **обязательно с `"insecure": true`**, иначе `CERTIFICATE_VERIFY_FAILED`
(потерян один прогон). `browser_probe` **обязательно с `"proxy": ""`** — дефолтный
`PROXY_URLV3` даёт `ERR_TUNNEL_CONNECTION_FAILED` на этом хосте (потерян ещё один).

```
# реестр ПЛАНОВ 223-ФЗ (карточка содержит заказчика с ИНН/КПП/ОГРН в href)
/epz/orderplan/search/results.html?searchString=<текст>&morphology=on&fz223=on
    &sortBy=BY_PUBLISH_DATE&sortDirection=false&recordsPerPage=_50&pageNumber=<N>

# реестр ПОЗИЦИЙ плана (даты и суммы, но БЕЗ заказчика)
    ... + &searchType=true&isPg2020=true

# фильтр по заказчику — составной токен, работает только в полном виде ИНН+КПП
&customerIdOrg=-1:zZzZzZzZ<ИНН>zZzZ<КПП>zZ

# карточка плана -> заказчик, ИНН, КПП, ОГРН, рег.номер (130 КБ)
/epz/orderplan/purchase-plan/card/common-info.html?guid=<planGuid>

# печатная форма плана -> все позиции таблицей (12 КБ … 1,8 МБ)
/epz/orderplan/purchase-plan/printForm/view.html?guid=<planGuid>

# карточка позиции (158 КБ, ИНН внутри)
/epz/orderplan/tru-plan/card/common-info.html?guid=<planGuid>_<posGuid>&infoGuid=<planGuid>

# поиск организации по ИНН -> ОГРН/ИНН/КПП открытым текстом в карточке, плюс agencyId
/epz/organization/search/results.html?searchString=<ИНН>&recordsPerPage=_50

# реестр ПРОЦЕДУР 223-ФЗ (тот же фильтр по заказчику работает, и вместе с searchString)
/epz/order/extendedsearch/results.html?fz223=on&customerIdOrg=<токен>&morphology=on
    &searchString=<текст>&recordsPerPage=_50&pageNumber=<N>
```

Все параметры, которые реестр планов вообще принимает (сняты с id полей формы):
`searchString`, `morphology`, `strictEqual`, `fz223`, `fz44`, `searchType`, `isPg2020`,
`structured`, `notStructured`, `publishDateFrom`, `publishDateTo`, `customerPlace`,
`customerPlaceCodes`, `actualPeriodRangeYearFrom/To`, `pageNumber`, `recordsPerPage`,
`sortBy`, `sortDirection`, `selectedOrderPlanName`, `showLotsInfoHidden`.

## Приём, которым это сделано за 20 заданий

`eval_js` возвращает промис, Playwright его дожидается. Значит из контекста страницы
`zakupki.gov.ru` можно циклом делать `fetch` по своему же домену (cookie и сессия
прикладываются сами), разбирать HTML через `DOMParser` **на сервере** и возвращать только
сжатые строки. Замеры: **36 страниц по 600 КБ = 21 МБ за 17 секунд**, 440 карточек планов
по 130 КБ = 57 МБ за 70 секунд. Результат до 730 КБ JSON дроп принимает.

Ограничение найдено эмпирически: цикл на ~210 `fetch` в одном задании падает с
`Page.evaluate: Target page, context or browser has been closed`. Держать до ~150.

Урок «гнать по одному слову» подтверждён численно и на этом источнике: фразовый запрос
проваливается не постепенно, а в ноль. Флаг «Искать точно, как в запросе» (`strictEqual=on`)
**обнуляет выдачу почти по всем ключам** — 24 записи вместо 100 000 по «компрессор» и нули
по шести ключам из восьми. Пользоваться им нельзя, хотя в интерфейсе он выглядит как
уточнение.

Счётчик ЕИС округляет и обрезает: «более 21 000», «более 100 000». Настоящее число видно
только когда пагинация кончается: по «компрессорная» счётчик говорил «более 1 100», а планов
оказалось ровно 1 196.

## Что оказалось важнее самой выгрузки: реестр смотрит назад

Заявление «план закупки говорит, что купят в следующем квартале» верно для позиции, но
**неверно для реестра**. Реестр планов 223-ФЗ — это архив всех версий планов с 2014 года,
и «Срок проведения закупки» распределён так:

| Год планируемого размещения | Позиций (из 7 435 промышленных) |
|---|---:|
| 2014–2019 | 1 395 |
| 2020–2023 | 2 049 |
| 2024 | 1 139 |
| 2025 | 1 177 |
| **2026** | **1 631** |
| **2027** | **13** |
| не указан | 31 |

То есть на «купят в следующем квартале» приходится **336 позиций из 7 435, это 4,5 %**.
Остальное — прошлое, ровно то, чего в проекте и так много. Годовой план 2027 появится
в декабре 2026, и до этого срока источник даёт максимум полгода вперёд, а не год.

Практический вывод: **фильтровать надо не по ключу, а по планируемой дате**, и заново
обходить реестр в декабре, когда лягут планы на 2027.

# Задача 3. Прогон по ИНН наших 202 предприятий

## Фильтр по заказчику в реестре планов: найден формат

В реестре планов **нет поля «Заказчик» в форме**, и семь угаданных простых параметров
(`customerIdOrg=41478`, `organizationIdOrg`, `customerId`, `agencyId`, `orgIds`, `customer`,
`customerIdOrg`+`WithNested`) молча игнорируются — счётчик остаётся 570 000, то есть весь
реестр. Формат нашёлся в разметке **реестра договоров 223-ФЗ**: там ссылка на закупки
организации собрана составным токеном через разделители `zZzZ`.

Проверено разбором на заведомо существующем плане (ООО «ЭН+ Торговый дом»):

| Вариант токена `customerIdOrg` | Результат |
|---|---|
| `-1:<НАЗВАНИЕ>zZzZzZzZ<ИНН>zZzZ<КПП>zZ<ОГРН>` | **8 записей, все с нужным ИНН** |
| `-1:zZzZzZzZ<ИНН>zZzZ<КПП>zZ` (без названия и ОГРН) | **8 записей** — работает |
| `-1:<ЧУЖОЕ НАЗВАНИЕ>zZzZzZzZ<ИНН>zZzZ<КПП>zZ<ОГРН>` | 8 записей — название не проверяется |
| `-1:<НАЗВАНИЕ>zZzZzZzZ<ИНН>zZzZzZ<ОГРН>` (без КПП) | 570 000 — фильтр отброшен |
| `-1:zZzZzZzZ<ИНН>zZzZzZ<ОГРН>` | 570 000 — фильтр отброшен |

**Значимы ровно ИНН и КПП.** Название и ОГРН можно не заполнять.

КПП по ИНН не выводится: у ООО «ЭН+ Торговый дом» ИНН 3808118560, а КПП 384901001, то есть
правило «первые четыре цифры ИНН плюс 01001» ломается на любой смене места учёта. КПП надо
брать из поиска организаций ЕИС по ИНН — в тексте карточки стоит `ОГРН … ИНН … КПП …`.

# Чему верить нельзя

**1. `strictEqual=on` («Искать точно, как в запросе») обнуляет выдачу.** По «компрессор»
24 записи вместо более 100 000, по шести ключам из восьми ноль. Выглядит как уточнение
морфологии, работает как убийца запроса. Если бы я поверил флагу, отчёт был бы «в планах
закупки компрессоров почти нет».

**2. Счётчик ЕИС округляет и обрезает.** «более 21 000», «более 100 000», «более 1 100».
Настоящее число видно только по исчерпанию пагинации: заявлено «более 1 100» планов по
«компрессорная», фактически 1 196. Ни одну цифру со счётчика нельзя приводить как точную.

**3. Четыре ключа из восьми выгружены срезом, а не полностью.** «компрессор» —
1 785 позиций из более 100 000, то есть **1,8 %**. «турбоагрегат» 1 799 из более 5 400,
«турбокомпрессор» 1 798 из более 3 100, «компрессорная» 1 100 из более 1 900. Срез взят
сортировкой по дате размещения по убыванию, то есть смещён к свежим планам — для задачи
это правильное смещение, но **любое утверждение вида «всего в планах N компрессорных
позиций» по этим четырём ключам неверно.**

**4. Фильтр по заказчику теряется в режиме позиций.** `customerIdOrg` вместе с
`searchType=true` **молча отбрасывается**: счётчик становится «более 32 000 000», а выдача
по «воздуходувка» даёт те же 308 записей, что и без фильтра. Это ровно тот класс ошибки,
где чужие позиции легко приписать своему заказчику. Фильтр действует только в реестре
планов и в реестре процедур.

**5. `selectedOrderPlanName` и `searchString=<рег.номер плана>` не фильтруют по плану.**
Хотя именно так собрана ссылка «Перейти к позициям» в самой разметке ЕИС: по рег. номеру
2210528975 счётчик отдал «более 25 000 записей». Позиции конкретного плана надёжно
берутся только из печатной формы.

**6. Классификация предмета — моя, а не ЕИС.** Отсев 870 непрофильных позиций и колонка
`centrobezhnyy_predmet` построены на словарях в коде, а не на ОКПД2 (в карточке позиции
ОКПД2 нет вовсе, он есть только в печатной форме). Границы спорные: «турбокомпрессор»
в предмете про автобус МАЗ — деталь двигателя, а «турбокомпрессор ТВ-80» — наша машина,
и разделяет их только список слов-исключений. Проверять по колонке
`priznak_centrobezhnosti`, где выписано, какое слово сработало.

**7. «Нет в реестре организаций ЕИС» проверено вторым запросом, но не третьим.**
98 предприятий из 202 не нашлись по ИНН. По правилу В8 отрицательный результат
перепроверен по восьми из них поиском **по названию**: семь дали ноль и по названию тоже,
восьмой (АО «АЗП») дал 388 записей, но ни одной с нашим ИНН — короткая аббревиатура
совпала с «Газпромбанк», «Будденновскгазпромбытсервис», «Востокгазпром». Это тот же
капкан короткого признака, что «комбинат» и «ТОР». Вывод «не является заказчиком по
223-ФЗ» держится на двух независимых запросах к одному источнику; выписки из ЕГРЮЛ
я не смотрел, и что предприятие живо, отсюда не следует.

**8. Печатные формы разобраны эвристикой по ячейкам.** В таблице печатной формы нет
заголовков у строк, порядок колонок плавает: у одних планов есть колонка «Минимально
необходимые требования», у других нет, из-за чего предмет сначала подменялся текстом
«1. Участник должен являться членом саморегулируемой организации…». Правило «предмет
стоит сразу после кода ОКПД2 и содержит кириллицу» починило 23 строки из 23, но это
правило, а не разметка. Кроме того строки в форме дублируются (вложенные таблицы), дубли
сняты по кортежу ячеек.

**9. Одиннадцать печатных форм из 27 весят 12 КБ и содержат 17 строк.** Это планы
закупки инновационной и высокотехнологичной продукции — по 223-ФЗ их публикуют на 5–10
лет, и они, как правило, пустые. Считать их «планом без компрессоров» нельзя, там нет
ничего вообще. Отличать по периоду действия: годовой план — ровно календарный год.

**10. Заказчик у 96 % позиций взят из выгрузки уровня планов, а не из карточки самой
позиции.** Связь — `planGuid`. Если ЕИС когда-нибудь переиспользует guid плана или
позиция окажется в перевыпущенной версии плана другого заказчика, ИНН уедет. У одного
плана из 3 220 заказчик не разрешился вовсе, строка в CSV с пустым ИНН.

**11. Год «2066» в сроках исполнения** встретился один раз — опечатка заказчика в самом
плане. Даты в CSV приведены как в источнике, без чистки.

**12. Про АЭС: 670 закупок это то, что нашли семь ключей, а не всё.** Прогон шёл по
компрессорной лексике. Сколько всего закупок у концерна, видно из energybase (4 241
страница по 20 = порядка 84 000), и по ним ключи не гонялись. Утверждение «после 2023
ничего нет» проверено только внутри компрессорной выборки — по ней ноль записей за
2024–2026, тогда как дочерние общества за те же годы публикуют. Это сильный признак,
но не доказательство, что концерн не публикует вообще ничего.

**13. Что осталось непроверенным.** Фильтры `publishDateFrom` / `publishDateTo` и
`actualPeriodRangeYearFrom` в реестре позиций — они могли бы сузить «компрессор»
со 100 000 до текущих планов и снять пункт 3, но проверены не были. Вкладка «Протоколы»
у карточек закупки, названная в задании, к планам не относится вовсе (у плана есть
«Документы», «Изменения», «Сведения о подписи») и в этой работе не открывалась.
