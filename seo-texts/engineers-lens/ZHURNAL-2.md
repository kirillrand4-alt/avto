### Поправка к моей же записи: про XMLRIVER я сказал шире доказанного

Владелец поправил, и он прав. Я написал «ключа нет ни у кого из сессий, задание не выполнить».

Как на самом деле. Ключ живёт **в окружении раннера на сервере владельца**, а не в сессии и не
в env-файлах. Смотрите `enrich_contacts.py` на дропе, строки 551-573:

```
def find_site_via_xmlriver(company):
    user = os.environ.get('XMLRIVER_USER', '')
    key  = os.environ.get('XMLRIVER_KEY', '')
    if not key: return None, 'no-xmlriver-key', {}
```

То есть скрипт читает ключ из окружения **того процесса, который его исполняет**. Раннер на
сервере запущен с этим окружением — значит xmlriver доступен ЛЮБОЙ сессии, но только через
задание раннеру, а не из песочницы. Проверил заодно имена переменных в `rs.env`,
`runner-secrets.env`, `sender-secrets.env` (значения не смотрю): XMLRIVER там действительно нет,
и это не «ключа нет», это «ключ не в этих файлах».

Практический вывод для `ZADANIE-sessii-s-klyuchom-XMLRIVER.md`: задание выполнимо, и выполнять
его надо **не через попытку достать ключ, а через раннер**. Рядом есть ещё две переменные,
которыми управляется поведение: `XMLRIVER_CHANNELS` (параллельные слоты, по умолчанию 4 —
xmlriver лимитирует именно каналы аккаунта, при массовом прогоне это узкое место) и
`XMLRIVER_TRIES` (по умолчанию 3).

Гоню контрольную пробу: `enrich_contacts` на две компании с ПУСТЫМ полем `site`. Если раннер
вернёт найденный сайт с `site_source`, отличным от `given`, это и есть работающий xmlriver.
