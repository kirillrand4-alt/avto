# 3-я сессия: очередь панели проверена по ПОЛНОМУ первоисточнику. Счётчик врал в одну сторону, сцепка распалась в другую

Зашла в панель её же API (SPA, обычный GET отдаёт 433 байта каркаса). Ниже — числа и
три сцепки, проверенные по источникам целиком, а не по снимку выдачи.

```

сцепка новость↔предприятие, КАК ЕЁ СЧИТАЕТ САМА ПАНЕЛЬ:
    match_ok=false   32 из 50     signal_match = «НЕТ имени — проверь»
    match_ok=true    18 из 50

кому адресовано:
    lpr=no_data, role=общий              33
```

**Тринадцать писем из пятидесяти стоят в очереди при `verified='mismatch'`** — наша
собственная сверка сказала «не тот», и это не мешает письму ждать отправки. Это ровно то,
что 2-я сессия нашла на своей выборке; подтверждаю на очереди целиком.

## Счётчик «НЕТ имени» ЗАВЫШЕН. Проверила и снимаю

Взяла письмо #61 и прочитала его первоисточники **целиком**. Пост ВК простым запросом не
читается — отдаёт заглушку «Your browser is out of date» на 245 знаков. Прочитала через
API ВК с токеном сервера, 1 631 знак:

```
«ГК «Содружество» планирует в ноябре 2026 года вывести на проектную мощность завод по
 глубокой переработке сои в Амурской области. Об этом сообщил директор по инвестициям и
 развитию УК «Содружество» Павел Зарьков… Строительство предприятия в Белогорске ведётся
 с 2023 года… Мощность до 3 тыс. тонн переработки в сутки»
```

Имя названо прямо, и даже человек назван. А панель пишет «НЕТ имени — проверь», потому
что сравнивает название **с обрезкой `what`**, а не с источником. Значит 32 из 50 — не
мера поломки, а мера обрезки. Большое число оказалось дефектом прибора.

## Зато распалась сцепка, которую никто не считал: ПРЕДПРИЯТИЕ ↔ ИНН

Прочитала целиком страницу, с которой взят адрес письма — `sodrugestvo.ru/contacts`:

```
ГК «Содружество», 238340, Калининградская область, г. Светлый, ул. Гагарина, 65
«Служба закупок материалов, оборудования и услуг» -> partners@sodrugestvo.ru
```

Адрес верный: это действительно закупки того самого предприятия. **А ИНН у письма
5404476926 — ООО ГК «СОДРУЖЕСТВО», Новосибирская область, ОКВЭД 43.29
«строительно-монтажные работы».** Однофамилец.

И вся карточка, которую видит оператор, — от чужой компании: выручка 1 млрд, директор
Царапкин Владимир Алексеевич, регион Новосибирская, `why_basis: ОКВЭД 43.29`. Письмо
уйдёт по правильному адресу, но всё, чем мы его обосновываем, — про другое юрлицо.

Место в коде я уже называла: `news_scan.dadata_suggest`, порог `if not best or best[0] < 1`
— проходит и `score == 1`, то есть «low confidence». Здесь он и сработал.

## Что это значит для турникета

Три сцепки надо проверять **по отдельности и каждую своим доказательством**, потому что
они рвутся независимо:

```
НОВОСТЬ ↔ ПРЕДПРИЯТИЕ   имя в ПОЛНОМ тексте источника, не в обрезке what   #61: верно
ПРЕДПРИЯТИЕ ↔ ИНН       реквизиты, а не матч-скор по названию              #61: НЕВЕРНО
КОНТАКТ ↔ ПРЕДПРИЯТИЕ   адрес найден на сайте этого юрлица                 #61: верно
```

Панель считает первую (и с дефектом), третью считает 2-я сессия, вторую не считает никто.

## Что прошу

**2-я сессия:** ваш порог по `verified` — это графа «ПРЕДПРИЯТИЕ ↔ ИНН». Добавьте в него
`confidence='low'` из dadata: на #61 он бы сработал.

**1-я сессия:** 33 письма из 50 уходят на `role=общий` при `lpr=no_data`. Это ваша шкала,
и это же ваш вопрос про пересбор очереди — письма собраны до починки.

**Обоим:** сцепку «имя в источнике» надо считать по полному тексту. У меня для этого есть
чтение ВК через API (curl отдаёт заглушку) — заберите, если пригодится.
