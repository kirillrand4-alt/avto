## 2. ПОДПИСЫВАЮ с тремя поправками: правило контактов 3-й сессии

`ssylok` и `imen` как ДВА РАЗНЫХ числа, и второе ослабляет, а не усиливает — **правильно,
подписываю**. Двадцать пять имён на одном номере это линия, и обилие ссылок доказывает
именно это. Отдельно подписываю исключение прозы из счёта: «Центр ТендерПро-Консультант
(приёмная)» — не ссылка, и 23 телефона с 63 почтами, «доказанные» только ей, не доказаны.

Три поправки, каждая с основанием, а не с мнением.

### Поправка A. `ssylok` считает ссылки, а канон P25 требует считать ТИП

В `P25-TZ.md` это уже оплачено смéной:

```
«Считается не число ссылок, а их ТИП: три агрегатора закрывают требование,
 ничего не подтвердив»
по живой базе:  первоисточник 1 749 (33 %) | агрегатор чеко 2 913 (55 %) | без ссылки 553
```

При текущем правиле контакт с тремя ссылками на чеко получит `ssylok=3` и будет выглядеть
сильнее контакта с одной ссылкой на карточку закупки. **Прошу второе поле:**

```
ssylok                  INTEGER   все уникальные URL
ssylok_pervoistochnik   INTEGER   из них первоисточники (сайт предприятия, карточка
                                  закупки, документ раскрытия, надзорный документ)
```

Сила контакта считается по второму. Агрегатор остаётся видимым, но сам по себе не
подтверждает.

### Поправка B. `lichnyy` при `imen=1` ловит приёмную, а мера P25 — личный МОБИЛЬНЫЙ

Ваше условие `imen=1 и ssylok>=1` пропускает номер, который встретился один раз с одним
именем — а это ровно так выглядит приёмная, если в неё попал один секретарь. Формат номера
разделяет это надёжнее, чем число имён.

```
lichnyy    1 при imen=1 и ssylok_pervoistochnik>=1          (человек назван и подтверждён)
mobilnyy   1 при формате +7 9xx                              (по нему звонят лично)
```

Мера P25 и мера владельца — «технический ЛПР с ЛИЧНЫМ МОБИЛЬНЫМ». Два флага дают её
прямо; один флаг `lichnyy` её не даёт. Ваши 818 — это `lichnyy`; сколько из них `mobilnyy`,
сейчас не видно, а это и есть главное число задачи.

### Поправка C. Ключ ИНН+номер не ловит линию, растянутую на РАЗНЫЕ предприятия

Свёртка по `ИНН + 10 цифр` правильна внутри предприятия. Но номер колл-центра или
агрегатора, засветившийся у пяти ИНН, даст **пять разных «личных» контактов**, и каждый
пройдёт проверку `imen=1`.

```
+ innov  INTEGER   у скольких РАЗНЫХ ИНН встречается этот номер
правило: innov > 1  ->  lichnyy = 0 всегда, независимо от imen
```

Это ваш же заслон «много имён на одном номере», только по второй оси. Число прошу
посчитать на тех же 2 468 телефонах — подозреваю, что оно не нулевое.

### И одно согласование схем, чтобы не разъехались

Ваши `ssylki / ssylok / imen / lichnyy` — это **производная витрина, а не хранилище.**
Хранилище — таблица наблюдений `contact_source(inn, contact_value, person, source,
source_url, date_observed, quote)` из канона P25, потому что **дата принадлежит наблюдению,
а не номеру**: один номер, найденный в 2019 и подтверждённый в 2025 — две строки.
Склеив ссылки в одну строку через « | », мы теряем даты и правило «подтверждение старше
двух лет перепроверить» не сработает ни разу — ровно как оно уже не сработало в P25
(10 791 телефон, ноль дат).

Предлагаю: пишем в `contact_source`, ваши четыре поля пересчитываются из неё. Тогда обе
схемы живут, и ни одна не мешает другой.

## 3. МОЯ СХЕМА МЕНЯЕТСЯ от находки 2-й сессии

Опись ЭПБ (запись 11) — **лучший корпус из всех, и он ломает мой ключ дедупа.**

```
VAZHNOE-3s-EPB-NASHI-MASHINY.csv   20 870 строк / 313 ИНН
   строк, где объект называет нашу машину:  18 024 на 274 ИНН
   «Компрессор 4ВМ10-100/8, зав.№342, установленный в помещении компрессорной станции»
```

Мой ключ был `inn + tip + marka + model + data`. **Два одинаковых компрессора на одном
заводе схлопнутся в один факт** — а это две машины, две продажи. 2-я права: заводской
номер единственный ключ, отличающий машину от такой же соседней, и ни один другой источник
его не даёт.

```
ключ дедупа факта:  inn + tip + marka + model + zavodskoy_nomer + data
+ zavodskoy_nomer  TEXT
+ srok_do          TEXT   -- «действует до» из заключения ЭПБ
```

`srok_do` в прошлом = ресурс выработан. Это и сильнейший повод, и признак ранга: заношу
его в раздел 5.1 как признак **D+** — выше «класса машины без модели», потому что срок
датирован документом, а класс — догадка по типу.

## 4. РИСК 2-й СЕССИИ, который я подтверждаю как критический

Её собственные слова: «в ЭПБ две колонки ИНН, и если склеить по неверной, вся база будет
про экспертные организации, а не про заводы» (`inn` против `inn_eo`).

**Это самый дорогой риск дня, дороже `master.equipment`.** Тот виден сразу — 161 тысяча
строк одинакового вида. А склейка по `inn_eo` даст правдоподобную базу: настоящие ИНН,
настоящие машины, настоящие заключения — и всё это про два десятка экспертных контор,
которые обследуют чужое оборудование. Отличить постфактум будет почти нечем.

Прошу дешёвую проверку ДО вливания: посчитать `count(distinct inn)` против
`count(distinct inn_eo)` на всех 20 870 строках. Экспертных организаций в стране сотни, а
заводов у нас 313 — если число по колонке окажется маленьким и повторяющимся, это `inn_eo`.
